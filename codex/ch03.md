# 第 3 章：配置、项目指令与信任范围

<!-- block: codex-ch03.b-opening -->
配置决定程序怎样运行，AGENTS.md 提供项目工作说明；项目被信任也不等于其中每条指令都能越过执行权限。

仓库根的“使用 pnpm”、子目录的“这里运行独立测试”和命令行指定的模型，经过不同的加载路径。前两者作为项目说明进入上下文，模型选择则由配置处理。本章先看这些信息怎样加载，再用运费项目写一份能直接指导工作的说明。

跟做运费任务时，可以先到“从运费小仓库开始”准备副本，再回来读配置与指令发现。前面的多目录项目图和通用项目说明用于解释机制，运费练习采用本章后半段给出的文件与测试命令。

## 3.1 配置与文字指令不是同一层

`config.toml` 主要提供运行设置，例如模型选择、provider、权限相关配置、MCP 和功能开关。`AGENTS.md` 是给代理读的项目说明，适合放构建命令、代码规范、测试要求和目录约定。它能影响模型选择动作，却不是操作系统的访问控制表。

在 `AGENTS.md` 中写“不要修改数据库”很有价值，因为它传达项目意图；但若你需要硬性限制某个路径，就要同时检查沙箱、工具与执行环境。反过来，沙箱允许写入也不意味着用户要求修改：能力与任务授权仍然是两件事。

```toml
# 教学配置片段：明确模式，其他字段按实际 provider 配置。
sandbox_mode = "read-only"
approval_policy = "on-request"
```

这个片段说明两个设置分别表达什么，不是全功能配置文件。本书所用 CLI 的命令行枚举与官网旧示例可能不同，实际接受的值先看同版本 `--help`。本机 0.167.0 顶层帮助列出 `on-request` 与 `never`，不要直接搬用旧教程的选项。

## 3.2 项目指令沿目录形成上下文

项目指令的发现以项目根到当前工作目录为线索。根目录说明适合定义全仓规则；更深目录说明适合补充局部构建与测试信息。把每个子项目的详细流程全堆在根文件里，会让无关任务也背上额外上下文。

```text
project/
  .git/
  AGENTS.md
  backend/
    AGENTS.md
    src/
  frontend/
    AGENTS.md
```

在 `backend` 开始任务时，你希望代理同时知道全仓约定和后端命令。不要期待它在任务开始时自动把每个兄弟目录的说明都读进来。若任务跨到前端，应让执行过程重新确认前端的局部规范，而不是拿已加载的后端说明代替。

<!-- block: codex-ch03.b-term-cwd -->
这一版本的具体发现入口见 `core/src/agents_md.rs`。当项目根标记、备用文件名、读取预算或缓存方式变化时，实际结果可能不同。排查时记录 cwd 与被读文件，不只贴出一份 `AGENTS.md` 就要求别人推断全局行为。

这个版本还有一个不能省略的条件：项目处于 untrusted 状态时，加载函数会跳过项目说明，只保留已有用户指令。默认项目根标记是 `.git`；找不到根标记时只考虑当前目录，空标记列表会关闭向父目录查找。局部 `AGENTS.override.md` 则是优先的覆盖文件名。遇到文件存在却未读入，应先核对这些条件。

## 3.3 一个有用的项目文件应包含什么

```markdown
# 项目约定

运行环境：Python 3.12。
修改业务逻辑后运行 python -m unittest discover -s tests。
src/ 下是实现，tests/ 下是行为测试，generated/ 由脚本生成。
不要直接编辑 generated/；修改 scripts/build_index.py 后重新生成。
提交说明写明用户可见变化和实际执行的检查。
```

这份说明给出了实现与测试的位置、检查命令和文件生成关系。代理读到后，可以据此选择文件和下一步操作。

如果存在特殊测试条件，也要写具体。例如集成测试需要本地数据库，而普通单元测试不需要；代理可以先跑哪一组，缺依赖时应记录什么。这样“无法运行全套测试”不会自动退化成“不运行任何测试”。

## 3.4 命令行覆盖要防止壳先改写

`-c key=value` 的值按 TOML 解析，解析失败时可能按字符串处理。把数组、引号或路径塞进 shell 字符串之前，要知道经过几层解析。最常见的错误不是字段名拼错，而是命令行送到程序时引号已经消失。

稳定的项目设置适合写入文件；临时覆盖才放命令行。Python 或 Node 自动化可直接传参数数组，避免拼成一整条 shell 命令。公开示例中也应使用无凭据的值，不能把认证 token 当普通调试字段输出。

本版 `exec --ignore-user-config` 的帮助特别说明：它跳过用户 `config.toml`，认证仍使用 Codex 用户目录。因此这不是“完全隔离账号”的开关。需要隔离实验时，要依据实际加载路径设计环境；本书的无模型实验使用不启动会话的子命令，从源头避开认证需求。

## 3.5 配置被读取之后，还要看谁消费

某个字段出现在文件里，不代表当前入口使用它。TUI 设置可能不影响 `exec`；实验特性可能需要功能开关；管理配置也可能限制用户可选值。使用 `--strict-config` 能帮助发现未知字段，但不能代替理解业务语义。

排错时按这个顺序缩小范围：确认二进制版本，确认 cwd，确认配置来源，确认字段被识别，确认对应功能被启用，最后观察实际行为。不要一次改五项设置再以“现在好了”结束，因为下一次升级你仍不知道关键因素是什么。

## 3.6 从运费小仓库开始

后面的章节都沿用一个只有两份 Python 文件的小项目。它按重量计算快递费：首千克 600 分，每增加一个不足或达到一千克的区间，加 200 分；重量必须是 1 至 30000 的整数克。1000 克收费 600 分，1001 克就应收费 800 分。仓库故意把向上取整改成了向下取整，供我们跟踪一次真实代码修复。

从本书仓库根目录把 `codex/examples/workshop/` 中的文件完整复制到独立空目录，例如 `parcel-lab`，然后进入它。这个目录下应直接看到实现、测试、项目说明和最终报告 schema，不要再套一层 workshop。模板是实验材料，保留原样供以后重做。以下命令在自己的新目录运行：

```powershell
git init
python -B -m unittest -v
```

测试进程应返回非零，输出含 `grams=1001` 和 `grams=2001` 两个失败子用例。这个结果说明问题已经复现；不需要先启动 Codex，也不需要模型账号。若出现的是 `ModuleNotFoundError: parcel`，先检查当前目录和复制结果。它与运费计算错误是两件事，后续提示词不能把导入失败当成目标缺陷。

先保存这份失败输出，暂时保留错误公式。若要跟做后面的 Git 差异审阅，在修复前将复制进来的原始文件建立为本地初始提交；只有初始化仓库，文件仍可能全部未跟踪，普通差异命令看不到修改前后的比较。暂不使用 Git 时，可以先跟做公式与测试，但应保留原始副本，记录当前没有提交。

项目的 `AGENTS.md` 很短：

```markdown
# Parcel workshop

金额使用整数分，重量使用整数克。不增加运行依赖。
先运行 `python -B -m unittest -v`，保留失败，再修改 `parcel.py`。
修复后运行同一命令；不要通过删除边界用例让测试通过。
最终说明改动、测试命令和退出码。提交与发布由任务指令决定。
```

第一句约束数据表示，避免代理为了消除一个整数边界错误而引入浮点金额。第二句给出能执行的检查入口，第三句保护测试所表达的需求，最后一句约束交付形式。这里没有把安装依赖、自动提交和发布绑在一起；这个小任务不需要那些步骤。

这些要求都可以从结果核对：金额是否仍用整数分，测试是否保留，是否运行了指定命令。现在已有可失败的项目和工作说明，跟做路线可以接第 11 章修复公式；下面继续追踪这份说明怎样进入上下文。

## 3.7 沿 `load_project_instructions` 读一次目录发现

固定源码 `agents_md.rs` 的入口先用已有用户指令初始化 `LoadedAgentsMd`。若活动项目被标记为 untrusted，就直接返回已有内容，不继续加入项目文档。通过这一关以后，才为各执行环境取得文件系统、cwd 和剩余字节预算，调用 `read_agents_md`。因此，“目录里有文件”与“本轮已注入文件内容”之间还有运行条件。

`agents_md_paths` 先确定项目根。默认根标记是 `.git`，找到后只遍历根到 cwd 的路径；找不到则只看 cwd。这里读根标记配置时跳过项目配置层，不能靠在陌生仓库里随手写一个项目配置，改变它向上搜寻的信任范围。得到目录链以后，在每层选择优先候选，再按由外到内的顺序加载正文。

以这棵目录树为例：

```text
parcel-lab/
  .git/
  AGENTS.md                 金额用整数分；运行项目测试
  packages/
    AGENTS.md               修改此目录时保留公开函数名
    shipping/
      AGENTS.override.md    本轮只检查运费边界
      AGENTS.md             旧的 shipping 说明
      parcel.py
```

从 `packages/shipping` 启动，预期候选是根层 `AGENTS.md`、`packages/AGENTS.md`、`shipping/AGENTS.override.md`。同目录的 override 替代常规文件候选，祖先目录已经提供的说明仍然保留。

若从 `parcel-lab` 启动，自动发现不会因为某个子目录里有 `AGENTS.md` 就遍历整个仓库、把所有说明一次性读入。后续进入子目录工作的行为要按实际加载时机判断。排错时记录启动 cwd，比只截图目录树有用。

读取还受 `project_doc_max_bytes` 限制。函数按实际字节扣减剩余预算，内容过长时截断；中文 UTF-8 字符通常占多个字节，所以“我写了两万字”不能直接与“预算若干字节”比较。越外层的长文档越可能吃掉后面说明的空间。把构建命令和数据约束放前面，长参考资料用明确路径指向单独文件，既方便人读，也减少关键要求被截断的机会。

## 3.8 把配置错误与项目说明错误分开

回到运费项目目录，先只讨论两个 TOML 字段：

```toml
approval_policy = "on-request"
sandbox_mode = "read-only"
```

这是可选的项目配置练习，不要求修改个人配置。TOML 解析只能判断引号、字段和值的语法；配置层合并决定同名字段最终取值；项目文档加载则读取 Markdown 文本。把 `sandbox_mode` 写进 `AGENTS.md` 的代码块，不会自动变成配置；在配置里写一句“金额使用整数”，也不能代替项目说明。

选择做这个可选练习时，先在运费项目目录建立 .codex/config.toml，写入上面的两个字段，再从该项目目录用 Python 3.11 及以上版本的 `tomllib` 做本地语法解析：

```python
import tomllib
from pathlib import Path

data = tomllib.loads(Path(".codex/config.toml").read_text(encoding="utf-8"))
print(data.get("approval_policy"))
print(data.get("sandbox_mode"))
```

输出 `on-request` 和 `read-only` 只说明这份文件可解析并含有两个键，没有证明 Codex 实际采用它。下一层应对照启动参数、有效配置层和管理要求。固定版本拒绝显式 `approval_policy = "untrusted"`，恰好说明通用 TOML 解析通过后，产品自己的语义校验仍可能失败。

可以用两项要求检查自己的理解：根层写“不要增加依赖”，子层写“通过测试再交付”，本轮应同时保留两项。若实际执行漏掉其中一项，按文件发现、正文读取、预算和注入位置逐步核对，确认加载结果后再检查代理行为。
