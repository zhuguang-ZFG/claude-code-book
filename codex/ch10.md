# 第 10 章：命令规则要用真实参数检验

<!-- block: codex-ch10.b-opening -->
执行规则按有序 token 匹配前缀，多条命中时取最严格决定；无匹配并不等于允许。

本章把固定命令 token 交给 CLI 策略检查器，观察规则如何匹配。实验不调用模型，也不执行 Git 操作，读者可以直接运行随书规则和驱动。

## 10.1 一份小而有区分度的规则

原创文件 [review.rules](https://github.com/zhuguang-ZFG/claude-code-book/blob/main/codex/examples/review.rules) 包含三条规则。第一条允许检查仓库状态与差异；第二条要求推送前审批；第三条拒绝这里列出的强制推送形式。

```python
prefix_rule(
    pattern = ["git", ["status", "diff"]],
    decision = "allow",
    match = [["git", "status", "--short"], ["git", "diff", "--stat"]],
    not_match = [["git", "commit"]],
)

prefix_rule(pattern = ["git", "push"], decision = "prompt")
prefix_rule(pattern = ["git", "push", "--force"], decision = "forbidden")
```

文件语法是 Starlark，代码块借用 Python 高亮，不意味着可以直接用 Python 解释执行。`pattern` 中每个位置表示一个 token；嵌套列表表示该位置的替代值。因此第一条接受第二个 token 是 `status` 或 `diff`，而不是任意位置出现这两个单词。

`match` 与 `not_match` 将正反例保存在规则文件中，加载时会验证它们是否符合预期。例子可以是数组或字符串；本书采用数组，减少额外分词差异。

## 10.2 用 CLI 得到可观察结果

下面的命令在书籍仓库根目录运行，规则文件的相对路径从这里解析；不需要进入运费项目。

```powershell
codex.cmd execpolicy check --rules codex/examples/review.rules git status --short
codex.cmd execpolicy check --rules codex/examples/review.rules git push origin review
codex.cmd execpolicy check --rules codex/examples/review.rules git push --force origin review
```

<!-- block: codex-ch10.b-term-execpolicy -->
这里不会执行 `git push`。`execpolicy check` 只评价传入命令，返回 JSON。不要把规则文件里的演示命令复制到普通 shell 后直接运行，尤其是带有外部副作用的形式。

本机结果如下：

| 输入 token | 结果 | 解释 |
| --- | --- | --- |
| `git status --short` | allow | 命中状态检查前缀 |
| `git diff --stat` | allow | 命中同一条规则的另一个替代值 |
| `git push origin review` | prompt | 命中推送规则 |
| `git push --force origin review` | forbidden | 同时命中推送与更长的拒绝规则 |
| `git commit -m example` | 无 decision | 没有任何规则命中 |
| `C:/book/bin/git.exe status` | 无 decision | 默认没有把绝对路径转换成 git 规则 |

强制推送例子的 JSON 同时列出两条匹配规则，最终决定是 `forbidden`。对应版本的文档给出的严重程度为 `forbidden > prompt > allow`。所以不能靠在后面追加一条宽泛 allow 来覆盖前面更严格的命中；判断时要看完整匹配集合。

## 10.3 无匹配不是一张通行证

```json
{"matchedRules": []}
```

无匹配结果省略 `decision`。这表示当前显式规则没有给出判断，之后怎样处理取决于调用方和其他策略。客户端若把字段缺失当作字符串 `allow`，会自行扩大权限。解析这类结构时，用明确的未知状态，比用一个方便的默认值更合理。

规则语法损坏、例子不满足规则或路径不存在时，策略加载会失败，需要先修复输入。实验为此生成了一条错误的正例，固定 CLI 返回非零退出码；调用方应保留这项错误，避免将其降为无匹配结果继续执行。

## 10.4 前缀规则无法读懂全部命令语义

第三条规则只覆盖 `git push --force ...` 这一种 token 顺序，不等于禁止了所有重写远端历史的方法。参数换位置、短旗标、别名、包装脚本或另一套程序，都需要独立分析。这个例子适合学习匹配机制，不应直接宣称是完备的 Git 安全策略。

同样，第一条允许 `git diff`，并不意味着任何运行环境中的同名程序都可信。PATH 可以影响实际执行文件，Git 配置也可能影响部分命令行为。规则描述命令形状，执行环境与工具可信性仍然是另一层问题。

需要更强约束时，还可以固定可执行文件路径、限制环境、使用专门的包装程序，或在操作系统层缩小可访问资源。前缀规则与这些机制分别约束命令形状和实际执行环境。

## 10.5 绝对路径与 host_executable

本书所用版本支持 `host_executable(name=..., paths=[...])` 声明以及检查器的 `--resolve-host-executables` 选项。默认先检查精确第一 token；开启解析后，在没有精确规则匹配时，才可能按 basename 回退。声明可以限制哪些绝对路径获准进行这种回退。

```python
host_executable(
    name = "git",
    paths = ["/usr/bin/git", "/opt/homebrew/bin/git"],
)
```

这是上游文档结构的教学说明，尚未在 Linux/macOS 上验证这两个路径。Windows 的 `.exe` 名称、路径规范化与别名也应分别测，不能只把路径分隔符替换一下就写成跨平台证明。

本版还支持 `canonical_matching=True`，用于 Unicode 规范化的不区分大小写匹配；默认 token 比较仍区分大小写。是否启用应由具体规则目的决定，不能为了“匹配得更多”就无条件开启。名称相似与同一可执行文件没有必然关系。

## 10.6 把规则当作需要维护的代码

至少保留三类例子：应允许、应提示、应拒绝，另加一组应该无匹配的输入。修改规则后运行全部例子，再检查真正执行入口送进来的 token 是否与例子相同。若上层加了一层 shell，原来针对程序的测试就可能不再覆盖真实输入。

本书驱动会核对二进制版本，并把结果写入独立证据目录。规则内容与驱动都有 SHA-256，便于确认后来读到的结论属于哪一份输入。版本升级时先复跑这一组，再决定是否需要修改工作流。

## 10.7 让规则正例和反例承担一部分维护工作

项目已有 `review.rules`，继续增加测试入口时，可以写成下面的独立规则。它限制的是 token 前缀，不会检查 Python 模块内部做了什么：

```starlark
prefix_rule(
    pattern = ["python", "-B", "-m", "unittest"],
    decision = "allow",
    justification = "Run the parcel project's local unit tests.",
    match = [["python", "-B", "-m", "unittest", "-v"]],
    not_match = [
        ["python", "-c", "print('different entry')"],
        ["python", "-m", "pip", "install", "some-package"],
    ],
)
```

若有人将 pattern 缩短成 `["python"]`，上面两个反例也可能命中。`match` 与 `not_match` 的加载校验会因此失败，提醒评审者检查这次扩大的匹配范围。

但例子不替代全面分析。`python -B -m unittest discover -s other_dir` 仍有相同前缀，后续参数可能改变测试发现范围；仓库中的测试文件本身也能执行任意 Python。规则表达的意图应与实际工作区信任相配，不能把一条宽前缀称为安全解释器。

## 10.8 绝对路径匹配要显式打开对应行为

默认检查把第一个 token 按给定内容匹配。`git` 与 `/usr/bin/git` 不相同，所以先前绝对路径用例没有命中。固定版本提供 `--resolve-host-executables`，允许在没有精确规则命中时尝试 basename 回退。

```starlark
host_executable(name = "git", paths = ["/usr/bin/git"])
prefix_rule(pattern = ["git", "status"], decision = "allow")
```

```powershell
codex.cmd execpolicy check --rules paths.rules --resolve-host-executables /usr/bin/git status
codex.cmd execpolicy check --rules paths.rules --resolve-host-executables /opt/other/git status
```

这是对规则输入的检查，不会启动这些路径下的程序；因此也可以在没有 `/usr/bin/git` 的机器上讨论该匹配例子。第一条预期通过允许路径回退命中，第二条被声明的路径列表排除。真实行为以你运行的固定 CLI 输出为准，特别查看命中项是否带 `resolvedProgram`，不要只看最后的 decision。

当命令 basename 与规则程序名都存在声明时，路径要同时满足两边约束；没有适用声明时，回退规则又不同。读源码或 README 时把“开启回退”和“限制回退路径”分成两件事，能避免误以为仅写 `host_executable` 就改变所有默认检查。

## 10.9 规则不是按第一条命中短路

假设一份文件允许 `git push`，另一份禁止 `git push --force`。同一命令可以同时命中两条，结果保留两项 matchedRules，最终采用更严格的 forbidden。把文件顺序调换，不应把更严格的决定隐藏掉；读取报告时也不要只截第一条命中。

本机强制推送用例由固定发布程序检查，命中前缀保存在 `facts/local-cli-20261110.json`。打开该记录即可核对两条规则及最终决定，实验未实际推送。

处理 `{"matchedRules":[]}` 时，还要注意解析代码的默认值：`result.get("decision", "allow")` 会把缺少 decision 改成允许。教程使用 `None` 保留无匹配状态，交给上层策略继续判断。

## 10.10 参数顺序改变的是输入本身

`git push --force origin main` 与 `git push origin main --force` 在 Git 的某些调用场景下可能产生相似作用，但前缀匹配看到的是不同 token 顺序。只写禁止第一种形式的规则，没有证明第二种也会被拒绝。这里应读完整策略和调用方命令解析，不能把一个教学前缀升级成完整 Git 发布防护。

Hook 示例接收 shell 文本，只识别一个精确字符串；execpolicy 则接收 token。扩展任一层的规则时，都需要为引号、复合命令、解释器嵌套和脚本内容考虑实际输入形式，增加正反例，并说明哪些形式交给其他层处理。

最后再看大小写。默认前缀区分大小写；`canonical_matching=True` 才启用 Unicode canonical caseless 比较。它比较的是提供的 token，不访问文件系统确认程序身份。Windows 文件系统或命令查找可能有自己的大小写行为，不能从操作系统习惯倒推出规则引擎一定如何比较。遇到匹配差异，先打印完整 token 数组、选项和命中结果。
