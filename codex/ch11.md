# 第 11 章：补丁、Git 与可审阅的修改

<!-- block: codex-ch11.b-opening -->
代理产生补丁之后，还需要核对差异、运行项目检查并保留基线；会话成功与代码正确是不同判断。

<!-- block: codex-ch11.b-term-git -->
审阅一次代码修改，需要确认文件位置、保留的行为和项目约束。补丁展示修改内容，Git 提供修改前后的比较，测试检查行为。本章将它们用在运费函数的一行修复上。

继续使用第 3 章的运费副本，先确认失败输出仍是两个跨千克边界。第一次跟做可先读“真正修复运费边界”，动手改公式并运行后续测试，再回看前半章的 Git 审阅方法。这里可以手动完成；第 14 章再把同一任务交给真实模型。

## 11.1 修改前先知道哪些差异不是本次产生的

以下命令在运费项目目录运行。最后一条要求仓库已有提交；若刚初始化且尚未提交，记录“无提交”，不要把查询失败当作项目损坏。跟做差异审阅前，按第 3 章先保留原始文件的初始提交。

```powershell
git status --short
git diff --stat
git diff --cached --stat
git rev-parse HEAD
```

工作树可能已经有用户的未提交修改。代理开始任务前应识别这些文件，而不是把它们当成自己造成的错误去还原。若同一文件同时需要修改，先读现有差异，理解用户意图，再在其上做最小调整。

基线可以包含未提交修改，关键是记清当前状态。例如测试原本就失败，而本次只改文档；或依赖锁已经由用户更新。这些信息有助于判断后续失败是否由本轮造成。

## 11.2 应用补丁需要检查上下文

补丁通常包含目标路径、上下文行和修改内容。文件已经变化时，补丁可能无法匹配，或只能部分应用。不要为了让工具返回成功而强行删除上下文、扩大替换范围。先重新读取目标段落，确认旧假设为何失效。

若修改涉及重命名，还要搜索引用、测试路径和配置文件。Git 能显示文件移动，但它不会自动保证所有运行时引用正确。代理也不能只因为编译通过，就忽略文档、脚本或生成产物中的旧路径。

## 11.3 生成文件应沿生成链修改

仓库里常有构建出的 HTML、索引或代码。如果直接修改生成文件，下一次构建就可能覆盖。项目指令应说明源文件与生成命令，代理交付时也应报告源与产物是否同步。

本书所在仓库的电子书就是例子：Markdown 是内容来源，HTML/PDF/EPUB 由构建器生成。修正文档应改 Markdown，再实际构建；不能直接把 PDF 文本当成可维护源码。这个原则同样适用于 API client、数据库迁移快照和资源清单。

## 11.4 审阅差异要回答三个问题

第一，修改是否解决了用户提出的具体问题。第二，它有没有引入不必要的范围扩张。第三，验证是否覆盖了变化带来的风险。只看行数少不够，五行认证逻辑可能比几百行排版变化影响更大。

```text
问题：1001 克与 2001 克的运费少算一档。
修改：把整数向下取整改为向上取整，保留类型和范围校验。
验证：运行现有边界、类型与范围用例，核对差异没有修改测试预期。
```

审阅者可以按这份说明代入两个重量、查看取整公式，再核对实际运行的用例。说明中的检查范围也只涵盖本次执行的内容。

## 11.5 撤回要区分已提交和未提交

未提交修改、已有提交、已经推送到共享分支的提交，撤回方式不同。团队历史应优先保持可理解，不能为了清理本地体验而擅自重写他人的提交。对于用户原有修改，更不能用一条宽泛还原命令一并清掉。

可以先把代理修改放在独立分支或工作树，再由人审查合并。即使任务失败，研究过程中有用的日志和最小复现也可以保留。恢复到已知状态前，确认要保留的工作已经明确识别。

## 11.6 `codex apply` 与普通本地编辑

固定 CLI 帮助中，`apply` 用于把代理产生的最新 diff 按 `git apply` 方式应用到本地工作树。它是特定入口，不能用它概括所有本地工具修改。代理也可能通过文件工具、shell 脚本或其他执行器直接改文件。

因此审计应围绕最终文件差异，不能只数“应用了几次补丁”。如果一个脚本改了十个文件，工具调用数量可能只有一次；若补丁应用失败，也可能仍有此前成功的修改。任务结束时重新读取 `git diff` 是必要的收尾动作。

## 11.7 真正修复运费边界

打开运费副本中的实现文件。下面是模板保留的错误公式；如果已经手动修过，先保存现有成果，要重做时从原模板另取副本：

```python
def fee_cents(grams):
    if type(grams) is not int:
        raise TypeError("grams must be an integer")
    if not 1 <= grams <= 30_000:
        raise ValueError("grams must be between 1 and 30000")
    kilograms = grams // 1000
    return 600 + max(0, kilograms - 1) * 200
```

把 1001 代进去，整除结果是 1，附加千克数为 0，所以得到 600。需求要求任何超出首千克的部分进入下一档，整数向上取整应写成 `(grams + 999) // 1000`。修改只有一行：

```diff
-    kilograms = grams // 1000
+    kilograms = (grams + 999) // 1000
```

`round(grams / 1000)` 仍会把 1001 克算作 1 千克，还引入浮点除法；直接给价格加 200，又会让 1000 克涨价。将相邻边界值代入，就能看出这两种改法不符合计费要求。

类型检查使用 `type(grams) is not int`，以排除 Python 布尔值。`bool` 是 `int` 的子类，换成 `isinstance(grams, int)` 会接受 True，而本项目不接受这类重量。修复公式时应保留原校验。

## 11.8 用例要能击中错误，也要守住原行为

完整测试文件已经随书提供。价格表覆盖每个关键区间：

| 输入克数 | 预期分数 | 这一项检查什么 |
| --- | --- | --- |
| 1 | 600 | 最小有效重量仍收费首档 |
| 1000 | 600 | 刚好首千克不额外收费 |
| 1001 | 800 | 超出一克进入下一档 |
| 2000 | 800 | 刚好第二千克不多收费 |
| 2001 | 1000 | 同类边界在下一档仍正确 |
| 30000 | 6400 | 最大有效重量 |

另有类型与范围用例：True、字符串、浮点数、None 触发 TypeError；0、负数和超过上限触发 ValueError。测试不是照着新公式复制一个计算式，再比较两边是否相等；它把业务预期写成具体数字，因此能在公式改变时独立指出偏差。

第 1 章的 `check_workshop.py` 将模板复制到临时目录，运行错误版测试，只替换公式，再运行同一测试。实际结果为修复前 exit 1、修复后 exit 0；修改由 Python 驱动完成，未调用 Codex 模型。你手边的副本需要自己修改，并运行下一节的检查。若之后想比较模型修复，保留这份结果，另取同一错误基线交给模型。

## 11.9 把最终差异和测试证据连起来

修改后，在运费项目目录依次查看工作树差异与测试结果。若同时出现 `test_parcel.py` 大量删除、依赖文件更新、全目录格式化，就需要解释这些变化与一行取整修复有什么关系。它们可能有合理原因，但不能因为测试变绿就忽略额外范围。

```powershell
git diff -- parcel.py test_parcel.py
python -B -m unittest -v
git diff --check
```

`git diff --check` 检查空白等补丁问题，不会验证运费行为；单元测试检查函数行为，不会证明暂存区没有额外文件。准备提交时，还要读取 `git diff --cached`，确认要提交的正是刚刚检查的内容。

如果测试完成后又编辑了文件，旧测试记录不能自动覆盖新状态。可以保存测试时源码哈希，或者更简单地在最后一次修改后重跑这组很短的测试。对大型项目则按变化范围选择检查，但要让记录对应当前代码，而不是某个相近版本。

## 11.10 补丁冲突时保留问题的最小范围

假设另一位协作者已经把变量 `kilograms` 改名，原补丁上下文就可能匹配失败。此时重新读取函数，确认取整行为，再调整具体行。不要把整个文件覆盖成教材版本，否则可能丢掉协作者新增的校验和说明。

这一行修改可以直接对照原失败用例和修复后测试审阅。最终提交围绕取整问题保留必要改动，讨论中探索过而未采用的方案留在任务记录即可。
