# 第 14 章：把 exec 放进脚本，完成条件要自己写清楚

<!-- block: codex-ch14.b-opening -->
非交互任务应同时保存退出码、事件与最终输出，并用项目检查验证实际改动，不能只读取最后一句答复。

给 CI 命令加上 `--json` 后，还要编写错误、审批和结果处理。终端里的用户可以追问，脚本则必须自己识别空文件、失败和超时，决定后续是否继续。

本章有两种跟做方式。没有模型配置时，先到“离线读一段完整 JSONL”，用随书数据读懂完成与失败，再回来理解输出选项。准备运行真实任务时，从“把运费任务写成可以核对的输入”开始，使用一份仍保留错误公式的运费副本。第 12 章的插件安装不是这项任务的前提。

## 14.1 四种输出，各有用途

<!-- block: codex-ch14.b-term-jsonl -->
`exec` 的帮助列出 JSONL 事件输出、最终消息文件和输出 schema 等选项。它们解决不同问题：事件记录过程，最后消息面向读者，schema 限制最终结构，退出码表达进程结果。

下面是只读分析示例，在要检查的项目目录运行，并先准备该目录下的 .scratch 输出目录。它演示如何保存最后答复；后面的运费修复入口会另外保存完整事件与诊断日志。

```powershell
codex.cmd exec --json --output-last-message .scratch/result.md `
  --sandbox read-only "检查当前仓库的测试入口并列出缺少的验证"
```

这条命令需要读者自己的可用模型配置，未在本书真实运行。脚本应立即保存退出状态，再进行日志处理，避免后续命令覆盖原始结果。PowerShell 的 `$LASTEXITCODE` 与 Bash 的管道退出行为不同，应按所用 shell 实现。

本书所用版本的 exec 源码开头明确约定：`--json` 模式 stdout 必须是逐行合法 JSONL。不要向这个流里混入你自己的进度文字；诊断信息使用单独日志或 stderr。否则一个正常消息就可能把下游 JSON 解析器弄坏。

## 14.2 最终结构化输出不等于结构化全过程

```json
{
  "type": "object",
  "properties": {
    "summary": {"type": "string"},
    "checks_run": {"type": "array", "items": {"type": "string"}},
    "remaining_risks": {"type": "array", "items": {"type": "string"}}
  },
  "required": ["summary", "checks_run", "remaining_risks"],
  "additionalProperties": false
}
```

这是原创的最终报告 schema。`--output-schema` 可以用于约束模型最后回答的形状，但不能证明 `checks_run` 中每条命令真的执行过。要核实检查，仍应对照事件与实际测试日志。

报告结构要能表达失败和未测项。只接受 `success: true` 与一段说明，会限制失败的表达；这里增加 `remaining_risks` 保存尚未确认的事项，业务系统也应保留相应状态。

## 14.3 无人值守时处理审批

这一版本的 exec 通过进程内 app-server 客户端运行。其服务器请求处理函数会拒绝命令执行审批、文件变更审批与用户输入请求，MCP elicitation 则按取消处理；这些不是普通终端用户可随时点击的完整交互体验。把需要人工输入才能完成的工作流塞进普通 CI，会遇到明确的不支持路径。

可以将工作流拆成两个阶段：先生成差异与报告，运行自动检查；再由有权限的人审阅这些产物，触发发布或其他外部动作。

## 14.4 失败不应被日志处理吞掉

同版本 exec 的事件循环给出了具体判断方法。它按主线程 ID 和当前回合 ID 筛选通知：当前回合收到不再重试的 `Error`，或结束状态是 `Failed`、`Interrupted`，就会设置 `error_seen`。关闭客户端之后，程序仍会调用 `print_final_output`，随后才根据这个标记以状态码 1 退出。程序写出了最后一段文字，仍可能以失败状态退出；脚本必须保留退出码。

中断也有明确对象。收到中断信号后，exec 发送带有当前 `thread_id` 和 `turn_id` 的 `turn/interrupt`，随后继续接收事件。用户按下 Ctrl-C 不是立即把当前任务的所有痕迹清空，已完成的文件修改仍要通过 Git 差异检查。

一个常见错误是 `command | tee log` 后只看最后一个程序的退出码。另一个是捕获异常后写出“请查看日志”，却让 CI 返回零。这样流水线会绿，但实际任务失败。

跨平台脚本可以使用结构化子进程调用，分别保存 returncode、stdout、stderr，再决定退出码。上传失败日志之后，继续保留原失败状态。

```python
# 教学框架：真实命令和凭据由使用者自己的 CI 配置提供。
import subprocess
from pathlib import Path

result = subprocess.run(command_args, capture_output=True, text=True)
Path("events.jsonl").write_text(result.stdout, encoding="utf-8")
Path("diagnostics.log").write_text(result.stderr, encoding="utf-8")
raise SystemExit(result.returncode)
```

`command_args` 在这里刻意留作调用者提供的参数数组，它不是可以原样运行的完整脚本。发布版脚本应加入超时、工作目录、编码和产物验证，并避免在异常中输出凭据。

## 14.5 任务完成的三道检查

第一道是运行完成：进程与回合到达明确终态。第二道是产物存在且可读：所要求的文件确实生成，内容不是空占位。第三道是行为正确：项目测试、构建或人工检查符合目标。

运行结束、产物可读和行为正确需要分别检查：代理可能结束了却未实现需求，PDF 可能存在却无法打开，测试也可能漏掉新分支。CI 的检查应覆盖任务实际需要的这些结果。

对于修改代码的任务，还应在结束后保存差异摘要。必要时将产物、日志和基线提交关联，方便之后重现。不要把日志当成永久无限增长的存储；设置保留时间，并根据敏感程度控制访问。

## 14.6 固定输入，逐步扩大自动化

可以从只读分析开始，固定仓库版本和输入，比较多次运行的输出结构与错误处理；稳定后加入可逆文件修改，再考虑外部操作。每次扩展能力，都增加对应的行为检查。

对开放来源的仓库输入，要把内容视为数据。issue 正文、README 或日志中的句子可能看起来像指令，但它们不自动成为用户授权。工作流自身应说明哪些来源可以提供任务目标，哪些只用于分析。

## 14.7 把运费任务写成可以核对的输入

进入第 3 章复制的运费项目，确认原测试仍会失败。如果第 11 章已经手动修好，保留那份结果，从模板另取新副本；否则模型接到的是已经完成的任务，无法观察修复过程。项目说明与测试已经足够表达本次要求，技能可在完成真实发现验证后再接入。任务文本可以写成：

```text
修复 parcel.py 中 1001 克与 2001 克的收费边界。
先运行 python -B -m unittest -v，确认失败输入。
金额保持整数分，重量保持整数克，保留类型和范围校验。
不增加依赖，不删除测试。改完运行同一组测试并检查 Git 差异。
最终返回 summary、changed_files、checks、remaining 四个字段。
```

配套 `report.schema.json` 已在模板中，与实现文件位于同一层，四个字段都是必需项，且拒绝额外字段。summary 是字符串，其余是字符串数组。这里使用的是运费任务的报告格式，前面的三字段 schema 仅用于解释结构化输出，不要用它覆盖模板文件。这份 schema 约束最后报告的形状，不会自动运行 checks 里提到的命令。报告写“测试通过”，仍要与事件中的命令和实际输出对照。

具备自己的模型配置后，可以在项目副本运行下面的命令。此处是读者的完整任务入口，本册没有实际调用模型：

```powershell
codex.cmd exec --json --sandbox workspace-write `
  --output-schema report.schema.json `
  --output-last-message result.json `
  "修复 parcel.py 的重量取整边界，遵守 AGENTS.md，保留全部测试。" `
  1> events.jsonl 2> diagnostics.log
$taskExit = $LASTEXITCODE
Write-Output $taskExit
```

立即把 `$LASTEXITCODE` 保存到自己的变量，后续的日志处理才不会覆盖它。PowerShell 的文本重定向编码随版本存在差别；若 JSONL 读起来不是 UTF-8，先确认 shell 版本或用下面的 Python 调用器明确处理字节，不要把编码错误误诊成模型没有遵守 JSON。

## 14.8 一个保留原始输出的完整调用器

下面的程序可保存为 `run_codex.py`，并从运费项目目录启动；程序以当前目录查找报告 schema 和运行任务。它与上一节的 PowerShell 命令是两种调用方式，选择其中一种即可，不必连续执行两遍修复。参数是原生 Codex 程序的明确路径；它把完整任务交给该程序，所以只有读者配置好真实环境并决定运行时才使用。Windows npm 的 `.cmd` 包装器不属于本例的原生程序参数。

```python
import argparse
import json
import subprocess
from pathlib import Path

parser = argparse.ArgumentParser()
parser.add_argument("--binary", required=True, type=Path)
args = parser.parse_args()
root = Path.cwd()
output = root / "run-output"
output.mkdir(exist_ok=False)
command = [str(args.binary.resolve()), "exec", "--json",
           "--sandbox", "workspace-write",
           "--output-schema", str(root / "report.schema.json"),
           "--output-last-message", str(output / "result.json"),
           "Fix the parcel weight rounding boundary; follow AGENTS.md."]
with (output / "events.jsonl").open("wb") as stdout, \
     (output / "diagnostics.log").open("wb") as stderr:
    process = subprocess.run(command, cwd=root, stdout=stdout, stderr=stderr)
(output / "process.json").write_text(
    json.dumps({"exit_code": process.returncode}, indent=2) + "\n",
    encoding="utf-8",
)
raise SystemExit(process.returncode)
```

`exist_ok=False` 防止覆盖上一轮记录。再次运行时，指定新的输出目录或使用新的运行编号，保留旧结果。stdout 和 stderr 直接写入二进制文件，省去调用器的解码与编码；读取时再按 CLI 输出契约处理。

这段调用器没有设置超时，读者需在 CI 工作流和执行环境中补上任务时限、进程树终止与现场保留策略。超时应保留中断状态。第 17 章继续讨论怎样读取中断后的文件和日志。

## 14.9 离线读一段完整 JSONL

本书的三份 `exec-*.jsonl` 是人工编写的协议练习数据。`exec-success.jsonl` 从 thread.started 开始，经过 turn.started、命令 item 开始和结束、最后消息，最终到 turn.completed。以下是其中的关键两行：

```json
{"type":"item.completed","item":{"id":"test-1","type":"command_execution","command":"python -B -m unittest -v","aggregated_output":"Ran 3 tests\nOK","exit_code":0,"status":"completed"}}
{"type":"turn.completed","usage":{"input_tokens":0,"cached_input_tokens":0,"cache_write_input_tokens":0,"output_tokens":0,"reasoning_output_tokens":0}}
```

零 token 是为了明确它是 fixture，不是实际用量。固定 `exec_events.rs` 用 type 区分顶层事件，item 内部又有自己的 type；解析时要处理这两层。只按文件里是否出现字符串 `completed` 搜索，会把命令完成和回合完成混为一谈。

以下命令切回书籍仓库根目录运行，读取的是随书 fixture；它们与刚才真实任务的输出文件分开放置：

```powershell
python -B codex/examples/inspect_exec.py codex/examples/fixtures/exec-success.jsonl --exit-code 0
python -B codex/examples/inspect_exec.py codex/examples/fixtures/exec-command-failed.jsonl --exit-code 0
python -B codex/examples/inspect_exec.py codex/examples/fixtures/exec-incomplete.jsonl --exit-code 0
```

第一条输出 `stream_ok: true`、`needs_review: false`，脚本退出 0。第二条回合正常结束，但 test-1 非零，所以 `needs_review: true`，脚本退出 1。第三条缺少终态且有未完成 item，也退出 1。再给第一份文件传 `--exit-code 1`，即便事件内容看起来完整，结果仍需检查。

检查自己的真实日志时，仍从书籍仓库运行这个检查器，将输入文件换成运费项目中保存的事件文件完整路径，并传入当时记录的进程退出码。PowerShell 示例把文件写在项目目录，Python 调用器则写在项目的 run-output 下；不要把检查器自己的退出码当成 Codex 的退出码。

## 14.10 检查器如何保留不同层面的失败

`inspect_exec.py` 逐行解析 JSON，以 item.id 保存该活动最新对象。它允许只有 item.completed 的项目，因为固定类型中有些活动只在完成时发出；但遇到没有 item.id 的对象会报错。它还记录未知事件、重复 thread、终态之后出现事件等异常。

`stream_ok` 只回答一轮事件记录和进程状态是否一致完整；`failed_commands` 保存没有成功的命令；`failed_items` 保存失败或被拒绝的活动；`unfinished_items` 保存未终结对象。最终 `needs_review` 把这些事实合起来。保留分项使读者能看出失败到底在传输、执行还是工作内容。

这个检查器有意把“复现失败后再修复成功”留给审阅。它不会因为后面出现一次 exit 0，就删除前面失败命令的记录；也不自动猜两次命令是否验证同一对象。要做更自动化的门禁，需要明确测试身份、代码版本和允许的复现阶段，再定义成功条件。

对运费修复，事件检查之后回到运费项目，按第 11 章读公式差异，运行当前工作树的测试。完整的 events.jsonl 可能只记录了一轮问题解释，需要项目检查确认修改已完成。CI 分别保存事件检查、报告 schema 校验和项目测试的输出即可。若得到的是缺少终态的记录，下一步接第 17 章排查现场。
