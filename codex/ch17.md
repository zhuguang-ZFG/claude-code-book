# 第 17 章：从失败现场恢复任务

<!-- block: codex-ch17.b-opening -->
排错先确定失败阶段与已发生副作用，再选择恢复、重试或开始新任务；保存证据比盲目重跑更有用。

模型连接、命令启动、测试、审批和客户端显示都可能失败，恢复方法各不相同。本章先定位最后完成的动作，再用一份不完整的 JSONL 记录检查日志、进程和工作树，决定从哪里继续。

沿用第 14 章最后一份不完整 fixture，就能先练习读故障记录，不必故意中断真实任务。日志检查在书籍仓库进行；需要确认公式与测试的现状时，再回到运费副本。已有真实运行记录的读者，用自己的日志和退出码替换教学数据。

## 17.1 先确认最后一个可靠事实

把任务链倒着看：最后一个明确成功的事件是什么？文件已经写入了吗？进程已经启动了吗？审批是否收到回应？模型响应是否已经形成完整工具参数？先找到这一点，再看之后的缺口。

| 现象 | 首先检查 | 不应立刻推断 |
| --- | --- | --- |
| 参数被拒绝 | 固定版本帮助和配置 schema | 模型服务不可用 |
| 任务无输出 | 连接、进程状态、stderr | 任务从未开始 |
| 命令非零 | 程序契约和原始错误 | 所有修改都已回滚 |
| 会话恢复后结论过时 | Git 基线和现有文件 | 恢复功能没有保存历史 |
| Hook 没有执行 | 发现、启用、信任与事件条件 | 脚本内容一定错误 |

错误报告可以围绕这张表组织。不要只给一张终端截图，最好保留可复制的命令和脱敏文本；截图容易遗漏退出码、前置警告和参数转义。

## 17.2 把重试分为三类

第一类是无副作用查询，例如版本与显式规则检查，通常可以安全重复。第二类是可逆的本地修改，需要先检查部分结果，再决定是否重做。第三类是外部副作用，例如推送、发消息、提交业务任务，必须先查询是否已经发生。

分类时要读具体动作的契约和当前状态。一条 shell 命令可能只读，也可能调用外部 API；查询工具也可能触发刷新或写缓存，仅凭名称无法判断能否重复。

对于模型请求，网络重试还要考虑运行时是否已经执行上一批工具。客户端断开与服务端停止并不同时发生。恢复前读取线程状态或检查文件，能减少重复执行。

## 17.3 日志应帮助定位，而不是收集一切

保存时间、版本、入口、任务 ID、命令摘要、退出状态和错误类别，通常比保存完整环境更有价值。敏感参数、账号令牌、个人文件正文应避免进入公开日志。需要原始数据复现时，在受控位置保存，并另外生成脱敏版本。

本书规则实验未启动会话，记录固定命令 token、匹配规则和二进制摘要即可复核结果，无需公布账号配置。其他实验也可先确定要检查的问题，再选择需要保存的字段。

## 17.4 用最小复现区分版本与环境

当一个复杂任务失败时，抽出最小输入，在同一版本运行。如果失败仍在，再比较另一版本；若最小输入不失败，逐步加回配置与文件。一次只改变一个因素，才能判断关键差异。

第 10 章的错误正例就是这种方法：只写一条规则，让它声称一个不匹配命令应匹配。固定 CLI 返回非零，因此我们知道加载器验证了例子，不需要启动整个模型会话来推断。

升级问题也可以用这种方式处理。先保持旧版本结果和输入，记录新版本的不同输出；不要立刻改测试让它通过。测试变更应说明契约为何改变，而不是把每个新行为自动接受为正确。

## 17.5 恢复记录应写给下一位接手者

下面借一个依赖数据库的项目说明交接格式，运费练习本身没有数据库。记录它时，填写自己实际完成的公式修改、测试与待处理事项即可：

```text
目标：修复空输入崩溃。
基线：提交与工作树状态已记录。
已完成：增加边界处理，相关单元测试通过。
未完成：集成测试因数据库未启动而未运行。
下一步：启动测试数据库后重跑指定命令，再检查最终差异。
```

这份记录列出已完成工作、未确认事项和下一步操作，接手者可以直接从缺失的集成测试继续。跨多个会话的任务也可沿用这种写法。

用户改变目标后，更新记录中的当前目标，并标清旧计划哪些已经失效，后续工作就有明确依据。

## 17.6 故障结束之后留下可复用知识

值得保留的是触发条件、根因、修复与防止复发的方法。例如“PowerShell 选择了被策略阻止的 ps1，改用同包 cmd 入口”是可复用结论；“重试第三次就好了”只是现象。网络间歇错误若未确定根因，也应诚实写成暂时恢复，不要编一个确定解释。

同类问题反复发生时，可以让脚本自动核对版本、规则输入或产物，将已确定的修复条件加入工作流。

## 17.7 从一份“不完整但退出为零”的记录排查

打开书籍仓库 codex/examples/ 下的 `fixtures/exec-incomplete.jsonl`，它就是上一章检查的第三份数据。它只有 thread 开始、turn 开始和一条命令开始，没有命令结束或回合终态。文件本身每行都能解析成 JSON，但这一点无法证明任务完成。日志截断、父进程提前退出、输出复制不完整，都可能留下这种形状。

在书籍仓库根目录沿用第 14 章的第三条检查命令：运行 `inspect_exec.py`，传入 `--exit-code 0`，结果仍为 `stream_ok: false`：`turn_terminal` 是 null，`unfinished_items` 含 test-1。检查器据此保留“进程退出为零，但事件尚不完整”的状态。

排查时先检查原始日志是否完整：文件是否还在增长、是否读取了当前运行目录、是否被上传工具截断。再看进程记录：究竟是 Codex 的退出码，还是执行 `type`、`cat`、压缩或上传日志那条命令的退出码。若退出码采集位置错误，修改模型提示词没有帮助。

真实运行出现同样现象时，最后要回到运费项目检查工作树；教学 fixture 本身不会修改任何项目。命令开始之后可能已经产生部分文件修改，即使没有终态事件也不能推断“什么都没发生”。重新读取公式、运行测试就能确认运费项目的现状；有网络写入的任务则还要查询目标服务，不能简单重试可能重复的副作用。

## 17.8 让失败用例指向不同责任层

把本书已有练习排成一张诊断表：

| 观察到的现象 | 先检查的对象 | 不应立即做的推断 |
| --- | --- | --- |
| 1001 克得到 600 分 | 取整公式与边界测试 | 模型或协议坏了 |
| ModuleNotFoundError | cwd、解释器、文件副本 | 沙箱阻止了测试 |
| Hook fixture 返回坏 JSON | 处理器 stdout 与字段 | 宿主没有发现插件 |
| Hook 修改后不运行 | 声明与内容信任、启用状态 | matcher 必然错误 |
| thread_id 校验失败 | 接口字段名 | thread 身份已过期 |
| turn 完成但测试 exit 1 | 任务目标与命令结果 | 回合一定失败 |
| 最后报告存在但进程 exit 1 | exec 终态与错误通知 | 只要有报告就可发布 |

表格给出首个排查位置，原因仍需继续核对。以 Hook 为例，直接运行 `hook_guard.py` 通过后，下一步查宿主是否找到配置、是否启动了 Python。分别保留脚本结果与宿主记录，可以缩小故障范围。

## 17.9 恢复前保存一个足够小的现场

对运费仓库，保留这些信息就足够继续工作：当前提交或无提交状态、`git status --short`、`git diff -- parcel.py test_parcel.py`、测试日志和进程退出码，以及本次使用的 CLI 版本。若确实运行过代理，再加 thread 身份和本次 events.jsonl。

不必为一个小问题导出所有用户配置。认证文件、环境变量全量快照和完整个人 transcript 往往既无助于复现，又增加无关信息。需要配置时，构造包含相关字段的最小配置；需要 Hook 输入时，使用本书这种明确的 fixture，先确认问题能否在简化输入上重现。

保存现场后，按现状继续：公式修好且测试通过，核对差异并补交付说明；公式未改，继续修复；测试发生变化，先确认修改原因。这样可以保留已有有效工作。

## 17.10 为重试区分可重复动作和不可重复动作

读取文件、计算哈希、运行无副作用的运费单元测试通常可以重复。写入最终报告需要考虑覆盖旧结果；提交可能产生新的历史；外部发布、付款、发消息则可能造成重复副作用。恢复流程应先分类，再决定自动重试范围。

假设任务在“测试通过”后、“写入 result.json”前中断。重跑测试并写到新结果目录是合理的；把原目录全部清空再执行，可能丢掉第一次失败证据。若任务已推送提交而客户端断线，下一步应查询远端状态，不能仅凭本地未收到成功消息再次发布。

本书自动检查脚本在临时副本里修复一行，结束后删除自己创建的临时目录；它不触碰读者工作树。这种可重跑性来自明确的文件所有权。给真实代理设计工作流时，也要说明它拥有哪个目录和哪些输出，避免“清理临时文件”跨出本次任务范围。

## 17.11 对照固定 exec 的退出路径

固定 `exec/src/lib.rs` 中，当前主线程和当前 turn 的不可重试 Error 会设置错误标记；当前 turn 终态为 Failed 或 Interrupted 也会设置它。事件处理器决定何时关闭，随后 client.shutdown，再输出最终内容，最后按错误标记退出 1。这条顺序解释了为什么自然语言结果可能已经保存，进程仍明确失败。

工具的非零退出不一定设置上述标记。代理可以先运行失败测试复现问题，再继续修复。离线检查器因此单列失败命令，保留它在任务中的位置，由审阅者结合最终目标与状态判断。

排错完成后，把最小复现留在项目中。此次是 1001 和 2001 克两个边界；一次 Hook 故障则可以留下触发它的 stdin；一次客户端故障则留下脱敏消息序列。下一次升级重新运行这些小例子，比再读一遍很长的聊天记录更快。
