# 第 11 章：插件事件与 next

<!-- block: deepseek-ch11.b-opening -->
两个插件都监听同一个事件，一个负责计时，一个负责权限。计时器写得很简单，却让后面的工具再也没有执行。原因可能只有一行：它没有调用 next。要读懂这类问题，先确定事件使用哪种分发方式。

## 11.1 先查模式，再写回调

| 模式 | 调用者是否等待 | 常见用途 |
| --- | --- | --- |
| emit | 不等待异步返回 | 同步通知与观察 |
| parallel | 等待并发监听完成 | 可并行的协作工作 |
| serial | 逐个等待，遇 bail 值停止 | 有序决策或阶段通知 |
| bail | 同步寻找首个有效结果 | 快速选择实现 |
| waterfall | 由 next 构成环绕返回链 | 拦截、包装与短路 |

事件声明的 mode 决定调用约定。同步 emit 的监听器即使写成 async，发送者也不会自动等待；parallel 并发执行监听器，若 B 依赖 A 写完数据，就需要另行表达这个顺序。

## 11.2 Waterfall 从外到内，再从内到外

这里的中间件是包在实际动作外面的一层函数。它拿到的 next 用来进入下一层；await next() 等里面的工作结束后，当前函数才继续往下走。reviewWrapper 就是先记 before，等待 next，再记 after，最后原样返回结果。两个包装器 A、B 的组件实跑顺序如下：

```text
A:before:x.ts
B:before:x.ts
body
B:after
A:after
```

结果仍是 body 返回的 read-result。这不是把每个插件的结果放进数组再合并，而是一条嵌套调用链。外层可以捕获内层错误、改变结果或根本不进入内层。

```javascript
ctx.on('book/dispatch', async (request, next) => {
  const started = performance.now();
  try {
    return await next();
  } finally {
    record({ file: request.file,
             durationMs: performance.now() - started });
  }
});
```

把记录放进 finally 能覆盖内层抛错，但记录动作本身也可能失败。观察器若因日志失败替换了原始错误，会让用户失去真正原因。要不要吞日志错误、怎样限制日志延迟，应由观察器自己的契约决定。

## 11.3 不调用 next 有时正是需求

权限插件决定拒绝时，不应继续调用工具主体。实验里的 veto 监听直接返回 blocked；断言确认 body 没有执行。问题不在于短路本身，而在于观察型插件意外短路，或者决策插件在拒绝后仍然调用 next。

回调的职责会影响 next 的用法：观察器通常委派并保留结果，变换器修改约定字段，决策者可以截断。把这些行为写清楚，就能判断一次短路是否符合设计。

调用两次 next 也不是重试办法。固定版本的事件实现为每层维护 called 标记，第二次会抛 `next() called multiple times`，本书已实跑确认。重试应进入专门的请求恢复或工具机制，不能重进一个已经向前推进的中间件游标。

## 11.4 前置顺序与全局耦合

prepend 能让监听器排到普通注册前面，但多个插件都声称自己必须第一，就会形成隐含竞争。一个策略依赖另一个策略先完成时，应考虑把关系表达成服务或明确组合，而不是不断 prepend。

系统提示词组装、pre-step、模型请求和工具管线各有自己的 waterfall。若读过 OpenCode 册第 8 章，需要留意接口差异：那里 V1 trigger 通过修改共享 output 传递结果，忽略回调返回值；这里 Cordis waterfall 的返回链则是协议的一部分。两种机制都能用来实现 Hook，代码不能直接互换。

## 11.5 选择错误传播方式

在环绕链中 await next 才能让外层 try/catch 捕获异步失败。只写 next 然后立即 return，会把 Promise 留在另一条路径，记录的 after 也会过早发生。emit 不等待 Promise，因此需要异步协作的地方应选择相应模式，而不是把每个监听器都写成 fire-and-forget。

遇到链路卡住，逐层记录进入、委派、返回和异常四个位置。若只看到 A 进入，看不到 B 进入，先检查 A 是否委派；若看到主体完成却无 A 返回，检查等待的日志或清理是否悬挂。这样的定位方式能避免把每次卡住都归咎于模型服务。

## 11.6 错误沿哪一条链返回

给计时插件加上 try/finally，可以记录失败耗时；给它加 catch 并返回一个普通值，则可能把失败变成成功。两者表面上都“处理了错误”，但对调用者的含义完全不同。默认做法应是保留内层返回值和原始错误，只有明确承担错误映射责任的中间件才改变它们。

权限插件 P 与重试插件 R 的顺序会改变行为。R 包在 P 外面时，可能把拒绝当作临时故障重试；P 在最外面时，拒绝后 R 不会进入。选择顺序前，需要确定哪些错误允许重试、重试是否重新审批，以及如何识别已经发生的工具副作用。

日志也应区分进入、离开和完成。before 只说明监听器收到调用；after 可能在 body 返回后出现，但若外层随后失败，整个请求仍没有成功。要统计最终工具结局，应使用 tools/result 这类明确观察点；要测某个环绕层的耗时，才在那一层记时间。把不同阶段的计数器都叫 success，会让故障分析出现互相矛盾的数字。

A/B 实验验证了普通注册顺序下的委派与返回链。交换 A、B 或让 body 抛错，可以继续观察顺序变化；这些是扩展练习，需要另存运行记录，现有事实文件只对应原场景。

## 11.7 沿着 ReviewTools.call 走一遍

连续实例的 ReviewTools.call 做三件事：找到定义，复制调用参数，进入 book/execute waterfall。找不到定义时先抛 TOOL_NOT_FOUND，连策略层都不进入。找到后使用递增 id 创建 request，并冻结顶层对象；策略和工具收到同一份调用身份。

```javascript
const request = Object.freeze({
  id: ++this.nextId,
  name,
  args: Object.freeze(structuredClone(args)),
});
return this.ctx.waterfall('book/execute', request,
  () => entry.execute(request));
```

最后一个函数就是本次调用的最内层。只有每个外层都继续委派，它才会执行。book/execute 是本书自己定义的事件，名字与官方 tools/execute 不同；这里把调用链缩到足以完整阅读，再去理解官方管线中的更多阶段。

policy 在 before 记录之后检查 reject。拒绝时抛 POLICY_DENIED，既不调用 next，也不进入后面的 try/finally。因此本例拒绝日志只有 policy:before:1，没有 policy:after:1。这里的 after 表示已经委派的内部调用收敛，不表示策略回调无论做了什么都结束。命名和放置位置必须一起读。

正常分支使用 `return await next()`。return 把内部结果交还调用者，await 让 finally 真正包住内部 Promise 的结算。若写成 `return next()`，函数仍会返回这个 Promise，但 finally 会在返回动作时执行，计时可能提前结束。若只写 `await next()` 忘了 return，工具算出的结构化值就丢了。

## 11.8 callbacks 副本与每层 called 标记

events.ts 的 `_resolve()` 先识别可选 thisArg 与事件名，再从 `_hooks[name]` 选出符合过滤条件的 Hook，映射成 callback 数组。waterfall 使用这份本次分发的数组，取出最后一个 inner，再由 dispatch 逐个 shift。每次进入一个 callback，都会创建属于这一层的 called 布尔值和 next 闭包。

每个 next 都绑定到本次分发的某一层游标。首次调用置 called=true 并向内推进，第二次直接抛错；这也是前面重复 next 实验失败的具体位置。

还有一个容易误读的地方：某监听器被从全局注册表撤掉，不会凭空修改已经取得的 callbacks 数组。撤销注册阻止未来分发再选中它，正在进行的业务需要自己的取消与等待。连续实例的插件 disposer 才会主动给 active 调用发 abort；不能因为它的监听器已撤掉，就以为先前进入监听器的 Promise 自动消失。

ctx.on 的返回值也不是监听结果。它是撤销这次注册的函数。事件服务把注册封装进当前 fiber.effect，清理时按 callback 身份从 Hook 数组移除。业务回调返回什么，由 emit、serial、waterfall 等分发方式决定；注册函数返回什么，由资源管理决定。这两个返回通道在代码里都可能写 return，职责却不同。

## 11.9 false 和零为什么不一样

新实验为 book/select 连续注册三个监听器：第一个返回 false，第二个返回 0，第三个返回 7。serial 得到的最终值是 0，记录只有 false、zero，第三个没有执行。按照普通 JavaScript 真值习惯，0 和 false 都是假值，但这里不能使用 `if (result)` 代替框架的判定。

固定实现的 isBailed 明确只排除 null、false 和 undefined。零、空字符串与其他值都能终止 bail 风格分发。这个选择允许某些查询以零表示一个有效结果：例如“允许的追加次数是零”，不能被误当成没有回答，继续让后面的默认值覆盖。

```javascript
ctx.on('book/select', async () => false);
ctx.on('book/select', async () => 0);
ctx.on('book/select', async () => 7);
const selected = await ctx.serial('book/select'); // 0
```

插件作者应根据事件契约选择“没有意见”的返回值。一个只想观察的 async 监听器，如果最后写了 `return records.push(event)`，push 返回数组新长度，这个正数就可能截断后续监听器。错误甚至不是刻意的决策，只是把便捷写法带进了有返回语义的事件。

## 11.10 parallel 的失败不会抢先宣告其他工作结束

events.ts 的 parallel 对每个回调创建异步任务，使用 Promise.allSettled 收集所有结果，最后把拒绝原因组成 AggregateError。它与一遇拒绝就让外部 await 返回的 Promise.all 有不同的等待边界。这里的“等所有”不等于“所有都成功”，只是没有把还在运行的监听器留在结论之后。

新实验让第一个监听器立刻抛 LISTENER_FAILED，第二个进入一个受控等待。第二个进入后，断言 parallel 还没结算；释放它以后，检查 AggregateError.errors 中仍是同一个错误对象，且慢监听器确实已完成。这个实验没有给其他工作自动发取消，固定实现也没有这样的承诺。

在业务上，这适合收集独立工作。若某监听器失败后必须停止其他监听器，应在事件之外建立共享取消协议，并让监听器遵守；不能仅因选择 parallel 就得到“失败取消全组”。相反，如果它们彼此依赖，就应重新考虑为何要同时执行。

## 11.11 once 先撤销，再调用用户代码

once 的实现可以压缩成两步：注册一个包装器，包装器先 dispose 自己，再调用原监听器。本书实验在监听器内部再次 emit 同名事件，计数仍是 1。这说明撤销发生在用户回调之前，递归发出事件也不会再次进入它。

如果自己写成“调用用户回调，最后移除监听器”，递归触发会在移除之前再次进入，轻则重复计数，重则无限递归。带 Promise 的回调还会延长这个窗口。源码把一次性保证放在同步进入处，避免把它依赖于回调是否顺利返回。

once 限制当前事件服务中这一份注册的调用次数。重启后重新注册，或由其他服务转发给不同监听器，业务事件仍可能再次执行。外部操作若要求只发生一次，还需要业务身份与持久去重。

## 11.12 让事件名字携带明确职责

连续实例只用了 book/execute 和 book/note。前者有返回值、可拒绝、必须等待；后者是同步内存记录，没有异步工作。它们的差异体现在代码路径，而不只是说明文档。以后若把 note 改为发网络日志，应该重新选择发送方式和失败处理，不能保持 emit 不变却假定调用者会等待上传。

新事件的分发方式取决于调用者需要什么：等待所有观察器完成可用 parallel，按首个有效答案决策可用 serial，需要包住实际执行则用 waterfall。返回值和错误传播也随这一选择确定。

这些实验对应几处常见故障：结果丢失查 return，after 太早查 await，后续监听未进入查 bail 值或 next，卸载后任务仍运行查取消过程，一次性回调重复则查移除时机。
