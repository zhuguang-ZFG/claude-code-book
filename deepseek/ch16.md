# 第 16 章：发布一个插件包

<!-- block: deepseek-ch16.b-opening -->
插件交给别人安装之前，需要核对包入口、版本约束、配置组合和卸载行为。本章先说明这些要求，再把连续实例打成本地包，从解包后的入口运行测试。

## 16.1 先决定包承担哪一种责任

单一观察插件可以放在一个包里；可替换能力通常需要分清接口、实现和消费者。例如文件系统契约、远程实现、模型可调用工具可以独立演进。过早拆成十个包会增加安装成本，但把所有职责塞进一个包又会让替换变得困难。

先用七项基础实验里的 review-observer 说明单插件包：它依赖 bookCounter，订阅事件并持有受管资源，不提供审计存储，也不启动模型。第 16.2–16.5 节据此讨论包装方式。第 16.6 节实际打包的是另一份程序 review-lab，也就是前面连续实例的工具表、日志与审查插件组合；它有自己的包入口，两个例子不需要合并。

## 16.2 元数据需要对应实际文件

包的 exports 指向发布后存在的 JavaScript 和声明文件，files 限定需要分发的内容。不能把本机 tsconfig 路径别名当成 npm 消费者一定拥有的能力。仓库内源码入口与发布入口的解析条件可能不同，要在新空目录中解包检查。

以下是单一观察插件的包结构示意，字段值需随实际构建产物调整。它不是随书 examples/package.json 的内容；复现本书实际包入口时，使用第 16.6 节的配置与命令。

```json
{
  "name": "book-review-observer",
  "version": "0.1.0",
  "type": "module",
  "exports": { ".": "./dist/index.js" },
  "files": ["dist", "README.md", "LICENSE"],
  "peerDependencies": { "@deepseek-ai/cordis": "4.1.0" }
}
```

指定 peer 范围表达需要哪份宿主契约，不等于代码已经兼容范围内每个版本。范围越宽，作者承担的验证就越多。本册固定快照的实践更适合先写窄范围，再用相同生命周期实验验证升级差异。

## 16.3 插件代码与 bundle 配置

模块插件提供执行逻辑，bundle 还可以携带补丁行，把一个或多个插件装进应用组合。profile 的 bundles 列表决定它们的层次。安装依赖、选中 bundle、启用 row、运行成功应分别检查，不应都显示成同一个“已安装”。

局部禁用 row 通常只写 disabled 覆盖；重新启用 bundle 会改变组合列表位置，可能改变后层优先级。用户升级包后“设置丢了”，有时其实是包内默认值变了，有时是 profile 仍覆盖旧 config。提供升级说明时应讲清楚哪些字段继续保留、哪些需要迁移。

完整包管理操作可能触发 HMR，也可能返回 restart-required。保存成功是磁盘状态，激活成功是运行状态；没有 HMR 的 profile 仍可能运行旧组合。界面和自动化都应展示这一区别，不能只检查 pnpm 退出码。

## 16.4 用打包产物做测试

下面两条通用命令在准备发布的插件包根目录执行，也就是该包 package.json 所在的目录。随书 review-lab 的命令显式指定了包目录，见第 16.6 节。

```powershell
npm.cmd pack --dry-run
npm.cmd pack
```

先检查列表不含 .env、缓存、上游源码副本或个人日志，再把生成的 tarball 安装到独立测试目录。测试目录只装公开声明的依赖，避免仓库根 node_modules 替你补齐漏声明的包。

运行加载、缺依赖、初始化失败、重复卸载、重新挂载和中间件短路测试。若包提供工具，还要加 schema 错误、取消、结果序列化和后端断线。对外发布前把运行版本、命令和边界写进 VERIFY；不要把静态类型通过写成宿主所有功能可用。

本册没有实际发布 npm 包，也没有向上游仓库发送消息。examples 是可直接运行的书籍样例，组件测试使用固定源码；上面的 pack 流程是读者把自己插件交给别人之前应做的检查。

## 16.5 许可证与升级说明

原创代码可以采用明确许可证；引用上游机制时链接固定 SHA。若分发了上游代码或资产，还要保留对应许可和归属。本书只提交原创样例与分析，下载的框架源码留在忽略目录。

升级说明需写明行为变化，例如“依赖提供者消失后观察器会重新初始化，closure 中缓存因此重置”。同时列出版本范围、清理语义与数据格式，使用者才能判断是否需要迁移状态。

## 16.6 给连续实例做一个实际包入口

`examples/package.json` 把 review-lab.mjs 作为唯一代码导出，包名为 book-deepseek-review-lab，版本 0.2.0。它还声明 private:true，允许本地 pack 与安装练习，但不把这份教材误发布到 npm。包内只带代码、README 和 npm 自动包含的 package.json，不包含下载的 Cordis 源码、事实目录或测试临时数据。

```json
{
  "name": "book-deepseek-review-lab",
  "version": "0.2.0",
  "private": true,
  "type": "module",
  "exports": "./review-lab.mjs",
  "files": ["review-lab.mjs", "README.md"],
  "license": "CC-BY-NC-SA-4.0"
}
```

createReviewLab 接收调用者传入的 Cordis 模块，Service 因而来自明确指定的固定源码。这个包用于组件实验；若要交给 dsh 加载，还需按宿主的模块入口、依赖和 bundle 契约包装。

从书仓根目录执行如下命令，可以查看实际分发内容。这里显式指定仓库内 npm cache，避免把测试写到个人缓存目录：

```powershell
npm.cmd pack ./deepseek/examples --dry-run --offline --ignore-scripts --cache .scratch/npm-cache --json
```

列表只有 README.md、package.json 与 review-lab.mjs。dry-run 确认候选文件范围，下面再生成 tarball，从解包入口运行相同断言，检查实际加载是否正常。

## 16.7 从 tarball 看见开发目录掩盖的问题

开发目录里有 check-review-lab.mjs、有下载器、有事实文件，分发包没有这些文件。消费者只应依赖 exports 指向的入口。若 review-lab.mjs 引用了相邻测试文件，源码目录能跑，tarball 解开就会失败。因此用文件白名单打包，能够主动暴露不小心跨越发布边界的 import。

以下命令继续从书仓根目录运行，沿用第 1.5 节准备的 Cordis 与 tsx。前三步生成并准备解包目录，随后解包，再让原来的十三项检查加载包内代码；测试驱动仍留在书仓。

```powershell
New-Item -ItemType Directory -Force .scratch/deepseek-pack | Out-Null
npm.cmd pack ./deepseek/examples --offline --ignore-scripts --cache .scratch/npm-cache --pack-destination .scratch/deepseek-pack
New-Item -ItemType Directory -Force .scratch/deepseek-package-check | Out-Null
tar -xzf .scratch/deepseek-pack/book-deepseek-review-lab-0.2.0.tgz -C .scratch/deepseek-package-check
node --import ./.scratch/deepseek-runtime/node_modules/tsx/dist/loader.mjs deepseek/examples/check-review-lab.mjs --source .scratch/deepseek-runtime/pinned-cordis/src/index.ts --lab .scratch/deepseek-package-check/package/review-lab.mjs
```

`--source` 仍指定固定的 Cordis 入口，`--lab` 改为解包后的 review-lab.mjs，测试驱动继续使用书仓中的文件。本次 tarball 文件集合与白名单一致，解包入口的十三项断言全部通过；SHA-256 与 npm 完整性字段保存在 review-lab 事实文件。

如果你改过源码，要重新 pack 并解到新的实验目录，再运行这条命令。否则可能刚修好开发目录，却一直在测试旧包。比较源文件与包内文件摘要，就能先排除这种误判。这个实验仍不涉及远端发布权限，也没有经过 dsh 的安装和 bundle 加载链。

同样，路径别名只对配置了相同 tsconfig 的工程有效。一个 `@book/internal` 在开发机解析成功，不能证明使用者的 Node 能找到它。这里的教学代码只依赖语言和调用者传入的 Service，没有隐含编译器路径，所以适合先学习包边界，再逐步加入声明文件与构建步骤。

包的 README 应说明需要怎样的调用者。本例的使用方式是导入 createReviewLab，把经过验证的 Cordis 模块传进去，取得 ReviewJournal、ReviewTools 和 reviewPlugin，再由根 Context 挂载。若只写“支持 DeepSeek 插件”，读者可能直接把包名填到 profile，遇到入口不匹配后无从判断。

## 16.8 上游工作区包还有自己的约束

固定版本 adding-a-package 文档面向在 Harness 仓库内新增 `@deepseek-ai/dsh-*` 包。它要求包位于两层 group/package 结构，普通包归入一个 Host 或 Client 聚合，版本与根包匹配，主入口和类型声明位于约定的 lib 路径。Cordis 同时出现在 peerDependencies 与 devDependencies，相关 dsh peer 也要有开发期镜像依赖。

这些要求适用于上游工作区模块，由检查脚本、统一构建和聚合 tsconfig 管理。本书的本地 ESM 工厂是独立包，迁移时应根据目标选择结构。

客户端包还要声明 client 入口并使用客户端构建约定，不能把 Host 里的 Node 文件工具直接导出给浏览器。TypeScript 的 Context 声明合并也会看见不同面的声明，因此同一个 ctx key 不应在 Host 与 Client 表示互不兼容的类型。运行时分开进程，不会自动解决编译时的名称冲突。

## 16.9 安装状态、组合状态、活跃状态

回到 plugin-manager：包存在、bundle 被选中、row 已启用和节点就绪，分别对应安装、组合、disabled 覆盖与运行时状态。下面的升级例子会用到这四层。

比如你升级了审查包，磁盘上的入口已经是新版本，但当前 profile 没有启用它，运行中的旧节点也没有重新加载。此时检查包版本只能证明第一层。需要同时记录有效 profile、最终树和 fiber 状态，才能回答新代码是否进入进程。

restart-required 是明确的状态差异：配置已保存，运行时需要重启才采用。自动化若把保存成功当成当前任务已经切换，就可能用旧策略继续执行。部署脚本应把“写入配置”和“确认新能力活跃”作为不同步骤，后者可以通过版本标识或可观察小调用确认。

## 16.10 升级说明围绕状态变化写

假设 0.3.0 把 todo 从布尔改为计数。需要检查的不只是返回类型：输出 schema、renderer、旧日志 presenter、消费者断言和包说明都受影响。若只改 execute，旧消费者可能把数值 2 当 true 使用，暂时没报错，却已经丢掉新语义。

另一类变化是生命周期：新版本在提供者替换后保留计数，旧版本每次从零开始。这个差异会影响审计与监控，不能藏在“优化稳定性”里。最好给出触发条件、旧行为、新行为和迁移需要的数据；连续实例的提供者替换测试就能直接揭示差异。

保留旧包 tarball，可以直接比较使用者收到的内容。构建工具、文件白名单和导出条件都可能让同一提交生成不同包，所以发布内容摘要需要与对应的包入口实验关联。
