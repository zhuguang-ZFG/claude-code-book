## MAJOR：按重要性排序

### M1．用一个违反因果顺序的故事给真实错误作确定归因

**位置：** `source/llm/ch03.md:4`、`:66`、`:138–146`；PDF 第 30、32、34–35 页。

开头设定“第一份是订单，第二份是地址”，随后却断言错误“在机制上就是订单位置的查询把地址位置的值混了进来”。若按该叙述顺序拼接，订单 token 位于地址 token 之前；本章自己规定的 `j <= i` 遮罩使该订单位置无法读取后面的地址。这也与 §3.4 的“前面位置的键和值没有变”一致：追加地址不会倒回去更新更早的订单表示。后来生成答案的位置可以同时访问两份回执，但这不是文中所写的查询位置。

即便改成“回答位置”，单凭三份回执仍在窗口和最终答案错误，也不能排除输入数据关联错误、字段歧义、任务指令或后续层计算等原因；“问题不在有没有读到”及“在机制上就是”没有相应干预实验支持。§3.6 随后又说单头权重不能作因果解释，形成自我矛盾。表格中的“所有 token 在同一个 softmax 里竞争”还遗漏了每层、每头、每个查询位置各自归一化的限定。

**具体修复：** 保留客服案例作为要解释的现象，但把开头改为“回执都在窗口，并不保证模型能正确绑定订单和地址”；在手算后明确“生成回答的位置可混合此前多个位置的信息；本例只演示混合算术，不能据此确定一次地址错配的原因”。表格改为“可能相关的机制/需检查的问题”，准确写成“同一头、同一查询位置对可见键归一化”，将结构化关联 ID、结果校验作为可测试的工程措施。无需增加真实模型实验，只需撤去未经证明的归因。

### M2．MLA 被写成共享 KV 之后更小的一档，且缓存内容与推理流程不准确

**位置：** `source/llm/ch03.md:115`；对应 `source/llm/ch16.md:62`；PDF 第 34 页。

“第三档”“再压小一个量级”“同一件事的三个深度”接在 MHA/GQA/MQA 表后，会自然被理解成 MLA 比 GQA 或 MQA 再节省约十倍。所引 DeepSeek-V2 并不支持这个比较：摘要的 93.3% 缓存减少以 **DeepSeek 67B** 为基线；§2.1.4 / Table 1 的同形状比较给出 MLA 缓存约等于 **2.25 个 GQA 组**，在该比较下还大于单组 MQA。不能用一种不同架构的实际模型结果给上表追加统一等级。

“读的时候再投影回多头形状”被写成必要的运行过程，而论文明确说明可以把上投影矩阵吸收到查询/输出投影，避免为每次查询还原完整的内容 K/V。DeepSeek-V2 的实际缓存也不只有压缩潜在向量，还要保留解耦 RoPE 的键，元素数为 `(d_c + d_h^R) × layers`。对应术语表继承了同一个误导性流程。

段末“各要模型训练时就选定”可以表达“不是部署开关”，但宜避免暗示不能从既有 MHA 权重转换；所引 GQA 论文恰恰提供转换后继续训练的方案。

**具体修复：** 将该段写成另一类缓存表示方法，去掉“第三档/三个深度/再小一个量级”的线性排序。说明 MLA 联合压缩内容 K/V，DeepSeek-V2 另外缓存位置键，推理可通过矩阵吸收直接使用压缩表示。若保留 93.3%，明确 DeepSeek 67B 比较基线及论文版本；若不展开数字，删除量级断言即可。最后写成“这些结构需要匹配权重与训练；MHA 可经过转换和继续训练得到 GQA/MQA，不能只改部署参数保持行为不变”。同步更正 ch16 的 MLA 一句话定义。无需实现 MLA 示例。

### M3．两幅注意力图缺少可见语义标签，不能独立支持正文教学

**位置：** `source/llm/ch03.md:28–34` 的 `llm-ch03-causal-mask`、`llm-ch03-attention-fan`；PDF 第 31 页图 3-1、3-2；HTML 对应 figure。

图 3-1 包含两个网格和几条斜线，但没有查询轴、键轴、可见/遮挡区、位置编号或图例。图 3-2 有发散线、圆点、条块和合并箭头，但没有 Q/K/V、权重、softmax 或加权和标签。两图图注完全相同，仅重复“3.1 每个 token 带着三个角色”。正文无法帮助读者判断第一图中斜纹究竟是允许还是禁止，也不能把第二图元素逐一对应到公式。

## MINOR：按重要性排序

### m1．0.6 的平均值分母写错

**位置：** `source/llm/ch03.md:88`；PDF 第 33 页。

“输出前两个位置第一维的平均值 0.6”不成立：前两个值是 1 和 0.8，平均值为 0.9。实际权重是 `[1/3, 1/3, 1/3]`，输出是 **全部三个可见位置**的平均值 `(1 + 0.8 + 0) / 3 = 0.6`。代码和表格正确，改这一句即可。应优先修复，因为它位于手算教学的解释句中。

### m2．参数表把完整整数拆成两到三行，妨碍核算

**位置：** `source/llm/ch03.md:107–111`；PDF 第 33 页；HTML 桌面/手机参数表。

桌面与 PDF 中 `16 777 216` 被拆成 `16 777` / `216`，`67 108 864` 拆成两行；390px 视口中的 Q 列甚至显示成 `16` / `777` / `216` 三行。数字仍在单元格内，并非数据被裁掉，但核对百万级参数时很容易误读。移动端表格本身已有横向滚动容器（clientWidth=324、scrollWidth=687），没有必要同时拆散数值。

**具体修复：** 合并相同的 Q/O、K/V 列，或拆成“参数表”和“缓存表”，同时保持整数内部不换行。也可用不换行数字分组或针对数值列设置不换行；不要为了塞下八列把字号继续缩小。保持源码改动，不直接修改生成产物。

### m3．公式与配套代码使用相反的矩阵存储约定，未告知读者

**位置：** `source/llm/ch03.md:13–15`，`source/llm/examples/attention_demo.py:29–36`，以及 `HEADS`。

正文写行向量 `q_i = x_i · W_Q`，脚本 `matvec(matrix, vector)` 实际计算列向量约定的 `W_Q · x_i`，一维头用 `[[1.0, 0.0]]` 的 1×2 矩阵。单位阵会隐藏这一区别，练习自行改投影时才会暴露。数学上可转置等价，默认结果无误。

**具体修复：** 在指向脚本处补一句“脚本按输出维存每一行，使用 `W @ x`，是上述行向量公式的转置约定”，或统一正文公式与脚本。不需要为这个小例子加通用矩阵库。

### m4．“一个头只能学一种怎么比较”容易被读成单一语义功能

**位置：** `source/llm/ch03.md:78`。

一个头有一组投影/兼容性计算，但不能由此推出它只能承担一种语义关系。当前句子把“共享一组参数”写成了能力上限，也容易让后文头维度例子被误读为真实头的固定分工。

**具体修复：** 改为“一个头用一组投影，在每个查询位置得到一组权重；多头并行学习不同投影”。无需增加关于头功能的实证讨论。
