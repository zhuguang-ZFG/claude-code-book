### C1 — CRITICAL：MCP 消息不符合正文固定引用的 2026-07-28 版本

**位置：**`llm/ch12.md:59–72,144`；`llm/examples/toolcall_demo.py:94–103,129–134`；`tests/test_llm_examples.py:397–404`；`llm/ch16.md:203–207`；`llm/VERIFY.md:91`。来源登记 `yuyu-book/sources-llm.json:341–352` 也把此条固定为 2026-07-28。

[新版基础规范](https://modelcontextprotocol.io/specification/2026-07-28/basic) 要求请求 `_meta` 含 `io.modelcontextprotocol/protocolVersion` 和 `io.modelcontextprotocol/clientCapabilities`；本例二者都缺失。[新版工具规范](https://modelcontextprotocol.io/specification/2026-07-28/server/tools) 的完成结果还带 `resultType: "complete"`。其错误部分区分未知工具等 JSON-RPC 协议错误与 `isError: true` 工具执行错误，而练习让读者把不存在工具名构造成 `isError`，没有说明两层区别。

**具体修复：**选一个明确版本并实现一致的教学报文。若保留 2026-07-28，就按现代请求元数据、可选 `server/discover`、规范结果及错误对象重写；若为了简洁选 2025-11-25，就同步更换全部版本引用，并展示初始化响应与必须发送的 `notifications/initialized`，不能只替换日期。明确 Python 本地执行结果不是 MCP 网络结果，让适配层负责协议包装。测试应检查所选协议的关键必需字段及错误类别，不能只断言当前错误的三条 method 顺序。练习若仍不连接服务器，应要求构造和比较报文，而不是运行此纯打印脚本后“观察真实服务器会不会拒绝”。

### M1 — MAJOR：约束解码的保证被扩展成工具任务成功，并混淆 JSON mode

**位置：**`llm/ch12.md:51`；对应术语 `llm/ch16.md:200`。

按可接受 token 屏蔽 logits 的基本解释正确，但“模型写不出不合 schema 的 JSON”“结构化任务一次过、工具链路不再兜圈”把语法保证扩展到了完成、业务正确性和权限。合法的 `{"order_id":"ORD-9999"}` 仍可能查不到订单，生成也可能被截断或拒绝。把托管 API“结构化输出 / JSON 模式”并列为这一 schema 保证，会使读者以为 JSON mode 同样约束字段和枚举。

本次读取的 [OpenAI Structured Outputs 文档](https://platform.openai.com/docs/guides/structured-outputs) 明确写道：两者都确保合法 JSON，只有 Structured Outputs 确保 schema adherence；保证针对完成且非拒绝的输出，应用仍处理拒绝、不完整响应及 schema 未表达的业务规则。原文“引号没开就不许出非转义字符”也不是正确的通用 JSON 语法规则，应改用未闭合字符串中的引号/转义或枚举值的具体例子。

**具体修复：**保留 logits mask 机制，用一小段区分 JSON 语法、受支持的 schema 约束、业务判断三个层次；直接说约束解码减少结构错误，不承诺任务一次成功。保留服务端校验即可，不需扩写一整段通用免责声明。加可读取的官方文档引用，记录查阅日期或快照。

### M2 — MAJOR：讲“验证后返回错误”的示例没有验证参数对象本身

**位置：**`llm/examples/toolcall_demo.py:49–70,86–91`；`llm/ch12.md:31–49,124–126`；`tests/test_llm_examples.py:376–395`。

`arguments: dict` 只是 Python 类型标注，不能阻止 JSON `null`、数组或字符串进入。当前 `required` 检查和 `.items()` 在这些输入上直接抛异常，违背本节强调的“坏模型输出应转成可恢复错误”的教学契约。这个缺口就在校验边界，不属于必须补齐生产权限系统的额外要求。

**具体修复：**先验证工具名与参数根节点形状，再进入已支持的 schema 子集；让失败稳定返回明确错误。说明这是适用于这两个工具的简化校验器，而非完整 JSON Schema 实现。加 `None`、数组、字符串、缺字段、额外字段、枚举非法值和合法参数的针对性测试。若订单号只允许 ASCII 数字，建议把 Python 的 Unicode `\d` 改成 `[0-9]`，避免与常见 JSON Schema 正则语义和订单格式预期不一致。

### M3 — MAJOR：二元严格过半模拟被当作一般自洽投票，成本表又静默换了假设

**位置：**`llm/ch13.md:18–36,48–57,115`；`llm/examples/cot_demo.py:18–30,41–58`；`llm/VERIFY.md:92`。

脚本抽取的是独立“答对/答错”布尔量，只在答对次数超过 n/2 时成功，没有生成答案类别或对答案字符串投票。这等价于一个二元过半模型，也可以看作正确答案获得严格多数的概率；它不是一般多类别答案的得票最多选择。真实 self-consistency 中，错误可能分散为多个不同答案，正确答案的单次概率即使低于 0.5，仍可能是概率最大的类别，随样本数增大而赢得投票。因此练习中的 0.5 阈值必须限定到这个 toy 模型。

第一表用 p=0.60，第二表直接回答=.45、CoT=.65 是新设假设；虽然脚本可看出，正文只宣布换了单价，没有宣布换了基础正确率。读者容易把第二表当成同一实验的成本重述。“每道正确题成本”只包含输出 token 成本，未含重复输入、工具调用或其他费用。这可以作为清楚的简化，不需要升级成真实模型基准。

**具体修复：**第一表就标明独立同分布 Bernoulli、二元严格过半，解释真实答案 plurality 与错误类别分布；保留现有数表亦可。成本表前直接列出 `.45/.65` 假设，并把列名或说明写成“输出 token 成本 / 正确题”。可用二项分布精确尾概率作为模拟的参考值，并补 p<.5 的反向例子或多类别小例子来防止误推广。不要把确定的 toy 结果改成含糊的“也许”；只需把模型说准。

### M4 — MAJOR：多模态架构和训练路线被拼成一条不存在的统一流程

**位置：**`llm/ch15.md:4,25,29–35`；`llm/ch16.md:250,254–256`；来源登记 `yuyu-book/sources-llm.json:537–545`。

“无论哪类……图的分辨率越高，这段 token 越长”被所引 BLIP-2 直接反例推翻：[BLIP-2 原文 §3.1](https://arxiv.org/html/2301.12597v3) 明确说明 Q-Former 输出固定数量特征、与输入分辨率无关，实验使用 32 queries。[Flamingo §2](https://arxiv.org/html/2204.14198v2) 用 Perceiver Resampler 输出 64 个视觉表示，再通过新插入的 cross-attention 层条件化冻结的语言模型；这不是所有图像 token 与文本直接拼入同一序列的结构。

“对齐靠两步训练：对比预训练、交错预训练”也不是 CLIP、LLaVA、BLIP-2 的统一规定。[LLaVA 原文 §4.2](https://arxiv.org/html/2304.08485v2) 只有 stage 1 同时冻结视觉编码器和 LLM、训练投影；stage 2 继续冻结视觉编码器，但更新投影与 LLM。正文与来源 scope 把前一阶段写成完整方案，再得出“训练量集中在投影层”“不必重训两头”的泛化结论。

**具体修复：**用简短对照说明直接拼接、固定查询压缩、cross-attention 三类接口；明确视觉编码器 patch 数、送入语言模型的表示数不必相等。将对比学习、连接器对齐、图文交错训练、指令微调写为可组合路线，按引用说明其具体作用。LLaVA 的冻结表述限定到第一阶段，并补第二阶段更新哪些模块；同步改来源登记和术语。保留“借用预训练模块可以减少训练量”的有效结论，无需否定整个章节的工程价值。

### M5 — MAJOR：patch 数、语言模型上下文和计费 token 三种口径混在一张“账单”里

**位置：**`llm/ch15.md:39–67,76,83`；`llm/examples/multimodal_demo.py:46–59,78–103`；`llm/ch16.md:250,257,262`；`llm/VERIFY.md:94`。

`ceil(宽/patch) × ceil(高/patch)` 是指定切块策略的 patch 计数，不能直接称所有 VLM 的上下文和收费公式。表中“缩到最长边 1568 再切”给 5488 / 7252 / 6860，下一段却说缩放后的 token 同在“一两千”；后者来自另一列像素除 750，必须说明口径。`768/1568`、`pixels/750` 是这个脚本组合出的两档预算设定，既无完整厂商限制，也不是统一 API detail 档位。表头还没说明除 750 使用的是缩放后像素。

“原始像素直切不可用”“所有实现都先缩放”“整图高档账单翻四倍”均超出该脚本的证明范围。视频“一分钟 30 帧就是 1800 张图的账”仅对显式逐帧提交 1800 张图的实现成立；已引用的 Flamingo 以 1 FPS 抽帧并压缩时空特征，不能当通用视频 API 计价机制。先低分辨率全貌再局部高分辨率，合计是否更省也取决于裁剪次数与重复调用，不能无条件说便宜得多。

**具体修复：**把表格明确命名为三种教学计数口径，分别写清输入尺寸、patch 大小和像素换算。将 `low/high` 改成“示例缩放方案 A/B”，或选择一个具名 API 的完整且可核对规则重算；二者选一即可。公式名称改为 patch 数，明确后续连接器及厂商计数规则会改变语言序列长度与计费量。视频按“若每帧独立作为图像提交”限定，并解释实际抽帧和压缩。保留 8160、47628 等可复现算术，不要为减少问题删除有用的数量比较。

### M6 — MAJOR：多模态脚本声称走完四步，实际没有位置编码或 Transformer

**位置：**`llm/ch15.md:10–23,92`；`llm/examples/multimodal_demo.py:27–43,63–75`；`tests/test_llm_examples.py:739–767`。

正文四步包括位置编号和过 ViT；脚本只切块、线性投影、打印行主序坐标，既没把位置向量加进表示，也没有注意力/Transformer。说“把四步走一遍”是可直接证伪的源文—示例不一致。手设线性投影的亮块数值较大也不能证明“这块里有什么”这种语义已经学入向量；当前输出只展示像素数值的线性组合。

另外正文说边缘不足补齐，而 `patches` 在不整除尺寸上越界；`resized` 的参数叫最大边，文中称缩小，函数却会把更小图片放大。
