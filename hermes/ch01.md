# 第 1 章：安装与隔离配置

<!-- block: hermes-ch01.b-opening -->
第一次试用 Hermes，先留意它把数据写到哪里。聊天记录、记忆、技能、调度任务和凭据都可能持续存在；沿用日常配置做实验，可能影响下一次真实任务。本章说明怎样建立独立的数据目录，再准备后面一直使用的 Aurora 资料库。还没安装 Hermes 时，可先做第 1.6–1.7 节：随书检查器只使用 Python 标准库，能先生成一份可查看的项目与报告。

## 1.1 程序、数据和工作目录分开看

程序目录保存 Python 模块和安装依赖；Hermes home 保存用户配置与持续状态；工作目录是本次任务要处理的项目。三者可以在同一块磁盘上，但含义不同。升级程序不应被理解为清空记忆，切换项目也不必然切换用户档案。

本书所用版本的 `hermes_constants.py` 通过 `get_hermes_home()` 统一解析当前 home，并支持上下文覆盖。默认位置在不同平台上不必相同，不能把 Linux 示例中的 `~/.hermes` 原样当成所有 Windows 安装的实际位置。检查明确设置的 `HERMES_HOME`，再看安装方式，是排查“为什么读到另一份配置”的起点。

| 位置 | 常见内容 | 改动后的影响 |
| --- | --- | --- |
| 源码或安装目录 | Agent、工具、运行依赖 | 改变程序实现与兼容性 |
| Hermes home | config.yaml、记忆、技能、会话和 cron 状态 | 影响后续会话与后台任务 |
| 项目目录 | 源码、资料、任务产物 | 形成用户能直接看到的文件副作用 |

实验使用 Hermes 自己的配置入口，保留操作系统的 HOME。这样 Git、SSH 等其他程序仍使用各自原来的目录。

## 1.2 固定源码，比复制最新版命令更可复现

该版本的 `pyproject.toml` 声明 Python 范围为 `>=3.11,<3.15`，CLI 入口为 `hermes_cli.main:main`。这个范围说明包接受哪些 Python 版本，不表示所有可选终端后端在这些组合上都经过验证。本书组件实验使用 Python 3.13。

下面的命令在本书仓库根目录执行，会把上游源码放到 hermes-source。它为第 4 章的组件实验准备输入；安装完整应用前，仍需阅读对应版本的安装说明：

```powershell
git clone https://github.com/NousResearch/hermes-agent.git hermes-source
git -C hermes-source checkout 2bd378ed1b8d6bf2192cb26e0a55ff3091e6bd19
git -C hermes-source rev-parse HEAD
```

用最后一行输出的完整提交核对版本。分离 HEAD 是正常结果：这份副本用来对应本书，不承担日常更新。官方一键安装器面向当前发行流程，还会管理更多运行组件，安装结果与检出本书提交不同，需要另行核对。

## 1.3 给实验一个明确的 home

已经安装 Hermes 后，在本书仓库根目录打开 PowerShell，可以为当前终端会话设置独立目录。这里的 .scratch/hermes-profile 保存助手数据；稍后创建的 .scratch/aurora-lab 保存待检查资料：

```powershell
$hermesLab = Join-Path (Get-Location) '.scratch/hermes-profile'
New-Item -ItemType Directory -Force $hermesLab | Out-Null
$env:HERMES_HOME = $hermesLab
hermes --help
```

这会改变当前 shell 后续启动的 Hermes 进程，不会改变此前已经运行的 gateway。后台进程是否采用新目录，要看它启动时的环境和内部路由。新建目录后先运行帮助命令，确认命令确实来自预期安装，再进行模型配置。

若希望试完恢复，可以在独立终端窗口完成整组实验，退出该窗口；或者在设置前保存原来的 HERMES_HOME，并在结束时恢复原值。清理时只删除自己创建的实验 home，真实 `.env` 则留在原来的私人配置中。

## 1.4 配置模型时不要混淆三件事

provider 决定请求交给哪套服务或适配器，model 是该服务识别的模型名称，凭据决定访问身份。模型名称可识别，不等于当前账号有权限使用；请求 URL 正确，也不表示工具调用、流式事件或图片输入全部兼容。

对应的 README 提供 `hermes model` 作为配置入口。本书不会把某个商业模型写成 Hermes 的必要条件。第一次真实任务可以很小：在只有一个文本文件的临时项目里，让它列出文件中的三条事实，并要求说明信息来源。保留请求失败的完整错误类别，但分享日志前移除密钥和用户内容。

如果目标只是验证记忆持久化，根本不需要先配置模型。第 4 章脚本直接运行真实存储组件，帮助我们先回答“有没有写入”“重载后是否看见”等确定问题。把组件、宿主、模型分阶段验证，出错时就不必同时猜依赖、网络和推理过程。

## 1.5 一个干净的开始应留下什么

最小记录包含程序来源、完整提交、Python 版本、实验 home、工作目录和运行命令。路径可以只留相对于实验根目录的形式，避免公开个人用户名。“启动成功”的截图通常缺少这些信息，尤其是实际配置与工具的工作目录。

首次启动后观察新产生的文件，再决定是否需要备份。对已有使用者而言，迁移前应先停掉可能继续写入的进程；对新实验而言，使用全新的目录比清空原配置可靠。第 15 章会细讲备份和恢复，包括为什么 SQLite 的在线复制需要比普通 Markdown 更多考虑。

## 1.6 建立后面一直使用的 Aurora 资料库
本书的 Aurora 是一个虚构项目，文件里没有真实客户资料。它只维护一份安装说明、一个索引、一页发布记录，以及一份已经过时的计划。规模小，是为了让每次变化都能用眼睛核对；后面的记忆冲突、技能修订和定时检查都围绕这些文件发生。

从本书仓库根目录执行：

```powershell
python hermes/examples/aurora_lab.py init .scratch/aurora-lab
python hermes/examples/aurora_lab.py check .scratch/aurora-lab
$LASTEXITCODE
```

init 要求目标目录尚不存在，避免覆盖上次实验。如果已经跟做过，保留原目录，换一个尚不存在的目录，并把两条命令最后的项目参数一起换掉。第二条命令在资料库自己的 reports/latest.json 写入结果，终端返回 checked，紧接着查看的退出码为 0。此时三个 docs 文件进入清单，archive/old-plan.md 没有进入，因为 rules.json 明确排除了归档目录。检查器不会联网，也没有启动 Hermes。

```text
.scratch/aurora-lab/
  rules.json
  docs/
    index.md
    setup.md
    release-notes.md
  archive/
    old-plan.md
  reports/
    latest.json
```

Aurora 项目与 Hermes home 继续分开保存：前者供不同工具复用，后者保存某个助手的配置与历史。将来让另一位编辑检查同一项目时，他可以拿到 docs 和 rules.json，而不需要顺便得到你的会话、用户偏好和模型凭据。

## 1.7 看懂第一份结果再接入模型
先用编辑器打开 .scratch/aurora-lab/docs/index.md，沿其中两个链接找到 setup.md 和 release-notes.md；然后打开同一项目的 rules.json 与 reports/latest.json。规则中的两个扫描开关起初都是 false，报告中的 issues 与 observations 都为空。这样就能将“检查通过”对应到实际被检查的三份文档。

这里的 issues 保存需要处理的问题，例如项目内链接指向不存在的文件；observations 保存供人判断的观察，例如代码示例中的占位 URL。第 6 章会打开示例扫描开关，届时 observations 可以有内容，而检查仍然通过。

报告的 snapshot.files 保存相对文件名与 SHA256，rules_sha256 保存规则文件摘要，input_digest 则把这两部分合在一起标识一次输入。可以先把 input_digest 理解为“本次规则与文件内容的指纹”：被检查文件的内容或规则字节改变后，摘要也会随之改变。报告不保存机器上的绝对私有路径，因此可以在另一台机器上比较同一份资料。文件内容相同、规则字节相同，连续两次检查应产生相同报告；这项行为已经由配套测试验证。

这份结果的含义很窄：检查器在规定范围内检查了简单 Markdown 行内链接。它没有评价论证是否可信，没有访问远程 URL，也没有解析所有 CommonMark 语法。让模型接着工作时，可要求它阅读 reports/latest.json 并解释问题，同时保留 checked 所对应的有限检查范围。

如果命令返回 2，先看终端中的 error。规则字段写成字符串、目录不存在、文件编码损坏，都属于程序没有完成本次检查。此时 reports/latest.json 可能还保留上一次成功结果。故障排查要同时看本次退出码和报告，而不能只看磁盘里是否有一个 JSON 文件。

现在可继续[第 3 章](ch03.md)的改名练习，或先运行[第 17 章](ch17.md)自动串起的八步流程。接入 Hermes 后，第一项任务可以写得很短：“读取 rules.json，运行这个检查器，报告本次退出码、输入摘要和发现的问题，不修改原文。”这句话给出了读取对象、执行步骤和可核对的返回内容。等它在你的实际环境里完成一次，再逐渐加入记忆、技能和调度，便于判断后来出现的问题究竟在哪一层。
