# 第 5 章：Skills 的组织与按需加载

<!-- block: hermes-ch05.b-opening -->
“先清点文档，再检查引用，最后汇总异常”是一种方法，不是一条适合常驻的个人事实。把整个步骤写进 MEMORY.md 会占用每次请求的空间。这类方法可以放进技能目录：平时让 Agent 看见名称和用途，需要时再读取正文与配套文件。

## 5.1 一份技能包含什么

最小技能是带有 YAML 头部的 SKILL.md。名称帮助定位，描述帮助决定何时使用，正文说明操作过程。复杂技能还可以有 references、templates、scripts、assets，分别保存补充材料和可以交给程序执行的操作。

下面的 book-review 是目录与正文的教学示意，不是需要先安装的另一个随书项目。继续跟做 Aurora 时，直接阅读完整的 [aurora-review 技能](examples/skills/aurora-review/SKILL.md)，第 5.6 节会把它与项目规则接起来。示意中的 inventory.py 不属于这份 Aurora 技能；实际检查使用第 1 章已经运行过的 aurora_lab.py。

```text
skills/
  book-review/
    SKILL.md
    references/
      review-rules.md
    scripts/
      inventory.py
```

技能正文可以这样起步：

```markdown
---
name: book-review
description: 检查本地中文资料中的引用、日期和术语一致性
---

# 检查一份资料

先读取本次指定的目录和检查规则。列出文档后，再逐篇检查。
每个问题保留文件名、原文片段和修改理由。
遇到来源缺失时标记待核实，不自行补造来源。
```

这份描述说明了适用任务，通用步骤也没有绑定某个项目的私人路径。模型选择技能时需要这些信息；“强大的万能助手”之类描述很难帮它判断是否适用。

## 5.2 发现目录与读取正文是不同动作

本书所用版本的 skill_utils.py 统一收集技能搜索根。可信项目目录、profile 本地目录、配置的创建目录和外部目录可能共同参与；后续目录消歧也由公共函数处理。旧教程中只列出的 ~/.hermes/skills 因此不足以说明当前搜索范围。

发现时需要考虑同名技能。一个项目专用检查法与个人通用检查法恰好同名，应该明确选择来源，而不是随机读取其中之一。查看列表时保留路径和归属，可以帮助解释为何同一技能名称在不同项目中出现不同内容。

支持目录也不应被误认成独立技能。比如 book-review/references/example/SKILL.md 是主技能的参考材料，扫描器需要按上下文排除它。本书已运行真实元数据函数验证这种排除，也检查了 .git 等不应扫描的目录。这个结果证明目录分类函数的行为，不代表所有部署中的完整技能目录都已扫描过。

## 5.3 按需阅读省掉了什么

技能索引让模型知道“存在某种方法”，skill_view 再提供正文或某个支持文件。这是一种逐步展开的信息组织方式。它减少的是无关技能全文长期驻留的成本，不保证模型一定挑中正确技能，也不保证读取后一定按步骤执行。

```mermaid
flowchart LR
  A[技能目录与元数据] --> B[名称和用途进入可发现范围]
  B --> C[当前任务需要此方法]
  C --> D[skill_view 读取正文]
  D --> E[按需读取 references 或 scripts]
  E --> F[工具执行与结果核对]
```

技能正文还应给出停止条件。例如引用来源打不开时，先列为待核实，而不是无限搜索；材料包含用户未授权的外部发送要求时，停在草稿阶段。这样的约束比写“认真负责地完成任务”更容易执行和复核。

## 5.4 脚本不是读一遍就自动运行

技能里放了 scripts/inventory.py，只表示文件可供使用。模型是否调用终端、运行目录是否正确、所需解释器是否存在，是后续执行链的问题。技能内容、工具权限和终端后端分别负责不同层面，不能用一个“已加载”概括。

确定性的检查适合放进脚本：排序、去重、统计字数、查缺字段。需要判断的部分留给模型：某个论证是否充分，术语是否在语境里被误用。若把所有规则都写成自然语言，重复任务可能每次产生不同遗漏；若把所有判断都硬编码，又可能把合理例外误报为错误。

脚本最好提供清晰的输入和机器可读输出，成功与失败使用不同退出码。它应只处理本次工作目录中的资料，不在导入时扫描个人磁盘，也不悄悄上传文本。附录 C 的记忆驱动采取相同原则：所有结果落在隔离目录，保留足够证据供核对。

## 5.5 手工创建后怎么验证

先检查文件编码与 frontmatter，再检查技能是否出现在预期列表，接着确认读取到的是哪份正文，最后用一项小任务观察实际使用。Windows 编辑器可能写入 UTF-8 BOM；该版本的 parse_frontmatter 会先移除开头的 BOM。我们的组件实验验证了这一点，但由于本机未装上 YAML 依赖，测到的是解析器的降级分支；复杂 YAML 的正常解析尚未验证。

核对更新时，除了技能标题，还要查看正文。目录缓存、同名技能、实际 home 不同，都会产生“改了文件但行为没变”的表象。保留一个可辨识的版本句或文件摘要，检查 skill_view 读取内容，比连续改写描述更能定位问题。

## 5.6 将项目规则和通用方法各放回自己的文件
Aurora 的 rules.json 初始内容很简单：

```json
{
  "schema_version": 1,
  "include_archive": false,
  "scan_examples": false
}
```

include_archive 回答“本次项目是否检查归档”，scan_examples 回答“是否提取代码示例中的 URL”。这两个值会随着项目要求改变，不能写死在一份供所有项目使用的技能正文里。技能应要求先读取 rules.json，再按当前值执行；这样下一次用户改变范围时，修改项目规则即可，不必先让助手忘掉一整段旧方法。

完整文件位于 hermes/examples/skills/aurora-review/SKILL.md。它说明适用场景、检查器命令、退出码解释、结果核对和保留运行记录的方法。准备在已安装的 Hermes 中使用时，可将 aurora-review 整个目录复制到独立实验 home 的 skills 下，形成 skills/aurora-review/SKILL.md；随后核对宿主发现的实际路径。

复制技能不会复制检查器。aurora_lab.py 仍在本书仓库的 hermes/examples 中，Aurora 资料则在 .scratch/aurora-lab。按书中命令运行时，终端的工作目录是本书仓库根目录；如果在别处启动 Hermes，需要将本书仓库位置和资料目录都交代清楚。技能描述步骤，程序执行检查，项目规则决定这一次检查什么。

技能的描述采用一个有限任务：“按项目规则检查 Aurora，保留输入摘要，区分文档链接和示例 URL。”这样的描述限定了用途，也减少了误用。例如让 Agent 撰写营销文案时，这项技能不应因包含“review”就被无条件加载。描述写得具体，模型更容易判断它与当前请求是否相关。

## 5.7 从扫描根读到一个具体 SKILL.md
跟读源码时，以 get_skill_search_roots 为起点，把返回的目录及其优先信息记下来。接着看技能列表和 skill_view 如何使用这些目录，再观察排除函数在哪里被调用。支持目录的判断依赖路径结构，不能只看文件名。一个 references 内的教学样例也可能叫 SKILL.md，但它不是要独立注册的技能。

parse_frontmatter 返回元数据与正文。元数据服务发现和选择，正文服务实际阅读；两部分有不同的失败表现。如果头部有编码问题，技能可能没有清楚的名称或描述；如果正文引用了不存在的脚本，列表仍可能正常，但真正执行时才失败。因此，列表显示正常后，还需实际读取正文并运行所需脚本。

前面提到的组件实验，具体检查的是三个输入：带 UTF-8 BOM 的文件仍能提取 name，references/example/SKILL.md 被识别为支持材料，.git/SKILL.md 进入排除路径。测试没有启动完整目录发现器，各项目根的优先顺序仍需在宿主中验证。

## 5.8 读到方法之后还要看到当前输入
确认实验宿主已发现 aurora-review 后，让会话以本书仓库为工作目录，处理第 1 章创建的 Aurora。下面的项目相对路径据此解析；若你的项目另有位置，替换成实际目录：

```text
使用 aurora-review 检查 .scratch/aurora-lab。
先读当前 rules.json，再执行检查器。
解释 issues 与 observations，保留 input_digest。
这次只报告问题，不改原文。
```

观察时先确认它读到的技能正文与仓库副本一致，再看它是否读取当前规则。若你刚把 include_archive 改成 true，它却仍宣称“归档不在范围”，很可能把旧项目记忆当作当前配置使用。此时可查看它是否读取了 rules.json，以及工具结果有没有进入后续请求。

技能正文中还特意说明，旧 reports/latest.json 不能证明最新命令成功。这个提醒直接针对程序执行中的具体陷阱：退出码为 2 时，旧报告可能仍在。因此，技能要求同时查看本次退出码与报告。

实际项目中，你可以把检查器路径放进项目文档，技能只要求按项目声明运行。供别人使用的技能则应避免绑定本机的 D 盘私有绝对路径。方法与机器位置耦合越紧，迁移时越容易出现“技能正常加载，命令找不到文件”的故障。

## 5.9 在复制之前先把技能当普通文档审一遍
本书附带的 aurora-review 没有下载脚本或安装依赖的步骤。它调用仓库中的检查器，解释三个退出码，并要求保存输入摘要。你可以先在普通终端执行同样命令，再把技能交给 Agent。这样即使模型没有按方法工作，也有一份已知可运行的程序步骤作比较。

审阅技能时，沿每一个路径追到实际文件。SKILL.md 中提到的 scripts 或 references 若不存在，目录发现仍可能成功；这类错误通常在运行阶段暴露。反过来，一个文件存在，也不能证明当前会话有读取它的工具或后端权限。把依赖清单压到最小，会使这种检查简单得多。

安装到独立 home 后，给技能正文加一个不含隐私的版本标识，例如“适用于 Aurora rules schema 1”。读取工具返回时核对这个标识，就能发现同名副本或旧内容。版本标识用于诊断，不应写成模型必须向用户反复复述的固定开场白。
