# 第 17 章：长期项目实战

<!-- block: hermes-ch17.b-opening -->
Aurora 里的文件和规则会继续变化：第一天的清单可能第二天就过期，旧技能可能漏掉新要求，定时任务也可能在错误配置下继续显示上次报告。本章把前面的代码连成一套能在本机重复的流程，再说明怎样把同一份输入交给三次真实 Hermes 会话观察。

## 17.1 先跑完不需要模型的部分
这一节可以在尚未安装 Hermes 时先做。无论前面手工项目已经改到哪一步，下面的驱动都会另建样本；不需要清空 .scratch/aurora-lab。

从本书仓库根目录运行：

```powershell
python hermes/examples/check_aurora_workflow.py
```

[八步驱动](examples/check_aurora_workflow.py)会新建 .scratch/agent-series/aurora-* 目录，在其 project 子目录中初始化资料，并通过子进程八次调用真实的 aurora_lab.py check。它没有创建 Hermes 会话，没有调用模型，也没有使用 FakeContext。我们实际执行了这条命令，八步全部符合预期，脱敏报告位于 facts/aurora-workflow-20261110.json。

运行结束后，终端会给出 report.json 的实际路径。先打开这份驱动报告，它的 cases 数组依次保存八步的 exit_code、stdout 和 saved_report；再查看同目录下 project/reports/latest.json，那是项目最后一次检查留下的报告。两份文件用途不同：前者保留整个过程，后者只保留当前项目报告。

同时保留退出码、标准输出与当时磁盘报告，是为了后面那个容易误判的场景：最新执行失败时，旧报告仍然存在。仅保存最后的 checked 字样，就无法重建中间发生了什么。

项目结构与第 1 章完全相同。docs/index.md 链接到 setup.md 和 release-notes.md，archive/old-plan.md 包含一条指向 removed.md 的旧链接。rules.json 初始关闭归档和示例扫描。所有内容都是合成材料，你可以反复改名、恢复和比较，不会碰到真实业务数据。

## 17.2 八步结果应当怎样读
| 步骤 | 改了什么 | 退出码 | 当前观察 |
| --- | --- | --- | --- |
| 1 | 初始输入 | 0 | 三份当前文档，未发现本地断链 |
| 2 | setup.md 改名为 install.md | 1 | 索引仍指向旧文件 |
| 3 | 更新索引里的文件名 | 0 | 本地链接恢复 |
| 4 | 开启 scan_examples | 0 | 增加一条占位 URL observation |
| 5 | 开启 include_archive | 1 | 归档中的旧链接进入 issues |
| 6 | 把布尔值误写成字符串 | 2 | 配置错误，旧报告保持不变 |
| 7 | 恢复有效规则并排除归档 | 0 | 当前文档通过，仍保留示例观察 |
| 8 | 不改输入再执行 | 0 | 报告与前一步相同 |

第 2 步发现的是我们故意制造的断链，程序本身正常运行；第 6 步才是程序无法完成本次检查。让 Agent 解释这两种结果，是观察它是否真正使用工具状态的好机会。若它把所有非零退出码都理解成“环境坏了”，就会错过第 2 步已经提供的文件和行号。

第 8 步验证的是确定性。报告没有把当前时间混进输入摘要，因此相同文件与规则会得到相同结果。这让后续自动任务可以比较内容变化。运行时间仍可由调度层单独记录，既能区分执行，也能保留用于比较内容的输入指纹。

## 17.3 第一次真实会话：完成任务并留下小而准确的记忆
从本节开始是三次真实会话的复做方案，需要已安装的 Hermes 与可用模型；前面八步完成后，不会自动进入这些会话。先准备一份第 1 章的初始 Aurora：安装说明仍叫 docs/setup.md，索引指向它，rules.json 的两个开关都是 false。八步驱动中的 project 已经改名并开启示例扫描，不能直接作为这里的初始样本。

若手工目录也已经跟做过后续修改，可保留它，按第 1.6 节的方法初始化另一个尚不存在的目录，并在接下来的三次会话中一直使用这份新项目。准备好第 5 章的 aurora-review 技能后，新建 Hermes 会话，使用独立 home，并交代本书仓库与项目的实际位置。下面是任务正文；让终端命令仍从本书仓库根目录执行：

```text
检查 Aurora 项目，先读取 rules.json 和 docs/index.md。
运行本书的 aurora_lab.py check，报告本次退出码、input_digest 和问题。
不要修改文档，也不要发送外部消息。
完成后给出一条值得下次保留的项目事实，先展示内容。
```

第一份结果应解释检查范围，而不只是复述 checked。值得保留的事实可以是“Aurora 的当前检查范围由项目根目录 rules.json 决定”。它提供一个下次应读取的稳定入口，比保存“归档永远不检查”更耐用。文件名列表和这次零问题的结论留在报告中，因为它们很容易变化。

若随后确认保存，查看 memory 工具返回与磁盘。第 4 章已经说明，本轮系统提示快照可能仍保持旧内容；这个差异来自快照的生命周期，无需因此重装。真正的跨会话观察发生在第二次启动：它能否读到这条入口事实，并据此读取当前规则、完成实际检查。

方法则放进 aurora-review 技能。它负责解释三个退出码、issues 与 observations，以及何时需要重读当前文件。memory 与 skill 相互补充：前者告诉它这个项目的规则在哪里，后者告诉它怎样执行一类检查。

## 17.4 第二次会话：改名之后恢复工作
关闭第一次会话，手工把 setup.md 改名为 install.md，保留索引中的旧引用。开始第二次会话，只给出“继续检查 Aurora”的任务，但仍明确本次不应自动发布或发送消息。观察它是否重新清点文件、读取当前规则并运行检查器。

正确结果应发现 index.md 的旧链接。若它拿出第一次报告说“一切正常”，沿执行链查它是否真的运行了新命令。若运行了却仍引用旧报告，查它是否忽略本次退出码或读取了别的项目目录。这样可以查明它是在执行命令还是读取结果时沿用了旧状态。

确认修复后，让它只修改索引里的引用，重新执行检查。最后应留下当前输入摘要、修改文件和原因。archive 中的旧计划仍按原样保留：规则排除了归档，旧计划也可能承担历史记录用途。

这一轮还可观察 memory 中的项目入口事实是否帮了忙。比较时可查看它是否从正确入口读到了新规则，以及是否采用当前文件而非旧报告；单问“你记得什么”还看不出这些行为。记住一句话和在变化条件下正确使用这句话，是两项不同能力。

## 17.5 第三次会话：修改方法而保留决定来源
完成第二次会话后，安装说明已经是 docs/install.md。现在把 rules.json 的 scan_examples 改成 true，保留 include_archive=false；代码围栏里的 example.invalid 地址会被检查器列为 observation。要求 Agent 解释这个变化，并审阅现有 aurora-review 是否足以处理它。

随书技能已经包含示例 URL 的分类要求。使用原样副本时，可以观察它是否正确采用这段方法，审阅结果也可以是“无需修改”；只有使用了尚未包含这项要求的旧技能，才做下面的局部修订。

如果旧技能将任何 URL 都当成线上链接，就只修改这条分类方法，保留其他步骤。新的规则应说明：示例 URL 可以是有意的占位值，先解释用途；项目内文件链接不存在则仍属于需要处理的问题。用第 6 章的反例同时验证两类结果，避免通过全局忽略链接来消除误报。

把决定来源留在本次记录中：“发布说明要求列出读者可能照抄的示例地址，因此开启 scan_examples；这不是用户对所有项目的永久偏好。”下一次追问“为什么不把它算成死链”，可以检索这段理由，再核对当前规则。只留下“用户不喜欢检查示例链接”会误导后续项目。

第三次会话的结果取决于实际模型与宿主。本书只执行了底层文件流程与规则变化，尚未测量三次模型对话的表现。复做时也保留失败记录，尤其是技能未被读取、旧报告被误用、历史理由被简化的情况，便于随后定位和修改。

## 17.6 让插件承担一个清楚的小动作
若要接入[第 9 章的完整插件](ch09.md)，沿用该章的两个源文件、安装目录和配置方法。book-inventory 可以替 Agent 提供受限的资料清单。将 root 配到项目的 docs 目录，调用只能返回这个范围里的 Markdown 相对路径。规则文件在项目根目录，因此 Agent 仍需通过适当的文件读取工具读取它；只列出 docs 的清单尚不足以了解全部项目配置。

把清单和检查器报告比较，会发现二者有不同用途。清单回答“当前有哪些 Markdown”，报告回答“在规则指定范围内，哪些简单链接有问题”。清单没有文件哈希，也没有解析内容，因此不能替代报告中的输入摘要。若你想增强插件，可以新增一个明确的摘要工具，保留原有工具的返回契约。

在完整宿主里，应保存插件发现来源、有效键、注册工具名和实际调用返回。离线测试已经覆盖处理器与注册返回检查；这一步才把它与真实工具集和模型请求连接起来。遇到“插件加载了但模型不用”，先确认它是否进入本轮可用工具，再判断描述是否足以帮助模型选择。

## 17.7 故意保留旧报告，练习一次误判恢复
把 rules.json 中的 scan_examples 改成字符串 "false"。运行检查器后，终端返回配置错误，退出码 2；磁盘里的 latest.json 仍是前一份结果。驱动第 6 步实际断言了报告字节没有变化。

保留上次成功结果有助于诊断，使用时需要注明它属于哪次检查。Agent 应明确说“本次未完成，旧报告仅供参考”，随后修正配置再执行。若工具包装只把 latest.json 内容返回、丢掉进程退出码，就会在你的接入层制造成功假象。

修复之后再比较 input_digest。因为规则文件字节进入摘要，即使语义相近，改变格式也可能得到新的指纹。这是当前示例的选择，便于确认输入原样相同。生产系统若需要忽略 JSON 空白，可以对规则作规范化后再散列，但摘要的含义也会随之变化，需要增加测试，并与既有记录区分。

## 17.8 再把稳定部分交给调度
三次会话中的确定性检查可以定时执行，解释与修改仍按需要触发。先在 local 投递模式下观察到期、领取、执行和保存结果。确认失败能留下本次状态后，再考虑真实平台通知。

如果一天内输入没有变化，就复用报告的内容摘要避免重复解释；如果输入未变但执行失败，则保留故障记录，不能因为旧摘要相同就当作无事发生。分别记录内容变化与本次运行状态，便能发现输入未变但任务已停止工作的情况。

到这里，Aurora 的日常检查可以从 memory 找到规则入口，按 skill 执行方法，通过插件列举资料，需要时从历史查明决定，再由 cron 重复触发。维护时可以逐项查看这些结果，确认当前文档采用了哪套规则、为什么这样处理。

## 17.9 打开报告时先看这几个字段
初始报告的主体可以缩成下面的形状。这里省略真实哈希，只展示字段关系；完整值保存在随书事实文件中：

```json
{
  "schema_version": 1,
  "input_digest": "<由规则与文件摘要计算>",
  "snapshot": {
    "rules_sha256": "<规则文件摘要>",
    "files": [
      {"path": "docs/index.md", "sha256": "<内容摘要>"}
    ]
  },
  "status": "checked",
  "issues": [],
  "observations": [],
  "scope": {
    "schema_version": 1,
    "include_archive": false,
    "scan_examples": false
  }
}
```

snapshot 回答这次实际检查了哪份输入，scope 保留规则值，issues 和 observations 保存两种不同结果。status 是便于阅读的概括，不能取代前面的字段。报告不记录模型的思维过程，本地程序的动作可以通过输入与输出独立复查。

本机驱动报告以及[随书结果文件](facts/aurora-workflow-20261110.json)都为每一步保存 stdout 与 saved_report。第 6 步中，stdout 是错误，saved_report 则是上一步旧内容。并列保存两者，可以直接看见“本次执行失败，但旧报告仍在”的状态。删除旧报告后，就无法从记录中重现这次误判。
