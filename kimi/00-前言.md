# 前言

<!-- block: kimi-front.b-opening -->
Kimi Code 把会话、工具、技能和插件组织在同一个运行时中，本书用库存审查案例解释它们怎样配合。

第一次请代码助手审查一个函数，通常只需贴上代码，问一句有没有问题。第二次，你会补上业务规则；第三次，还要提醒它只读文件、不要直接修复、给出触发条件。事情开始重复时，值得研究的便是怎样把这套工作方式留在项目里。

本书的项目叫“澄明库存”。它只有一个预留函数：输入库存和预留数量，返回剩余数量。代码很短，却犯了两个常见错误：把恰好用尽库存当成失败，允许负数预留把库存变多。输入类型的约束也不完整。我们先在终端复现这些行为，再把业务规则、审查步骤和报告格式接入 Kimi。

## 从能运行的例子开始

全部示例位于 `kimi/examples/`。没有模型账号也能运行库存检查、Hook 子进程和规则查询服务。有 Kimi 2.5.2 时，还能核对 CLI 参数并完成真实 ACP 握手。需要模型生成内容的部分，书中给出操作和观察方法，实际验证范围集中写在附录 C。

前半册讲清程序从哪里启动、配置从哪里读取、会话留下什么。中段把 Skill、自定义 Agent 和插件装配起来，随后加入 Hook、MCP 与 ACP。最后几章处理无人值守输出、恢复与交付。读者始终面对同一个库存项目，前一章留下的文件会在后一章继续使用。

代码助手的答复与程序结果要分别看。报告说“已修复”时，我们仍运行原来的边界输入；协议说“支持会话恢复”时，我们还要区分能力声明和实际恢复。这样做不是为了增加文书，而是让下一次故障有地方下手。

## 两个名字相近的项目

本书研究 `MoonshotAI/kimi-code`，固定版本为 `@moonshot-ai/kimi-code@2.5.2`，完整提交为 `1c142a007c10e881602690def96057c23a2baa12`。它使用 TypeScript 工程和 `agent-core-v2` 引擎，采用 MIT 许可证。旧 `MoonshotAI/kimi-cli` 是另一套 Python 实现，迁移命令与旧配置需要结合各自版本阅读。

命令名都叫 `kimi`，不代表安装来源相同。遇到旧文章中的 YAML Agent、旧工具名称或旧配置路径，先确认文章对应哪个仓库。把两套机制拼在一起，会得到一个语法看起来合理、运行时却无法识别的示例。

本书中的上游链接均指向固定提交。说明性文字由作者重新组织，示例为随书原创。书籍与 Moonshot AI 无隶属关系，也不替代产品支持文档。

## 选择一条阅读路线

初次使用可沿第 1、3、4、6、7 章走一遍，然后完成第 18 章。希望做团队扩展，可以先跑第 1 章的库存案例，再连续阅读第 9—13 章。编写客户端的读者重点看第 2、5、14、16、17 章。

书中使用两类目录：“书籍仓库根目录”包含 `scripts/`、`yuyu-book/` 与 `kimi/`；“练习副本”是第 4 章复制出来的独立小项目。构建书籍在前者运行，启动审查助手在后者进行。命令旁边会写出所需目录，避免把练习的修改落在书稿上。

## 怎样理解实验结果

离线业务检查证明输入与输出；真实源码组件实验验证解析器和 Hook 执行器；CLI 实验验证已安装程序的帮助和 ACP 握手。它们覆盖的范围不同。模型能否正确发现全部缺陷、IDE 是否完整实现反向调用，都需要在实际环境中继续观察。

随书保留源码摘要、实验脚本和 JSON 结果。升级版本时，可以重跑同一组检查，再决定哪些章节需要修改。读到结尾时，你将得到一套可复用的审查插件，也能解释其中哪些行为由提示词引导，哪些由工具配置决定，哪些最终要靠宿主和操作系统落实。
