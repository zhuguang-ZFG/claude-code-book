# 第 4 章：准备工作区，把业务规则放对地方

<!-- block: kimi-ch04.b-opening -->
工作目录决定相对路径，AGENTS.md 提供项目说明；独立练习副本让审查、修复与书稿互不混淆。

本章把随书文件复制成一个完整小项目。后面章节会在这个项目中安装插件、创建会话和检查修复结果，先把目录约定统一起来。

## 4.1 建立练习副本

在书籍仓库根目录运行以下 PowerShell 命令。`chengming-lab` 应是一个尚不存在的新目录；如果已经做过练习，换一个名字即可。

```powershell
Copy-Item -LiteralPath kimi/examples -Destination .scratch/chengming-lab -Recurse
Set-Location .scratch/chengming-lab
git init
python check_inventory.py
```

最后一条仍会报告预期的失败。此后书中的“练习目录”都指当前目录。里面的 `inventory.py` 是待审代码，`check_inventory.py` 是观察驱动，`inventory_fixed.py` 是参考答案，`review-plugin/` 是完整插件。

如果希望自己完成修复，可以暂时不打开参考答案。运行 `git status --short` 看一眼文件列表，确认这里没有书稿和出版配置。Kimi 的任务范围也应指向这个小项目。

## 4.2 给项目写一份短说明

在练习根目录新建 `AGENTS.md`：

```markdown
# 澄明库存练习

待审实现是 inventory.py。业务规则在
review-plugin/skills/review-inventory/references/rules.md。

审查任务只报告问题，不自动修复。报告必须包含触发输入、
实际行为、预期行为和文件位置。没有运行的代码标为静态推演。

在当前目录运行 python check_inventory.py 复现练习缺陷。
python check_inventory.py --fixed 运行参考实现。
```

这份说明回答三件事：读什么，怎样检查，什么算完成。不要把每个章节的全部解释都塞进去；稳定的项目规则放在这里，某一次审查的目标写进当前请求。

`AGENTS.md` 的内容进入上下文后仍属于项目说明。它不是 Python 验证器，也不会自动禁止写文件。真正的工具集合在第 10 章配置，流程拦截在第 12 章观察。

## 4.3 信任工作区意味着什么

从一个新仓库启动助手时，不只有源码值得阅读。项目里的技能、自定义 Agent 和 MCP 配置也可能改变运行方式。尤其是自定义 Agent 文件，它的正文可以成为系统提示词；这与普通 `AGENTS.md` 作为参考材料的角色不同。

本书的练习文件全部可读且规模很小，安装前可以逐个检查。面对真实项目，应先理解这些配置的来源与作用，再决定是否让程序加载它们。单纯把项目路径加入某个列表，不能代替阅读其可执行脚本。

## 4.4 相对路径有三个参照点

| 路径出现的位置 | 通常相对哪里解释 | 本书例子 |
| --- | --- | --- |
| 终端命令中的文件 | 当前 shell 目录 | `python check_inventory.py` |
| 插件清单中的 `./` 路径 | 插件根目录 | `./skills/` |
| 插件 Hook 命令 | 插件根目录 | `python ./hooks/review_only.py` |

错误经常出在这三个参照点被混用。把 Hook 写成 `python kimi/examples/...`，安装到用户数据目录后就会失效，因为宿主切换到了插件根目录。

Skill 的辅助材料也要考虑安装后的位置。随书规则保存在 Skill 自己的 `references/` 目录中，避免依赖作者机器上的绝对路径。若使用 `${KIMI_SKILL_DIR}`，应按固定版本的模板语法编写。

## 4.5 保留审查时的文件状态

第一次审查前，可以在练习副本里提交一个基线，或保存文件摘要。这样，当你修复代码后重新运行检查，能知道模型报告对应的是哪个版本。

Git 记录代码变化，会话记录对话变化，两者不会自动等价。即使恢复了旧会话，磁盘上的 `inventory.py` 也可能已经修复；即使切回旧代码，助手上下文里也可能还记着新实现。第 7 章将沿这个问题讨论恢复。
