# 第 6 章：工具集合、审批模式与 Plan

<!-- block: kimi-ch06.b-opening -->
工具集合决定 Agent 能提出哪些操作，审批模式决定操作怎样得到处理；Plan 还影响任务从探索进入执行的过程。

“自动运行”容易被理解成一个总开关。实际上，一个动作先得成为可用工具调用，还要经过策略与宿主处理；当前模式只是其中的一部分。

## 6.1 三种审批模式

固定版本文档使用新的界面名称，同时保留配置中的旧值：

| 界面名称 | 配置值 | 主要行为 |
| --- | --- | --- |
| Always Ask | `manual` | 常规只读自动，其余动作逐项确认 |
| Ask When Needed | `yolo` | 常规编辑和命令自动，敏感动作仍询问 |
| Never Ask | `auto` | 工具审批自动处理，也不向用户提问 |

这些是版本 2.5.2 的产品语义，不能把别的工具中同名 `yolo` 的含义搬过来。模式也不能证明操作系统已经提供文件或网络权限。

本书的审查练习使用受限 Agent，不需要为了方便先启用自动模式。读者可以先在默认模式观察动作，再决定自己的修复任务需要怎样的审批节奏。

## 6.2 Plan 与审批模式不是同一件事

Plan 让助手先探索和提出计划。固定文档说明，退出 Plan 需要用户确认，这一点在 Never Ask 模式下也保留。配置中的 `default_plan_mode` 又不直接应用于 `-p` 非交互模式。

因此“我设置了自动模式”不能推导出“任何等待都消失”。先看正在等待的是工具审批、计划确认，还是用户问题，再查对应机制。

Plan 也不意味着程序完全没有写入：运行时需要保存自己的计划和状态。讨论只读时，应说明是业务文件、Agent 工具集合，还是整个进程的文件系统访问。

## 6.3 静态规则表达持久选择

配置允许声明规则，例如：

```toml
[[permission.rules]]
decision = "deny"
pattern = "Bash(rm -rf*)"
```

这是固定文档中的规则形状。具体命令匹配具有语法与边界条件，不能把一条字符串规则当成完整 shell 分析器。若项目明确只需读取文件，更直接的办法是不给该 Agent 提供 `Bash`、`Write` 和 `Edit`，第 10 章会采用这种方式。

Hook 的拒绝与权限规则也不同。Hook 是运行本地程序后解释结果；它会遇到程序缺失、超时和错误退出。权限配置则由宿主自己的策略系统读取。

## 6.4 工具列表怎样限制审查角色

库存审查员只需要 `Read`、`Grep`、`Glob`。它可以寻找文件、读取规则并给出静态判断，却不能自己运行 Python 测试。这个限制必须在报告里体现：测试由用户在终端执行，结果交给它解释。

若你希望助手也运行测试，可以创建另一个明确允许命令的角色，并重新考虑其工作范围。给同一个角色加上 `Bash`，再期待一段“只运行测试”的文字可靠阻止其他命令，会改变原来的约束条件。

## 6.5 非交互模式需要单独理解

固定 CLI 文档说明，`-p` 不请求人工审批，常规工具调用按 `auto` 策略处理，静态 deny 规则仍生效。它不是“交互模式但恰好没人按键”。将审查脚本放进 CI 前，应先检查这个差异。

本书第 16 章使用受限 Agent 和结构化输出解释无人值守流程。判断任务是否成功，还要运行独立的业务检查，不能只根据进程没有弹窗得出结论。
