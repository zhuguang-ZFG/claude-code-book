# 第 7 章：恢复、分叉和导出会话

<!-- block: kimi-ch07.b-opening -->
会话保存对话与运行状态，恢复它不会自动还原工作目录中的代码；分叉会话也不会创建独立工作树。

昨天的审查还没做完，今天打开终端继续，是最常见的使用场景之一。恢复之后，助手记得什么、文件又处于什么状态，需要分别核对。

## 7.1 从当前目录找到旧会话

在练习目录运行：

```powershell
kimi --continue
```

它继续当前目录最近的会话。`kimi --session` 打开选择界面，带上 ID 则指定某个会话。`--continue` 和 `--session` 不能同时使用。若从另一个目录启动，最近会话的选择范围也会变化。

在终端界面内，`/sessions` 用于选择会话，`/title` 可以给审查命名。一个包含项目和阶段的标题，如“库存预留：边界审查”，比默认的模糊标题更容易定位。

恢复旧会话后，先让助手重新读取当前文件和测试结果。不要仅说“接着改”，尤其是你已在外部编辑器中修改了代码时。

## 7.2 磁盘上保存了什么

数据目录中的 `state.json` 保存会话元数据；`agents/main/wire.jsonl` 保存主 Agent 的通信记录；子 Agent 有各自的记录目录。请求轨迹还可能包含工具 schema、请求参数和 MCP 工具列表。

这些记录服务于恢复与重放，不等于 Git 快照。对话里保存了旧函数文本，磁盘却可能是新函数；恢复过程也不应被理解为撤销外部编辑器做过的修改。

| 想恢复的东西 | 应检查的载体 |
| --- | --- |
| 审查目标与讨论 | 会话历史 |
| 当前函数实现 | 工作目录文件 |
| 修复前后的差异 | Git 或你自己的版本副本 |
| 测试是否真正完成 | 命令退出状态与输出 |

把这些载体分清，能避免“会话恢复成功，所以代码也回去了”的误判。

## 7.3 分叉用于探索另一条讨论路线

`/fork` 复制当前会话，原会话仍然保持打开；可以通过 `/sessions` 切到分叉。它适合比较两种修复解释，或让另一条讨论重新审查已经提出的结论。

分叉并不复制工作树。两条会话如果都指向同一个目录，仍能观察或修改同一批文件。要比较两种实现，应另建工作副本或 Git worktree，再把各自任务指向不同位置。

固定文档还说明，已保存的 `/goal` 不会自动复制到分叉。会话历史和持续目标属于不同状态，不宜凭一个 fork 操作推断全部运行安排都被继承。

## 7.4 导出调试资料与导出可读记录

在 shell 中，`kimi export` 导出诊断 ZIP。可以指定会话与输出位置，并用 `--no-include-global-log` 排除全局日志：

```powershell
kimi export SESSION_ID -o review-debug.zip --no-include-global-log
```

`SESSION_ID` 需要替换成实际 ID。终端界面中的 `/export-md` 输出可读 Markdown，`/export` 是它的别名；Web 界面的 `/export` 则导出诊断 ZIP。命令拼写相近，产物不同。

给同事解释一个缺陷通常只需可读记录和最小重现。只有排查运行时问题时才需要诊断包。导出包可能包含路径、工具输出和代码，分享前先查看内容。

## 7.5 导入历史保留了怎样的连续性

`kimi import-sessions` 可以导入 Claude Code 与 Codex 的近期会话。固定文档说明转换在本地完成，不修改原始会话，也不调用模型。导入后的会话以整理过的对话内容接续，完整原始资料另行保存。

这不是把另一个运行时的全部内存状态迁入 Kimi。原工具的权限决定、后台进程或未完成命令，不会因为对话被导入就自然成为 Kimi 的活跃执行状态。开始继续前，重新检查工作目录和未完成动作。
