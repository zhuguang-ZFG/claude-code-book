# 第 8 章：长任务里的上下文与压缩

<!-- block: kimi-ch08.b-opening -->
上下文压缩把长历史整理成后续可用的材料；可靠的审查还需要把业务规则与验证结果保存在可重新读取的文件里。

一个小函数可以在一轮里审完，真实项目却可能先查需求，再追调用者，最后运行几十个测试。随着材料增加，原先的关键约束容易被大量输出淹没。

## 8.1 历史长度不是有效信息量

模型需要知道库存输入域、恰好用尽的规则、已发现的缺陷以及尚未完成的验证。它不一定需要再次看到每一次目录列表，也不需要重复十遍相同的异常堆栈。

整理上下文时，先区分稳定规则、当前状态和临时观察。稳定规则放进项目说明或 Skill；当前状态记录文件版本与下一步；临时输出在需要时保留定位入口。这样，恢复任务时可以重新读取依据，不必完全依赖一段压缩摘要。

## 8.2 手动压缩与自动压缩

Kimi 在上下文接近窗口限制时自动压缩，也提供 `/compact`。可以附上一条保留重点的说明：

```text
/compact 保留库存业务规则、已复现输入、当前文件版本和未完成验证。
```

这条说明是在引导压缩重点，不能保证摘要逐字保留所有历史。压缩后若要引用具体代码，仍应重新读取文件；若要声称测试通过，仍要找到对应运行结果。

运行中的 `/compact` 会进入队列；固定文档还描述了重复压缩排队和自动压缩先发生时的处理。看到指令暂未执行，不一定是程序卡死，应先检查当前回合是否仍在运行。

## 8.3 给任务写一个可恢复的检查点

在练习目录保存 `review-checkpoint.md`，例如：

```markdown
# 库存审查检查点

目标：只读审查 inventory.py。
规则：正整数预留量；允许恰好用尽。
已复现：10/10 被拒，10/-2 返回 12。
输入版本：记录实际 Git commit 或文件 SHA-256。
尚未完成：核对布尔值、小数与零输入。
下一步：运行 check_inventory.py，按当前实现复核报告。
```

其中的版本字段应填写真实值，不要照抄占位文字。检查点能帮助恢复目标，但不替代运行输出。若只把“测试通过”写进笔记，却没有说明测的哪个版本，未来仍很难复核。

## 8.4 压缩之后为什么会重新出现旧建议

可能是摘要遗漏了限制，也可能是当前请求没有明确任务阶段，还有一种情况是文件已经变化，旧结论失效。处理方式应对应原因。

先检查重新送入模型的规则，再看当前文件与原输入是否一致。若规则缺失，补回稳定材料；若实现变化，重新验证；若只是模型把审查误当修复，重申阶段并使用受限 Agent。不要把所有偏差统称为“记忆差”。

## 8.5 窗口配置与模型能力

配置中的 `max_context_size` 参与运行时预算，但服务端能力是另一项约束。把值增大可能推迟本地整理，却不能让服务端接受超限请求。某些模型还声明单次输入限制，不能简单用“总窗口减输出”替代全部判断。

阅读长日志时，可以先定位失败附近，再按需要扩大范围。这样做保留了信息的可追溯性，也减少无关输出进入上下文。第 17 章会用同样的方法排查中断与重复执行。
