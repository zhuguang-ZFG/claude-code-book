# 第 9 章：把审查步骤写成 Skill

<!-- block: kimi-ch09.b-opening -->
Skill 用文件保存可重复的工作步骤，描述字段帮助发现它，正文与辅助材料在调用时进入任务。

项目规则告诉助手哪些行为正确，Skill 则告诉它怎样完成一类任务。库存规则可以供测试和代码审查共同使用，但审查步骤还需要规定证据、报告格式和遇到不确定情况时的处理。

## 9.1 一个 Skill 的完整结构

随书插件包含：

```text
review-plugin/
  skills/
    review-inventory/
      SKILL.md
      references/
        rules.md
```

目录形式的入口名为 `SKILL.md`，开头是 YAML frontmatter，后面是 Markdown 正文。随书版本的关键字段如下：

```yaml
name: review-inventory
description: 以业务规则和边界输入审查库存预留函数，输出带证据的缺陷报告
type: prompt
```

`description` 应说明任务，而不是写一句“高级专家助手”。模型是否适合选择它，需要从描述中得到具体线索。正文再交代读取规则、检查边界、区分静态推演和运行结果。

## 9.2 正文怎样从提醒变成工作步骤

一句“认真审查，不要漏掉错误”很难转成可检查的动作。随书正文要求先确定目标文件，再读取业务规则，随后查看检查驱动与已有输出，最后给出触发输入、预期和实际行为。

顺序有原因：先看实现再猜规则，容易替代码找解释；先看规则再审实现，才有独立的判断依据。报告中保留具体输入，则能把争论从“这段代码可能有问题”落到一个可以运行的例子上。

Skill 还要求初次练习不读取参考答案。读者知道答案在哪儿，并不妨碍练习；关键是不能把参考答案当作独立审查的证据。

## 9.3 发现目录与显式覆盖

Kimi 可以从专用目录和通用 `.agents` 目录发现技能，也支持配置额外目录。`--skills-dir` 提供启动时的显式目录选择，并替代自动发现的用户与项目目录。它可以重复使用，适合实验时控制候选集合。

在练习目录中，尚未安装插件时，可以这样测试普通 Skill：

```powershell
kimi --skills-dir ./review-plugin/skills
```

进入界面后调用 `/skill:review-inventory`。此时它是按普通目录发现的技能。第 11 章安装为插件后，名称会带上插件前缀，两种调用方式不能混淆。

这项操作会启动真实模型会话，需要你自己的模型配置；本书验证了文件与解析规则，未把模型选择该技能的效果列为已实跑。

## 9.4 普通技能与插件技能的名字

安装插件后，调用方式为：

```text
/skill:chengming-review:review-inventory
```

前缀让不同插件中同名技能能够共存。裸名称不会自动解析到插件技能。如果插件命令与技能同名，`/插件名:名称` 优先表达命令；显式的 `/skill:` 形式用于调用技能。

这种差异会影响排错。文件明明存在、命令却找不到时，先判断它是普通目录资源还是插件资源，再核对注册名称，不要反复改文件名碰运气。

## 9.5 Skill 不授予执行权限

正文里写“运行测试”不会凭空增加 `Bash` 工具，写“只读”也不会自动移除写入工具。步骤与能力配置需要配合。

本书的审查员没有命令工具，因此 Skill 允许它阅读用户提供的测试结果，也要求无结果时标为静态推演。这样，工作步骤与角色能力是相容的。若改成自动执行测试的角色，应该同步修改 Agent 配置、报告证据和实验范围。

## 9.6 维护一份会被真正复用的技能

把经常变化的业务规则放进辅助文件，保持入口短而清楚。新增一条规则后，先运行离线案例验证预期，再检查 Skill 是否仍能定位它。相对路径应在安装后的插件副本中成立，而不是只在作者仓库里成立。
