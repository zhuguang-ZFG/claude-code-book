# 第 10 章：定义一个只读审查 Agent

<!-- block: kimi-ch10.b-opening -->
自定义 Agent 文件规定角色提示词与工具列表，选择结果绑定到新会话；恢复会话会恢复原来的角色绑定。

Skill 可以教助手怎样审查，但同一个主 Agent 可能同时具备写代码、执行命令和委派任务的能力。如果任务只需要读取材料，创建一个职责清楚的角色会更容易观察其行为。

## 10.1 随书审查员的定义

`review-plugin/agents/inventory-reviewer.md` 是完整可用的 Agent 文件，核心配置为：

```yaml
name: inventory-reviewer
description: 只读检查库存预留函数的边界条件，报告可复现的缺陷
tools:
  - Read
  - Grep
  - Glob
disallowedTools:
  - Bash
  - Write
  - Edit
subagents: []
```

正文是该角色的系统提示词，要求给出触发输入、位置与影响，并说明没有执行过的检查。`tools` 只列出三个读取与检索工具；重复写出的 deny 列表便于维护者看清意图。

工具允许列表不是操作系统沙箱。它约束这个 Agent 可用的工具入口，宿主本身、插件 Hook 或其他进程仍可能拥有各自的能力。这里的“只读审查员”专指这份角色配置与当前任务。

## 10.2 缺省值与空列表的差别

省略 `tools`，或将其写成单独的 `*`，表示不以该字段限制全部工具；`tools: []` 则禁用全部工具。两者看起来都没有列出名称，语义却相反。

普通内置工具按精确且区分大小写的名称匹配。MCP 名称可以使用规定的 glob 形式，如 `mcp__server__*`。不要把普通工具名写成 `Read*` 并期待它自动扩展。

`disallowedTools` 在允许列表之后应用。裸 `*` 放进 deny 列表不等于拒绝所有工具；固定文档将这种形状列为无效匹配。若需要一个不能调用工具的纯文本角色，用明确的空允许列表表达。

## 10.3 启动与恢复的角色绑定

在练习目录中启动：

```powershell
kimi --agent-file ./review-plugin/agents/inventory-reviewer.md
```

然后提交第 1 章的审查请求。`--agent-file` 是本次启动的显式选择，不能与 `--agent` 同用，也不能与 `--session`、`--continue` 混用。原因是角色在会话创建时绑定，恢复流程使用已保存的绑定。

修改 Agent 文件之后，如果要比较新定义，先创建一个新会话。不要在恢复旧会话时追加 `--agent-file`，试图悄悄换掉角色。这样既不符合参数约束，也会让审查结果难以解释。

## 10.4 同名文件怎样决定优先级

固定版本的优先级从高到低为：显式文件、项目、额外目录、用户、插件、内置。目录发现的同名自定义角色还需要 `override: true` 才能替换内置角色；显式 `--agent-file` 则体现启动者的直接选择。

这使团队可以提供插件默认角色，同时让某个项目定义自己的版本。代价是排错时不能只看插件目录：项目里更高优先级的同名文件可能已经覆盖了它。

正文成为系统提示词也意味着，随意使用 `override: true` 可能改变整个默认角色的工作方式。库存练习使用独立名字，不覆盖内置 Agent。

## 10.5 模板变量决定哪些内容被继承

自定义提示词拥有自己的模板。插件贡献的系统说明若需要进入模板，应按文档放入 `${plugin_sections}`；若使用 `${base_prompt}`，又应避免重复注入已经存在的插件区块。

随书审查员刻意只使用简短明确的正文，没有依赖额外系统说明。业务规则由用户指定文件或 Skill 提供。这样读者可以清楚看到角色定义与任务材料之间的关系。

## 10.6 实际解析器验证了什么

随书 `verify_source.mjs` 编译固定源码里的 `agentFile.ts` 并直接调用解析函数。检查确认：审查员的允许与拒绝列表得到保留；`subagents: []` 保持为空；缺少 `description` 的文件被拒绝；空工具列表不会被变成缺省的全部工具。

这证明配置文件符合解析器契约，没有证明模型一定只提出合理的审查结论，也没有代替完整宿主中的工具执行实验。后者还要观察角色选择、运行时策略和实际工具结果。
