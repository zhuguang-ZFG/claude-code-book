# 第 15 章：让子 Agent 接到完整任务

<!-- block: kimi-ch15.b-opening -->
子 Agent 使用独立上下文，主 Agent 应把目标、材料和完成条件明确交给它，再核对返回结论。

库存函数很小，不值得为了展示并行而拆成很多任务。真实仓库中，如果规则、调用者与测试分散在不同模块，委派才可能减少主上下文中的无关细节。

## 15.1 独立上下文带来的好处与成本

固定文档说明，子 Agent 看到明确传入的任务说明，不自动拥有主 Agent 的整段聊天历史。它的中间工具记录不直接混进主上下文，最终结论再返回主 Agent。

这能减少探索日志对主任务的干扰，也要求任务说明足够完整。“再看一下那个问题”对刚创建的子 Agent 没有明确含义；应写清文件、规则和问题本身。

每个子 Agent 独立消耗模型 token。拆分不是免费的性能开关，任务很短时，多一次准备与汇总反而可能比直接完成更慢。

## 15.2 一个可执行的委派说明

可以把库存项目的调用者检查描述成：

```text
检查库存预留函数的调用位置，只读取文件。
规则：quantity 必须为正整数，允许等于 stock。
列出调用者是否可能传入零、负数、小数或布尔值。
每项给出文件位置、输入来源与确定程度。
不要修改代码，不要把没有执行的路径标成已复现。
```

这份说明没有依赖主对话中的指代词。返回结果也容易验收：主 Agent 可以按文件位置复读，确认输入来源是否真的存在。

对于独立的边界审查，插件中的 `inventory-reviewer` 也可以作为子 Agent 类型被发现。但它只能使用允许的读取工具，不能替主 Agent 运行测试。

## 15.3 工具权限与委派能力分开配置

自定义 Agent 的 `subagents` 字段限定可委派类型，工具列表还决定 `Agent` 等入口是否可用。固定实现会在展示和实际委派时检查相关列表。仅仅在提示词中写“不许再派人”，不等于配置已经移除了委派能力。

随书审查员使用 `subagents: []`，并且工具列表只保留读取工具。它是一个边界清楚的叶子角色。其他角色若需要更深的委派链，应明确列出类型，并考虑如何防止循环与重复任务。

内置 `coder`、`explore`、`plan` 的用途与能力也不同。不要仅凭名字把它们视为同一工具集合的不同提示词，具体行为应对照钉版文档和当前配置。

## 15.4 后台结果怎样回到主任务

子 Agent 可以后台运行，结果完成后返回主 Agent。固定文档说明，如果它结束当前回合时仍有后台任务，完成报告会等待相关工作稳定后再返回。

主 Agent 收到结论后仍需要检查内容。一个子 Agent 报告“没有问题”，可能只覆盖了调用者；另一个发现类型约束缺失，也未必分析了持久化。汇总时保留各自范围，比简单投票更有意义。

## 15.5 独立上下文不等于独立文件系统

多个 Agent 即使各自有上下文，也可能共享工作目录。若允许它们同时编辑同一个文件，需要额外解决冲突、版本与验证问题。把任务拆给多个角色并不会自动得到 Git worktree 隔离。

本书的审查任务只读，因此可以把“规则是否完整”和“调用者输入是否符合规则”作为相对独立的观察。真正修复时，先让一个明确的执行者落下改动，再用同一版本运行检查。

## 15.6 让主 Agent 保留判断责任

最终报告应由主任务的目标来组织，标明发现、证据和未覆盖范围。子任务返回的错误路径、猜测或无关建议需要筛选，不能因为来自另一个 Agent 就提高可信度。
