# 第 16 章：在脚本中读取 JSONL 输出

<!-- block: kimi-ch16.b-opening -->
JSONL 将输出组织成逐行 JSON，消费者仍需区分助手消息、工具结果、元信息和错误，不能只取最后一行。

交互界面适合人类观察，自动检查则需要稳定的数据边界。`kimi -p` 配合 `--output-format stream-json`，让脚本能逐行处理输出。

## 16.1 从受限角色启动一次审查

在已配置模型的练习目录中，可以运行：

```powershell
$previousEncoding = [Console]::OutputEncoding
try {
    [Console]::OutputEncoding = [System.Text.UTF8Encoding]::new($false)
    kimi --agent-file ./review-plugin/agents/inventory-reviewer.md `
        -p "按业务规则只读审查 inventory.py，报告触发输入与证据。" `
        --output-format stream-json 2> review.stderr.log |
        Set-Content -LiteralPath review.jsonl -Encoding UTF8
    $reviewExitCode = $LASTEXITCODE
} finally {
    [Console]::OutputEncoding = $previousEncoding
}
"Kimi exit code: $reviewExitCode"
```

这是一项需要模型服务的读者练习。正文没有把它列为本次实跑。运行前确认所选角色、工作目录和数据根；第 6 章已经说明，非交互模式不会弹出常规人工审批。

stdout 保存结构化消息，stderr 保存进度和诊断。将两者合并到一个文件，会让 JSON 解析器遇到普通日志文本。

Windows PowerShell 5.1 的 `>` 默认写入 UTF-16；PowerShell 7 的默认编码又不同。上面先按 UTF-8 解码原生命令的 stdout，再显式用 UTF-8 保存，并立即保留 Kimi 的退出码。5.1 写入的 BOM 由下文的 `utf-8-sig` 处理。stderr 仅用于诊断，不交给 JSON 解析器。

## 16.2 消息有哪些形状

固定 `prompt-render.ts` 定义的助手消息包含 `role: assistant`，可带文本和 `tool_calls`；工具消息包含 `role: tool`、`tool_call_id` 与文本结果。重试等元信息使用 `role: meta`。其他错误路径还可能输出带 `type: error` 的对象。

下面是为说明字段而写的教学示例，不是模型实跑记录：

```json
{"role":"assistant","tool_calls":[{"type":"function","id":"read-1","function":{"name":"Read","arguments":"{\"file_path\":\"inventory.py\"}"}}]}
{"role":"tool","tool_call_id":"read-1","content":"file contents"}
{"role":"assistant","content":"库存恰好用尽的边界需要复核。"}
```

`function.arguments` 本身是 JSON 字符串，不能当作已经解析好的对象。消费者首先解析整行，再在需要时解析该字段。

## 16.3 按 ID 对应工具结果

收集工具调用 ID，再用 `tool_call_id` 找到结果。不要简单假设“下一行一定就是当前工具结果”，因为重试、并发或其他消息可能插在中间。

如果进程结束时仍有未对应的调用，应保留未完成状态。不能因为最后一条助手消息包含“完成”就自动忽略缺失结果。对于只读审查，至少应能看出它读取了哪些材料，以及最终结论基于什么。

```python
import json

with open("review.jsonl", encoding="utf-8-sig") as stream:
    for number, line in enumerate(stream, 1):
        if not line.strip():
            continue
        message = json.loads(line)
        role = message.get("role")
        if role == "tool":
            print(number, message.get("tool_call_id"))
        elif role == "meta" or message.get("type") == "error":
            print(number, "diagnostic", message.get("type"))
```

这段代码只展示分类，不判断审查是否成功。生产消费者还应记录进程退出码、解析异常和消息完整性，并限制日志体积。

## 16.4 重试信息不是新的业务结论

源码中的重试元信息带有失败次数、下一次尝试、等待时间和错误类型。它能帮助区分服务端暂时错误与业务检查失败，但不应被当成新的助手答复追加进报告。

如果整个脚本外层也自动重试，要考虑某些工具是否已经执行。本书的只读角色降低了写入重复的复杂性；一旦扩展为发工单、提交代码或更新数据库，重试就需要独立的幂等设计。

## 16.5 CI 的通过条件应在模型之外

模型报告可以作为审查输入，业务测试仍应由确定的命令执行。库存案例中，修复后的检查必须覆盖原来的 8 个场景，不能为了让流水线通过而删掉失败输入。

把模型输出、工具轨迹、代码差异和测试结果分别保存，才能解释“为什么这次允许合并”。一个退出码或一段自然语言都不够承载全部含义。
