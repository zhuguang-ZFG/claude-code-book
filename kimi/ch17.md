# 第 17 章：中断之后，先判断停在哪里

<!-- block: kimi-ch17.b-opening -->
恢复任务要先识别最后完成的动作，再核对文件和会话状态；盲目重发请求可能重复已经执行的操作。

最难排查的故障往往不是明确的错误，而是“窗口没反应了”。此时可能有模型请求、工具进程、审批等待或客户端连接仍在进行。先确定停在哪一层，才能选择合适的恢复方式。

## 17.1 建立一条最短排查链

先看是否有待处理的交互，再看工具是否仍在运行，随后检查进程退出状态，最后查看会话与诊断日志。每一步都寻找具体证据，而不是只根据等待时间猜测。

| 观察 | 下一步 |
| --- | --- |
| 界面显示计划待确认 | 检查 Plan 状态 |
| 工具已启动但没有退出结果 | 检查进程与输出 |
| JSONL 出现重试元信息 | 核对请求错误与重试次数 |
| MCP 服务已连接但工具不可见 | 核对新旧会话与 Agent 工具列表 |
| 插件源文件改了，行为未变 | 核对安装副本与重载 |

这张表把前面各章的机制放到同一个故障现场中。它不是所有错误的清单，但足以避免几种常见的误诊。

## 17.2 审查报告与磁盘不同步

假设助手已经指出负数预留的问题，你在编辑器里修好了函数，然后恢复旧会话。旧上下文仍可能保存错误实现。最直接的处理是说明文件已改变，让它重新读取当前源码，并提供新的运行结果。

反过来，如果助手声称已修复，却看不到文件差异，应检查它是否只提出了修改建议，是否因工具权限被拒绝，或者修改落在另一工作目录。不要先运行更多测试来掩盖文件尚未改变的事实。

## 17.3 Hook 失败不能伪装成成功拦截

如果 Python 不在 Hook 进程的 PATH 中，处理器可能根本没启动。超时或退出 `1` 也会走放行路径。出现这种情况，应查看诊断并直接运行处理器，而不是只检查清单里是否写了 `PreToolUse`。

随书真实源码实验把这些状态分别验证。错误放行是运行时的既定行为，不应通过改写实验报告把它描述成“成功保护”。需要更强约束时，应调整角色工具和宿主策略。

## 17.4 取消并不保证外部世界回滚

取消可以阻止继续推进，但已经完成的写入、请求或子进程动作可能仍留下效果。本书案例的核心函数没有外部状态，便于测试；真实任务中则要逐项确认最后完成的动作。

例如创建工单的网络请求可能已到达服务端，只是响应丢失。直接重试可能创建第二张工单。应先用业务标识查询结果，再决定重发。这是工程设计建议，不是 Kimi 自动提供的事务保证。

## 17.5 记录一个别人能重现的问题

有用的报告包含版本、入口、工作目录结构、必要的非敏感配置、最小输入和实际结果。若问题与插件有关，附上插件版本和安装来源；若与 ACP 有关，附方法名、请求 ID 与错误码。

先在新的实验数据根中复现，再判断是否与旧配置或会话有关。`KIMI_CODE_HOME` 能隔离 Kimi 专用状态，但通用 `.agents` 资源的发现仍需考虑。不要为了快速复现删除自己的全部会话。

## 17.6 升级之前留住比较材料

本书的 `source-lock.json` 固定提交与关键文件摘要，CLI 结果记录发布程序摘要。升级后重跑库存检查、源码组件实验和 ACP 握手，就能判断差异发生在业务样例、解析器还是协议面。

如果新版本改变字段或语义，先更新实验，再更新正文。只有这样，维护记录中的“支持”与“已验证”才会对应可重复的观察。
