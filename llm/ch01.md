# 第 1 章：token 不是字，也不是词

<!-- block: llm-ch01.b-opening -->
> **白话先看懂**：模型不直接读文字，它读的是 tokenizer 切出的整数编号。token 可能是一个词、半个词、一个标点，也可能只是汉字的一部分。计费和窗口都按 token 算，所以字数不能直接当预算。

先数一段短文本：`青禾工作坊` 在 Python 中长度是 5，编码成 UTF-8 后是 15 字节，用本章的玩具 tokenizer 切分后是 8 个 token。三个数字回答的是不同问题。模型的窗口预算要按它自己的 token 口径计算；费用还要看输入、输出和缓存各自的单价。

系统提示、工具 schema、历史消息、检索结果和工具返回的 JSON 都占窗口。按字数估算，很难知道还能放多少材料。本章用几十行 Python 展开 byte-level BPE 的训练与编码，配套脚本直接复用 minbpe 的基础实现；按本书环境使用 Python 3.12+，只用标准库即可运行。

## 1.1 模型收到的不是字符串

打个比方：你把一封信寄进模型，传达室（**tokenizer**）不会把整封信原样递进去，而是先把文字按词表拆成一片片积木，再把每片积木换成对应的**整数编号（token ID）**。模型内部只做数字运算；答完之后，再把挑出来的一串编号交给传达室，拼回人能读懂的文字。

本书讨论的文本生成模型先把 token ID 送入 embedding 表，取出对应的向量。文本由 tokenizer 切分并映射成 ID；生成时模型输出词表上的分数，解码程序选出 ID，tokenizer 再把它们还原为文字。


token 不是“字”，也不是“词”。它可能是：

- 一个完整单词，例如 `token`；
- 一个词的一部分，例如 `token` 被拆成 `tok` 和 `en`；
- 一个标点或空格；
- 一个汉字的 3 个 UTF-8 字节中的一部分；
- 一个特殊标记，例如对话角色分隔符或工具调用边界。

所以，“一个汉字等于一个 token”只在某些模型、某些常用字上偶尔成立。生僻字、emoji、代码缩进和 JSON 标点都可能占更多 token。反过来，常见英文单词可能只占一个 token，比字符数少。

## 1.2 UTF-8 给出 256 个起始符号

你可以把 UTF-8 想成一套“可长可短的装箱规则”：英文字母和常见标点只装 **1 字节**，常用汉字占 **3 字节**，生僻字和 emoji 占 **4 字节**——只有按完整边界拆箱才读得出原字，从多字节箱子正中间硬掰开就会变成乱码。

byte-level BPE 先把文本编码成 UTF-8 字节，再在字节序列上做合并。UTF-8 用 1–4 个字节表示一个 Unicode 码点：

```python
len("青禾".encode("utf-8"))      # 6：两个汉字各 3 字节
len("🙂".encode("utf-8"))        # 4：一个 emoji 占 4 字节
len("hello".encode("utf-8"))     # 5：ASCII 每字符 1 字节
```

字节只有 256 种取值，所以 byte-level BPE 可以从 256 个基础符号开始，覆盖有效 UTF-8 文本中的所有字节，不需要另设“未知字节”。常见汉字通常占 3 字节，扩展区的一些汉字占 4 字节；合并前，每个字节各算一个符号。合并规则能把常见片段合成一个 token，未学到的片段仍会占多个 token。

```python
text = "青禾"
assert text.encode("utf-8").hex() == "e99d92e7a6be"
```

UTF-8 的编码规则见 [RFC 3629](https://www.rfc-editor.org/rfc/rfc3629)。tiktoken 等 byte-level BPE 实现还会加入预切分规则和特殊 token。生产 tokenizer 也有基于字符或 unigram 的方案，不能把 256 个字节当作所有分词方法的共同起点。

## 1.3 五十行 BPE

BPE（Byte Pair Encoding，字节对编码）听着学术，其实就像**给常用词组造简写**：先从最碎的 256 个字节起步，哪两个紧挨着的符号一起出现得最勤，就把它们粘成一个新符号并给它一个新编号。一轮粘一对，反复粘几万轮，常用的英文单词、常见汉字和代码关键词就都成了“一个整体号”，少见的片段则退回到多个碎块。

BPE 的训练只有三步，重复若干轮：

1. 把所有文本拆成字节序列。
2. 统计相邻两个符号组成的 pair，出现次数最多的获胜。
3. 把这个 pair 合并成一个新符号，加入词表。

下面是可运行的最小实现。为了便于观察，它省略了生产 tokenizer 的预切分、特殊 token 和词表压缩，只保留机制。

<!-- block: llm-ch01.b-bpe -->
```python
from collections import Counter

BASE = 256

def apply(seq, pair, new_id):
    out, i = [], 0
    while i < len(seq):
        if i + 1 < len(seq) and (seq[i], seq[i + 1]) == pair:
            out.append(new_id)
            i += 2
        else:
            out.append(seq[i])
            i += 1
    return out

def train(texts, merges):
    seqs = [list(t.encode("utf-8")) for t in texts]
    vocab = {i: bytes([i]) for i in range(BASE)}
    rules = []
    for _ in range(merges):
        counts = Counter()
        for seq in seqs:
            counts.update(zip(seq, seq[1:]))
        if not counts:
            break
        pair = max(sorted(counts), key=lambda p: counts[p])
        new_id = BASE + len(rules)
        vocab[new_id] = vocab[pair[0]] + vocab[pair[1]]
        seqs = [apply(seq, pair, new_id) for seq in seqs]
        rules.append(pair)
    return rules, vocab

def encode(text, rules):
    seq = list(text.encode("utf-8"))
    for rank, pair in enumerate(rules):
        seq = apply(seq, pair, BASE + rank)
    return seq
```

`pair = max(sorted(counts), key=...)` 先排序再取最大值，是为了在出现次数相同时固定选择顺序。没有这个约束，同一份语料换一次运行顺序就可能学到不同的合并表，后面的计数也就不可复现。

编码时按学到的顺序逐条应用合并规则，每条规则只扫一遍。解码则把每个 token 对应的字节拼起来，再按 UTF-8 解码：

```python
def decode(ids, vocab):
    return b"".join(vocab[i] for i in ids).decode("utf-8")
```

完整脚本见 [`llm/examples/bpe_demo.py`](examples/bpe_demo.py)。其中的相邻合并直接调用 minbpe 的 `merge`，编码调用 `BasicTokenizer.encode`：每次检查当前仍存在的 pair，优先合并排名最早的，直到没有可用规则。上面的短实现按完整合并表依次扫描，便于逐行阅读；对于本例训练得到的规则，两者得到相同的 ID。

复用代码固定在 [minbpe 提交 `1acefe8`](https://github.com/karpathy/minbpe/tree/1acefe89412b20245db5a22d2a02001e547dc602)，原文件、MIT 许可证与哈希记录一起保存在 [`vendor/minbpe/`](examples/vendor/minbpe/README.md)。只导入基础 tokenizer，因此不需要 `tiktoken`、PyTorch 或网络。本书仍自行处理多条训练文本的边界、并列候选排序和严格 UTF-8 解码；上游的单字符串训练与容错解码规则不同。

## 1.4 跑一次，先看三个数字

在仓库根目录运行：

```bash
python llm/examples/bpe_demo.py
```

本次实测的样本表如下。“toy tokens”指上面 32 条合并规则得到的 token 数，不是任何厂商的计数。

| 样本 | 码点数 | UTF-8 字节 | toy tokens | tokens / 码点 |
| --- | ---: | ---: | ---: | ---: |
| `agent 需要数 token。` | 16 | 24 | 12 | 0.75 |
| `青禾工作坊` | 5 | 15 | 8 | 1.60 |
| `工具调用的 JSON 也占 token。` | 20 | 36 | 23 | 1.15 |
| `🙂` | 1 | 4 | 4 | 4.00 |
| `hello` | 5 | 5 | 5 | 1.00 |

表中的码点数来自 Python 的 `len(text)`。这些样本里，一个可见字符恰好对应一个码点；组合字符就不同了：`len("é")` 是 1，`len("e\u0301")` 是 2，后者由字母与组合重音组成，显示时通常仍像一个字。Unicode 把这类用户感知的字符按[字素簇](https://www.unicode.org/reports/tr29/tr29-47.html#Grapheme_Cluster_Boundaries)处理。码点、字节和 token 不能互换。

窗口预算不能靠一个固定的“中文 1 字 = 2 token”换算。请求前应使用目标模型的计数接口，或用对应 tokenizer 连同消息模板估算；请求后再用 API 返回的 usage 校正。OpenAI 的 [tiktoken](https://github.com/openai/tiktoken/blob/79dc2c0533685b893616c78160b5d9e40876e724/README.md) 可用于对应生产词表；minbpe 的[公开讲义](https://github.com/karpathy/minbpe/blob/1acefe89412b20245db5a22d2a02001e547dc602/lecture.md)适合追踪训练与编码过程。本例复用了基础算法，但词表仍只来自这七行语料。训练语料、预切分、特殊 token 和词表大小都会改变最终计数。

## 1.5 Agent 工程落点

把一次请求拆成预算项，比记一个“平均 token 数”更有用：

| 预算项 | 典型内容 | 为什么会变 |
| --- | --- | --- |
| 系统提示 | 角色、规则、输出约定 | 规则越长，每轮固定成本越高 |
| 工具定义 | 名称、描述、JSON Schema | 工具越多，schema 越细，成本越高 |
| 历史消息 | 用户与助手往返、工具调用与回执 | 轮数增长，旧内容仍占位置 |
| 检索材料 | 文档片段、代码、日志 | 片段数量和长度直接进入窗口 |
| 输出预留 | 回答、工具参数、结构化 JSON | 不留余量会在生成中途截断 |
| 安全余量 | 重试、格式修复、额外工具轮次 | 多一轮就多一份输入 |

一个算术例子：20 个工具，每个定义平均 150 token，单是工具 schema 就约 3 000 token；每轮都带，50 轮就是 150 000 token 的输入。这里还没算系统提示和历史消息。150 000 是这 50 次请求累计送入的 token 数，单次窗口仍只占其中的 3 000。缓存命中可能改变这些输入的计费单价，不会把它们从窗口里拿走。

<!-- block: llm-ch01.b-truncation -->
硬砍超长对话时有两个常见雷区：砍在汉字几个字节的正中间，解码直接报错；或者删掉了发起调用的那条工具消息、却留着半截返回结果，让模型下轮分不清做过没有。

截断要同时保住文本边界和消息结构。`"青".encode("utf-8")[:2]` 只留下 3 个字节中的前两个，严格解码会抛出 `UnicodeDecodeError`；只有显式使用 `errors="replace"` 才会得到替换字符。Python 字符串切片按码点切，不会留下半个 UTF-8 字节序列，但仍可能拆开字素簇、JSON 或工具消息。按 token 切片也要检查解码边界，因为一个 token 可能只包含某个汉字的部分字节。

历史压缩应按消息或任务块进行。保留最近轮次、固定事实和待处理的动作；已经执行的工具调用与回执成对保留，或把动作和结果一起写入摘要。否则，下一轮就可能把已执行动作当作待执行动作。

窗口预算和长上下文的成本在[第 6 章](ch06.md)展开；主书[第 7 章](../第二部分-核心系统篇/07-上下文管理-Agent的工作记忆.md)从 Agent 工作记忆的角度讲同一件事。

## 1.6 常见翻车

| 常见翻车 | 后果 | 正确做法 |
| --- | --- | --- |
| 用字符数估算 token | 中文、代码和 JSON 上误差大，窗口被提前撑爆 | 用目标 tokenizer 或 API usage 实测 |
| 认为一个汉字就是一个 token | 生僻字和 emoji 被低估 | 把 token 当作模型相关的计数单位 |
| 直接切字节或 token 序列 | 解码失败、字符或工具调用残缺 | 按消息或结构边界截断，保留配对 |
| 拿 A 模型的 token 数套 B 模型 | 预算和价格都算错 | 每个模型单独测量，换模型重算 |
| 忽略工具 schema 和特殊 token | 固定开销被漏掉 | 把系统提示、工具定义和输出预留都计入 |
