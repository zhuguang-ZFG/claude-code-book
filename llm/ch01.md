# 第 1 章：token 不是字，也不是词

<!-- block: llm-ch01.b-opening -->
同一段中文，按字符数是 40 个字，按 UTF-8 是 120 字节，按某个模型的 tokenizer 可能是 35 个 token，换一个模型又可能是 52 个。三个数字都“对”，只有最后一个决定上下文窗口和账单。

Agent 系统里，这个问题每天都会出现：系统提示、工具 schema、历史消息、检索结果、工具返回的 JSON 一起挤进同一个窗口。按字符数估算，往往在长会话或中文材料上失准。先用 50 行 Python 写一个 byte-level BPE，把文本变成 token 的过程走一遍。不训练模型，也不需要 GPU。

## 1.1 模型收到的不是字符串

模型的第一层是 embedding 查表，表的每一行对应一个整数 ID。文本先被 tokenizer 切成 token，再映射成 ID；生成时模型输出词表上的分数，tokenizer 再把 ID 还原成字节和文字。

```ill

```

token 不是“字”，也不是“词”。它可能是：

- 一个完整单词，例如 `token`；
- 一个词的一部分，例如 `token` 被拆成 `tok` 和 `en`；
- 一个标点或空格；
- 一个汉字的 3 个 UTF-8 字节中的一部分；
- 一个特殊标记，例如对话角色分隔符或工具调用边界。

因此，“一个汉字等于一个 token”只在某些模型、某些常用字上偶尔成立。生僻字、emoji、代码缩进和 JSON 标点都可能占更多 token。反过来，常见英文单词可能只占一个 token，比字符数少。

## 1.2 UTF-8 给出 256 个起始符号

byte-level BPE 先把文本编码成 UTF-8 字节，再在字节序列上做合并。UTF-8 用 1–4 个字节表示一个 Unicode 码点：

```python
len("青禾".encode("utf-8"))      # 6：两个汉字各 3 字节
len("🙂".encode("utf-8"))        # 4：一个 emoji 占 4 字节
len("hello".encode("utf-8"))     # 5：ASCII 每字符 1 字节
```

字节只有 256 种取值，所以词表可以从 256 个基础符号开始，任何文本都能表示，不会出现“未知字符”。代价是：一个汉字在合并之前至少是 3 个基础符号。合并规则学得好，常见字可以合成一个 token；学不到的生僻字仍会留下多个片段。

```python
text = "青禾"
assert text.encode("utf-8").hex() == "e99d92e7a6be"
```

UTF-8 的编码规则见 [RFC 3629](https://www.rfc-editor.org/rfc/rfc3629)。生产 tokenizer 还会加入特殊 token 和预切分正则，但起点仍是这 256 个字节。

## 1.3 五十行 BPE

BPE 的训练只有三步，重复若干轮：

1. 把所有文本拆成字节序列。
2. 统计相邻两个符号组成的 pair，出现次数最多的获胜。
3. 把这个 pair 合并成一个新符号，加入词表。

下面是可运行的最小实现。为了便于观察，它省略了生产 tokenizer 的预切分、特殊 token 和词表压缩，只保留机制。

<!-- block: llm-ch01.b-bpe -->
```python
from collections import Counter

BASE = 256

def apply(seq, pair, new_id):
    out, i = [], 0
    while i < len(seq):
        if i + 1 < len(seq) and (seq[i], seq[i + 1]) == pair:
            out.append(new_id)
            i += 2
        else:
            out.append(seq[i])
            i += 1
    return out

def train(texts, merges):
    seqs = [list(t.encode("utf-8")) for t in texts]
    vocab = {i: bytes([i]) for i in range(BASE)}
    rules = []
    for _ in range(merges):
        counts = Counter()
        for seq in seqs:
            counts.update(zip(seq, seq[1:]))
        if not counts:
            break
        pair = max(sorted(counts), key=lambda p: counts[p])
        new_id = BASE + len(rules)
        vocab[new_id] = vocab[pair[0]] + vocab[pair[1]]
        seqs = [apply(seq, pair, new_id) for seq in seqs]
        rules.append(pair)
    return rules, vocab

def encode(text, rules):
    seq = list(text.encode("utf-8"))
    for rank, pair in enumerate(rules):
        seq = apply(seq, pair, BASE + rank)
    return seq
```

`pair = max(sorted(counts), key=...)` 先排序再取最大值，是为了在出现次数相同时固定选择顺序。没有这个约束，同一份语料换一次运行顺序就可能学到不同的合并表，后面的计数也就不可复现。

编码时按学到的顺序逐条应用合并规则，每条规则只扫一遍。解码则把每个 token 对应的字节拼起来，再按 UTF-8 解码：

```python
def decode(ids, vocab):
    return b"".join(vocab[i] for i in ids).decode("utf-8")
```

完整脚本还包含导入、示例语料和输出格式，见 [`llm/examples/bpe_demo.py`](examples/bpe_demo.py)。它只用 Python 标准库，不依赖 `tiktoken`、PyTorch 或网络。

## 1.4 跑一次，先看三个数字

在仓库根目录运行：

```bash
python llm/examples/bpe_demo.py
```

本次实测的样本表如下。“toy tokens”指上面 32 条合并规则得到的 token 数，不是任何厂商的计数。

| 样本 | 字符数 | UTF-8 字节 | toy tokens | tokens / 字符 |
| --- | ---: | ---: | ---: | ---: |
| `agent 需要数 token。` | 16 | 24 | 12 | 0.75 |
| `青禾工作坊` | 5 | 15 | 8 | 1.60 |
| `工具调用的 JSON 也占 token。` | 20 | 36 | 23 | 1.15 |
| `🙂` | 1 | 4 | 4 | 4.00 |
| `hello` | 5 | 5 | 5 | 1.00 |

同一套规则下，emoji 的 1 个字符是 4 个字节、4 个 token；`hello` 是 5 个字符、5 个字节、5 个 token；`青禾工作坊` 的 5 个字符被合并成 8 个 token。三个样本的“字符数”与“token 数”关系完全不同。

这也是为什么不能用一个固定的“中文 1 字 = 2 token”去卡窗口。正式估算应使用目标模型的 tokenizer，或直接读 API 返回的 usage。OpenAI 的 [tiktoken](https://github.com/openai/tiktoken/blob/79dc2c0533685b893616c78160b5d9e40876e724/README.md) 是 byte-level BPE 的一个参考实现；Karpathy 的 [minbpe](https://github.com/karpathy/minbpe/blob/1acefe89412b20245db5a22d2a02001e547dc602/lecture.md) 用更短的代码讲同一套训练与编码过程。两个实现都与本章的玩具版本有差别：语料规模、预切分、特殊 token 和词表大小都会改变最终计数。

## 1.5 Agent 工程落点

把一次请求拆成预算项，比记一个“平均 token 数”更有用：

| 预算项 | 典型内容 | 为什么会变 |
| --- | --- | --- |
| 系统提示 | 角色、规则、输出约定 | 规则越长，每轮固定成本越高 |
| 工具定义 | 名称、描述、JSON Schema | 工具越多，schema 越细，成本越高 |
| 历史消息 | 用户与助手往返、工具调用与回执 | 轮数增长，旧内容仍占位置 |
| 检索材料 | 文档片段、代码、日志 | 片段数量和长度直接进入窗口 |
| 输出预留 | 回答、工具参数、结构化 JSON | 不留余量会在生成中途截断 |
| 安全余量 | 重试、格式修复、额外工具轮次 | 多一轮就多一份输入 |

一个算术例子：20 个工具，每个定义平均 150 token，单是工具 schema 就约 3 000 token；每轮都带，50 轮就是 150 000 token 的输入。这里还没算系统提示和历史消息。工具定义不是“配置一次就免费”，它跟着每次请求走。

<!-- block: llm-ch01.b-truncation -->
截断时按消息或块删除，不要按字节切片。把一个多字节汉字切成两半，解码会出现替换字符；把工具调用和它的回执拆开，下一轮模型就不知道动作是否执行过。保留最近轮次、固定事实和未完成的工具调用，压缩更早的对话，通常比“删掉最后 N 个字符”可靠。

## 1.6 常见翻车

| 常见翻车 | 后果 | 正确做法 |
| --- | --- | --- |
| 用字符数估算 token | 中文、代码和 JSON 上误差大，窗口被提前撑爆 | 用目标 tokenizer 或 API usage 实测 |
| 认为一个汉字就是一个 token | 生僻字和 emoji 被低估 | 把 token 当作模型相关的计数单位 |
| 直接切字符串截断 | UTF-8 半个字符、工具调用残缺 | 按消息或结构边界截断，保留配对 |
| 拿 A 模型的 token 数套 B 模型 | 预算和价格都算错 | 每个模型单独测量，换模型重算 |
| 忽略工具 schema 和特殊 token | 固定开销被漏掉 | 把系统提示、工具定义和输出预留都计入 |

## 1.7 本章小实验

1. 运行 `python llm/examples/bpe_demo.py`，记下五个样本的字符数、字节数和 toy token 数。
2. 把 `CORPUS` 换成你自己的三句话，重新训练，观察前八条合并规则有没有变化。
3. 在 `SAMPLES` 里加入一段 JSON 和一段生僻字，比较字节数与 token 数。
4. 如果你安装了 `tiktoken`，用它同一段文本的计数与 toy token 对比；没有安装也不影响本章练习。不要把对比结果当成所有模型的统一比例。
