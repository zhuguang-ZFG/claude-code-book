# 第 2 章：向量空间里的“像”

<!-- block: llm-ch02.b-opening -->
用户说“钱还没退”，知识库里写的是“退款未到账”。检索需要把这两种说法联系起来。嵌入模型把文本映射成向量，训练目标让相关文本在选定的相似度度量下靠近；但高相似度不保证答案正确。否定、反义和领域词都可能让检索选错片段。

取几个手设的三维向量，走一遍 embedding 查表、余弦相似度、top-k 检索和一次精确扫描的成本；再看嵌入模型怎样用对比学习训练、近似索引怎样用召回换速度。代码只用标准库。

## 2.1 从 token ID 到向量

[第 1 章](ch01.md)把文本变成了整数 ID。模型的第一层是一张 embedding 表 `E`，形状是 `词表大小 × d_model`；ID 是行号，查表得到这一层的输入向量。这张表是学出来的参数，不是人工编码。

| 配置 | 参数量 | fp16 体积 |
| --- | ---: | ---: |
| 词表 32000，`d_model=4096` | 131 072 000 | 250.0 MiB |
| 词表 32000，`d_model=768` | 24 576 000 | 46.9 MiB |

同一个 token 在表里只有一个向量，但经过注意力和 FFN 之后，它的上下文表示会随句子变化。检索系统需要的是整段文本的表示，通常使用为检索训练的模型，把多个 token 的上下文表示汇成一个向量。底座可以采用不同架构；仅凭“encoder”或“decoder”的名称，不能判断输出能否用于检索。

这几步要分开看：输入表回答“这个 ID 对应哪一行”，上下文表示回答“这个 token 在当前句子里怎样使用”，检索向量则把查询或片段压成可比较的表示。Raschka《Build a Large Language Model (From Scratch)》的[第 2 章配套代码](https://github.com/rasbt/LLMs-from-scratch/blob/22c637fdf9aa2f5fdd39c2cc80c1d36b4ab7d8d8/ch02/01_main-chapter-code/ch02.ipynb)演示了前一种查表；词向量的早期工作见 [word2vec](https://arxiv.org/abs/1301.3781)，句子级编码与检索见 [Sentence-BERT](https://arxiv.org/abs/1908.10084)。

## 2.2 余弦相似度

两个向量的余弦是点积除以模长：

```text
cos(a, b) = (a · b) / (||a|| × ||b||)
```

它只看方向，不看长度，取值在 `[-1, 1]`。`llm/examples/embedding_demo.py` 用一个长度不同的例子说明点积和余弦会给出不同排序：

| 候选 | 点积 | 余弦 |
| --- | ---: | ---: |
| A：与查询同方向的短向量 | 3.000 | 1.000 |
| B：与查询不同方向的长向量 | 6.000 | 0.707 |

```ill
llm-ch02-dot-cosine
```

查询是 `[3.0, 0.0]`；A 是 `[1.0, 0.0]`，B 是 `[2.0, 2.0]`。按点积，B 排第一；按余弦，A 排第一。使用内积索引而未归一化时，向量长度也会影响排序。若模型要求余弦检索，就在入库和查询时都归一化后用内积，或选择索引提供的余弦度量；具体做法要和模型的训练、使用说明一致。

```ill
llm-ch02-vector-space
```

脚本里七条客服短语的三维向量，查询“退款”和“物流”的近邻如下（按记录名称排除查询自身）：

| 排名 | “退款”的近邻 | 余弦 | “物流”的近邻 | 余弦 |
| ---: | --- | ---: | --- | ---: |
| 1 | 不退款 | 1.000 | 发货 | 0.889 |
| 2 | 退货 | 0.991 | 换货 | 0.625 |
| 3 | 换货 | 0.827 | 发票 | 0.543 |
| 4 | 发货 | 0.220 | 退货 | 0.217 |

“退款”的第一名是“不退款”，余弦 1.000。脚本没写错：这套玩具几何里，“退款”与“不退款”的向量方向几乎相同，余弦没能把语义否定分开；若极性被编码成相反方向，余弦会给出负值。真实编码器可能在训练中学会区分否定，但不能假设它一定区分；检索结果必须回到文本和业务规则核对。

记录身份与向量数值也要分开。`top_k(..., exclude_name="退款")` 只排除这一条记录；不同记录即使向量完全相同，也应留在候选里。外部查询默认不排除任何记录。[Faiss 的精确搜索教程](https://github.com/facebookresearch/faiss/blob/b14b3d693161c7b1cbc5f2e398c8234b42b04c8b/tutorial/python/1-Flat.py)用索引 ID 返回近邻，也用库内向量查询自身做检查；去重或排除自身是另需明确的规则。

## 2.3 相似不等于相关

余弦高只说明“方向接近”，不保证“对当前问题有用”。常见的四类偏差：

- **否定与极性**：`退款` 与 `不退款`、`通过` 与 `未通过` 可能共享大量词和语境；
- **反义与对比**：`便宜` 与 `贵`、`成功` 与 `失败` 常出现在相似句式里；
- **多义**：`苹果` 是水果还是公司，要看上下文；切块太短时，向量抓不到区分；
- **领域漂移**：同一个词在客服、法律和代码库里指向不同对象。

检索链路常把关键词召回（BM25）与向量召回结合起来，按来源、时间、权限过滤，再用交叉编码器或 LLM 重排，最后把来源和片段一起交给模型。重排可以进一步判断查询与片段是否相关，规则可以排除不满足条件的结果；两者也需要用标注样本检查，不能替代答案核验。

高维空间还有一些工程现象：某些向量容易成为“中心”，和谁都接近；不同模型的余弦分布不同，阈值不能跨模型照搬。阈值要在自己的查询集上校准，别直接抄一个 0.8。

向量方向也可以从数据中学出来。`llm/examples/embedding_train_demo.py` 用 30 轮 SGD 训练一个 12 词、16 维的 skip-gram 示例。语料由三个互不混杂的主题序列各重复 12 次组成，共 36 条；窗口内的词对作正例，脚本排除当前句子的已知上下文词后再抽负例。在这份特意简化的语料上，负例都来自其他主题。

脚本维护两张表：中心词的输入向量 `v` 与上下文词的输出向量 `u`。每个正负词对单独做一次二元分类更新，标签 `y` 为 1 或 0：

```text
s = v · u
loss = softplus(-s)  （正例）或 softplus(s)（负例）
g = sigmoid(s) - y
v_new = v_old - lr × g × u_old
u_new = u_old - lr × g × v_old
```

两个梯度都使用本次更新前的向量。先改 `v`，再把改后的值用于更新 `u`，就不再是这一步损失的 SGD 更新。示例的 `sgd_pair` 先保存旧坐标；测试对正、负标签分别做数值差分，核对两张表的更新。打印的 `pair loss` 是一轮中各词对更新前的损失均值，包含当轮重新抽取的负例，不是固定验证集上的损失。

本例从剩余词 ID 中均匀、有放回地抽取负例，并排除中心词与当前句子中该中心词的已知上下文；候选为空就明确报错。[word2vec 原始实现](https://github.com/tmikolov/word2vec/blob/20c129af10659f7c50e86e3be406df663beff438/word2vec.c)则按词频的 0.75 次幂构建噪声分布，还有不同的窗口和更新安排。[D2L 的数据准备](https://github.com/d2l-ai/d2l-en/blob/23d7a5aecceee57d1292c56e90cce307f183bb0a/chapter_natural-language-processing-pretraining/word-embedding-dataset.md)与[训练代码](https://github.com/d2l-ai/d2l-en/blob/23d7a5aecceee57d1292c56e90cce307f183bb0a/chapter_natural-language-processing-pretraining/word2vec-pretraining.md)展示了词频采样和批量反向传播。本书保留逐词对的标准库实现，便于检查算术，不能把它的训练曲线当作这些实现的复现结果。

近邻比较使用训练后的输入表。固定 seed=11，训练前“退款”的近邻是随机取向的“换货 +0.39、配送 +0.32”；训练后变成“售后 +0.99、换货 +0.99、退货 +0.98”，12 个词各自的前三个近邻都属于同一主题。这是这份受控语料上的观测；损失直接约束的是输入表与输出表之间的点积，并不保证任意语料上输入词向量的余弦都会按主题聚类。它没有测试否定、多义或真实检索，也没有证明 2.2 节的手设向量会由训练自然产生。

skip-gram 用中心词预测邻近词，学的是静态词表示；[《动手学深度学习》的词嵌入章节](https://d2l.ai/chapter_natural-language-processing-pretraining/word2vec.html)给出了这个目标。现代检索模型常用 Transformer 计算上下文表示，再经池化得到句子或段落向量，并用查询与文档的配对数据训练。后者同时改变了表示方式和训练目标，不能当成扩大语料后的 skip-gram。2.6 节接着说明这种区别。

## 2.4 一个最小检索流程

一条可用的检索链路至少包含：

```text
切块 → 编码 → 建索引 → 查询编码 → 召回 top-k → 过滤/去重 → 重排 → 带来源注入
```

`llm/examples/embedding_demo.py` 还算了两笔账：

- 10 万个 4096 维 fp32 向量，光向量本体约 1.5 GiB，不含索引结构、元数据和副本；
- 一次精确扫描是 409 600 000 次乘加。数据量再大，通常要用近似最近邻索引（如 [HNSW](https://arxiv.org/abs/1603.09320)）在召回率和速度之间取舍，见 2.7。

切块大小、重叠、是否按标题分段，会直接影响召回。块太短，指代和条件被切断；块太长，一个向量要代表多个主题。真实系统还要处理同一文档的多个版本，避免旧版本压过新版本。

## 2.5 维度与参数

输入 embedding 表的参数量是 `词表大小 × d_model`；如果语言模型的输出层与输入嵌入共享（tied），只算一张表，否则输出投影再算一张。这个公式不包括检索编码器的 Transformer 层。检索向量的输出维度影响存储和距离计算成本，质量还取决于训练数据、领域匹配和切块方式，不能仅凭维度判断。

对 Agent 来说，还要区分三种“向量”：

1. **decoder 的输入 embedding**：静态查表，进入模型后会被上下文改写；
2. **检索编码器的输出**：专门为相似度训练，通常做归一化；
3. **模型隐藏层的激活**：维度、分布和训练目标都不同，不适合直接拿来当检索向量。

把三者混用，是“离线评测很好、线上召回很差”的常见原因之一。

## 2.6 嵌入模型：对比学习、难负例与选型

2.3 的 skip-gram 用的是共现统计；今天主流的检索编码器用**对比学习**（contrastive learning）在句对、段落对上训练。样本是三元组：查询 `q`、正例 `p`（能回答问题的那段）、若干负例 `n`。目标是让 `q` 与 `p` 的相似度高于 `q` 与每个 `n` 的相似度。InfoNCE 把它写成一个 softmax（[van den Oord 等，arXiv:1807.03748](https://arxiv.org/abs/1807.03748)）：

```text
L = -log( exp(s(q, p) / τ) / (exp(s(q, p) / τ) + Σ_j exp(s(q, n_j) / τ)) )
```

`τ` 是温度，`s` 通常是归一化向量的点积。分母里的负例从哪来，决定模型学到什么：

- **批内负例**（in-batch negatives）：同一批里其他样本的正例充当负例，可以复用已算好的文档向量，但仍要计算查询与候选的相似度。如果批里混进“同一答案的不同说法”，会把正例当负例惩罚，造成假负例。
- **随机负例**：从语料里随便抽。太容易——问“阿姆斯特丹有多少人”，随机负例是“香蕉价格”，模型学不到细分。
- **难负例**（hard negatives）：相关但答非所问的段落。同一个问题，难负例是讲“阿姆斯特丹旅游”的段落；模型必须区分“同一个话题”和“同一个答案”。`sentence-transformers` 的训练文档把难负例与 `MultipleNegativesRankingLoss` 列为主流组合（[钉版仓库](https://github.com/huggingface/sentence-transformers/blob/3b17a2c948120350315245030f71d52f356d0c05/docs/sentence_transformer/training_overview.md)）。

难负例的难点在标注：要么用当前模型从 top-k 里挖（mine），要么用 BM25 召回再人工过滤。挖出来的负例可能本来就是正例，直接训练会教坏模型；这就是“假负例”问题，需要去重和阈值。

**选型**看四件事，而不是只看榜单第一名：

1. 任务匹配：检索、聚类、分类、STS 是不同子任务，MTEB 分项看；
2. 语言与领域：中文、代码、法律、客服话术要单独测；
3. 成本：维度 × 条数 × 副本决定内存，编码器大小决定吞吐；
4. 最大输入长度：超过就截断，长文档要么切块，要么换模型。

MTEB（Massive Text Embedding Benchmark，[Muennighoff 等，arXiv:2210.07316](https://arxiv.org/abs/2210.07316)）把多任务、多语言的榜单放在一起，适合筛候选，不适合直接当结论——榜单分数和你的语料分布不是一回事。

还有一个省内存的手段：**Matryoshka 表示**（[Kusupati 等，arXiv:2205.13147](https://arxiv.org/abs/2205.13147)）。训练时让前 256 维、前 512 维等前缀各自都能用，推理时按需截断：1024 维存全量、256 维做粗筛。这要求模型专门支持前缀截断；普通向量不能直接套用。向量本体的存储和距离计算量随维度下降，召回损失则要实测，不能预先保证只掉“一点”。

## 2.7 近似最近邻：召回、延迟、内存

2.4 算过：10 万个 4096 维向量，一次精确扫描约需 4 亿次乘加。精确扫描的代价按 `N × d` 增长；当它无法满足延迟预算时，可以用近似最近邻（ANN）减少候选比较。能省多少时间、漏掉多少近邻，取决于索引、数据分布和搜索参数。常见结构有四类：

| 结构 | 怎么找 | 代表 | 旋钮 |
| --- | --- | --- | --- |
| 哈希 | 相似向量投进同一桶 | LSH | 桶数、哈希位数 |
| 图 | 多层近邻图上贪心走 | HNSW | 每层连接数 `M`、搜索宽度 `ef` |
| 倒排桶 | 先找最近的聚类中心，再扫桶内 | IVF | 桶数、`nprobe` |
| 量化 | 把向量压成短码再比 | PQ | 子向量数、每段位数 |

图与量化索引的工程实现可参考 [Faiss](https://arxiv.org/abs/1702.08734)，HNSW 原始论文见 [Malkov 与 Yashunin](https://arxiv.org/abs/1603.09320)。

`llm/examples/ann_demo.py` 把 IVF 摊开：400 个二维点分成 8 个桶，查询先和 8 个中心比，只扫最近的 `nprobe` 个桶，再和精确答案比 top-10 的重合：

| nprobe | 扫描比例 | recall@10 |
| ---: | ---: | ---: |
| 1 | 13.2% | 0.865 |
| 2 | 25.0% | 0.997 |
| 4 | 51.9% | 1.000 |
| 8 | 100.0% | 1.000 |

[Faiss 的 IVF 教程](https://github.com/facebookresearch/faiss/blob/b14b3d693161c7b1cbc5f2e398c8234b42b04c8b/tutorial/python/2-IVFFlat.py)同样先训练分桶，再加入向量并调整 `nprobe`。这里用欧氏距离，Faiss 的 `METRIC_L2` 返回平方欧氏距离；两者排序相同，数值不能直接混用。本例的精确扫描与 IVF 都按“距离、记录 ID”打破平局，扫完全部桶时返回相同 ID。若两个实现采用不同的等距规则，ID 集合不一致未必表示漏掉了更近的点。表中扫描比例只计桶内候选，不含查询与 8 个中心的比较，也不代表运行时间比例。

`nprobe=1` 只扫 13% 的向量，就拿到 86.5% 的召回；再扫一个桶，几乎补齐。但平均数字会掩盖坏情况：脚本里最差的一条查询只拿到 0.30 的召回——它落在两个桶的边界上，top-10 里有 7 个点不在被扫描的桶里。ANN 的错误不是均匀的，边界和稀疏区域最容易漏。

所以评估向量索引时，“支持十亿向量”不等于“你的 top-10 够准”。要拿自己的查询集和精确答案比，报 `recall@k` 与 p95 延迟，再决定 `nprobe` 或 `ef` 取多少；换模型、换切块、换数据分布都要重测。检索质量的完整指标见[第 11 章](ch11.md)。

## 2.8 Agent 工程落点

| 场景 | 用什么 | 注意 |
| --- | --- | --- |
| 工具选择 | 工具描述向量 + 名称/参数关键词 | 工具名和 schema 要结构化，别只靠语义 |
| 知识库 RAG | 切块 + 向量召回 + 重排 | 带来源、版本和时间，处理否定与冲突 |
| 长期记忆 | 向量 + 时间/权限过滤 | 过期条目要淘汰，不能只增不减 |
| 去重 | 余弦 + 校准过的阈值 | 阈值按模型和语料调，不跨模型照搬 |
| 多语言 | 多语编码器 | 跨语相似度要实测，不能假设对齐 |

## 2.9 常见翻车

| 常见翻车 | 后果 | 正确做法 |
| --- | --- | --- |
| 用未归一化向量做内积却以为在算余弦 | 长向量主导排序 | 入库与查询都归一化，或确认索引度量 |
| 余弦高就当成答案正确 | 否定、反义、旧版本混入 | 重排、规则过滤、回到原文核对 |
| 一个阈值走天下 | 换模型或语料后召回崩 | 在自有查询集上校准 |
| 只做向量召回不做重排 | 召回多、精度低 | 混合召回 + 交叉编码器/LLM 重排 |
| 拿 decoder 输入 embedding 当检索向量 | 静态表与上下文表示混淆 | 用专门的检索编码器 |
| 切块不看结构 | 条件、指代、标题被切断 | 按标题/段落切，保留重叠与元数据 |


然后试四组改动：

1. 给 `VECTORS` 增加“换发票”“催发货”，观察查询“退款”和“物流”的 top-k 怎样变化；再故意加一个和“退款”方向几乎相同、含义相反的词，验证余弦能不能区分。
2. 把 A、B 两个候选都归一化，再比较点积排序；你会看到它和余弦排序一致。
3. 把查询换成“不退款”，看它的近邻是不是仍然以“退款”开头；思考真实业务里应该加什么规则或重排特征。
4. 把 `ann_demo.py` 的 `NOISE` 从 0.85 调到 1.4，让八个桶互相重叠，再看 `nprobe=1` 的召回掉到多少；把 `NPROBES` 改成 `(1, 3, 6, 8)`，观察“多扫一个桶”的边际收益在哪里变缓。

`embedding_train_demo.py` 再试两组：用现有词表混入一个包含两个主题的序列（比如 `['退款', '退货', '发货', '物流']`），看哪些跨组词进入近邻；再把 `EPOCHS` 调到 60，同时记录 pair loss、同组近邻与跨组余弦的变化。若语料与窗口使某个中心词没有可用负例，脚本会报错；应调整语料或窗口，不能靠反复重抽解决。训练损失下降不代表检索质量一定提高；是否过拟合，还需要独立的验证样本，不能只凭这份训练语料判断。
