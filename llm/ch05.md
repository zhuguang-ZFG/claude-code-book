# 第 5 章：同一个提示，为什么每次答案不同

<!-- block: llm-ch05.b-opening -->
一个负责调用工具的 Agent 在 `temperature=1.2` 下连续三次生成了同样的意图，却给出三种 JSON：一次字段名正确，一次多了一个逗号，一次把数字写成了字符串。提示没有改，模型也没有换。变化来自生成过程本身：模型每一步给出的是一组概率，采样器从这组概率里挑一个 token。

采样参数决定的是稳定与多样之间的取舍。知道哪些任务要稳定、哪些要多样性，比记住一个“最佳温度”有用；temperature=0 也不能替代校验。

## 5.1 模型一次只决定下一个 token

给定已有 token 序列，模型输出词表上每个候选 token 的分数，叫 logits。softmax 把分数变成概率：

```text
p_i = exp(z_i) / Σ_j exp(z_j)
```

然后采样器按概率选一个 token，把它接回序列，再预测下一个。整段回答的概率是每一步条件概率的乘积。训练时模型见过大量文本，学到的是“在这个上下文后面，哪些 token 更常见”，不是一份事实数据库。这些分数由最后一层输出投影得到；前面各层怎样用[注意力](ch03.md)混合位置，是第 3 章的主题。

如果每一步都选概率最高的 token，叫 greedy decoding。它通常更稳定，适合格式固定的短输出；但它仍然不是正确性的保证：最可能的下一个 token 组合起来，可能是一条流畅而错误的句子。

## 5.2 温度改变的是分布形状

温度 `T` 在 softmax 之前除 logits：

```text
p_i(T) = exp(z_i / T) / Σ_j exp(z_j / T)
```

- `T < 1`：分布更尖，高概率 token 更容易被选中；
- `T = 1`：不改变原始分布；
- `T > 1`：分布更平，低概率 token 获得更多机会；
- `T → 0`：趋近 argmax；不少 API 直接把 0 当作 greedy，具体行为要看提供方文档。

温度不改变模型“知道什么”，只改变从已知分布里抽取的方式。把温度调高不会让模型获得新知识，只会让低概率分支更容易出现。

实现上有一个容易忽略的细节：softmax 从不直接算 `exp(z)`。logits 一旦涨到几百，`exp(800)` 在 64 位浮点里直接溢出成无穷大。本书每个示例的 softmax 都先减去行内最大值再取指数——分子分母同乘 `exp(-max)` 不改变比值，却把指数参数压回零附近。这不是教科书洁癖：写训练示例时 sigmoid 在点积涨大后真的溢出了，`log(sigmoid)` 在下溢后还会在 `log(0)` 上崩，两者都要换成数值稳定的形式（`embedding_train_demo.py` 里保留了这个修正版）。温度除法放在减 max 之前还是之后不影响结果，但两件事都得做。

## 5.3 top-k 与 top-p

只有温度还不够。词表有数万到数十万 token，即使低概率分支单个很小，加起来也可能形成很长的尾巴。两个常用过滤器把尾巴剪掉：

- **top-k**：只保留概率最高的 k 个 token，再归一化；
- **top-p**（nucleus sampling）：按概率从高到低累加，保留刚好达到 p 的最小集合，再归一化。

常见顺序是：先算温度后的分布，再应用 top-k 或 top-p，最后在保留集合内采样。不同框架和 API 的参数顺序可能不同；同时设置 top-k 与 top-p 时，先看文档，不要假设一个固定的优先级。

`llm/examples/sampling_demo.py` 用一个六候选的合成分布演示这套算术。它不是模型输出，只是把 softmax、top-k、top-p 和采样写成可运行代码。实测结果如下：

| 设置 | 保留 token 数 | 最高概率 | 2 000 次采样中的最高频 token |
| --- | ---: | ---: | ---: |
| `T=0.2`，不筛选 | 6 | 0.865 | 0.86 |
| `T=0.2`，`top-k=3` | 3 | 约 0.87 | 0.87 |
| `T=0.2`，`top-p=0.90` | 2 | 约 0.88 | 0.88 |
| `T=1.0`，不筛选 | 6 | 0.371 | 0.38 |
| `T=1.0`，`top-k=3` | 3 | 约 0.45 | 0.45 |
| `T=1.0`，`top-p=0.90` | 5 | 约 0.40 | 0.40 |

`T=0.2` 时，分布已经足够尖，`top-p=0.90` 只留下两个候选；`T=1.0` 时，同样的 p 需要五个候选才能覆盖 90% 的概率。过滤器的效果依赖温度，不能把“top-p=0.9”当成一个与温度无关的固定行为。

## 5.4 随机性从哪里来

采样需要随机数。固定 seed 可以让同一套代码、同一个库、同一串调用顺序得到相同结果；示例脚本用 `random.Random(11)` 连续生成两次，八次抽样完全一致。

但“同一个 seed”不等于“跨服务确定”：

- 服务端可能改变批处理组合，浮点归约顺序随之变化；
- GPU 内核、驱动和模型版本可能不同；
- API 可能不暴露 seed，或只把它当作 best-effort；
- 有些提供方把 `temperature=0` 实现为 greedy，有些仍保留极小随机性。

所以，复现实验要记录模型标识、版本、温度、top-k/top-p、seed（如果可设）和调用时间。只在同一套环境里承诺“同 seed 同输出”，不要把它写成跨厂商保证。

## 5.5 Agent 为什么要低温

工具调用、JSON 输出、补丁生成这类任务，需要的是可解析、可校验的结构。低温减少格式漂移，但解决不了三件事：

1. schema 本身有歧义；
2. 输入缺少必填信息；
3. 模型不知道该调用哪个工具。

因此，低温要和校验一起用：解析 JSON、检查必填字段、验证类型和范围、失败后带错误重试。把温度降到 0 却不校验，只是把错误变得更稳定。

需要多样性时，高温才有意义：起标题、列备选方案、做头脑风暴。此时评价标准也应变化，不能再用“格式是否完全一致”判断好坏。

<!-- block: llm-ch05.b-agent -->
| 任务 | 建议起点 | 还要做什么 |
| --- | --- | --- |
| 工具参数、结构化 JSON | 低温或 greedy | schema 校验、类型检查、失败重试 |
| 代码补丁 | 低温 | 测试、静态检查、人工 review |
| 文案备选 | 中高温度 | 用评分表比较，不逐字比对 |
| 事实问答 | 低温 | 检索、引用、回到来源核对 |
| 多轮规划 | 低温到中温 | 约束动作边界，检查计划是否可执行 |

温度是采样参数，不是权限，也不是正确性开关。一个低温度的 Agent 仍可能调用错误的工具；一个高温度的 Agent 也可能碰巧给出正确答案。

## 5.6 一个可复现的玩具实验

在仓库根目录运行：

```bash
python llm/examples/sampling_demo.py
```

观察三件事：

1. `T=0.2` 与 `T=1.0` 的概率表差异；
2. 同一个 `top-p=0.90` 在两个温度下保留的候选数；
3. 固定 seed 后，两次抽样是否一致。

然后把 `LOGITS` 改成更平或更尖的分布，重跑一次。你会看到 `top-p` 的候选数随分布形状变化，而不只随 p 变化。这个练习不调用模型，也不产生费用。

## 5.7 常见翻车

| 常见翻车 | 后果 | 正确做法 |
| --- | --- | --- |
| 用高温“激发创造力”来修 JSON | 格式错误更多，重试成本上升 | 结构化任务用低温，并加校验 |
| 认为 `temperature=0` 一定确定 | 跨批次、跨版本仍可能变化 | 记录环境，关键结果做重复运行 |
| 同时设 top-k 和 top-p 却不看文档 | 实际保留集合与预期不同 | 确认参数顺序和优先级 |
| 只比较一次输出就判断提示优劣 | 把采样波动当成提示效果 | 固定参数，多次运行，按任务判据比较 |
| 把 token 概率当事实置信度 | 流畅的错误答案看起来“很确定” | 回到来源、工具回执和测试核对 |

采样之后，下一件影响成本和质量的变量是上下文长度：同样的模型，窗口里放 8 000 token 和 80 000 token，延迟、费用和注意力分配都不同。[第 6 章](ch06.md)把这笔账算清楚；如何用配对实验判断提示改动是否真的有效，见[提示词分册第 15–18 章](../prompt/ch15.md)。
