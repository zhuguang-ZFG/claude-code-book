# 第 5 章：同一个提示，为什么每次答案不同

<!-- block: llm-ch05.b-opening -->
同一个提示重复发送，答案为什么会变？先看生成过程：模型为下一个 token 给出一组分数，解码程序再决定选哪一个。启用采样时，即使这组分数完全相同，也可能抽到不同的 token；选出的 token 又会影响后续分布。

采样参数决定的是稳定与多样之间的取舍。知道哪些任务要稳定、哪些要多样性，比记住一个“最佳温度”有用；temperature=0 也不能替代校验。

## 5.1 模型一次只决定下一个 token

给定已有 token 序列，模型输出词表上每个候选 token 的分数，叫 logits。softmax 把分数变成概率：

```text
p_i = exp(z_i) / Σ_j exp(z_j)
```

然后采样器按概率选一个 token，把它接回序列，再预测下一个。整段回答的概率是每一步条件概率的乘积。训练时模型见过大量文本，学到的是“在这个上下文后面，哪些 token 更常见”，不是一份事实数据库。这些分数由最后一层输出投影得到；前面各层怎样用[注意力](ch03.md)混合位置，是第 3 章的主题。

如果每一步都选概率最高的 token，叫 greedy decoding。它通常更稳定，适合格式固定的短输出；但它仍然不是正确性的保证：最可能的下一个 token 组合起来，可能是一条流畅而错误的句子。

**束搜索（beam search）**同时保留多个候选前缀。每步扩展当前的束，再按序列得分剪枝，最后从留下的候选中选一个；束宽为 1 且不采样时退化为贪心。有限束宽可能提前删掉通向高分答案的前缀，因此不能保证找到全局最优。比较不同长度时还常用长度惩罚，此时排序目标也不再是原始联合概率。

束搜索常用于翻译、语音识别等受输入约束的生成任务，但模型似然仍不等于任务质量。[Holtzman 等](https://arxiv.org/abs/1904.09751)在 GPT-2 等模型的开放文本生成实验中观察到，高似然搜索容易产生重复、空泛的文本；nucleus sampling 通过截掉概率尾部再抽样改善了这些实验中的结果。这说明选择解码目标会影响质量，不能据此断言所有 LLM 任务都应采样。[Transformers v4.57.3](https://github.com/huggingface/transformers/blob/47b0e478f324b54f177ea7998a0791870fdd0324/docs/source/en/generation_strategies.md)同时提供贪心、采样和束搜索。

## 5.2 温度改变的是分布形状

温度 `T` 在 softmax 之前除 logits：

```text
p_i(T) = exp(z_i / T) / Σ_j exp(z_j / T)
```

- `0 < T < 1`：分布更尖，高概率 token 更容易被选中；
- `T = 1`：不改变原始分布；
- `T > 1`：分布更平，低概率 token 获得更多机会；
- `T → 0⁺`：若最大值唯一，概率集中到该 token；若多个最大值并列，极限分布在它们之间均分。greedy 则按实现的规则打破平局。`T=0` 不能代入上述公式，部分接口用它表示 greedy。

温度不更新模型参数，只改变当前这一步的采样分布。把温度调高不会让模型获得新知识，只会让低概率分支更容易出现。

直接算 `exp(800)` 会超出 Python 双精度浮点的范围。稳定的 softmax 通常先减去最大 logit：

```text
p_i(T) = exp((z_i - max(z)) / T) / Σ_j exp((z_j - max(z)) / T)
```

所有指数参数都不大于 0，最大项的指数恰好为 1。数学上，先除温度再减最大值与这个式子等价；浮点实现却有区别：温度极小时，先算 `z_i / T` 可能已经溢出。本章脚本先平移，再缩放，并拒绝非有限输入。

## 5.3 top-k 与 top-p

温度之外，还可以限制参与采样的候选。词表有数万到数十万 token，即使低概率分支单个很小，加起来也可能形成很长的尾巴。两个常用过滤器把尾巴剪掉：

- **top-k**：只保留概率最高的 k 个 token，再归一化；
- **top-p**（nucleus sampling）：按概率从高到低累加，保留刚好达到 p 的最小集合，再归一化。这里先按概率降序排列，并列时沿用输入顺序。

常见顺序是：先算温度后的分布，再应用 top-k 或 top-p，最后在保留集合内采样。本例 top-k 恰好留下 k 个候选；有些实现会把第 k 名并列的 token 都留下。同时设置 top-k 与 top-p 时，要核对框架的处理顺序和边界规则。

`llm/examples/sampling_demo.py` 用一个六候选的合成分布演示这套算术。它不是模型输出，只是把 softmax、top-k、top-p 和采样写成可运行代码。固定 seed=7、按表中顺序各抽 2 000 次，最高频候选均为“首都”，占比如下：

| 设置 | 候选数 | 最高概率 | 抽样占比 |
| --- | ---: | ---: | ---: |
| T=0.2<br/>全部 | 6 | 0.865 | 0.86 |
| T=0.2<br/>k=3 | 3 | 约 0.87 | 0.87 |
| T=0.2<br/>p=0.90 | 2 | 约 0.88 | 0.88 |
| T=1.0<br/>全部 | 6 | 0.371 | 0.38 |
| T=1.0<br/>k=3 | 3 | 约 0.45 | 0.45 |
| T=1.0<br/>p=0.90 | 5 | 约 0.40 | 0.40 |

`T=0.2` 时，分布已经足够尖，`top-p=0.90` 只留下两个候选；`T=1.0` 时，同样的 p 需要五个候选才能覆盖 90% 的概率。过滤器的效果依赖温度，不能把“top-p=0.9”当成一个与温度无关的固定行为。

## 5.4 随机性从哪里来

采样需要随机数。示例用同一 seed 初始化两个生成器，每个生成器连续抽八次，再比较两段序列。生成器必须放在循环外，否则每次都从相同状态开始，只是在重复第一次抽样。

```python
dist = top_p(softmax(LOGITS, 1.0), 0.9)
first_rng, second_rng = random.Random(11), random.Random(11)
first = [sample(dist, first_rng) for _ in range(8)]
second = [sample(dist, second_rng) for _ in range(8)]
assert first == second
```

Raschka 的[公开配套教材第 5 章](https://github.com/rasbt/LLMs-from-scratch/blob/22c637fdf9aa2f5fdd39c2cc80c1d36b4ab7d8d8/ch05/01_main-chapter-code/ch05.ipynb)也用固定 seed 下的连续抽样解释概率分布。可复现的是这一串随机过程，序列内部仍可以出现不同结果。

但“同一个 seed”不等于“跨服务确定”：

- 服务端可能改变批处理组合，浮点归约顺序随之变化；
- GPU 内核、驱动和模型版本可能不同；
- API 可能不暴露 seed，或只把它当作 best-effort；
- 即使选择 greedy，分数极接近时，数值扰动也可能改变最大值的位置。

复现实验要记录模型标识、版本、温度、top-k/top-p、seed（如果可设）和调用时间。本示例在相同 seed 和调用顺序下可复现；真实模型还需控制确定性算法与执行条件，并通过重复运行验证。

## 5.5 Agent 为什么要低温

工具调用、JSON 输出、补丁生成这类任务，需要可解析、可校验的结果。低温或 greedy 可以作为减少输出变化的起点，是否改善成功率仍要用任务样本测量。降低温度不能修复 schema 歧义、补齐缺失信息，也不能判断工具选得是否正确。

应用仍要解析 JSON，检查必填字段、类型和范围，并处理失败。需要格式约束时，可使用接口支持的约束解码；它与温度分别控制合法候选和候选间的选择。[第 12 章](ch12.md)区分了 JSON 语法、schema 约束和业务校验。

起标题、列备选方案时，可以尝试较高温度扩大候选差异，再按事实、风格和用途筛选。高温也可能增加无关内容，不宜只看“变化更多”就认定效果更好。

<!-- block: llm-ch05.b-agent -->
| 任务 | 建议起点 | 还要做什么 |
| --- | --- | --- |
| 工具参数、结构化 JSON | 低温或 greedy | schema 校验、类型检查、失败重试 |
| 代码补丁 | 低温 | 测试、静态检查、人工 review |
| 文案备选 | 中高温度 | 用评分表比较，不逐字比对 |
| 事实问答 | 低温 | 检索、引用、回到来源核对 |
| 多轮规划 | 低温到中温 | 约束动作边界，检查计划是否可执行 |

温度是采样参数，不是权限，也不是正确性开关。一个低温度的 Agent 仍可能调用错误的工具；一个高温度的 Agent 也可能碰巧给出正确答案。

## 5.6 一个可复现的玩具实验

在仓库根目录运行：

```bash
python llm/examples/sampling_demo.py
```

观察三件事：

1. `T=0.2` 与 `T=1.0` 的概率表差异；
2. 同一个 `top-p=0.90` 在两个温度下保留的候选数；
3. 固定 seed 后，两次抽样是否一致。

然后把 `LOGITS` 改成更平或更尖的分布，重跑一次。你会看到 `top-p` 的候选数随分布形状变化，而不只随 p 变化。这个练习不调用模型，也不产生费用。

## 5.7 常见翻车

| 常见翻车 | 后果 | 正确做法 |
| --- | --- | --- |
| 用高温“激发创造力”来修 JSON | 没有约束格式，错误仍可能出现 | 用支持的结构化输出并校验，温度另做对照 |
| 认为 `temperature=0` 一定确定 | 跨批次、跨版本仍可能变化 | 记录环境，关键结果做重复运行 |
| 同时设 top-k 和 top-p 却不看文档 | 实际保留集合与预期不同 | 确认参数顺序和优先级 |
| 只比较一次输出就判断提示优劣 | 把采样波动当成提示效果 | 固定参数，多次运行，按任务判据比较 |
| 把 token 概率当事实置信度 | 流畅的错误答案看起来“很确定” | 回到来源、工具回执和测试核对 |

采样之后，下一件影响成本和质量的变量是上下文长度：同样的模型，窗口里放 8 000 token 和 80 000 token，延迟、费用和注意力分配都不同。[第 6 章](ch06.md)把这笔账算清楚；如何用配对实验判断提示改动是否真的有效，见[提示词分册第 15–18 章](../prompt/ch15.md)。
