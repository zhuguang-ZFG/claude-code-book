# 第 6 章：上下文窗口不是免费的抽屉

<!-- block: llm-ch06.b-opening -->
一个排查线上问题的 Agent 把 12 万 token 的日志、配置和最近的对话一起塞进窗口。请求变慢了，费用上升了，模型却在回答里漏掉了日志中间那行报错。窗口确实装得下，但“装得下”不等于“读得好”，也不等于“花得起”。

上下文窗口是按 token 计算的预算，装得下不等于读得好。下面把三笔账分开算：窗口里装了什么、注意力要算多少、KV cache 要占多少内存；然后再谈长上下文为什么还会带来质量损失。

## 6.1 窗口里装的是什么

大多数模型的上下文窗口限制的是输入与输出 token 的总和。一次请求至少要容纳：

```text
系统提示 + 工具定义 + 历史消息 + 检索材料 + 输出预留 + 安全余量
```

| 预算项 | 常见来源 | 容易漏掉的部分 |
| --- | --- | --- |
| 系统提示 | 角色、规则、输出格式 | 每轮重复的固定开销 |
| 工具定义 | 名称、描述、JSON Schema | 工具越多，schema 越长 |
| 历史消息 | 用户与助手往返 | 工具调用、回执和报错文本 |
| 检索材料 | 文档片段、代码、日志 | 片段之间的标题、来源和分隔符 |
| 输出预留 | 回答、工具参数、JSON | 长回答或多轮工具调用 |
| 安全余量 | 格式修复、重试 | 失败后追加的错误信息 |

这些项目共用一个上限。给检索材料多留 10 000 token，就得从历史、工具或输出预留里挪。没有输出预留，模型可能在生成 JSON 的中途撞到上限，留下一个无法解析的半截对象。


## 6.2 注意力的二次项

Transformer 的 self-attention 让每个位置和序列中的其他位置计算相关性。对长度为 n 的序列，完整的注意力分数矩阵有 n² 个位置；因果模型只看当前及之前的位置，所以是：

```text
n × (n + 1) / 2
```

`llm/examples/context_budget.py` 按这个公式算出的每层 pair 数：

| 序列长度 | 每层因果 pair 数 |
| ---: | ---: |
| 4 096 | 8 390 656 |
| 32 768 | 536 887 296 |
| 131 072 | 8 590 000 128 |

序列长度变成 4 倍，pair 数约变成 16 倍。再乘上层数，计算量还要继续放大。FlashAttention 一类实现通过分块和重计算避免把完整的 n² 矩阵写进显存，但它没有把算术量变成线性；长上下文的计算仍然显著更贵。

生成过程还分为两段：

- **prefill**：把整段输入并行送进模型，计算量随输入长度增长，通常更吃算力；
- **decode**：每次生成一个 token，要读取已有的 KV cache，通常更吃显存带宽。

输入越长，prefill 越慢；输出越长，decode 的每一步都要带着更长的 cache。两端都会影响体感延迟。

## 6.3 KV cache 的线性账本

自回归生成不会每一步都把整段历史重新算一遍。模型把每一层、每个已处理位置的 Key 和 Value 向量缓存下来，生成下一个 token 时直接复用。K 和 V 是什么、注意力怎样用它们加权，见[第 3 章](ch03.md)；这里只算账。缓存大小可以按下面的公式估算：

```text
每 token 字节数 = 2 × 层数 × KV 头数 × 每头维度 × 每个数值字节数
```

`2` 表示 Key 和 Value 各存一份。脚本用一组示意配置计算：32 层、8 个 KV 头、每头 128 维、fp16（每数值 2 字节）：

| 序列长度 | KV cache 大小 |
| ---: | ---: |
| 4 096 token | 512.0 MiB |
| 32 768 token | 4.0 GiB |
| 131 072 token | 16.0 GiB |

这还只是一条序列。并发请求、模型权重、激活值和显存碎片还要另算。GQA/MQA 通过减少 KV 头数降低这部分开销，量化通过减少每个数值的字节数降低开销，但都不会让长上下文变成免费。

```ill
llm-ch06-kv-growth
```

上面的 32 层、8 个 KV 头是示意值，不对应某一款具体模型。换成真实模型卡上的层数、KV 头数和精度，结论可能差几倍。公式的用途是让你在选窗口和并发数之前先算一遍；固定的 GiB 数字换个模型就不成立。

## 6.4 长上下文的质量代价

装得下只是第一关。Liu 等人的 [Lost in the Middle](https://arxiv.org/abs/2307.03172) 发现，模型对长上下文开头和结尾的信息利用更好，中间位置的信息更容易被忽略；这类“位置效应”在不同模型和任务上强度不同，但足以说明“把材料全塞进去”不是稳妥策略。

长上下文还会带来另外几类问题：

- **干扰**：无关片段越多，模型越容易抓住错误线索；
- **冲突**：旧版本和新版本文档同时出现，模型可能引用旧版本；
- **稀释**：关键的一句被大量重复内容包围，权重被摊薄；
- **过期**：缓存的历史里保留着已经失效的工具结果或配置。

检索增强生成（RAG）和 Agent 记忆的重点是取对、排序、标注来源、及时淘汰，不是尽可能多取。主书[第 6 章](../第二部分-核心系统篇/06-记忆系统-Agent的长期记忆.md)讲记忆分层，[第 7 章](../第二部分-核心系统篇/07-上下文管理-Agent的工作记忆.md)讲工作记忆；本卷第 11 章（RAG）展开切块、向量检索和重排，见[第 11 章](ch11.md)。

## 6.5 预算与压缩的工程做法

<!-- block: llm-ch06.b-engineering -->
先量后切，比凭感觉设一个 `max_tokens` 可靠。一次请求进入模型前，至少做这几件事：

1. 用目标 tokenizer 或上一轮 usage 估算各预算项；
2. 先扣掉输出预留和安全余量，再分配检索与历史；
3. 给工具回执设上限，日志和网页内容先截取关键段，而不是整段倾倒；
4. 历史按轮次或任务阶段压缩，保留未完成的工具调用和关键事实；
5. 检索先召回再重排，去掉重复和低相关片段，保留来源与时间；
6. 对稳定的系统提示和工具前缀使用提供方的 prompt caching（如果支持），降低重复 prefill 的费用和延迟；
7. 记录每次请求的输入 token、输出 token、缓存命中和耗时，按真实数据调整预算。

prompt caching 减少的是重复前缀的 prefill 成本，不会扩大窗口，也不会自动保证缓存命中。缓存键、过期策略和计费方式由提供方定义，换模型或换区域后要重新核对。

| 常见翻车 | 后果 | 正确做法 |
| --- | --- | --- |
| 把窗口当成“越大越好” | 费用、延迟和质量同时变差 | 按任务分配预算，留输出余量 |
| 工具回执整段回填 | 一次调用吃掉大半窗口 | 截取关键字段，失败时再取详细段 |
| 历史只增不减 | 旧版本和已完成动作继续干扰 | 按阶段压缩，保留动作与结果 |
| 检索只按相似度取 top-k | 重复片段和旧版本文档混入 | 去重、按时间过滤、重排 |
| 忽略缓存与并发 | 成本估算和显存规划失真 | 用真实 usage 与并发压测校正 |

## 6.6 本章小实验

在仓库根目录运行默认预算：

```bash
python llm/examples/context_budget.py
```

输出会显示 128 000 token 窗口下，系统提示、工具、历史、检索、输出预留和安全余量合计 87 444 token，剩余 40 556 token；KV cache 在 131 072 token 时约 16 GiB；1 000 次调用、每次 81 300 输入 token，在每百万 token 0.15 美元的假设下约 12.19 美元。

再试三组变化：

```bash
python llm/examples/context_budget.py --retrieved 120000
python llm/examples/context_budget.py --kv-heads 1
python llm/examples/context_budget.py --calls 10000 --price-per-million 0.30
```

第一组应看到 `OVER BUDGET`，提醒你先砍检索或历史，而不是动输出预留；第二组把 KV 头数从 8 降到 1，观察 cache 大小的变化；第三组把调用量和单价同时放大，观察账单如何增长。价格和模型形状都是输入参数，不是厂商报价；真实决策要替换成当前价格和模型卡。

窗口预算管放不放得下，采样管从分布里选哪个；两件事都不保证答案正确。第 7 章开始算预训练的账，看这些能力最初怎样被训练出来。想复习 token 计数回[第 1 章](ch01.md)，想复习采样读[第 5 章](ch05.md)。
