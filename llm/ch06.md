# 第 6 章：上下文窗口不是免费的抽屉

<!-- block: llm-ch06.b-opening -->
> **白话先看懂**：上下文窗口不是越大越好。材料越多，费用、KV cache 和注意力计算都增加，关键证据还可能被淹没。先留出输出空间，再决定放多少历史、工具结果和检索材料。

排查线上问题时，要给 Agent 放多少日志？假设窗口是 128 000 token，已有系统提示、工具定义和历史共占 21 300，再放入 60 000 token 的日志就用了 81 300。余下的位置还要留给输出。这些长度也决定输入费用，并影响预填充计算与 KV cache。

下面用同一份预算脚本算窗口、注意力位置对和缓存大小；能装进窗口不等于能从中找准证据。

## 6.1 窗口里装的是什么

可以把上下文窗口想成一张总面积固定的工作桌：系统提示、工具清单、历史消息、塞进去的资料，以及模型等会儿要写出来的回答，全都摊在同一张桌面上。输入占掉九成桌面，留给输出的空白就只剩窄窄一条。

本章按文本自回归模型的“输入加生成 token 共用窗口”口径算账。具体接口还可能有单独的最大输入或输出限制，推理 token 是否计入生成预算也要查对应文档。一次请求先列出：

```text
系统提示 + 工具定义 + 历史消息 + 检索材料 + 输出预留 + 安全余量
```

| 预算项 | 常见来源 | 容易漏掉的部分 |
| --- | --- | --- |
| 系统提示 | 角色、规则、输出格式 | 每轮重复的固定开销 |
| 工具定义 | 名称、描述、JSON Schema | 工具越多，schema 越长 |
| 历史消息 | 用户与助手往返 | 工具调用、回执和报错文本 |
| 检索材料 | 文档片段、代码、日志 | 片段之间的标题、来源和分隔符 |
| 输出预留 | 回答、工具参数、JSON | 本次回答或本次工具参数；多轮逐次预算 |
| 安全余量 | 格式修复、重试 | 失败后追加的错误信息 |

输入和输出共用窗口上限，安全余量是应用主动留出的空位。窗口接近满额时，检索材料多放 10 000 token，就需要减少其他输入。没有输出预留，模型可能在生成 JSON 的中途撞到上限，留下一个无法解析的半截对象。


## 6.2 注意力的二次项

> **先看增长**：注意力位置对大致按长度平方增长；KV cache 大致按长度线性增长。

对稠密的全上下文 self-attention，长度为 n 的序列在每层、每个查询头上有 n² 个位置；因果掩码只允许看当前及之前的位置，有效位置对的数量是：

```text
n × (n + 1) / 2
```

`llm/examples/context_budget.py` 按这个公式算出的每层、每查询头的有效 pair 数：

| 序列长度 | 每层、每查询头的因果 pair 数 |
| ---: | ---: |
| 4 096 | 8 390 656 |
| 32 768 | 536 887 296 |
| 131 072 | 8 590 000 128 |

序列长度变成 4 倍，pair 数约变成 16 倍。pair 数还不是 FLOPs：计算点积与加权和时要考虑每头维度、查询头数和层数，实际内核也可能计算被掩码遮住的部分。滑动窗口或稀疏注意力的连接范围不同，不能套用这张全上下文表。

[FlashAttention](https://arxiv.org/abs/2205.14135)通过分块和在线 softmax 避免将完整的 n² 中间矩阵写入显存；训练反向时还会重算所需片段，以换取更少的存储与读写。对稠密注意力，它仍计算二次规模的位置关系，降低的是内存开销和数据搬运，并没有把算术量变成线性。

生成过程在计算和访存上劈成两截，就像先“通读全题”再“逐字落笔”：

- **prefill**：一口气并行处理全部输入并构建 KV cache，像快速通读几十页材料，未命中的长前缀最吃显卡算力；
- **decode**：一个接一个 token 往外生成，每吐一字都要重新翻读已有 KV cache，小批量时往往卡在显存搬运带宽上。

缓存命中、批量、模型结构和硬件都会改变瓶颈。对同一套稠密模型配置，增加未缓存输入会增加 prefill 工作量；生成越长，decode 要读取的历史也越长。实际延迟还包含排队和调度，不能只按 token 数等比例外推。

## 6.3 KV cache 的线性账本

模型逐 token 生成时，如果每写一个新 token 都重算前面所有位置的注意力，开销会迅速增加。**KV cache** 把每层、每个已处理位置的 Key 和 Value 存进显存，下一步只计算新位置并读取旧缓存。省下的是重复计算，代价是缓存占用随上下文长度线性增长。

自回归生成时，模型把每一层、每个已处理位置的 Key 和 Value 向量缓存下来，生成下一个 token 时直接复用。K 和 V 是什么、注意力怎样用它们加权，见[第 3 章](ch03.md)；这里只算账。对保留完整历史、逐层存储 K/V 的普通 MHA/GQA/MQA，单条序列的有效数据大小可按下面的公式估算：

> **选读**：缓存公式只在算显存时读。先记住“层数、KV 头数、每头维度和上下文越长，cache 越大”。

```text
每 token 字节数 = 2 × 层数 × KV 头数 × 每头维度 × 每个数值字节数
```

`2` 表示 Key 和 Value 各存一份。脚本用一组示意配置计算：32 层、8 个 KV 头、每头 128 维、fp16（每数值 2 字节）：

| 序列长度 | KV cache 大小 |
| ---: | ---: |
| 4 096 token | 512.0 MiB |
| 32 768 token | 4.0 GiB |
| 131 072 token | 16.0 GiB |

这还只是一条序列的 K/V 数据量。并发请求、模型权重、激活值、缓存元数据、分块余量和显存碎片还要另算。GQA/MQA 通过减少 KV 头数降低这部分开销，量化通过减少每个数值的字节数降低开销，但都不会让长上下文变成免费。

```ill
llm-ch06-kv-growth
```

上面的 32 层、8 个 KV 头是示意值，不对应某一款具体模型。换模型时要换参数，也要确认缓存结构：滑动窗口层的缓存可在窗口长度处停止增长，[MLA 则缓存压缩表示](https://arxiv.org/abs/2405.04434)，不能直接套这条普通 K/V 公式。具体实现可对照固定版本的 [Transformers KV cache 文档](https://github.com/huggingface/transformers/blob/47b0e478f324b54f177ea7998a0791870fdd0324/docs/source/en/kv_cache.md)。

## 6.4 长上下文的质量代价

资料能塞进窗口，不代表模型从头到尾读得一样仔细——人读长文容易记住开头和结尾、漏掉夹在中间的那一句，大模型也会出现**中间迷失（Lost in the Middle）**。

Liu 等人的 [Lost in the Middle](https://arxiv.org/abs/2307.03172)在多文档问答和键值检索任务中改变证据位置，发现所测模型往往更善于使用开头或结尾的信息，中部证据的利用效果较差。这个结果支持把“证据放在哪里”纳入评测；它不是所有模型、所有长度上的固定损失曲线。

长上下文还会带来另外几类问题：

- **干扰**：无关片段越多，模型越容易抓住错误线索；
- **冲突**：旧版本和新版本文档同时出现，模型可能引用旧版本；
- **重复**：相同材料占去窗口，却没有增加新证据；
- **过期**：缓存的历史里保留着已经失效的工具结果或配置。

检索增强生成（RAG）和 Agent 记忆的重点是取对、排序、标注来源、及时淘汰，不是尽可能多取。主书[第 6 章](../第二部分-核心系统篇/06-记忆系统-Agent的长期记忆.md)讲记忆分层，[第 7 章](../第二部分-核心系统篇/07-上下文管理-Agent的工作记忆.md)讲工作记忆；本卷第 11 章（RAG）展开切块、向量检索和重排，见[第 11 章](ch11.md)。

## 6.5 预算与压缩的工程做法

<!-- block: llm-ch06.b-engineering -->
先量后切，比凭感觉设一个 `max_tokens` 可靠。一次请求进入模型前，至少做这几件事：

1. 用目标计数接口或含消息模板的 tokenizer 估算当前请求；上一轮 usage 只能校准估算，不能代替新输入的计数；
2. 先扣掉输出预留和安全余量，再分配检索与历史；
3. 给工具回执设上限，日志和网页内容先截取关键段，而不是整段倾倒；
4. 历史按轮次或任务阶段压缩；调用与回执成对处理，摘要保留执行状态、关键事实和待处理动作；
5. 检索先召回再重排，去掉重复和低相关片段，保留来源与时间；
6. 对稳定的系统提示和工具前缀使用提供方的 prompt caching（如果支持），降低重复 prefill 的费用和延迟；
7. 记录每次请求的输入 token、输出 token、缓存命中和耗时，按真实数据调整预算。

prompt caching 复用重复前缀的计算结果，命中后通常可减少 prefill 工作量。是否省钱还要比较缓存读写单价与命中次数；缓存不会扩大窗口。缓存键、过期策略和计费方式由提供方定义，换模型或换区域后要重新核对。自部署可参看 [vLLM 固定版本的前缀缓存说明](https://github.com/vllm-project/vllm/blob/b8b302cde434df8c9289a2b465406b47ebab1c2d/docs/design/prefix_caching.md)，费用则仍需查所用服务的价格表。

| 常见翻车 | 后果 | 正确做法 |
| --- | --- | --- |
| 把窗口当成“越大越好” | 费用、延迟和质量同时变差 | 按任务分配预算，留输出余量 |
| 工具回执整段回填 | 一次调用吃掉大半窗口 | 截取关键字段，失败时再取详细段 |
| 历史只增不减 | 旧版本和已完成动作继续干扰 | 按阶段压缩，保留动作与结果 |
| 检索只按相似度取 top-k | 重复片段和旧版本文档混入 | 去重、按时间过滤、重排 |
| 忽略缓存与并发 | 成本估算和显存规划失真 | 用真实 usage 与并发压测校正 |

## 6.6 本章小实验

在仓库根目录运行默认预算：

```bash
python llm/examples/context_budget.py
```

输出会显示 128 000 token 窗口下，系统提示、工具、历史、检索、输出预留和安全余量合计 87 444 token，剩余 40 556 token；KV cache 在 131 072 token 时约 16 GiB；1 000 次调用、每次 81 300 输入 token，在每百万 token 0.15 美元的假设下，单算输入约 12.19 美元，不含输出费。128 000 是预算参数，131 072 是缓存表选用的 2 的幂，二者不是同一个窗口值。

再试三组变化：

```bash
python llm/examples/context_budget.py --retrieved 120000
python llm/examples/context_budget.py --kv-heads 1
python llm/examples/context_budget.py --calls 10000 --price-per-million 0.30
```

第一组应看到 `OVER BUDGET`，提示先减少检索或历史，保住所需输出空间；第二组把 KV 头数从 8 降到 1，观察 cache 大小的变化；第三组把调用量和单价同时放大，观察账单如何增长。价格和模型形状都是输入参数，不是厂商报价；真实决策要替换成当前价格和模型卡。

如果还要看多轮累计账单，可运行 `python llm/examples/session_ledger.py`：四轮输入合计 19 500 token，其中工具回执占 4 800、回填的助手输出占 1 500；它们都是重复发送后的累计量。脚本比较三种缓存策略，假设固定吞吐、缓存一直存活且不收写入费，时间还未计缓存读取、排队和网络开销。这里的算术用于检查预算，不能当作服务压测结果。

窗口预算决定放多少，采样决定选哪个。第 7 章开始算预训练的账，看这些能力最初怎样被训练出来。想复习 token 计数回[第 1 章](ch01.md)，想复习采样读[第 5 章](ch05.md)。
