# 第 7 章：预训练：一笔算力账

<!-- block: llm-ch07.b-opening -->
模型卡上写着“2T tokens、7B 参数”。有人问，加到 10T 会不会更好。只凭这两个数字回答不了：训练算力、数据质量、模型要服务的上下文长度，都会改变结论。预训练的第一笔账，是算力怎么分。

本章先估算训练与推理的浮点运算量，再运行一个 7 440 参数的小 Transformer，观察前向、反向和参数更新。算力表用于理解预算，小模型用于检查训练过程，两者都不能替代真实集群的测量。

## 7.1 预训练只做一件事

本章讨论自回归语言模型的预训练：根据前文预测下一个 token。模型通过这个目标学习文本中的统计关系。其他预训练任务还包括掩码预测和多模态目标，不能把所有预训练都归成同一种形式。

基座也可能从训练文本或上下文示例中学到指令、代码和工具调用形式，但“预测下一个 token”本身不保证它稳定遵守助手角色与接口约定。SFT、偏好训练和运行时约束会进一步塑造这些行为，见[第 8 章](ch08.md)与[第 9 章](ch09.md)。

预训练阶段决定的几个变量，会一直影响下游：

- 词表与 tokenizer：同样的中文，不同 tokenizer 的 token 数可能差不少，计费和窗口都受影响；
- 训练数据：规模、重复次数、语言配比、代码与数学比例、去重和过滤；
- 上下文长度：训练时处理过的长度是长输入能力的条件之一，还要看位置编码、后续扩展与评测；
- 参数量与层数：影响权重存储和主要计算量，推理延迟还受硬件与服务实现影响；
- 训练截止时间：提示参数内知识的时效范围，但不保证截止前的事实都被学到，也不限制模型使用检索得到的新信息。

## 7.2 训练算力：6ND

对稠密 Transformer 的主要权重矩阵乘法，一次前向每 token 的计算量可粗略估为 `2N` FLOPs（一次乘、一次加各计一次）。计算激活梯度和参数梯度的反向过程，常粗估为该部分前向的两倍。合起来得到：

```text
训练 FLOPs ≈ 6 × N × D
```

`N` 近似代表参与这些主要矩阵运算的参数量，`D` 是训练中处理的 token 数，包含重复读取，`6` 来自“前向 2 + 反向 4”。它省略了随序列长度变化的注意力等开销；长上下文、MoE 或不同实现要另算。激活重计算还会增加 FLOPs，通信、流水线等待和故障恢复则进一步影响耗时，不能把 `6ND` 当作精确恒等式。

`llm/examples/scaling_demo.py` 按这个式子算了一个 7B 模型在三组 token 预算下的账，假设单卡有效算力 `4e14 FLOP/s`：

| 训练 token | 训练 FLOPs | GPU-days | 训练状态（16 B/参数） |
| ---: | ---: | ---: | ---: |
| 140B | 5.88e21 | 170 | 104.3 GiB |
| 300B | 1.26e22 | 365 | 104.3 GiB |
| 2T | 8.40e22 | 2 431 | 104.3 GiB |

“GPU-days”是总 FLOPs 除以假设的单卡有效 FLOP/s，再除以一天的秒数，表示累计 GPU 时间。`4e14` 是教学输入，不是某张卡的规格；MFU 是利用率比例，要乘对应精度的峰值算力才能得到同量纲的估计。也可直接用实测 token/s 估算训练时间。

表中的 16 字节按一种混合精度 Adam 配置计算：fp16 权重 2 字节、fp16 梯度 2 字节、fp32 主权重 4 字节、两个 fp32 动量各 4 字节。7B 参数合计约 104.3 GiB，尚未包含激活值、临时缓冲和通信桶。实际 dtype、优化器、分片和卸载方式都会改变每卡占用。

`llm/examples/train_demo.py` 用标准库手写一个 7 440 参数的字符级 Transformer：一层因果注意力、一层 FFN，前向和反向均显式计算，SGD 在 Python 列表上更新参数。示例采用 12 步 warmup，再余弦衰减到初始学习率的 10%；这是本次实验的配置，并非所有训练的必选项。固定 seed 下的结果如下：

| 检查点 | 数值 |
| --- | --- |
| 训练前 loss（≈ ln 54 = 3.99） | 3.99 |
| 反向梯度 vs 数值差分，最大偏差 | 6.93e-12 |
| step 60 / 120 / 180 / 240 | 3.92 / 2.19 / 2.32 / 3.20 |
| 训练后同一窗口 | 1.49 |

中心差分检查了 8 个抽样权重，最大偏差为 6.93e-12。检查针对当前输入和参数：若某条计算路径的梯度本来就很小，错误实现也可能通过宽松的绝对误差阈值。配套测试另用两组非对称、较大权重的缩小模型，逐个核对全部参数，并重复输入同一个 token，检查嵌入梯度是否正确累加。

手写反向时，矩阵形状相同也可能把转置写错。本例前向用行向量：若 `Y = X·W`，损失对 `Y` 的梯度是 `G`，则：

```text
dL/dX = G·Wᵀ
dL/dW = Xᵀ·G
```

注意力输出投影与 Q、K、V 投影都要遵守这个方向。平方矩阵漏写转置仍能相乘，因此只检查形状、loss 下降或少量接近零的梯度，都不足以查出这类错误。

表中的 step loss 来自当步随机抽到的窗口，各步不是在同一组文本上测量，因此不能仅凭相邻数值判断训练回退。

训练前后的 3.99 与 1.49 使用同一个固定窗口，但该窗口也来自训练语料。这能展示模型拟合了语料，不能说明泛化已经改善。Raschka 的[第 5 章配套教材](https://github.com/rasbt/LLMs-from-scratch/blob/22c637fdf9aa2f5fdd39c2cc80c1d36b4ab7d8d8/ch05/01_main-chapter-code/ch05.ipynb)分别计算训练与验证损失，可用来继续理解这个区别。

warmup 逐步提高学习率，衰减则在后期降低步长，具体曲线并不统一：[Transformer 的 Noam 调度](https://arxiv.org/abs/1706.03762)采用 warmup 后的逆平方根衰减，[GPT-3](https://arxiv.org/abs/2005.14165)采用 warmup 与余弦衰减。在本例相同初始化和窗口抽样下，240 步恒定 `lr=0.6` 的固定窗口 loss 约为 1.12，低于当前调度的 1.49。这个对照只比较了一组预算、seed 和训练窗口，不能据此推出恒定学习率普遍更好，或某种调度必然改善长训练。选择调度与停止时机还需独立验证数据。

`6ND` 中的 `4ND` 近似记的是反向矩阵运算；优化器更新、重计算及其他操作并没有因此全部算进来。

## 7.3 参数量与 token 数怎么分

算力固定时，参数多一点还是数据多一点？[Kaplan 等](https://arxiv.org/abs/2001.08361)的 scaling law 给出了损失随参数量、数据量和算力变化的幂律形态。[Chinchilla](https://arxiv.org/abs/2203.15556)进一步研究每个训练预算下怎样分配参数与数据：沿这些最优配置增加算力预算时，参数量和训练 token 数应大致同比例增长；此前不少大模型的训练 token 偏少。经验比例常被概括为“每 1 个参数配 20 个 token”。

在某个固定预算内，`6ND` 约束的是两者的乘积，增大 `N` 就要减小 `D`。若 `N`、`D` 都翻倍，这部分计算量会增至四倍。

按 `D = 20N` 和 `C = 6ND` 反解，得到：

```text
N ≈ sqrt(C / 120)
D ≈ 20N
```

脚本算出的三档预算：

| 训练算力 | 参数量 | token 数 | GPU-days | 训练状态 |
| ---: | ---: | ---: | ---: | ---: |
| 1e22 | 9.1B | 183B | 289 | 136.0 GiB |
| 1e23 | 28.9B | 577B | 2 894 | 430.2 GiB |
| 1e24 | 91.3B | 1.83T | 28 935 | 1.3 TiB |

```ill
llm-ch07-scaling-curve
```

这张表是在固定比例假设下做预算分配，不是重新拟合 Chinchilla 的实验。部署还要考虑推理总量：同等任务质量下，更小的稠密模型通常有较低的权重与计算需求，但实际延迟取决于架构和服务实现。服务量很大时，可以比较“增加训练数据、减小模型”是否降低训练加推理的总成本。

“20 token/参数”是常用的经验概括，最优比例会随数据、目标损失、模型族和成本约束改变。新增 token 的质量与重复程度也影响收益，不能只用累计 token 数判断训练是否充分。

## 7.4 数据不是无限的

模型卡写“15T tokens”，先区分去重语料规模与训练累计处理量。“唯一 token”容易被误解成不同 token ID 的数量，这里要核对的是语料是否重复、重复多少轮。同一批数据可以读取多次，累计训练量因而增长，但独立信息不会同比增加；是否过拟合要看验证集，不能只看训练损失。

数据侧至少看五件事：

- **去重**：网页模板、代码镜像和翻译对会给某些片段过高权重；
- **质量过滤**：语言识别、垃圾页、机器生成内容的比例；
- **配比**：中文、英文、代码、数学、对话各占多少，直接影响能力分布；
- **授权与合规**：数据来源、许可、隐私和退出机制；
- **评测污染**：训练集是否混入 benchmark 或它的改写版本。

合成数据可以补数量，但会把生成模型的偏差一起带进来。用模型生成训练数据、再用同一族模型评测，很容易得到漂亮的闭环分数。

## 7.5 一页分布式：参数放不下怎么办

当训练状态或吞吐需求超过单卡能力时，就需要分布式训练。下面按拆分对象区分几种方法，用来阅读模型报告中的资源配置。

普通**数据并行**（DP）在每张卡上保留模型与训练状态副本，各自处理不同批次，再同步梯度。加速比受通信与本地计算比例影响，不能保证线性增长。按前述 16 字节/参数假设，7B 的训练状态约 104.3 GiB，已经超过 24 GB 卡的容量，不只是“有点紧”。

**张量并行**（TP）把矩阵或其他张量计算拆给多卡，层内通信依赖高速互连；**流水线并行**（PP）按层分配阶段，通过微批次调度减少等待，但仍可能有流水线气泡。这两种方式都可以和数据并行组合。

**ZeRO** 在数据并行中分片训练状态。[官方教程](https://www.deepspeed.ai/tutorials/zero/)区分三个阶段：Stage 1 分片优化器状态，Stage 2 再分片梯度，Stage 3 再分片模型参数，并在计算需要时收集。[FSDP 的完全分片配置](https://docs.pytorch.org/docs/2.15/distributed.fsdp.fully_shard.html)也按需收集参数、归约并分片梯度。它们降低每卡常驻状态，但会增加通信与调度要求，不能笼统说成“不切计算，也没有额外代价”。

| 并行方式 | 切什么 | 通信 | 一句话 |
| --- | --- | --- | --- |
| 数据并行 DP | 数据 | 反向同步梯度 | 吞吐好，卡要装下全模型 |
| 张量并行 TP | 张量计算 | 层内通信 | 依赖互连与分片策略 |
| 流水线并行 PP | 层 | 分阶段 | 有气泡 |
| ZeRO / FSDP | 按阶段或策略分片状态 | 参数收集、梯度同步等 | 节省常驻显存，另有通信开销 |

多卡不会自动减少同一训练任务的算术总量。理想墙钟时间可用总 FLOPs 除以卡数与每卡有效 FLOP/s 估算，真实结果还受通信、等待和故障影响。[LLaMA 论文](https://arxiv.org/abs/2302.13971)给出了大规模训练的实例；阅读时要同时看总 GPU 时间与实际训练天数。推理阶段的预算见[第 10 章](ch10.md)。

## 7.6 基座模型与 Agent

Agent 工程师通常不训练基座，但会选基座。选的时候，模型卡上的“参数量”只是第一行，下面这些字段更影响落地：

| 字段 | 对 Agent 的影响 |
| --- | --- |
| 基座 / instruct | 是否针对助手任务训练；两者都要核对输入格式与聊天模板 |
| 上下文长度 | 决定单次能放多少材料，也决定 KV cache 上限 |
| tokenizer | 决定同样文本的 token 数和计费 |
| 训练截止时间 | 参数内知识的时效线索，仍需逐项核验事实 |
| 工具调用能力 | 多数来自后训练；看有没有结构化输出与并行调用 |
| 许可与部署方式 | 能否商用、能否私有化、是否允许蒸馏 |
| 推理成本 | 参数量、激活参数、量化与批处理共同决定 |

“参数更大”不自动等于“更适合”。一个 30B 的 instruct 模型在工具调用上可能胜过一个 70B 基座；一个 7B 模型量化后跑在本地，延迟可能比 API 更可控。选型要用自己的任务评测，而不是只看排行榜。

## 7.7 常见翻车

| 常见翻车 | 后果 | 正确做法 |
| --- | --- | --- |
| 只看参数量不看 token 数 | 低估训练成本或数据不足 | 用 6ND 粗估，区分语料规模与累计处理量 |
| 把“15T tokens”当去重后的语料量 | 高估数据质量与多样性 | 问重复次数与去重策略 |
| 把 Chinchilla 最优当部署最优 | 推理成本过高 | 训练与推理总算账 |
| 用单卡峰值算集群时间 | 忽略 MFU、通信与故障 | 用实测吞吐与集群规模估算 |
| 忽略 tokenizer 差异 | 上下文和费用算偏 | 用目标模型实测 token 数 |
| 用 benchmark 分数代替任务评测 | 上线后工具调用失败 | 建自己的任务集与回归测试 |

## 7.8 本章小实验

在仓库根目录运行：

```bash
python llm/examples/scaling_demo.py
python llm/examples/train_demo.py
```

然后试三组改动：

1. 把 `TOKENS_PER_PARAM` 从 20 改成 10 和 100，观察同一算力下参数量与 token 数怎样移动；想想为什么部署时未必选 20。
2. 把 `EFFECTIVE_FLOPS` 从 `4e14` 改成 `2e14`，GPU-days 会翻倍；再用实测的单卡有效 FLOP/s 替换，比较差距。若测得的是 token/s，则另用训练 token 数除以该吞吐估时，不能直接填入 `EFFECTIVE_FLOPS`。
3. 把 7B 模型的 token 预算改成 1T、10T，观察训练 FLOPs 与 GPU-days；再算推理 1M token 的 FLOPs，理解训练与推理是两笔不同的账。

`train_demo.py` 再试两组：把 `STEPS` 翻倍，记录同一固定窗口的 loss，同时注意余弦调度的长度也随之改变，不能把差异全部归因于“多训了几步”；再把 `gradcheck` 的 `epsilon` 改成 `1e-2` 和 `1e-6`，记录解析梯度与差分的偏差。步长可能引入截断误差或浮点舍入误差，但这两个取值不保证一定出现明显失真。

scaling 示例用于估算运算量和训练状态，实际耗时需要测量吞吐；train 示例在 435 个字符、743 个 UTF-8 字节的语料上运行前向、反向和参数更新，适合逐步检查计算。下一章讨论 SFT 与 LoRA 怎样调整基座的回答与工具调用；上下文预算见[第 6 章](ch06.md)。
