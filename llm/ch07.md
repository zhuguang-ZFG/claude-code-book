# 第 7 章：预训练：一笔算力账

<!-- block: llm-ch07.b-opening -->
模型卡上写着“2T tokens、7B 参数”。有人问，加到 10T 会不会更好。只凭这两个数字回答不了：训练算力、数据质量、模型要服务的上下文长度，都会改变结论。预训练的第一笔账，是算力怎么分。

不训练模型，只算算术：训练和推理的浮点运算量、参数量与 token 数在固定算力下怎么分，最后回到 Agent 工程师要读的模型卡字段。

## 7.1 预训练只做一件事

预训练的目标函数很简单：给一段文本，预测下一个 token。模型在大量语料上反复做这件事，学到的是语言的统计结构、世界知识的片段，以及某种“继续写下去”的能力。

它不负责听指令，也不负责按格式调用工具。这些行为来自后面的 SFT 和对齐，见[第 8 章](ch08.md)与[第 9 章](ch09.md)。基座模型更像一个读过很多书、但没上过班的实习生；会用工具、会拒绝、会按 schema 输出，是后训练加上去的。

预训练阶段决定的几个变量，会一直影响下游：

- 词表与 tokenizer：同样的中文，不同 tokenizer 的 token 数可能差不少，计费和窗口都受影响；
- 训练数据：规模、重复次数、语言配比、代码与数学比例、去重和过滤；
- 上下文长度：训练时见多长，决定它能不能稳定处理长材料；
- 参数量与层数：决定权重显存、每 token 计算量和推理延迟；
- 训练截止时间：模型不知道之后发生的事。

## 7.2 训练算力：6ND

一次前向传播，每个参数大约做 2 次浮点运算（一次乘、一次加）；反向传播还要算激活梯度和参数梯度，约是前向的 2 倍。合起来，训练总运算量的常用估算式是：

```text
训练 FLOPs ≈ 6 × N × D
```

`N` 是参数量，`D` 是训练 token 数，`6` 来自“前向 2 + 反向 4”。这是一个记账公式，不是实测吞吐；真实训练还要付通信、流水线气泡、重计算和故障恢复的时间。

`llm/examples/scaling_demo.py` 按这个式子算了一个 7B 模型在三组 token 预算下的账，假设单卡有效算力 `4e14 FLOP/s`：

| 训练 token | 训练 FLOPs | GPU-days | 训练状态（16 B/参数） |
| ---: | ---: | ---: | ---: |
| 140B | 5.88e21 | 170 | 104.3 GiB |
| 300B | 1.26e22 | 365 | 104.3 GiB |
| 2T | 8.40e22 | 2 431 | 104.3 GiB |

“GPU-days”是把总 FLOPs 除以假设的单卡有效算力再除以一天秒数。`4e14` 不是任何一张卡的规格，而是一个便于比较的输入；换成真实集群的实测 MFU，数字会变。训练状态按每个参数 16 字节粗算（fp16 权重、梯度、Adam 两个矩和 fp32 主权重），7B 约 104 GiB；激活值、临时缓冲和通信桶还要另算，单卡装不下。

## 7.3 参数量与 token 数怎么分

算力固定时，参数多一点还是数据多一点？[Kaplan 等](https://arxiv.org/abs/2001.08361)的 scaling law 给出了损失随参数量、数据量和算力下降的幂律形态；[Chinchilla](https://arxiv.org/abs/2203.15556) 的结论更具体：在固定训练算力下，参数量和数据量应大致同比例增长，很多模型此前的训练 token 偏少。经验比例常被概括为“每 1 个参数配 20 个 token”。

按 `D = 20N` 和 `C = 6ND` 反解，得到：

```text
N ≈ sqrt(C / 120)
D ≈ 20N
```

脚本算出的三档预算：

| 训练算力 | 参数量 | token 数 | GPU-days | 训练状态 |
| ---: | ---: | ---: | ---: | ---: |
| 1e22 | 9.1B | 183B | 289 | 136.0 GiB |
| 1e23 | 28.9B | 577B | 2 894 | 430.2 GiB |
| 1e24 | 91.3B | 1.83T | 28 935 | 1.3 TiB |

这张表只回答“训练算力怎么分”，不回答“部署哪个更划算”。同样能力的两个模型，参数小的那个推理更便宜、延迟更低；如果服务量很大，宁可多花训练算力，把模型做小、数据加多。Chinchilla 最优是训练目标，不是部署目标。

“20 token/参数”也不是定律。数据质量高、重复少、领域集中时，比例可以变；数据枯竭或质量下降时，盲目加 token 只会把噪声学得更牢。

## 7.4 数据不是无限的

模型卡写“15T tokens”，先问是唯一 token 还是训练中看过的 token。高质量网页、代码、书籍的总量有限，很多训练会把同一批数据重复几轮。重复能继续降训练损失，但收益递减，还可能加重记忆和过拟合。

数据侧至少看五件事：

- **去重**：网页模板、代码镜像和翻译对会给某些片段过高权重；
- **质量过滤**：语言识别、垃圾页、机器生成内容的比例；
- **配比**：中文、英文、代码、数学、对话各占多少，直接影响能力分布；
- **授权与合规**：数据来源、许可、隐私和退出机制；
- **评测污染**：训练集是否混入 benchmark 或它的改写版本。

合成数据可以补数量，但会把生成模型的偏差一起带进来。用模型生成训练数据、再用同一族模型评测，很容易得到漂亮的闭环分数。

## 7.5 基座模型与 Agent

Agent 工程师通常不训练基座，但会选基座。选的时候，模型卡上的“参数量”只是第一行，下面这些字段更影响落地：

| 字段 | 对 Agent 的影响 |
| --- | --- |
| 基座 / instruct | 基座要自己写对话模板；instruct 已做过 SFT/对齐 |
| 上下文长度 | 决定单次能放多少材料，也决定 KV cache 上限 |
| tokenizer | 决定同样文本的 token 数和计费 |
| 训练截止时间 | 决定知识的新旧，检索能否补上 |
| 工具调用能力 | 多数来自后训练；看有没有结构化输出与并行调用 |
| 许可与部署方式 | 能否商用、能否私有化、是否允许蒸馏 |
| 推理成本 | 参数量、激活参数、量化与批处理共同决定 |

“参数更大”不自动等于“更适合”。一个 30B 的 instruct 模型在工具调用上可能胜过一个 70B 基座；一个 7B 模型量化后跑在本地，延迟可能比 API 更可控。选型要用自己的任务评测，而不是只看排行榜。

## 7.6 常见翻车

| 常见翻车 | 后果 | 正确做法 |
| --- | --- | --- |
| 只看参数量不看 token 数 | 低估训练成本或数据不足 | 用 6ND 估算，核对唯一 token |
| 把“15T tokens”当唯一数据 | 高估数据质量与多样性 | 问重复次数与去重策略 |
| 把 Chinchilla 最优当部署最优 | 推理成本过高 | 训练与推理总算账 |
| 用单卡峰值算集群时间 | 忽略 MFU、通信与故障 | 用实测吞吐与集群规模估算 |
| 忽略 tokenizer 差异 | 上下文和费用算偏 | 用目标模型实测 token 数 |
| 用 benchmark 分数代替任务评测 | 上线后工具调用失败 | 建自己的任务集与回归测试 |

## 7.7 本章小实验

在仓库根目录运行：

```bash
python llm/examples/scaling_demo.py
```

然后试三组改动：

1. 把 `TOKENS_PER_PARAM` 从 20 改成 10 和 100，观察同一算力下参数量与 token 数怎样移动；想想为什么部署时未必选 20。
2. 把 `EFFECTIVE_FLOPS` 从 `4e14` 改成 `2e14`，GPU-days 会翻倍；再用你手头显卡或云实例的实测吞吐替换，比较差距。
3. 把 7B 模型的 token 预算改成 1T、10T，观察训练 FLOPs 与 GPU-days；再算推理 1M token 的 FLOPs，理解训练与推理是两笔不同的账。

示例只算算术，不测真实吞吐；它给的是预算框架。下一章进入 SFT 与 LoRA，看预训练出来的基座怎样被改成能执行任务的助手；如果你更关心上下文预算，可以回到[第 6 章](ch06.md)。
