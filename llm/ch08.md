# 第 8 章：SFT 与 LoRA：把通用模型改成你的助手

<!-- block: llm-ch08.b-opening -->
一个团队要模型稳定输出固定的 JSON 信封，并且只调用他们内部的三个工具。提示词能把格式合规率做到八成，剩下的两成会在字段名、括号和工具参数上漂移。他们收集了两千条成功轨迹做监督微调（SFT），格式合规率上去了，但模型开始把用户的问题也当成助手回答来续写，通用问答能力也掉了。

先要定的是拿什么信号训练、改哪一部分参数；“要不要微调”反而排在后面。一组手设概率能说明 SFT 的损失掩码，一个小矩阵能说明 LoRA 的低秩更新和参数账。

## 8.1 SFT 在改什么

SFT 用示范数据继续训练模型：每条样本是一段对话，模型看到前面的 system、user 和工具回执，预测 assistant 的下一个 token。损失是交叉熵：

```text
loss = -log p(正确 token | 前面的上下文)
```

先看哪些位置参与损失。用户的问题和系统提示是条件，不是要模型模仿的输出；如果把它们也算进损失，模型会学着续写用户的话，而不是回答。`llm/examples/sft_demo.py` 用五个位置演示两种算法：

| 位置 | 目标概率 | 损失 | 是否训练 |
| --- | ---: | ---: | ---: |
| system | 0.95 | 0.051 | 0 |
| user | 0.80 | 0.223 | 0 |
| assistant | 0.70 | 0.357 | 1 |
| 已退款 | 0.60 | 0.511 | 1 |
| 请查收 | 0.50 | 0.693 | 1 |

全部 token 平均是 0.367，只算 assistant 是 0.520。后者看起来更大，但不代表模型更差：它只是换了一个平均口径。变化的是梯度：只算 assistant 时，三个回答 token 各占 `1/3` 权重，system 和 user 的权重是 0；算全部 token 时，五个位置各占 `1/5`，模型会花力气去拟合本来就已经给出的条件。

这也解释了为什么“损失降到多少”不能跨数据口径比较。两个实验的 mask 不同、token 数不同、任务难度不同，损失值没有可比性；要比就固定评测集和评测指标。

```ill

```

SFT 主要改的是行为、格式、风格和工具调用习惯，不能可靠地注入新事实。要更新知识，优先做检索增强（RAG）；要让模型遵守新的输出约定，SFT 更合适。把 SFT 当“往模型里灌文档”，通常会得到流畅但过时的回答。SFT 作为对齐流程的第一阶段，在 [InstructGPT](https://arxiv.org/abs/2203.02155) 里有完整描述。

数据侧至少检查五件事：去重、覆盖失败与恢复轨迹、授权与隐私、训练/评测按任务或时间切分、以及是否混入通用数据以减轻灾难性遗忘。只喂成功案例，模型学不会在工具报错后重试；训练集和评测集重叠，指标会虚高。

## 8.2 LoRA：冻结主干，训练低秩增量

全量微调要更新所有权重。LoRA 冻结原矩阵 `W`，只训练两个小矩阵：

```text
W' = W + (alpha / r) · B · A
```

`A` 的形状是 `r × d_in`，`B` 是 `d_out × r`，`r` 远小于 `d_in` 和 `d_out`。常见实现把 `A` 随机初始化、把 `B` 初始化为 0，于是训练开始时 `W' = W`，模型从原状态出发。`alpha / r` 控制更新幅度；改 `r` 时通常也要重调 `alpha` 或学习率。

<!-- block: llm-ch08.b-lora -->
示例用一个 4×4 的 `W` 和 rank 2 的 `A`、`B`，`alpha=4`，缩放因子是 2。对输入 `[1,1,1,1]`：

| 权重 | 输出 |
| --- | --- |
| 原始 `W` | `[0.300, 0.400, 0.300, 0.500]` |
| `W + (alpha/r)·B·A` | `[0.300, 0.500, 0.300, 0.540]` |

第二、四维发生了变化，第一、三维没变。低秩更新只能改动 `B·A` 张成的子空间；`r` 越小，能表达的方向越少，但可训练参数也越少。

```ill
llm-ch08-sft-lora
```

对一个 `4096 × 4096` 的矩阵，LoRA 的可训练参数是 `2 × 4096 × r`：

| 秩 | 可训练参数 | 占全量比例 | fp16 每层 |
| ---: | ---: | ---: | ---: |
| 1 | 8 192 | 0.049% | 16.0 KiB |
| 8 | 65 536 | 0.391% | 128.0 KiB |
| 16 | 131 072 | 0.781% | 256.0 KiB |
| 64 | 524 288 | 3.125% | 1.0 MiB |
| 4096 | 33 554 432 | 200.0% | 64.0 MiB |

最后一行说明 LoRA 不是“秩越大越省”：`r = d` 时 `A`、`B` 合起来是两个满矩阵，参数量反而是原矩阵的两倍。LoRA 的节省来自 `r << d`。r=8 的适配器在一个矩阵上是 128 KiB；如果 32 层每层只挂一个矩阵，约 4 MiB，但真实模型通常会在多个投影上挂适配器，要按实际配置乘。

训练完有两种部署方式：

- **保留适配器**：基座不变，按请求加载不同 LoRA，可做多租户、多任务切换；推理图里多两次小矩阵乘。
- **合并进基座**：把 `B·A` 加进 `W`，部署一张新权重；推理图里没有额外矩阵，但换适配器要换权重或重新加载。

合并是否更快取决于实现和批大小，不能一概而论；但“合并后无法在同一进程里热切换适配器”是确定的结构差异。

## 8.3 QLoRA 与显存

QLoRA 把基座量化到 4-bit，再在量化权重旁训练 LoRA，用较低的显存完成适配。它省的是基座权重的存储与部分计算带宽，不是把微调变成免费：量化会带来精度损失，适配器仍要在较高精度下训练，数据管线和评测一样不能省。方法细节见 [QLoRA](https://arxiv.org/abs/2305.14314)；是否可用要在自己的任务上做量化前后对比，不能只看显存占用。

## 8.4 微调、提示词与 RAG 的分工

| 需求 | 优先手段 | 原因 |
| --- | --- | --- |
| 固定输出格式、工具调用约定 | SFT / LoRA | 用示范轨迹塑造行为 |
| 注入最新事实、文档知识 | RAG | 检索可更新，不必重训 |
| 调整角色、规则、语气 | 提示词 | 最快、最便宜、可回滚 |
| 领域术语与写法 | SFT + RAG | 行为靠示范，事实靠检索 |
| 降低延迟与成本 | 蒸馏 / 小模型 + LoRA | 用小模型承接窄任务 |
| 多租户风格隔离 | 多 LoRA | 基座共享，适配器切换 |

三者不是互斥的。一个客服 Agent 可以先用提示词定规则，用 RAG 取订单和政策，再用 LoRA 固定工具调用格式和回复风格。每一层都要有独立的评测，否则出了问题分不清是哪一层造成的。

微调还有一个更小的子集：**分类微调**。不做完整对话，只把文本映到固定标签——意图识别、垃圾判定、工单分类、[第 10 章](ch10.md)路由器的难度判断都是它。做法从 [BERT 时代](https://arxiv.org/abs/1810.04805)就没变过：取最后一个位置的隐藏向量，接一个线性层输出每类的分数，训练时只在这个分类头上算损失。与对话 SFT 的区别是标签空间小、输出短，几百到几千条标注样本就能见效；在 Agent 系统里它是“小模型承接窄任务”的成本武器，比用大模型提示分类便宜一个数量级。不训练也可以：约束解码（见[第 12 章](ch12.md)）能让大模型直接吐合法标签，但吞吐要求高时，微调过的小分类器仍然占优。

## 8.5 Agent 工程落点

- 训练数据来自真实轨迹：assistant 的工具调用、参数、最终回答是监督信号；工具回执是观察，不要把回执当成助手要模仿的输出。
- 格式要有校验器：JSON Schema、工具参数类型、必填字段、失败重试；SFT 降低漂移，不替代校验。
- 评测按任务切分：留出未见过的时间段、租户或工具版本；随机切分容易把同一会话的相邻轮次泄漏到测试集。
- 记录版本四元组：基座模型、适配器、训练数据摘要、评测报告；缺一项就无法复现线上行为。
- 部署要有回退：适配器热加载失败、输出分布漂移或工具报错率上升时，能切回基座或上一版。
- 隐私与授权：训练轨迹里可能有用户地址、订单号和内部日志；脱敏、保留期限和访问控制要在训练前处理。

## 8.6 常见翻车

| 常见翻车 | 后果 | 正确做法 |
| --- | --- | --- |
| 在 prompt token 上也算损失 | 模型学着续写用户问题 | 只对 assistant 输出计算损失 |
| 只收集成功轨迹 | 不会处理报错与重试 | 加入失败、恢复和拒绝样本 |
| 训练集与评测集重叠 | 指标虚高，上线翻车 | 按会话/时间/租户切分 |
| 学习率过大或步数过多 | 通用能力遗忘、输出变窄 | 混通用数据，早停，做回归评测 |
| 只测格式不测事实 | JSON 正确但内容错误 | 格式、事实、工具执行三层评测 |
| 把 LoRA 合并后不回归 | 静默改变线上行为 | 合并前后跑同一套评测 |
| 量化后直接上线 | 质量或工具调用退化 | 量化前后对比，保留 fp16 回退 |
| 多适配器版本混用 | 请求打到错误的任务适配器 | 适配器注册表 + 请求级版本固定 |

## 8.7 本章小实验

在仓库根目录运行：

```bash
python llm/examples/sft_demo.py
```

然后试四组改动：

1. 把 `MASK` 改成全 1，观察 all-token 与 assistant-only 两个均值怎样变化；再把 mask 改成只保留最后一个 token，理解“权重集中在哪”。
2. 把 `B` 全部设成 0，确认输出回到基座；再把 `ALPHA` 从 4 改成 8，观察更新幅度翻倍。
3. 把 `RANK` 改成 1 或 4，先手算 `2 × 4096 × r`，再运行核对参数表。
4. 把 `W` 换成一个单位矩阵，观察低秩更新只改动哪些方向；思考 rank 不足时哪些任务学不会。

这些概率和矩阵是手设的，不包含反向传播和优化器；它们说明损失掩码与参数形状，不代表真实微调效果。想复习模型卡上的参数和显存账，读[第 4 章](ch04.md)；想理解采样波动对评测的影响，读[第 5 章](ch05.md)；RAG 的切块与重排会在第 11 章展开。
