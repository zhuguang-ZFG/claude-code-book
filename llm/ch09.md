# 第 9 章：对齐：模型为什么“听话”

<!-- block: llm-ch09.b-opening -->
假设一个代码审查 Agent 面对两份回答：一份同意用户，却把正确代码判错；另一份解释了用户判断中的错误。偏好标注选哪一份，会影响模型学到什么。评测也应分别记录用户偏好和代码检查结果，不能用“更让人满意”代替“判断更准确”。

本章先用手设分数计算偏好损失，再区分 DPO、GRPO、过程奖励与候选筛选。阅读时关注三个具体问题：谁提供监督，哪些参数被更新，以及生成、评分和训练各花多少资源。

## 9.1 从模仿到比较

[第 8 章](ch08.md)的 SFT 提高示范回答的似然；示范可来自人工，也可来自经过筛选的模型输出。本章从成对偏好学习开始：给同一个输入的两个回答，标注哪个更好。比较维度仍须写清，例如正确性、帮助程度或风格；成对标注也会有分歧。对齐的范围更广，SFT 和后面的规则奖励训练都可以参与其中。

Bradley-Terry 模型把“更好”变成概率：

```text
P(y_w 优于 y_l) = sigmoid(r_w - r_l)
loss = -log sigmoid(r_w - r_l)
```

`r_w` 和 `r_l` 是两个回答的奖励分数。差值越大，模型越确信 `y_w` 更好；差值小于 0 时，损失会大于 `log(2) ≈ 0.693`。这套偏好学习框架的早期工作见 [Christiano 等](https://arxiv.org/abs/1706.03741)。

## 9.2 奖励模型

一种常见奖励模型从预训练或 SFT 模型出发，在主干上接标量评分头，输入问题与回答，输出一个分数。训练数据是成对比较，损失就是上面的 Bradley-Terry 损失。`llm/examples/alignment_demo.py` 用四组分数演示：

| 比较 | 胜者分数 | 败者分数 | 差值 | 损失 | 判对 |
| --- | ---: | ---: | ---: | ---: | --- |
| 更有帮助 | 2.00 | 1.00 | 1.00 | 0.313 | 是 |
| 更安全 | 0.50 | 0.60 | -0.10 | 0.744 | 否 |
| 更诚实 | -1.00 | -0.50 | -0.50 | 0.974 | 否 |
| 格式正确 | 1.20 | 1.20 | 0.00 | 0.693 | 否 |

平均损失 0.681，成对准确率 1/4。差值 1.0 的样本损失只有 0.313；差值 -0.5 的样本损失 0.974；打平不是胜利，损失仍是 0.693。

奖励模型是一个代理指标：它学的是标注员的偏好，不是“正确”本身。把策略过度优化到奖励模型上，分数会继续涨，真实质量却可能下降，这叫奖励黑客（reward hacking）。[Reward Model Overoptimization](https://arxiv.org/abs/2210.10760) 讨论了这种过优化的 scaling 现象。Agent 系统里，奖励模型同样可能奖励“看起来礼貌”“格式完整”而忽略事实和工具执行结果。

## 9.3 RLHF：奖励、策略与 KL

以使用独立奖励模型的 PPO 流程为例，需要区分三个角色：

- **策略**（policy）：要训练的语言模型；
- **参考策略**（reference）：SFT 后的冻结副本，用来约束漂移；
- **奖励模型**（reward）：给回答打分。

PPO 通常还用价值函数（critic）估计状态下的期望回报。角色数量不等于必须同时常驻的完整模型副本数；是否共享主干、分片、卸载或分阶段运行，都会改变显存和调度成本。

目标可以写成：

```text
J = E[r(x, y)]
    - β · KL(π(·|x) || π_ref(·|x))
maximize J
```

第一项让回答拿高分，第二项惩罚策略偏离参考模型太远。`β` 控制“讨好奖励”与“保持原样”的权衡。PPO 是常见的优化算法，但训练不稳定、对超参敏感，工程上还要处理 rollout、批处理和奖励归一化。SFT、奖励模型与 PPO 的组合在 [InstructGPT](https://arxiv.org/abs/2203.02155) 中有完整描述。

估算资源时，分别列出策略的训练状态、参考与奖励模型的推理状态、critic 的实现以及 rollout 缓冲，再决定如何放置。

## 9.4 DPO：把偏好直接写进策略

DPO 跳过显式奖励模型，直接用偏好对优化策略。对一对回答 `(y_w, y_l)`，定义策略相对参考模型的对数概率差：

```text
gap = [log π(y_w|x) - log π_ref(y_w|x)]
    - [log π(y_l|x) - log π_ref(y_l|x)]
loss = -log sigmoid(β · gap)
```

`β` 放大或缩小同一个 gap。脚本中的两组案例：

| 案例 | β | 胜者 log 比 | 败者 log 比 | 边际 | 损失 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 偏好正确 | 0.1 | 0.30 | -0.20 | 0.05 | 0.668 |
| 偏好正确 | 1.0 | 0.30 | -0.20 | 0.50 | 0.474 |
| 偏好反转 | 0.1 | 0.10 | 0.40 | -0.03 | 0.708 |
| 偏好反转 | 1.0 | 0.10 | 0.40 | -0.30 | 0.854 |

训练开始时策略通常等于参考模型，两个 log 比都是 0，gap 为 0，损失是 `log(2) ≈ 0.693`。表中的“偏好正确/反转”只表示手设的相对 log 比是否支持 chosen 标签，不验证标签在事实或业务上是否正确。这里的 log 概率针对完整回答，通常由回答 token 的条件 log 概率求和得到。

固定 gap 时，增大 `β` 会放大边际；正 gap 的损失降低，负 gap 的损失升高。这个算术现象不能推出“β 越大，训练后越偏离参考”。在 DPO 对应的 KL 正则化奖励目标中，固定奖励函数时有 `π*(y|x) ∝ π_ref(y|x)·exp(r(x,y)/β)`，较大的 `β` 加强对偏离参考的惩罚。实际训练轨迹还取决于数据、学习率和步数，要测 KL、回答长度和任务表现。

对 gap 的导数是 `-β·sigmoid(-β·gap)`：在 gap 为 0 时，梯度绝对值为 `β/2`；在正 gap 的饱和区，增大 β 也可能减小梯度。脚本使用稳定的 `softplus(-β·gap)` 计算损失，避免先算 sigmoid 再取对数时发生下溢。

```ill
llm-ch09-alignment-scale
```

DPO 不需要在训练时跑奖励模型和 PPO，但仍需要：

- 一份高质量的偏好对数据；
- 一个冻结的参考模型（通常就是 SFT 模型）；
- 对 `β`、学习率和训练步数的调参；
- 对策略漂移、模式坍塌和过拟合的评测。

“不需要奖励模型”不等于“不需要偏好数据”，也不等于“不会奖励黑客”。方法细节见 [DPO](https://arxiv.org/abs/2305.18290)。

## 9.5 对齐不是什么

- **它不校验事实**：偏好数据里说错的事，模型会学得更像；事实要靠检索、工具和测试。
- **它不替代安全边界**：对齐降低了一部分有害输出，但权限、沙箱、输入过滤和人工审批仍要做；提示注入仍可能绕过。
- **顺从不是目标**：如果标注员偏好“同意用户”，模型会学会拍马屁（sycophancy）；对代码审查、风险判断这类任务，这是负资产。
- **它不是一次性动作**：数据分布、工具版本和用户群体变化后，偏好会漂移，要重新评测。
- **它不消除标注分歧**：标注员之间也会分歧；把分歧压成一个分数，会丢掉“在什么条件下更好”。

Agent 场景尤其要区分“礼貌”和“正确”。一个回答可以语气很差但结论正确，也可以语气完美但调用了错误工具；偏好模型如果只学到语气，就会奖励后者。

## 9.6 Agent 工程落点

| 目标 | 手段 | 注意 |
| --- | --- | --- |
| 固定工具调用格式 | SFT / LoRA | 对齐不替代 schema 校验 |
| 安全拒绝与升级 | 偏好数据 + DPO/RLHF | 同时测误拒与漏拒 |
| 减少拍马屁 | 偏好对里加入“坚持正确结论”的样本 | 评测要覆盖用户施压场景 |
| 事实更新 | RAG / 工具 | 对齐不能可靠注入新知识 |
| 多租户风格 | 多 LoRA / 提示词 | 版本与权限隔离 |
| 线上回归 | 成对评测 + 任务指标 | 胜率上涨不代表任务成功 |

偏好数据最好来自真实轨迹：工具调用失败后的恢复、应该拒绝的请求、用户施压时的正确坚持。只收集“用户满意”的回答，会把顺从学进模型。评测至少分三层：成对偏好胜率、任务成功率、安全/误拒率；三层都过，才算对齐没有把系统改坏。

经典 DPO 可使用离线偏好对训练，参考 log 概率还可预先计算；GRPO 需要为当前策略采样并计算奖励，省去 critic 仍有生成成本。二者不能仅凭“模型个数”比较开销。LoRA 减少可训练参数及相关梯度、优化器状态，基座权重仍要存储，显存预算见[第 4 章](ch04.md)。

## 9.7 常见翻车

| 常见翻车 | 后果 | 正确做法 |
| --- | --- | --- |
| 拿 SFT 数据直接做 DPO | 没有偏好对，目标函数对不上 | 构造 chosen/rejected 对 |
| 偏好数据只来自一个标注员 | 把个人偏好当全局标准 | 多标注、记录分歧、抽检 |
| 只优化奖励模型分数 | 奖励黑客，真实质量下降 | 保留任务指标与人工抽检 |
| 仅凭 β 大小推断漂移 | 把固定 gap 的损失变化当成训练结论 | 固定数据与预算，比较 KL、长度和任务指标 |
| 只看 DPO loss 下降 | 可能过拟合偏好标签 | 同时检查标签质量、留出集与任务结果 |
| 只测胜率不测任务 | 拍马屁赢评测，任务失败 | 胜率 + 成功率 + 安全率 |
| 把对齐当安全边界 | 提示注入仍可绕过 | 权限、沙箱、审批另做 |
| 训练/评测样本重叠 | 记住答案使指标虚高 | 去重并按会话、时间或租户切分 |

## 9.8 本章小实验

在仓库根目录运行：

```bash
python llm/examples/alignment_demo.py
python llm/examples/rejection_demo.py
```

先试四组对齐改动：

1. 把“格式正确”的胜者分数改成 1.3，观察损失从 0.693 降到多少；再把两者设成相等，确认损失回到 `log(2)`。
2. 把“更安全”的分数对调，观察成对准确率与平均损失的变化。
3. 把 DPO 的 `BETAS` 改成 `(0.01, 0.1, 1.0, 10.0)`，观察同一个 gap 下边际和损失怎样变化；正 gap 的损失会更快贴近 0，负 gap 的损失会继续变大。
4. 把“偏好反转”的四个 log 概率改成“策略已经偏好正确”，观察 gap 与损失；再思考为什么初始化时通常是 0.693。

再试两组拒绝采样改动：

5. 把 `P_CORRECT` 改成 0.2 和 0.6，观察 keep 率与至少一个候选通过的概率怎样变化。过滤没有更新这个参数，不能把筛选收益当成策略学会了新能力。
6. 把 `SIZES` 扩到 128，记录通过验证的 prompt 数和总生成次数，再换几个 seed。六题的一次结果只是抽样，不保证 N 增大时每次观测都上升。

这些分数和 log 概率是手设的，不包含奖励模型或策略训练；它们说明损失形状和 `β` 的作用，不代表真实模型的对齐效果。SFT 与 LoRA 的基础见[第 8 章](ch08.md)；采样波动会干扰评测，见[第 5 章](ch05.md)；完整评测会在第 14 章展开。

## 9.9 GRPO：把批评者去掉的比较学习

[DeepSeekMath](https://arxiv.org/abs/2402.03300) 提出 GRPO，用同一问题下多个回答的奖励估计基线，省去 PPO 中另行训练的价值模型。它仍然需要奖励来源：可以是学习型奖励模型，也可以是规则验证器。DeepSeekMath 论文的 §4.1–4.2 使用并训练了奖励模型。

对每个问题，用旧策略采样 G 个回答。以结果奖励为例，组内优势可写为：

```text
r_i = reward(x, y_i)
A_i = (r_i - mean(r)) / (std(r) + eps)
```

计算优势时，奖励和组统计量作为固定训练信号。若四个奖励为 `[1, 1, 0, 0]`，采用总体标准差并暂略 eps，均值和标准差都是 0.5，优势为 `[1, 1, -1, -1]`。若全组奖励相同，减均值后的分子全为 0；eps 只能避免除零，不能创造区分信号。G=1 时也有这个问题。

原始 GRPO 还包含新旧策略概率比、裁剪和参考策略 KL 项。其结果监督形式可概括为：

```text
p_theta = π_theta(y_i,t | x, y_i,<t)
p_old   = π_old(y_i,t | x, y_i,<t)
rho_i,t = p_theta / p_old
u_i,t = rho_i,t · A_i
v_i,t = clip(rho_i,t,
             1-epsilon, 1+epsilon) · A_i
J = mean_i mean_t [
      min(u_i,t, v_i,t) - beta·KL_i,t
    ]
```

训练最大化 J，或等价地最小化 −J。这里的 `mean_t` 在每条回答的有效 token 上平均，`KL_i,t` 表示论文采用的参考策略 KL 估计项。若只写 `-A·log π`，只能说明策略梯度方向，不能代替完整目标。`π_old` 是产生当前样本的策略快照；`π_ref` 是 KL 项使用的参考，两者用途不同。

实现也有变体。[TRL v0.25.0 文档](https://github.com/huggingface/trl/blob/55f5433e15cc6203d3c731f9de5247b00878bebd/docs/source/grpo_trainer.md)允许规则函数或奖励模型，提供不同的长度归一化与奖励缩放方式，默认 `beta=0.0` 不使用 KL 项。比较实验要记录这些配置，不能只记录算法名。增加 G 会增加采样预算，不保证每组都有不同奖励；输出长度偏差也要结合损失归一化检查，不能归结为某个 β 必然使输出变长。

[DeepSeek-R1 报告](https://arxiv.org/abs/2501.12948)区分了 R1-Zero 和 R1：前者探索没有前置 SFT 的强化学习，后者加入冷启动数据与多阶段训练。数学答案、代码测试等可核验任务能提供规则奖励，但规则只覆盖其检查的条件；格式通过并不证明内容正确。

| 方案 | 训练信号 | 主要资源账 |
| --- | --- | --- |
| 经典 DPO | 已有的 chosen/rejected 对 | 策略训练、参考 log 概率计算 |
| 奖励模型 + PPO | rollout、奖励与价值估计 | 策略、奖励、参考、critic 及采样 |
| GRPO | 同题多个回答的相对奖励 | 组内采样、策略训练、奖励计算；参考取决于 KL 配置 |

推理服务通常只需要部署学到的策略；训练时的评分器和 critic 不因参与训练就必须留在每次请求中。

## 9.10 过程奖励（PRM） vs 结果奖励（ORM）

[Lightman 等的《Let's Verify Step by Step》](https://arxiv.org/abs/2305.20050)比较了结果监督与过程监督。区别在于监督标注落在哪里，而不是是否存在中间计算的梯度。

**结果奖励模型（ORM）**学习对整段解答打分。该论文用最终答案检查生成训练标签；附录 E 说明，训练时给解答的各 token 使用同一个结果标签，推理时才取最后一个 token 处的预测作为整段分数。“结果监督”指标签的来源，不能据此推断损失只放在终点。

**过程奖励模型（PRM）**学习判断每个推理步骤。论文在步骤末尾预测表示正确性标签的 token，使用语言模型训练流程。PRM800K 包含约 80 万个人工步骤标签，区分正、负和中性；标签语义与数据结构可查[公开仓库](https://github.com/openai/prm800k/tree/7ecc794703b2877f63226f2477a49b34f9b25163)。这些数据不是由 ORM 自动生成的。

论文图 3 中 PRM 的 78.2% 和 ORM 的 72.4%，是对保留的 500 道 MATH 测试题、每题 1 860 个候选进行 best-of-N 选择后的解题率。它们比较的是候选选择能力，不是两种模型单次生成或强化学习训练后的通用胜率。该设置用步骤正确概率的乘积给整条解答评分；其他聚合方式需另行比较。

验证器、奖励模型与价值函数承担不同角色：

- 验证器（verifier）可以是规则程序，也可以是学习模型；本节的规则验证器执行答案比对、单元测试或工具调用约束，仍可能漏判或误判。
- ORM/PRM 是学习出来的评分模型，分别利用结果或步骤监督；在何处打分和怎样汇总要明确。
- 价值函数估计给定策略下状态的期望回报，可用于构造优势，不能直接等同于步骤正确率。

对多步 Agent 轨迹，可以先保存每一步的输入、动作与回执，定位工具错误和无依据推断。具备可靠的步骤标注后，再考虑训练或引入 PRM。按步运行规则检查是一种过程验证，但它本身不是训练了过程奖励模型。

## 9.11 拒绝采样：不训练也能变强

生成多个候选后再筛选，可以在不更新模型权重时提高返回答案的质量；用筛出的答案训练模型，则是另一个阶段。[RLHF Book 第 9 章](https://github.com/natolambert/rlhf-book/blob/b0926fd5f57c64295a086ebabcd8a04e4c71cce7/book/chapters/09-rejection-sampling.md)把这种数据构造与后续微调连起来讨论：

1. 选 prompt、生成策略与评分器，记录版本和每题候选数。
2. 生成并打分，按每题 top-1、全局 top-k 或阈值等规则筛选。
3. 核对通过样本的事实、覆盖和重复程度。
4. 若要更新策略，在筛选后的样本上做 SFT，并用留出集比较。

筛选本身没有梯度；后续 SFT 会更新可训练参数。GRPO 也不需要对离散采样动作直接求导，而是使用样本的 log 概率与优势构造策略梯度；二者的区别在训练目标和数据使用方式。[STaR](https://arxiv.org/abs/2203.14465)采用生成推理、检查答案、再训练的迭代流程，还包含借助正确答案生成推理的步骤。训练是否改善了策略，需要用留出集另行评测。

推理时的 **best-of-N** 生成 N 个候选，再用评分器选择一个，不更新策略。收益取决于候选中有没有好答案，以及评分器能否识别它。总生成 token、评分成本和等待时间都要计入；不能预设它是最便宜的改进方法。

`llm/examples/rejection_demo.py` 使用固定成功概率 `p=0.4`，并用精确字符串匹配检查六个任务。假设候选独立且每次通过概率相同：

```text
P(至少一个通过) = 1 - (1-p)^N
p=0.4，N=4：1 - 0.6^4 = 0.8704
```

这是理想验证器下的抽样概率，不是实测模型准确率。脚本先生成全部 N 个候选，再检查有无通过者；循环中的 `break` 不节省已花掉的生成。过滤始终保持 p 不变，没有训练网络或优化器。十六进制任务明确要求小写且不带 `0x`，因此 `FF` 和 `0xff` 被拒绝是格式不合要求，而非算错了 255。

真实任务需要分别检查候选覆盖、验证器误判和最终答案质量。单元测试通过只代表通过了这些测试，schema 合法只代表满足该结构；保留验证器版本，才能在规则变化后重新检查训练数据。

| 方法 | 监督或选择依据 | 更新什么 | 需要核算的工作 |
| --- | --- | --- | --- |
| SFT（第 8 章） | 示范 token | 策略的可训练参数 | 数据与监督训练 |
| 奖励模型 + PPO（9.3） | 奖励、价值估计 | 策略及价值模型 | 采样、评分、训练 |
| DPO（9.4） | 成对偏好与参考 log 概率 | 策略；参考冻结 | 偏好数据与训练 |
| GRPO（9.9） | 组内相对奖励 | 策略 | 多候选采样、奖励与训练 |
| PRM / ORM（9.10） | 步骤或结果标签 | 评分模型；策略另行训练 | 标注与评分器训练 |
| 筛选后 SFT（9.11） | 评分器选出的示范 | SFT 阶段更新策略 | 生成、筛选、监督训练 |
| best-of-N（9.11） | 候选分数或验证结果 | 不更新参数 | 每次请求的生成与评分 |

选择方法时，先确认手里有什么监督：偏好对、可执行的验证器，还是步骤标注。再用同一组任务比较输出质量与总成本，避免把筛选、评分器训练和策略训练记成同一件事。
