# 第 10 章：推理与部署：吞吐、延迟与显存

<!-- block: llm-ch10.b-opening -->
服务团队把批大小从 1 调到 32，吞吐上去了，首 token 延迟和 p95 却变差；换到 32K 上下文，32 路批处理直接 OOM。权重、KV cache、批处理三个旋钮互相牵扯，调一个，另外两个跟着变。

这一章把推理拆成 prefill 和 decode 两段，用一组假设的带宽与算力算清显存和吞吐，再看批处理、量化和部署框架各自解决哪一段的问题。

## 10.1 两段完全不同的计算

一次请求分两段：

- **prefill**：把整段输入并行送进模型，计算量随输入长度增长，通常更吃算力；
- **decode**：每次生成一个 token，要读取权重和已有 KV cache，通常更吃显存带宽。

前向每 token 的浮点运算量仍可按 `2 × 参数量` 粗算。prefill 一次处理 `L` 个输入 token，运算量约 `2 × N × L`；decode 每步只算一个新 token，但要把权重和整段 cache 从显存搬到计算单元。FLOPs 相同，瓶颈不同。

对 Agent 来说，两个延迟指标要分开看：

- **TTFT**（time to first token）：从请求到第一个 token，主要受 prefill 和排队影响；
- **TPOT**（time per output token）：首 token 之后每个 token 的间隔，主要受 decode 带宽和批处理影响。

一个 p95 很差的 Agent，可能 TTFT 正常，但 TPOT 被长上下文和大队列拖慢。

```ill
llm-ch10-prefill-decode
```

## 10.2 显存的三块账

`llm/examples/serving_demo.py` 用一个 7B、32 层、8 个 KV 头、每头 128 维的配置算账。每 token 的 KV cache 是 128 KiB，和[第 3 章](ch03.md)的公式一致。

权重部分：

| 精度 | 权重体积 |
| --- | ---: |
| fp16 | 14.0 GB（13.0 GiB） |
| int8 | 7.0 GB（6.5 GiB） |
| int4 | 3.5 GB（3.3 GiB） |

decode 的显存流量至少包括权重和 KV cache。8K 上下文下：

| 批大小 | KV cache | 每步耗时 | 吞吐 | 80 GiB 单卡 |
| ---: | ---: | ---: | ---: | --- |
| 1 | 1.0 GiB | 5.02 ms | 199 tok/s | 装得下 |
| 8 | 8.0 GiB | 7.53 ms | 1 062 tok/s | 装得下 |
| 32 | 32.0 GiB | 16.12 ms | 1 985 tok/s | 装得下 |

批大小翻 32 倍，吞吐约翻 10 倍，不是线性：每步要搬的 KV cache 也在涨。到 32K 上下文：

| 批大小 | KV cache | 每步耗时 | 吞吐 | 80 GiB 单卡 |
| ---: | ---: | ---: | ---: | --- |
| 1 | 4.0 GiB | 6.10 ms | 164 tok/s | 装得下 |
| 8 | 32.0 GiB | 16.12 ms | 496 tok/s | 装得下 |
| 32 | 128.0 GiB | 50.48 ms | 634 tok/s | 装不下 |

32 路批处理在 32K 上下文下需要 128 GiB 的 KV cache，加权重已经超过 80 GiB 卡。吞吐数字只是算术结果，装不下就没有意义。实际部署还要留激活值、显存碎片和框架开销；脚本按 10% 余量粗算。

## 10.3 批处理：吞吐换延迟

批处理把多个请求拼成一步，权重只读一次，吞吐通常上升。代价是每步要处理更多 KV cache，单步时间变长；排队中的请求也要等。调大批大小，吞吐和 p95 往往一起变好再变坏。

连续批处理（continuous batching）解决的是“等最慢的那条”问题。静态批处理要等一批里最长的请求结束才能换下一批；连续批处理在某个槽位空出来时立刻放入新请求。脚本用一个四请求、两槽位的玩具算占用率：

| 调度 | 槽位利用率 |
| --- | ---: |
| 静态批处理 | 60.9% |
| 连续批处理 | 97.5% |

这个玩具忽略了 prefill、每 token 时间波动和抢占，只说明槽位复用的方向。真实调度器还要处理前缀缓存、chunked prefill、优先级和超时。KV cache 的分页管理可以参考 [PagedAttention](https://arxiv.org/abs/2309.06180)：把 cache 切成块，按需分配，减少碎片和预留浪费。

## 10.4 量化

权重量化把每个参数的字节数降下来：fp16 14 GB，int8 7 GB，int4 3.5 GB。decode 每步要读权重，权重变小通常能降低显存带宽压力；但有三件事不能忘：

1. **量化有精度损失**：要在自己的任务上比较量化前后，尤其是工具参数、代码和长上下文；
2. **KV cache 不会自动量化**：权重量化省的是权重，32K 上下文的 cache 仍是几十 GiB；
3. **吞吐不一定线性提升**：瓶颈可能在 KV cache、调度或计算，换个模型和批大小，结论会变。

KV cache 也可以单独量化，但那是另一项配置，精度影响也不同。部署时把“权重量化”和“KV cache 量化”分开记录，不要笼统写“4-bit”。

量化的机制值得看一眼公式，免得“4-bit”像魔法。均匀量化把浮点区间 `[α, β]` 映到整数区间（比如 int8 的 `[-128, 127]`）：

```text
scale  S = (β - α) / 整数区间宽度
zero point  Z = 把 α 对齐到整数零点的偏移
量化 x_q = round(x / S) + Z    反量化 x ≈ S × (x_q - Z)
```

**对称量化**取 `Z = 0`，适合大致分布在零点两侧的权重；**非对称量化**保留 `Z`，适合偏一侧的激活值。粒度是第二条轴：按张量共用一组参数最省事，按通道各自算更准，再细可到按组——粒度越细误差越小，元数据开销越大。训练后量化另有专门的手艺，如 [GPTQ](https://arxiv.org/abs/2210.11423) 逐层用少量校准样本修整舍入误差。选型时问清“哪一档、什么粒度、校准数据是什么”，比只看 bit 数有用。

## 10.5 部署形态

| 形态 | 适合 | 代价 |
| --- | --- | --- |
| 托管 API | 快速上线、弹性、少运维 | 单价、限流、数据出境与版本不可控 |
| 自建推理 | 数据留在本地、可深度调优 | GPU、运维、容量规划、故障恢复 |
| 混合 | 敏感请求本地、峰值走 API | 路由、协议与评测要统一 |

推理框架负责批处理、KV cache 管理、量化和并行切分；不同框架的实现和调参项差别很大，选型要用自己的请求压测。投机解码、前缀缓存、prompt caching 都能降低某些场景的延迟或费用，但都有命中条件；把它们当成默认能力，容量规划会失真。

投机解码值得单独说清它的命中条件：一个小模型先“起草”几步，大模型一次性并行验证，起草被接受的步数等于这步白赚的算力，不被接受就回退重算。加速比完全取决于小模型与大模型分布的吻合度——输出可预测的任务（模板、代码补全）快，开放生成慢；且两个模型的词表和分词必须对齐，不是任意组合都能投机。

另一条常被忽略的省钱路是**模型路由**：一个轻量分类器先判断请求难度，简单请求给小模型、难题升级大模型，或按“先小后大”级联——小模型答对且自信就采纳，否则转大模型重答。收益取决于两个数：小模型能独占的请求比例，和误判难度时的返工成本。级联还多一段延迟。路由器和级联本身也要评测，别只看省了多少钱、不看转错的那部分。

## 10.6 Agent 工程落点

| 场景 | 关键指标 | 做法 |
| --- | --- | --- |
| 交互式助手 | TTFT、p95 | 控制输入长度，缓存稳定前缀 |
| 批量数据处理 | 吞吐、单价 | 大批处理，接受更高单请求延迟 |
| 长上下文排查 | KV cache、OOM | 限制并发，压缩历史，按需检索 |
| 工具调用密集 | TPOT、重试率 | 缩短输出，结构化参数，失败快速回退 |
| 多租户 | 隔离、配额 | 按租户限流，避免一个长请求拖垮全局 |

容量规划至少回答四个数：峰值并发、平均输入/输出长度、可接受的 p95、单卡能装下的 KV cache。只报“支持多少 QPS”没有意义，QPS 随输入输出长度和批处理策略变化。

## 10.7 常见翻车

| 常见翻车 | 后果 | 正确做法 |
| --- | --- | --- |
| 只用 FLOPs 估延迟 | 忽略 decode 的显存带宽 | 分开算 prefill 与 decode |
| 把批大小拉满 | p95 恶化、长请求排队 | 按 SLA 找吞吐与延迟的平衡 |
| 只算权重不算 KV cache | 长上下文 OOM | 权重 + cache + 激活一起预算 |
| 认为量化自动省 cache | 并发一开就爆显存 | 权重与 KV cache 分开量化 |
| 静态批处理等最长请求 | 槽位空转 | 连续批处理 + 前缀缓存 |
| 用平均延迟代替 p95 | 线上尾延迟不可接受 | 压测记录分位数与超时 |

## 10.8 本章小实验

在仓库根目录运行：

```bash
python llm/examples/serving_demo.py
```

然后试三组改动：

1. 把 `DTYPE_BYTES` 从 2 改成 1，观察 KV cache 和批大小上限怎样变化；再把权重精度改成 int8，比较两者节省的比例。
2. 把 `BANDWIDTH` 从 `3e12` 改成 `1.5e12`，decode 时间翻倍；用你手头设备的内存带宽替换，看看数量级差多少。
3. 把 `lengths` 改成 `[20, 20, 200, 200]` 或 `[200, 200, 200, 200]`，观察静态与连续批处理的利用率差异；再想想真实请求长度分布为什么很少这么整齐。
