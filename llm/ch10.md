# 第 10 章：推理与部署：吞吐、延迟与显存

<!-- block: llm-ch10.b-opening -->
假设要在一张 80 GiB 显卡上部署 7B 模型。fp16 权重约占 13 GiB，看上去很宽裕；但按本章配置，32 路请求各保留 32K token 时，仅 KV cache 就需要 128 GiB。模型能加载，不代表目标并发能运行。

这一章把推理拆成 prefill 和 decode 两段，用一组假设的带宽与算力算清显存和吞吐，再看批处理、量化和部署框架各自解决哪一段的问题。

## 10.1 两段完全不同的计算

一次请求分两段：

- **prefill**：把整段输入并行送进模型，计算量随输入长度增长，通常更吃算力；
- **decode**：每次生成一个 token，要读取权重和已有 KV cache，通常更吃显存带宽。

权重矩阵乘法的运算量可按每 token `2 × 参数量 N` 粗算：prefill 处理 L 个输入 token，约为 `2NL`。这个估计没有计入随序列长度增长的注意力计算，不能作为长上下文的完整 FLOPs。decode 每条序列每步通常只新增一个 token，仍需访问权重和历史 KV；小批量时常受带宽限制，大批量、长上下文和不同内核会改变瓶颈。

对 Agent 来说，两个延迟指标要分开看：

- **TTFT**（time to first token）：从请求到第一个 token，主要受 prefill 和排队影响；
- **TPOT**（time per output token）：首 token 之后每个 token 的间隔，主要受 decode 带宽和批处理影响。

一个 p95 很差的 Agent，可能 TTFT 正常，但 TPOT 被长上下文和大队列拖慢。

## 10.2 显存的三块账

`llm/examples/serving_demo.py` 用一个 7B、32 层、8 个 KV 头、每头 128 维的配置算账。每 token 的 KV cache 是 128 KiB，和[第 3 章](ch03.md)的公式一致。

权重部分：

| 精度 | 权重体积 |
| --- | ---: |
| fp16 | 14.0 GB（13.0 GiB） |
| int8 | 7.0 GB（6.5 GiB） |
| int4 | 3.5 GB（3.3 GiB） |

下面只估算显存搬运时间：假设带宽为 `3e12 B/s`，每步读取一份 fp16 权重和整批历史 KV，忽略缓存层次、写入、计算、通信与调度开销。时间为 `(权重字节数 + KV 字节数) / 带宽`，吞吐为 `批大小 / 单步时间`。这是理想化的带宽模型，不是设备基准。8K 上下文下：

| 批大小 | KV cache | 估算每步耗时 | 估算吞吐 | 80 GiB 粗预算 |
| ---: | ---: | ---: | ---: | --- |
| 1 | 1.0 GiB | 5.02 ms | 199 tok/s | 装得下 |
| 8 | 8.0 GiB | 7.53 ms | 1 062 tok/s | 装得下 |
| 32 | 32.0 GiB | 16.12 ms | 1 985 tok/s | 装得下 |

批大小翻 32 倍，吞吐约翻 10 倍，不是线性：每步要搬的 KV cache 也在涨。到 32K 上下文：

| 批大小 | KV cache | 估算每步耗时 | 估算吞吐 | 80 GiB 粗预算 |
| ---: | ---: | ---: | ---: | --- |
| 1 | 4.0 GiB | 6.10 ms | 164 tok/s | 装得下 |
| 8 | 32.0 GiB | 16.12 ms | 496 tok/s | 装得下 |
| 32 | 128.0 GiB | 50.48 ms | 634 tok/s | 装不下 |

32 路批处理在 32K 上下文下需要 128 GiB 的 KV cache，加权重已经超过 80 GiB 卡。吞吐数字只是算术结果，装不下就没有意义。脚本给权重与 KV 总和加 10% 余量，表中的“装得下”仅表示通过这项粗预算。实际所需的激活值、工作区、量化元数据、显存碎片和框架开销仍要测量。

## 10.3 批处理：吞吐换延迟

批处理让多个请求共享一次权重读取的成本，通常有利于吞吐。批量增大也会增加计算量和 KV 访问；为了凑批而等待，还会增加排队时间。吞吐与 p95 如何变化，取决于到达率、请求长度和调度策略，需要在目标负载下分别测量。

连续批处理（continuous batching）解决的是“等最慢的那条”问题。静态批处理要等一批里最长的请求结束才能换下一批；连续批处理在某个槽位空出来时立刻放入新请求。脚本用一个四请求、两槽位的玩具算占用率：

| 调度 | 槽位利用率 |
| --- | ---: |
| 静态批处理 | 60.9% |
| 连续批处理 | 97.5% |

这个玩具忽略了 prefill、每 token 时间波动和抢占，只说明槽位复用的方向。真实调度器还要处理前缀缓存、chunked prefill、优先级和超时。KV cache 的分页管理可以参考 [PagedAttention](https://arxiv.org/abs/2309.06180)：把 cache 切成块，按需分配，减少碎片和预留浪费。

## 10.4 量化

权重量化把每个参数的字节数降下来：fp16 14 GB，int8 7 GB，int4 3.5 GB。decode 每步要读权重，权重变小通常能降低显存带宽压力；但有三件事不能忘：

1. **量化有精度损失**：要在自己的任务上比较量化前后，尤其是工具参数、代码和长上下文；
2. **KV cache 不会自动量化**：权重量化省的是权重，32K 上下文的 cache 仍是几十 GiB；
3. **吞吐不一定线性提升**：瓶颈可能在 KV cache、调度或计算，换个模型和批大小，结论会变。

KV cache 也可以单独量化，但那是另一项配置，精度影响也不同。部署时把“权重量化”和“KV cache 量化”分开记录，不要笼统写“4-bit”。

均匀仿射量化用缩放因子 S 和整数零点 Z 表示浮点数。设校准区间 `[α, β]` 已扩展到包含 0，且 `β > α`；整数编码范围为 `[q_min, q_max]`：

```text
S = (β - α) / (q_max - q_min)
Z = clip(round(q_min - α / S),
         q_min, q_max)
x_q = clip(round(x / S) + Z,
           q_min, q_max)
x_hat = S × (x_q - Z)
```

Z 是浮点 0 对应的整数编码，`clip` 把越界值截到编码范围内。舍入约定、饱和行为和全零张量的处理要以实现为准。采用有符号整数编码的**对称量化**通常固定 `Z=0`，S 由绝对值范围确定；**非对称量化**允许零点偏移，用于不对称的数值范围。

粒度决定哪些数共享 S、Z：可以按张量、通道或组计算。更细的粒度常能减少重构误差，也增加元数据和内核处理成本；误差减少不保证任务得分提高。[GPTQ](https://arxiv.org/abs/2210.11423) 则用校准数据逐层补偿权重量化误差。选型时同时记录位宽、粒度、校准数据和实际任务分数。

## 10.5 部署形态

| 形态 | 适合 | 代价 |
| --- | --- | --- |
| 托管 API | 快速上线、弹性、少运维 | 单价、限流、数据出境与版本不可控 |
| 自建推理 | 数据留在本地、可深度调优 | GPU、运维、容量规划、故障恢复 |
| 混合 | 敏感请求本地、峰值走 API | 路由、协议与评测要统一 |

推理框架负责批处理、KV cache 管理、量化和并行切分；不同框架的实现和调参项差别很大，选型要用自己的请求压测。投机解码、前缀缓存、prompt caching 都能降低某些场景的延迟或费用，但都有命中条件；把它们当成默认能力，容量规划会失真。

投机解码让草稿模型先提出多个 token，目标模型并行计算这些位置的验证概率。[经典的精确算法](https://arxiv.org/abs/2211.17192)通过接受判定和拒绝后的残差采样，保持目标模型的采样分布；并非只比较两个模型各自概率最高的词。收益取决于接受数量、草稿耗时、目标模型验证成本和批量，接受的 token 也消耗过计算。基础实现通常共享词表；[Transformers v4.57.3 的 Universal Assisted Decoding](https://github.com/huggingface/transformers/blob/47b0e478f324b54f177ea7998a0791870fdd0324/docs/source/en/generation_strategies.md)已支持通过重编码与匹配对接不同 tokenizer。具体组合仍要验证兼容性与加速效果。

另一条常被忽略的省钱路是**模型路由**：一个轻量分类器先判断请求难度，简单请求给小模型、难题升级大模型，或按“先小后大”级联——小模型的输出通过已校准的置信度阈值或可执行检查时采纳，否则转大模型重答。线上通常不知道答案是否正确，置信度和检查都可能误判。收益取决于小模型独立处理的比例、错误放行率和转交大模型的成本。级联还多一段延迟。路由器和级联本身也要评测，别只看省了多少钱、不看转错的那部分。

## 10.6 vLLM 专项：PagedAttention、prefix caching 与框架分水岭

vLLM 的三个机制解决不同问题。以下说明对应 [v0.11.0 固定源码](https://github.com/vllm-project/vllm/tree/b8b302cde434df8c9289a2b465406b47ebab1c2d)，配置和后端支持应按使用版本核对。

| 机制 | 处理对象 | 作用 |
| --- | --- | --- |
| 分页管理 | KV 存储块与块表 | 减少预留浪费，支持共享 |
| 前缀缓存 | 上下文一致的 KV 块 | 减少重复 prefill |
| 连续批处理 | 每步的请求集合 | 及时补入新请求 |

[PagedAttention 论文](https://arxiv.org/abs/2309.06180)把逻辑 KV 块映射到不必连续的物理块。块大小由实现与后端决定；分块能减少浪费，也仍有尾块、块表和预留容量等开销。分页管理提供复用的基础，但不会自动免去所有重复计算。

自动前缀缓存（automatic prefix caching，APC）的[官方说明](https://github.com/vllm-project/vllm/blob/b8b302cde434df8c9289a2b465406b47ebab1c2d/docs/features/automatic_prefix_caching.md)明确区分收益范围：命中前缀时减少 prefill，不缩短随后生成新 token 所需的 decode。相同长文档被反复提问、相同工具说明被重复发送时值得测；输出很长或共享前缀很少时，整体收益可能很小。

这里的“相同”包含计算上下文。[缓存设计文档](https://github.com/vllm-project/vllm/blob/b8b302cde434df8c9289a2b465406b47ebab1c2d/docs/design/prefix_caching.md)用父块哈希、块内 token 和附加信息识别完整块；附加信息包括 LoRA 标识、多模态输入标识和缓存盐。只比较一段文字相同，不足以判断 KV 可复用。

压测时固定模型、量化方式、硬件和并发，分别运行冷缓存与热缓存。至少记录输入长度、公共前缀长度、输出长度、TTFT、TPOT、总吞吐和显存；再改变前缀复用率，观察收益何时消失。这比给所有请求套一个固定加速倍数更能支持容量规划。

框架选择也应沿这张负载表进行：目标模型和硬件能否运行，所需量化与结构化输出是否受支持，目标并发下是否满足延迟要求。TensorRT-LLM、SGLang、llama.cpp 等可以列入候选，但具体后端与功能要按版本逐项核对，框架名称本身不能替代压测。

**语义缓存（semantic caching）**复用的是已有回答。它先找相似问题，再判断缓存答案是否可用，命中后可能省去整次生成。“怎么重发验证码”和“怎么改密码”即使向量接近，也不能共用答案。缓存匹配必须纳入租户、权限、个性化状态及知识版本；写操作与依赖实时状态的请求通常不适合直接复用旧回答。过期、撤权和文档更新需要触发失效。

**多 LoRA serving**让多个 adapter 共享一个基座，减少重复存放基座权重的开销。[vLLM 的 LoRA 文档](https://github.com/vllm-project/vllm/blob/b8b302cde434df8c9289a2b465406b47ebab1c2d/docs/features/lora.md)展示了按请求指定 adapter 的接口。adapter 较小，但每条序列仍需 KV 存储；adapter 身份还参与前缀缓存匹配。容量规划应测量 adapter 加载、驻留数量及混合请求的调度成本。

## 10.7 Agent 工程落点

| 场景 | 关键指标 | 做法 |
| --- | --- | --- |
| 交互式助手 | TTFT、p95 | 控制输入长度，缓存稳定前缀 |
| 批量数据处理 | 吞吐、单价 | 大批处理，接受更高单请求延迟 |
| 长上下文排查 | KV cache、OOM | 限制并发，压缩历史，按需检索 |
| 工具调用密集 | TPOT、重试率 | 缩短输出，结构化参数，失败快速回退 |
| 多租户 | 隔离、配额 | 按租户限流，避免一个长请求拖垮全局 |

容量规划至少回答四个数：峰值并发、平均输入/输出长度、可接受的 p95、单卡能装下的 KV cache。只报“支持多少 QPS”没有意义，QPS 随输入输出长度和批处理策略变化。

`llm/examples/session_ledger.py` 把这条思路落成一张四轮会话的账单：每轮输入多少 token、其中多少是原样重发、三种缓存策略各花多少钱、峰值 KV cache 占多少显存。先把自己的会话按轮记账，再谈容量。

## 10.8 常见翻车

| 常见翻车 | 后果 | 正确做法 |
| --- | --- | --- |
| 只用 FLOPs 估延迟 | 忽略 decode 的显存带宽 | 分开算 prefill 与 decode |
| 把批大小拉满 | p95 恶化、长请求排队 | 按 SLA 找吞吐与延迟的平衡 |
| 只算权重不算 KV cache | 长上下文 OOM | 权重 + cache + 激活一起预算 |
| 认为量化自动省 cache | 并发一开就爆显存 | 权重与 KV cache 分开量化 |
| 静态批处理等最长请求 | 槽位空转 | 连续批处理及时补入请求 |
| 用平均延迟代替 p95 | 线上尾延迟不可接受 | 压测记录分位数与超时 |

## 10.9 本章小实验

在仓库根目录运行：

```bash
python llm/examples/serving_demo.py
```

然后试三组改动：

1. 把 `DTYPE_BYTES` 从 2 改成 1，观察 KV cache 和批大小上限怎样变化；再把权重精度改成 int8，比较两者节省的比例。
2. 把 `BANDWIDTH` 从 `3e12` 改成 `1.5e12`，这个带宽模型中的 decode 时间会翻倍；再与设备实测比较，检查计算和调度是否已成为主要开销。
3. 把 `lengths` 改成 `[20, 20, 200, 200]` 或 `[200, 200, 200, 200]`，观察静态与连续批处理的利用率差异；再想想真实请求长度分布为什么很少这么整齐。

示例只算显存流量和槽位占用，不测真实框架的吞吐。下一章进入 RAG：切块、向量检索与重排，看怎样在推理之前把上下文选对；想复习 KV cache 的结构，回[第 3 章](ch03.md)，想算窗口预算，读[第 6 章](ch06.md)。
