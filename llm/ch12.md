# 第 12 章：工具调用与 MCP：把动作写进协议

<!-- block: llm-ch12.b-opening -->
用户问“我的退款到账了吗”。模型回答“已经帮您退款”，听起来没问题，但它没有调用任何工具，订单状态也没变。另一种情况更常见：模型调用了查询工具，把订单号传成整数，运行时默默转成字符串，查错了订单。

工具调用不是让模型“说一句要调用工具”，而是让它在名字、参数和返回值上遵守一份协议。这一章用两个工具和一个脚本化的模型，走一遍参数校验、失败重试和 MCP 形状的 JSON-RPC 消息。

## 12.1 工具定义是一份契约

一个工具至少要有三部分：

- **名字**：模型和运行时都认得的唯一标识；
- **描述**：这个工具做什么、什么时候用、什么时候不要用；
- **输入 schema**：参数名、类型、必填项、枚举和约束。

示例里的两个工具定义：

| 工具 | schema 字符数 | 必填字段 |
| --- | ---: | --- |
| `get_refund_status` | 181 | `order_id` |
| `create_ticket` | 241 | `order_id`、`reason` |

这些字符会跟着每次请求进入上下文，成为固定开销。工具越多、schema 越细，输入 token 越高。一个 20 个工具的系统，单是定义就可能占掉几千 token；这和[第 1 章](ch01.md)的预算表是同一笔账。

描述也是提示词的一部分。`get_refund_status` 如果写成“查询订单”，模型可能拿它查物流；写成“查询订单的退款状态，不返回物流信息”，歧义就小得多。工具名、描述和参数名要一起设计，不能只改 schema。

## 12.2 一次调用的生命周期

一次工具调用通常走这条链：

```text
模型输出 name + arguments
  → 解析 JSON
  → 校验 schema
  → 权限与确认
  → 执行（带超时、幂等键）
  → 把结果作为工具消息放回上下文
  → 模型继续生成或结束
```

模型输出不是可信输入。示例的第一次调用把 `order_id` 传成整数 `1001`，校验器直接拒绝：

```text
validation failed: order_id must be a string
```

第二次传 `"ORD-1001"`，校验通过，执行器返回“退款处理中，预计 1–3 个工作日到账”。未知工具也会返回结构化错误，而不是让运行时崩溃。

这里有一个重要的设计选择：**校验失败要作为工具结果返回给模型，而不是抛异常终止**。模型看到错误信息，才有机会修正参数。但重试要有上限，否则一个坏 schema 会让 Agent 无限循环。

事后校验还有一条升级路线：**约束解码**（constrained decoding）。生成时每一步先算出词表上的 logits，再按语法把不合法的候选直接屏蔽——引号没开就不许出非转义字符，枚举字段只许从允许值里挑，于是模型“写不出”不合 schema 的 JSON。机制上这是在采样前对 logits 做掩码，高效的实现见 [Willard & Louf 的引导生成](https://arxiv.org/abs/2307.09909)。它把重试成本移到了生成中：好处是结构化任务一次过、工具链路不再兜圈；代价是每步采样多一层掩码开销，且约束写得太死会把“模型想补充一句说明”的合理输出也拦掉。托管 API 的“结构化输出 / JSON 模式”多是这条路线；自建推理栈也可以按 schema 编译自动机实现。两条路不互斥：开约束解码保证形状，服务端仍保留 schema 校验兜底——约束管生成、校验管边界。

## 12.3 MCP：把工具和资源变成协议

Model Context Protocol（MCP）用 JSON-RPC 2.0 把客户端和服务器连起来。一次会话通常先 `initialize`，协商协议版本和能力；然后 `tools/list` 拿工具清单；调用时发 `tools/call`。

示例打印的三条请求：

```text
{"jsonrpc":"2.0","id":1,"method":"initialize",
 "params":{"protocolVersion":"2026-07-28","capabilities":{},
           "clientInfo":{"name":"toy-agent","version":"0.1"}}}
{"jsonrpc":"2.0","id":2,"method":"tools/list","params":{}}
{"jsonrpc":"2.0","id":3,"method":"tools/call",
 "params":{"name":"get_refund_status","arguments":{"order_id":"ORD-1001"}}}
```

服务器返回 `tools/call` 的结果，`content` 里是文本块，`isError` 标明这次调用是否失败。MCP 还定义 resources 和 prompts 两类原语；工具只是其中一类。协议细节以官方规范为准：[MCP 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28)，JSON-RPC 的格式见 [JSON-RPC 2.0](https://www.jsonrpc.org/specification)。

MCP 解决的是“工具怎样被发现和调用”，不解决“模型该不该调用”。权限、确认、幂等和审计仍然在运行时和业务层。

## 12.4 权限、幂等与错误

读工具和写工具要分开对待。查询订单状态可以自动执行；退款、改地址、删数据要有权限检查、用户确认和审计日志。

| 风险 | 做法 |
| --- | --- |
| 重复执行 | 幂等键 + 去重表；写操作先查后写 |
| 超时/半成功 | 超时、取消、补偿；返回可重试的错误码 |
| 越权 | 最小权限、租户隔离、每次调用带身份 |
| 误操作 | 写工具要求确认；先 dry-run 或预览 |
| 不可追溯 | 记录调用者、参数、结果、时间与请求 ID |
| 工具被篡改 | schema 与实现同源版本化；服务端再次校验 |

工具结果是外部输入，可能包含提示注入。一个网页或工单里的“忽略之前的指令”不应该被当成系统指令；运行时要把工具结果当数据处理，不能让模型直接执行其中的动作。

## 12.5 Schema 设计

几个实用规则：

- 一个工具只做一件事；`refund_order` 和 `query_refund` 不要混成一个 `refund`；
- 参数名用业务语言，不用 `arg1`、`data`；
- 能用枚举就不用自由字符串；能用 pattern 就不靠模型自觉；
- `additionalProperties: false`，避免模型塞入未定义字段；
- 错误返回结构化字段：`code`、`message`、`retryable`、`details`；
- 分页、上限、排序参数写进 schema，不要靠提示词提醒；
- 工具版本与实现一起发布，旧版本保留兼容窗口。

工具调用的评测不只看“有没有调用”，还要看选对工具、参数正确、结果被正确使用，以及失败后是否能恢复。

## 12.6 Agent 工程落点

| 场景 | 工具设计 | 注意 |
| --- | --- | --- |
| 订单查询 | 只读、按订单号精确查 | 参数格式校验，脱敏返回 |
| 退款/改址 | 写操作、需确认、幂等键 | 权限、审计、补偿 |
| 代码执行 | 沙箱、超时、资源限额 | 不把宿主机权限交给模型 |
| 检索 | 查询 + top-k + 过滤条件 | 返回来源与片段 ID |
| 多工具协作 | 每个工具单一职责 | 编排层控制顺序与上限 |
| 多租户 | 每次调用带租户身份 | 服务端再校验，不信客户端 |

## 12.7 常见翻车

| 常见翻车 | 后果 | 正确做法 |
| --- | --- | --- |
| 把模型输出当可信参数 | 注入、越权、查错对象 | 服务端 schema 校验 |
| 参数类型自动强转 | 静默查错订单 | 类型不符就报错，让模型重试 |
| 校验失败直接抛异常 | Agent 中断，用户看到 500 | 把错误作为工具结果返回 |
| 写操作没有幂等键 | 重试导致重复退款 | 幂等键 + 去重 |
| 工具描述含糊 | 选错工具或漏调用 | 名字、描述、schema 一起评测 |
| 工具结果直接当指令 | 提示注入执行 | 结果当数据，动作走权限 |
| 没有调用上限 | 无限循环、费用失控 | 最大步数、超时、预算 |

## 12.8 本章小实验

在仓库根目录运行：

```bash
python llm/examples/toolcall_demo.py
```

然后试三组改动：

1. 把第一次调用的 `order_id` 改成 `"ORD-9999"`，观察执行器返回“order not found”；再改成 `"ord-1001"`，看 pattern 是否拦住大小写。
2. 给 `create_ticket` 加一个 `priority` 枚举参数，补上校验与执行，观察 schema 字符数怎样增长；再想想这些字符每轮请求要付多少 token。
3. 把 `mcp_messages` 的 `protocolVersion` 改成旧版本，观察真实的 MCP 服务器会不会拒绝；再给 `tools/call` 加一个不存在的工具名，构造 `isError` 结果。

示例没有权限、传输、超时和幂等，只演示协议形状。下一章进入思维链与推理模型，看模型在调用工具之前怎样“想一步”；想复习上下文预算，回[第 6 章](ch06.md)，想复习 RAG，读[第 11 章](ch11.md)。
