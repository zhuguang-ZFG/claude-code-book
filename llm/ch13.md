# 第 13 章：思维链与推理模型：多想一步值不值

<!-- block: llm-ch13.b-opening -->
一个排查线上故障的 Agent 直接给出结论，漏掉了“先看日志、再核对配置”的顺序；加上“先分析再回答”后，它找到了根因，但每次请求多花几百个输出 token，延迟也上去了。另一条路是采样五次取多数，准确率更高，账单是五倍。

思维链不是免费的“更聪明”。它用输出 token 换推理步骤，用延迟换准确率。这一章把自洽投票的收益和成本算清楚，再看推理模型与 Agent 的 plan-then-execute 应该怎么用。

## 13.1 思维链买的是什么

思维链（CoT）让模型在给出答案前先写中间步骤。对多步算术、逻辑和排查类任务，这些中间 token 相当于给后续 token 更多条件；对简单分类或格式转换，它们只是额外开销。

[CoT 原始论文](https://arxiv.org/abs/2201.11903)在特定模型和任务上展示了这种提升。它不是“只要写步骤就一定对”：模型可能编出一条看起来合理、实际算错的推理；步骤越多，错得更难发现。思维链是模型输出的一部分，不是内部真相。

对 Agent 来说，CoT 还有一层工程含义：推理 token 通常按输出计费。如果提供方把隐藏推理也计入 usage，预算要按总输出 token 算，而不是只看最终答案的长度。

## 13.2 自洽投票：多采样几次

自洽投票（self-consistency）让模型对同一问题采样多条推理路径，再对最终答案投票。[Self-Consistency](https://arxiv.org/abs/2203.11171) 的做法是不看推理过程，只看答案。

`llm/examples/cot_demo.py` 假设每条样本独立的正确率是 0.60，模拟 4000 道题，多数投票的结果：

| 采样数 | 多数投票准确率 | 每题 token |
| ---: | ---: | ---: |
| 1 | 60.7% | 400 |
| 3 | 66.0% | 1 200 |
| 5 | 69.4% | 2 000 |
| 9 | 75.2% | 3 600 |
| 15 | 79.5% | 6 000 |

准确率随采样数上升，但边际收益递减；token 线性增长。15 条样本比 1 条多 15 倍 token，换来的准确率提升约 19 个百分点（这里从 60.7% 到 79.5%）。


这套算术有一个强假设：错误彼此独立。真实模型对同一道题的多条采样往往错在同一个地方，投票会把同一个错误重复放大。采样温度、提示词和模型版本也会影响多样性；没有多样性，多数投票只是重复同一答案。

## 13.3 测试时计算与推理模型

自洽投票是最简单的测试时计算：不改模型，只改采样和选择。更复杂的做法包括：

- **验证器**：训练一个模型给候选答案打分，或按步骤给过程奖励；[Let's Verify Step by Step](https://arxiv.org/abs/2305.20050) 比较了结果监督与过程监督；
- **搜索**：在推理步骤上做树搜索，按验证器分数扩展和剪枝；
- **推理模型**：用强化学习训练模型生成长思维链，再把推理能力蒸馏到小模型；[DeepSeek-R1](https://arxiv.org/abs/2501.12948) 是一个公开例子。

[测试时计算 scaling](https://arxiv.org/abs/2408.03314) 讨论了在固定推理预算下，采样、验证和搜索怎样分配；结论依赖任务、模型和预算，不能概括成“多想一定更好”。

`cot_demo.py` 还算了一笔成本账，假设每百万输出 token 0.60 美元：

| 策略 | token/题 | 准确率 | 每道正确题成本 |
| --- | ---: | ---: | ---: |
| 直接回答 | 100 | 45.0% | $0.000133 |
| CoT 一次 | 400 | 65.0% | $0.000369 |
| CoT 五次投票 | 2 000 | 76.8% | $0.001561 |
| CoT 十五次投票 | 6 000 | 88.8% | $0.004053 |

准确率从 65% 提到 88.8%，每道正确题的成本从 $0.000369 涨到 $0.004053，约 11 倍。值不值，取决于答错的代价：一次退款查错可能只多一次客服工单，一次生产变更判断错可能损失更大。

## 13.4 Agent 的 plan-then-execute

Agent 的“思考”不一定要写成一篇长文。更常见的结构是：

```text
读任务 → 列 2–5 步计划 → 调工具验证关键事实 → 根据结果修正 → 执行
```

计划的作用是把动作排序，并在调用工具前暴露假设。计划太长会占用上下文和输出预算；计划里的每个事实仍要用工具回执核对，不能把“想出来的”当“查到的”。

对用户展示时，给结论、依据和下一步动作，不必把未校验的推理全文倒出来。推理过程可能包含错误假设、内部路径或敏感信息；对外输出要经过整理。

## 13.5 什么时候不值得

- 任务只有一步：分类、抽取、格式转换，直接回答更便宜；
- 延迟敏感：多采样和长推理会拉高 TTFT/TPOT；
- 错误高度相关：同一模型的多条采样错在一起，投票无效；
- 没有验证器：搜索和自洽投票可能只是在错误答案里挑一个；
- 任务本身不可验证：开放式写作可以多想，但“正确率”不能用投票定义。

## 13.6 Agent 工程落点

| 场景 | 推理策略 | 注意 |
| --- | --- | --- |
| 多步算术/对账 | CoT + 自洽投票 | 控制采样数，核对计算 |
| 故障排查 | 短计划 + 工具验证 | 计划中的事实要查日志/配置 |
| 代码修复 | 计划 + 测试 | 用测试而不是投票判断对错 |
| 简单抽取 | 直接回答 | 不要为了“更聪明”加长输出 |
| 高风险决策 | 多方案 + 人工复核 | 保留依据与不确定性 |
| 成本敏感批处理 | 小模型 + 验证器 | 先算每道正确题的成本 |

## 13.7 常见翻车

| 常见翻车 | 后果 | 正确做法 |
| --- | --- | --- |
| 所有任务都加“think step by step” | 延迟和费用上升，简单任务无收益 | 按任务选择是否推理 |
| 把 CoT 当事实来源 | 流畅的错误推理被当成依据 | 用工具、测试、检索核对 |
| 多数投票不看多样性 | 重复同一个错误 | 调温度/提示，检查错误相关性 |
| 采样数拉满 | 成本线性涨，收益递减 | 按答错代价定预算 |
| 对外输出完整隐藏推理 | 泄露、误导、难审计 | 给结论、依据与动作摘要 |
| 计划不验证就执行 | 基于错误假设调用工具 | 每个关键事实有回执 |

## 13.8 本章小实验

在仓库根目录运行：

```bash
python llm/examples/cot_demo.py
```

然后试三组改动：

1. 把 `majority_accuracy` 的 `p` 从 0.60 改成 0.45 和 0.75，观察多数投票在不同基础正确率下的收益；基础正确率低于 0.5 时，投票还有用吗？
2. 把 `TRIALS` 从 4000 改成 200，观察模拟结果的波动；再换几个 `seed`，理解“准确率”本身也有采样误差。
3. 把 `PRICE_PER_MILLION` 改成 3.00 或 0.15，重算每道正确题成本；再把 `REASONING_TOKENS` 改成 1000，看看长推理怎样改变排序。

示例只模拟独立错误下的多数投票，不调用模型；它给的是成本与收益的形状。下一章进入幻觉、评测与蒸馏，看怎样用评测而不是投票判断一个系统是否真的变好；想复习采样，回[第 5 章](ch05.md)，想复习工具校验，读[第 12 章](ch12.md)。
