# 第 13 章：思维链与推理模型：多想一步值不值

<!-- block: llm-ch13.b-opening -->
面对一道对账题，可以让模型直接给答案，也可以让它列出计算步骤，或者独立生成五份解答再投票。后两种做法都增加计算量，是否减少错误却要实际测量。五份答案若沿用同一个错误假设，只会让这个错误得到更多票。

本章用一个可复算的投票模型，比较采样数量、答对比例和输出费用，再讨论 Agent 怎样安排计划与验证。

## 13.1 思维链买的是什么

思维链（CoT）让模型在给出答案前生成中间步骤。后续生成可以利用前面的分解、计算和检查；在某些多步任务上，这比直接猜出最终答案有效。[CoT 原始论文](https://arxiv.org/abs/2201.11903)在特定模型与任务上展示了这种收益。

步骤也会出错。模型可能沿着错误的前提继续推导，写出流畅但不成立的解答。可见的推理文本是待检查的输出，不能当作模型内部机制的完整记录，更不能代替事实来源。

额外的中间 token 会增加生成工作。费用按提供方的 usage 与价格规则核算：若隐藏推理计入计费输出，就要连同答案一起计入预算；只看最终显示了多少字会低估成本。

## 13.2 自洽投票：多采样几次

[Self-Consistency](https://arxiv.org/abs/2203.11171) 采样多条推理路径，再按最终答案的出现频率选择结果。先要把“42”“42.0”等等价答案归一化；这种选择不需要额外训练一个验证器，但票数本身不能证明答案正确。

`llm/examples/cot_demo.py` 用更简单的二元模型解释投票：每次采样只记录“对”或“错”，独立同分布，正确概率固定为 `p=0.60`；超过一半样本正确才算这道题成功。它没有生成或比较实际答案。固定 `seed=7`，模拟 4 000 道题得到：

| 次数 | 模拟 | 精确 | 输出 token |
| ---: | ---: | ---: | ---: |
| 1 | 60.7% | 60.0% | 400 |
| 3 | 66.0% | 64.8% | 1 200 |
| 5 | 69.4% | 68.3% | 2 000 |
| 9 | 75.2% | 73.3% | 3 600 |
| 15 | 79.5% | 78.7% | 6 000 |

精确值由二项分布尾概率计算。设 `n` 为奇数，`C(n,k)` 为组合数：

```text
P(多数正确) = Σ C(n,k) × p^k × (1−p)^(n−k)
求和范围：k = (n+1)/2, …, n
```

每条样本假设用 400 个输出 token，因此 15 次采样的总量是一次的 15 倍。这组模拟从 60.7% 升至 79.5%，约增 19 个百分点；模拟值和精确值的差异来自有限次抽样。


这个模型有两处边界。第一，真实错误常有关联：同一题的歧义或知识缺口可能让多条路径一起出错。第二，多种答案的票选不一定要求超过半数。若正确答案出现 4 次，两个不同错误答案各出现 3 次，正确答案仍以最高票当选；二元“对/错”计数却会判失败。因此，`p>0.5` 时多数投票随样本增加而改善、`p<0.5` 时反而恶化，是这里二元独立模型的结论，不能直接用作真实自洽投票的统一门槛。

## 13.3 测试时计算与推理模型

自洽投票在推理时增加采样和选择，不改变模型参数。其他测试时计算策略包括验证候选、生成后修订，以及在候选推理步骤上搜索。验证器可以是算术检查、单元测试，也可以是学习得到的评分模型；[Let's Verify Step by Step](https://arxiv.org/abs/2305.20050) 研究了结果监督与过程监督下的验证器。

推理模型的训练属于另一层工作：通过监督微调、强化学习等方法，使模型学会分解问题和检查答案，再在使用时分配推理预算。[DeepSeek-R1](https://arxiv.org/abs/2501.12948) 展示了强化学习与多阶段训练路线，并另行训练蒸馏模型；蒸馏不是所有推理模型的必经步骤。[测试时计算研究](https://arxiv.org/abs/2408.03314)则讨论固定预算下怎样选择策略，收益随题目难度、模型和预算而变。

脚本的第二张表另设一个成本场景：直接回答的正确率假设为 45%，CoT 单次为 65%；投票沿用二元独立模型。这里并未通过实验测出“加 CoT 能从 45% 提到 65%”。输出单价假设为每百万 token 0.60 美元：

| 策略 | 输出 token/题 | 假设或模拟正确率 | 每道正确题输出成本 |
| --- | ---: | ---: | ---: |
| 直接回答 | 100 | 45.0% | $0.000133 |
| CoT 一次 | 400 | 65.0% | $0.000369 |
| CoT 五次投票 | 2 000 | 76.8% | $0.001561 |
| CoT 十五次投票 | 6 000 | 88.8% | $0.004053 |

最后一列用“每题输出费用 ÷ 正确率”计算，表示一批题目的输出总费用摊到预期正确题数上，包含答错题产生的输出费用。它不包含输入、工具和验证器成本，也不表示某一道题反复重试直到答对的保证费用。

在这组假设下，CoT 十五次投票比单次多答对约 24 个百分点，每道正确题输出成本约为 11 倍。实际选择需要把答错的损失与等待时间一起衡量，而不是只追求最高正确率。

## 13.4 Agent 的 plan-then-execute

Agent 可以用短计划安排动作，例如：

```text
读任务 → 列检查步骤 → 调工具核对关键事实
       → 按结果修正计划 → 执行
```

故障排查中的“配置与线上一致”是待查的假设，读取配置后的回执才是证据。计划应指出下一步需要核对什么，并能随结果调整。写得很长但不检查前提，照样会把错误带到后续动作。

给用户的说明应交代结论、依据与下一步动作。把尚未校验的推理全文直接展示出去，反而会让错误假设和已核实事实混在一起。

## 13.5 什么时候不值得

- 简单抽取或格式转换：先测直接回答的基线，只有额外推理带来可重复收益才增加预算。
- 延迟敏感：串行推理会延长完成时间；多路采样可以并行，但会增加资源需求。首个可见答案的等待时间与逐 token 延迟应分开测量。
- 候选高度相似：检查它们是否重复同一错误；增加条数可能收效很小。
- 搜索缺少可靠反馈：评分不准会把预算花在错误分支上。自洽投票虽不依赖独立验证器，也仍需要评测其选择规则。
- 开放式写作：偏好和质量不能简单换成“多数答案正确”，应另定可检查的评价标准。

## 13.6 Agent 工程落点

| 场景 | 推理策略 | 注意 |
| --- | --- | --- |
| 多步算术/对账 | 分解步骤，必要时多采样 | 用计算器核对关键值 |
| 故障排查 | 短计划 + 工具验证 | 查日志与配置，保留证据 |
| 代码修复 | 计划 + 测试 | 用测试检查行为，票数不能替代测试 |
| 简单抽取 | 直接回答作为基线 | 比较收益后再增加推理 |
| 高风险决策 | 多方案 + 人工复核 | 交代依据与未解决的问题 |
| 成本敏感批处理 | 比较模型与验证组合 | 同时统计正确率、总费用和时延 |

## 13.7 常见翻车

| 常见翻车 | 后果 | 正确做法 |
| --- | --- | --- |
| 每个任务都加“think step by step” | 增加开销却未必改善结果 | 按任务评测 |
| 把 CoT 当事实来源 | 流畅推理掩盖错误前提 | 用工具、测试、检索核对 |
| 投票前不归一化答案 | 等价答案分散票数 | 统一单位、格式与等价规则 |
| 二元模拟当真实模型收益 | 误判采样数与预算 | 测量实际答案分布与错误关联 |
| 只算最终答案费用 | 漏掉推理、输入或验证开销 | 对照完整 usage 与账单 |
| 计划未经核对就执行 | 基于错误假设调用工具 | 每个关键前提有依据 |

## 13.8 本章小实验

在仓库根目录运行：

```bash
python llm/examples/cot_demo.py
```

然后试三组改动：

1. 把第一张表的 `p` 从 0.60 改成 0.45 和 0.75，同时修改模拟与精确值的调用，观察二元模型的趋势。再用“4 票正确、3 票错误 A、3 票错误 B”说明这个趋势为什么不能覆盖所有答案票选。
2. 把 `TRIALS` 从 4 000 改成 200，并换几个 `seed`；对照精确值，观察抽样波动。参数 `p` 仍是假设，不是从模型测得的正确率。
3. 改变 `PRICE_PER_MILLION` 和 `REASONING_TOKENS`，观察成本表。脚本没有把推理长度与正确率联动；改变长度只改变费用，不能据此推断真实模型的效果。
