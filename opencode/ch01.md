# 第 1 章：安装与第一项任务

<!-- block: opencode-ch01.b-opening -->
第一次运行 OpenCode，先让它完成一项小到可以人工核对的任务：读取临时文件并指出内容。安装成功只说明程序能启动；读到正确的文件，才说明项目目录、模型配置和工具路径接上了。

本章可以先读 1.1 节确认版本，再到 1.6 节运行随书驱动，最后用 1.8 节找到结果文件。驱动会准备临时项目、完整配置和本地模型替身；1.2、1.3 与 1.7 节拆开解释它创建的内容，跟做时不用再手工拼一份配置。若要把这项读取任务交给真实模型，则需要另行配置模型及认证。

## 1.1 先确定自己启动的是什么

OpenCode 可以以终端交互、无界面服务和其他客户端入口运行。本书实验选择 `serve`，因为 HTTP 请求和日志方便逐步检查。它不需要把终端界面也放进测试，仍然会启动真正的项目和会话服务。

下载 Windows 发布 ZIP 后，校验摘要再解压。完整命令在附录 B 和示例说明中。使用固定程序路径运行，避免 PATH 中另一个安装覆盖你的判断：

```powershell
.scratch/opencode-bin/opencode.exe --version
.scratch/opencode-bin/opencode.exe --help
```

本书记录的版本输出是 `1.19.5`。复制程序或升级包后，请重新记录版本和摘要，避免文件名与实际程序不符。源码提交、包版本和二进制版本也分别记录，后面查兼容问题时会用到。

## 1.2 给第一项任务一个明确的工作目录

任务目标是读取临时目录中的 `fixture.txt`，报告其中的标记，不修改文件。随书驱动会创建它；手工做同类练习时，可以写入一行自己认识的文字。文件内容不依赖网络，便于单独检查文件读取是否接通。

```text
project/
  opencode.json
  fixture.txt
  .git/
```

真正使用时，你还需要选好模型及认证方式；本书的复现实验则由本地替身提供模型响应。`enabled_providers` 只启用实验提供者，`model` 和 `small_model` 都指向它，避免标题等附带请求走到别的提供者。这里的本地 API key 是固定无效占位符，只供协议形状使用。

宿主还可能为这条消息另发标题请求。只给主模型配置本地地址，会把这类附带请求留给默认模型，所以实验同时设置两者。统计时也要注意：一次任务可能包含多次请求。

## 1.3 配置一条真正可验证的只读路径

驱动的完整配置中包含下面的权限片段；模型部分在 1.7 节给出。手工准备配置时需要合并两部分：

```json
{
  "permission": {
    "*": "deny",
    "read": "allow"
  },
  "share": "disabled",
  "snapshot": false
}
```

关闭快照是为了让这个小实验只观察读取；它不是建议你在所有工程中关闭撤销功能。关闭分享则让实验不涉及发布会话。权限中的 read 允许了宿主内置读取路径，插件代码自身的权限范围将在第七章单独讨论。

配置完成后，宿主收到模型的 read 调用，解析文件路径，执行权限判断，再读取文件。看到工具结果中的标记，还要继续看下一次模型请求是否携带该结果。两处都出现，才说明工具结果走回了循环。

```mermaid
flowchart LR
  P[临时项目] --> C[读取配置]
  C --> S[创建会话]
  S --> M[模型请求]
  M --> T[read 与权限判断]
  T --> F[fixture.txt]
  F --> R[下一轮请求中的工具结果]
```

图 1-1：第一次任务需要接通的路径。模型响应在书中实验里由本地服务控制。

## 1.4 第一次运行失败时，先检查哪里

程序报找不到文件，先检查项目目录与传给 read 的路径。`serve` 可以服务多个项目，请求中的目录头决定实例；启动服务器时所在的目录并不能替所有后续请求决定项目身份。

出现模型错误时，分别检查提供者 ID、模型 ID、API 地址和认证字段。网络可达只说明连上了服务，不说明返回内容符合模型适配器需要的格式。第五章会用 SSE 的具体字段解释这一步。

插件没有事件时，检查它是否被发现、模块能否导入，以及是不是加了 `--pure`。第九章专门做了 pure 对照。只看终端没有红字并不充分：部分加载错误通过会话事件发布，需要结合实际工具列表与执行记录判断。

最后保存三样东西：版本、最小配置、实际结果。不要公开个人凭据、完整请求或绝对私有路径。将这些资料留在本机，就能在升级后重放同一项任务，知道问题来自版本变化还是项目自身。

## 1.5 从实验进入自己的工程

把这条小路径跑通后，再把任务换成读取项目说明、寻找一个函数或解释失败测试。一次只增加一种能力：先检索，再执行测试，最后才考虑写文件。这样遇到权限询问或环境问题，知道是哪一步引入的。

准备让 Agent 修改代码时，先看 Git 状态。已有改动不应被误当成这次任务产生的结果。第十七章的项目练习会保留失败测试、改动和复验输出，任务完成的依据也会从“回答正确”扩大到“代码经过检查”。

## 1.6 跑随书驱动，先看宿主做了什么
按 examples/README.md 的“Windows 真实宿主实验”准备发布程序和插件依赖：先下载并核对程序摘要，再安装隔离依赖。完成后留在书仓根目录，运行：

```powershell
python opencode/examples/check-host-plugins.py --binary .scratch/opencode-bin/opencode.exe --dependency-dir .scratch/plugin-types
```

驱动创建全新的临时项目，写入 fixture.txt，并启动两个仅监听本机的服务：OpenCode 的真实 serve，以及返回固定响应的模型替身。它不会用替身代替文件读取、插件发现或权限判断。模型只负责按约定要求调用 read，真正的读取动作仍由官方程序完成。

第一个场景把 BOOK_FIXTURE_ALPHA 写入 fixture.txt。替身要求 read 读取文件，宿主把工具结果放入下一次请求，替身随后返回 BOOK_FIXTURE_DONE。驱动会同时核对工具正文与最后回复；如果只收到完成标记，却没有读到文件内容，这项检查仍会失败。

成功时会出现四行 PASS，分别对应发现与执行、实例重建、进程重启和 pure 对照。先看第一项，确认文件内容已经回到模型请求中。后面三项涉及插件生命周期，读到第 9 章时再对照日志即可。

## 1.7 模型配置应当能指出每个字段的消费者
下面把驱动中的模型部分单独拿出来。端口是教学值；实际脚本会使用它启动的本地端口，不要求你手工寻找一个固定端口：

```json
{
  "model": "fixture/test",
  "small_model": "fixture/test",
  "enabled_providers": ["fixture"],
  "provider": {
    "fixture": {
      "npm": "@ai-sdk/openai-compatible",
      "name": "Fixture",
      "options": {
        "baseURL": "http://127.0.0.1:43121/v1",
        "apiKey": "local-fixture-only"
      },
      "models": {
        "test": {
          "name": "test",
          "limit": {"context": 32000, "output": 1024}
        }
      }
    }
  }
}
```

fixture 是配置中的提供者键，test 是它下面的模型键，二者组合成 model 字段。npm 指定适配器，baseURL 指向协议服务，limit 描述宿主用于请求和上下文处理的模型能力。把模型名写得与远端服务一样，并不能代替正确的适配器或地址。

这里的 32000 和 1024 是实验声明的限制，不是替身通过真实 tokenizer 测出来的能力。替身不生成复杂答案，所以这些值只帮助宿主按一份完整配置运行。换成真实服务时，要使用该服务实际支持的模型和限制，不能沿用教学数字推算上下文容量。

权限片段与这份模型配置合并后，形成的是一项有意受限的任务：可调用内置 read，其他能力默认拒绝。若你删掉 read 允许规则，模型仍可能提出读取请求，但宿主不应因此自动放行。模型响应描述想做什么，权限系统决定本次是否允许执行。

## 1.8 打开实验目录，按证据顺序读
每次驱动会在 .scratch/agent-series 下留下独立目录。先读 report.json 了解场景结果，再看 events.jsonl 中的 init、config、before、after、dispose，最后打开 model-requests.json 检查实际发送的消息。服务端日志用于解释启动、导入或请求错误，不必一开始就从几千行日志里找标记。

| 文件 | 主要回答的问题 |
| --- | --- |
| report.json | 哪个场景执行过，哪些断言通过 |
| events.jsonl | 插件回调实际按什么次序发生 |
| model-requests.json | 系统提示和工具正文有没有进入请求 |
| 服务端日志 | 进程、模块导入或服务请求在哪一步失败 |

脚本提前退出时，report 可能尚未写完，可以先查看最近一次运行目录中的日志，并确认进程是否仍在。保留这个目录，修正错误后再重跑，便于比较两次结果。驱动的 finally 会清理它启动的服务；人为中止或系统异常后，仍需核对实际进程。

公开排错时可以保留固定标记、版本和相对路径。原始请求包含项目路径及完整提示，不应直接当成面向所有读者的附件。随书 facts 文件就是从这些现场证据中提炼出的脱敏结果。

## 1.9 把第一次失败缩小到一个条件
脚本启动阶段有三个常见问题：--binary 路径错误、程序版本不符、依赖目录缺失。依次核对路径、程序来源和包准备步骤即可，这时请求可能还没有发出，修改提示词不会影响结果。

宿主启动后，文件读取失败可从请求里的 filePath 与项目目录核对。最终答复出现 BOOK_FIXTURE_DONE，但下一轮请求没有 ALPHA，说明只看答复会误判；驱动会明确拒绝这种结果。插件事件为空但 read 正常，先检查是否进入 pure 场景，而不是先认定插件程序损坏。

这组标记稳定出现后，就可以把 fixture 换成真实工程文件，继续核对文件路径、返回内容和下一轮请求。以后增加工具或插件时，也可以回到这项小实验，比较行为从哪一步开始变化。
