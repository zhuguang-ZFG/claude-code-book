# 第 6 章：工具注册与执行管线

<!-- block: opencode-ch06.b-opening -->
模型请求调用自定义工具后，宿主需要找到它的定义、检查参数、执行代码，再整理返回值。本章用一个文件读取工具走完这条路径，并查看权限拒绝、取消和执行失败分别发生在哪里。

第一章用的是宿主内置 read，本章换成书中原创的 book_probe。它们都读同一类临时文件，但 book_probe 的实现由我们编写，因此能把申请权限、开始读取和返回结果的位置逐个指出来。第七章继续用这个工具比较不同授权，两个章节共用一套实验。

## 6.1 从一个固定文件开始

本章的工具只读取当前项目的 `fixture.txt`，没有路径参数。这个限制是刻意的：先把注册、权限、执行和返回接起来，再增加任意路径、目录遍历等复杂情况。完整原创源码在 [read-fixture.ts](examples/read-fixture.ts)。

```typescript
import { readFile } from "node:fs/promises";
import { join } from "node:path";
import { tool, type Plugin } from "@opencode-ai/plugin";

export const ReadFixture: Plugin = async () => ({
  tool: {
    book_probe: tool({
      description: "Read fixture.txt after checking book_read permission.",
      args: {},
      async execute(_args, context) {
        await context.ask({
          permission: "book_read",
          patterns: ["fixture.txt"],
          always: ["fixture.txt"],
          metadata: {},
        });
        if (context.abort.aborted) throw new Error("Fixture read was cancelled");
        const output = await readFile(join(context.directory, "fixture.txt"), {
          encoding: "utf8", signal: context.abort,
        });
        return { title: "Project fixture", output, metadata: { source: "fixture.txt" } };
      },
    }),
  },
});
```

工具 ID 是 `book_probe`，内部申请的权限名是 `book_read`。这两个名字分开，便于下一章观察“工具对模型可见”和“执行中的读取获准”两道判断。普通插件也可以使用同名权限；这里不是强制命名规范。

## 6.2 工具从哪里注册

固定版本的 registry 有两条自定义入口：扫描配置目录中的 `{tool,tools}/*.{js,ts}`，以及读取已加载插件返回的 `Hooks.tool`。本例走第二条。工具目录的 default 导出使用文件名作工具 ID，其他导出则组合文件名和导出名；插件对象中的键则直接成为 ID。

同时使用两种入口时，要检查是否重复注册了同一个实现。几个名称也各有用途：ID 参与协议和权限匹配，description 帮助模型判断用途，返回的 title 用于展示某次结果。

公共 `tool()` 包装提供类型与 schema 辅助，这个版本的实现返回传入定义。真正的注册、参数转换和执行发生在宿主 registry 中。把一个普通对象包进 `tool()`，不会自动增加权限检查、重试或文件隔离。

## 6.3 schema 与执行器共同决定边界

添加参数时，使用明确的 schema。例如限定枚举比接收任意字符串再拼 shell 命令更容易检查。schema 是第一道格式约束，业务规则仍应在执行器里处理：文件是否位于允许目录、选项组合是否成立、目标是否已经存在，都不是一个 string 类型能保证的。

registry 会把公共 Zod 参数描述转换为模型所需的 JSON Schema，并在宿主一侧保留验证。工具定义还可能经过 `tool.definition` Hook 修改，因此排查“模型为什么传了这种参数”时，要看最后送出的 schema，而不只看初始源码。

```mermaid
flowchart LR
  D[插件工具定义] --> R[registry 转换参数与结果]
  R --> M[模型看到 schema]
  M --> A[调用参数]
  A --> B[before Hook]
  B --> E[执行器与 ask]
  E --> F[结果归一化和截断]
  F --> H[after Hook]
  H --> N[下一轮请求]
```

## 6.4 结果很大时会发生什么

工具可以返回字符串，也可以返回含 output、title、metadata 和附件的对象。registry 将它们归一化，再处理输出截断。固定源码中的默认上限是 2000 行与 50 KiB，同时允许配置或调用选项改变限制。

超限内容会保存到截断目录，模型收到预览和后续读取提示。上限按 UTF-8 字节计算，所以中文字符数量不能直接按字节上限估算。metadata 里会记录截断状态及输出路径，调试时应检查它们，而不是因为模型只看见一部分就断言工具执行丢了数据。

本书的 fixture 很小，没有触发截断；上述数字和保存路径行为来自固定版本源码。工具若返回包含密钥的超长日志，即使预览没显示密钥，完整日志仍可能已经写入截断文件。应该在产生结果时就筛掉不该返回的信息。

## 6.5 取消信号要送到真正干活的函数

样例先检查 `context.abort.aborted`，再把 signal 传给异步 readFile。这让等待中的操作有机会响应取消。它并不构成“所有工具取消都完整回滚”的保证；若操作是写数据库，取消通常不会把已提交事务倒回去。

本轮宿主实验验证的是允许与拒绝，不是中途取消。取消用例需要人为控制执行器停在可观察位置，再取消并检查文件与回调，不能只在函数开头传一个已取消信号就宣称覆盖真实时序。

失败时保留错误语义。文件不存在就让读取失败，不要返回一个与正常正文形状相同的“找不到文件”字符串，除非协议明确把它标成错误；否则模型和上层统计很难区分工具失败与成功读取到一段错误说明。

## 6.6 本书实际检查了哪些输出

权限驱动用包装器记录 entered、approved、read-done，包装器调用的仍是上述原创实现。允许时必须出现完整顺序，下一次模型请求还必须带有文件标记；拒绝时只允许 entered 出现。这样既观察权限结果，也观察副作用前后的代码位置。

准备步骤与第一章相同，入口在 examples/README.md 的“原创工具与权限”：从书仓根目录运行 check-tool-permissions.py，并传入同一发布程序和依赖目录。脚本会自行准备项目并执行十个场景，不需要手工把本章片段装进日常项目。结果文件里的 entered 表示进入工具，approved 表示权限等待已通过，read-done 表示读取已完成；按这个顺序看，再读第七章的拒绝和批准记录。

示例按真实 `@opencode-ai/plugin@1.19.5` 类型严格检查，并在官方宿主中运行。读者修改返回值、错误处理或导入依赖后，可以复跑同一脚本；只检查 TypeScript 编译通过不能代替宿主加载实验。

## 6.7 逐步拆开 registry 的适配工作

`fromPlugin` 把插件提供的普通对象转换成宿主的 `Tool.Def`，补上参数验证、执行上下文和结果处理。公共 `tool.ts` 只描述工具定义，要了解这些执行条件，还需要继续读这段转换代码。

首先处理参数。`def.args ?? {}` 把缺失参数声明归成空对象，随后检查每项是否属于可识别的 Zod 类型。全部是 Zod 时，宿主组装 `z.object(args)`，一方面生成 JSON Schema 交给模型，另一方面用 `safeParse` 的成功与否建立宿主验证。并非所有历史定义都走这一分支：兼容旧定义时，代码另做 schema 转换，验证侧可能保留 `Schema.Unknown`。因此“请求里有 JSON Schema”与“执行前一定做同样严格的验证”不能画等号。

本章的 `args: {}` 没有业务参数，便于单独观察工具注册与执行。以后加入 `path`、`limit` 或 `mode` 时，可以检查最终请求中的 schema，并用缺字段、错类型和越界值试出验证范围。

其次处理上下文。宿主执行器运行在 Effect 环境里，公开插件接受 Promise 风格的 `ask`。`EffectBridge.make()` 把宿主的询问操作接成可等待的 Promise；同时补入当前实例的 `directory` 与 `worktree`。这里不能用一个随手创建的 `Promise.resolve()` 替代真实 ask：那样虽然类型一样，等待审批与拒绝的行为已经消失。

最后调用 `def.execute`。在它返回之后，宿主才检查返回值是字符串还是对象、查询当前 Agent、执行截断并补结果 metadata。由此可以定位三类失败：模块导入阶段连工具定义都拿不到；执行阶段工具抛错；归一化阶段拿到了不符合协议的结果。它们不应该都记成“模型没调对工具”。

| 插件侧字段 | 宿主怎样使用 | 作者需要承担的事 |
| --- | --- | --- |
| description | 进入工具说明 | 说明真实用途和限制，避免承诺无法完成的操作 |
| args | 构造模型 schema 与参数验证 | 对业务边界另做判断，检查所用类型是否被兼容层识别 |
| execute | 在宿主工具上下文里调用 | 等待权限，响应取消，处理资源与失败 |
| output | 作为工具正文参与后续请求 | 保证正文能独立理解，别把关键数据只放 metadata |
| metadata | 与宿主补充字段合并 | 使用自己的命名空间，避开 truncated/outputPath |

合并顺序也会影响结果。实现先展开插件 metadata，再写入宿主计算的 `truncated`，超限时再写 `outputPath`。如果插件自己返回 `truncated: false`，不能用这个值阻止宿主截断。元数据是结果说明，不是指挥宿主跳过处理的控制参数。

## 6.8 同一份结果在三个地方长得不同

先看插件返回值。下面是一次成功读取的示意，字段取自本例，ID 和耗时不属于实跑记录：

```json
{
  "title": "Project fixture",
  "output": "BOOK_PERMISSION_ALPHA\n",
  "metadata": {"source": "fixture.txt"}
}
```

宿主包装后会补截断信息；如果第八章观察器也安装了，after Hook 还可以添加自己的 `reviewTrace`。这些字段服务于客户端显示和调试。但模型适配器最终看到的是模型协议里的工具结果，不能假设原来的 title、metadata、附件都原样成为一段 JSON。模型协议与宿主消息模型之间有转换层。

实验在下一次模型请求中搜索 `BOOK_PERMISSION_ALPHA`，确认 output 已经过转换并进入模型输入。会话数据库里的 metadata 和终端上的标题，分别反映另外两个阶段。

你可以用下面的脚本检查一次权限实验生成的请求。把 `evidence_dir` 改成脚本打印的目录；它只显示工具结果的短前缀，不整段输出请求中的源码。

```python
import json
from pathlib import Path

evidence_dir = Path('.scratch/agent-series/permissions-替换为本次目录')
requests = json.loads((evidence_dir / 'model-requests.json').read_text(encoding='utf-8'))
for request_no, request in enumerate(requests, 1):
    for message in request.get('messages', []):
        if message.get('role') == 'tool':
            print(request_no, message.get('tool_call_id'),
                  str(message.get('content', ''))[:100])
```

这段检查可以回答“结果有没有进入下一轮”，却不能回答“模型是不是理解正确”。本地替身只根据是否存在工具结果来结束，不读取复杂业务含义。以后换真实模型做练习时，还要用测试或文件差异判断任务结果。

## 6.9 一个工具请求多个目标时，权限怎样设计

如果把固定 fixture 扩展成多个审查文件，权限申请也要覆盖整个列表。只对第一个文件 ask，会让其余读取超出用户批准的范围。可以先规范化全部目标，对确定的集合申请权限，再逐项读取。

这里的“规范化”不能只靠删除 `..`。相对路径要以约定根目录解析，绝对路径要明确接受或拒绝，符号链接可能改变真正目标，文件在检查后还可能被替换。普通插件能做静态边界检查，但它无法凭几行字符串判断消除所有检查与使用之间的竞争。边界要求很高时，把读取工作交给受限进程或容器，权限提示只负责交代本次意图。

本例故意不接收任意路径，也仍需承认 `fixture.txt` 可能是符号链接。当前实验创建的是普通文件，所以验证范围是这个临时项目中的固定普通文件读取。把本例拿去处理不可信仓库时，应先增加文件类型检查、大小限制和目标身份核对，再讨论开放路径参数。

批量工具还需要提前决定部分失败的语义。假设 A 成功、B 不存在、C 尚未读取：返回 A 的正文并抛错，会丢失前面成功结果的可见性；返回一个大字符串“B 失败了”又会让调用看起来全部成功。可选做法是把批次定义成显式结果集合，每项有 `status`、相对路径和短错误，同时让整体正文清楚说明哪些项没有完成。对于写入工具，更应先选择事务、补偿还是允许部分完成，不能等出错后临时决定。

这个设计问题与宿主有没有 after Hook 无关。Hook 可以观察工具返回，不能替工具补出它从未记录的中间状态。

## 6.10 失败应在什么地方被看见

readFile 报 ENOENT 时，保留异常能让宿主把调用记成错误，模型随后可以换路径或向用户说明。若执行器捕获所有异常并返回空字符串，宿主看到的却是一次成功但无内容的读取，原本的文件错误就被隐藏了。

| 注入的问题 | 应观察的位置 | 容易造成误判的处理 |
| --- | --- | --- |
| 固定文件不存在 | 工具错误、宿主消息、后续模型输入 | 返回空正文并标成功 |
| permission 被拒绝 | entered 后没有 approved/read-done | 先读文件再等待权限 |
| 返回值缺 output | 结果归一化阶段的错误 | 把任意对象强制断言成工具结果类型 |
| 输出超限 | 预览、truncated、outputPath | 只检查字符串末尾是否出现 |
| 取消发生在读取中 | signal、工具终态、残余操作 | 只在函数入口检查一次 aborted |
| 日志服务失败 | 观察器错误与业务工具结果分别检查 | 为发日志把已经完成的工具改成失败 |

排查时一次只改一个条件。先保留宿主版本、工具源码与配置，删除临时 fixture 观察读取失败；恢复文件后改成 deny，观察权限失败。两种失败都可能在界面显示红色，但 entered/approved/read-done 会把位置分开。等这些最小情况清楚后，再加入并发与取消，故障才不会互相遮盖。
