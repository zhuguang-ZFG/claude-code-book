# 附录 A：任务说明、上下文清单与交接单

<!-- block: prompt-apxa.b-opening -->
这三份样稿用于保存任务、输入和进度。按实际工作删减字段；需要保留的是会改变判断的信息，不必为每次简短提问填写整张表。

## A.1 一份可以直接改写的任务说明

下面的内容使用第 1 章的初始通知。它是人工教学样稿，未包含后来的时间修订。

```text
任务版本：qinghe-task-01
用途：供组织者核对后，向第一次参加活动的居民说明安排。
输入：N01-v1 活动通知；R01-v1 名额、候补与取消规则。
交付：一段居民说明，以及关键事实、出处、待确认项的核对表。
必需信息：活动起止时间及北京时间、社区中心、房间未确认、费用、报名截止时间、12人容量、候补与递补办法。
缺失处理：直接说明尚未确认，不猜房间号和联系方式。
行动范围：只起草，不发布、不办理报名。
完成检查：逐条对照原通知与规则；保留首轮原始回答和核对记录。
```

“用途”决定什么信息需要优先出现。“输入”应能找到实际文件或粘贴文字。“行动范围”用于区分草稿和真实操作；有工具时还要用宿主权限落实。只写“准确、完整、专业”，接手者仍无法判断哪些遗漏影响完成。

发生修改时复制成新版本，注明替换哪条要求。若只把居民说明改成问答，不应顺带改掉日期或候补规则。版本说明可以只有一句：“v2 将居民说明改为五个问答，事实与只起草范围沿用 v1。”

## A.2 把实际输入记清楚

上下文清单记录这一轮真正提供了什么，不把整个资料库都列成已经使用。

| 字段 | D02 所选材料示例 | 什么时候需要 |
| --- | --- | --- |
| 任务与提示 | D02，A 版提示 | 每次需要比较或复做时 |
| 实际材料 | U01-v2、N01-v1、R01-v1 全文 | 材料有多个版本时 |
| 顺序 | 修订、原通知、名额规则 | 研究排序或长输入时 |
| 未选材料 | C01-v1、A01-v1、D01-v1 | 需要解释取舍时 |
| 未选原因 | 当前只整理现行安排，正式资料已足够 | 任务改变后便于重新判断 |
| 其他输入 | 另列产品加入的规则、历史或工具结果 | 使用带记忆、项目配置的宿主时 |
| 快照与指纹 | 以导出的 request.txt、context.json 为准 | 文件可能继续修改时 |

本书脚本会保存前几类可确定内容，无法替你查明聊天产品暗中加入的全部上下文。能观察到的如实记录，无法确认的写明未知。

摘要还需记录生成方式、依据和删掉的关键信息。人工摘要、模型摘要和程序摘录的形成过程不同，不能都写成“原始材料”。

## A.3 恢复工作所需的交接单

交接单的第一行先写现在停在哪里，接手者便不用读完整聊天记录再猜。

```text
当前停在：已准备验证输入，尚未发送模型请求。
任务目标：比较 A/B 提示在固定七题上的表现。
已有文件：列出计划、输入目录、冻结判据的位置。
实际完成：输入已导出；离线检查入口已核对。
尚未完成：实际环境确认、模型响应、逐项评审、配对汇总。
不得重复：如果已有成功工具回执，先核对操作号与状态，再决定是否重跑。
下一步：读取计划，确认环境；按编号运行尚未开始的请求。
变化处理：材料或提示需要调整时，新建计划，不覆盖当前输入。
```

如果当前已经在运行模型，把实际完成编号、故障编号与未运行编号分别列出。“大部分做完”不便于恢复。对于文件修改，附候选版本或指纹；对于外部操作，附可核查的操作号和回执。

交接单应指向现存文件，不要把所有原始日志再复制一遍。文件是证据，交接单负责让人知道先看哪一份。
