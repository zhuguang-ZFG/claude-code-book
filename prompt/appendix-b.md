# 附录 B：实验记录与核对依据

<!-- block: prompt-apxb.b-opening -->
实验记录要能把一次响应还原到对应的任务、输入和运行条件。下面列出随书工具保存的内容，以及仍需操作者补充的实际环境与人工判断。

## B.1 一次运行对应哪些文件

`lab.py prepare` 为每次运行建立独立目录。文件名中的题号、重复次数和提示版本，应与原始响应一一对应。

| 文件 | 作用 | 保存时机 |
| --- | --- | --- |
| plan.json | 题目、次数、顺序、环境说明和文件指纹 | 运行前 |
| criteria.json | 本次冻结的逐题人工判据 | 运行前；只给评审者 |
| request.txt | 实际待发送文字 | 运行前 |
| context.json | 当前提供的材料、遗漏来源与输入信息 | 导出时 |
| response.txt | 原始响应，不修格式或内容 | 每次收到响应后 |
| reviews.jsonl | 人工评审结果、说明和响应指纹 | 检查后 |

JSONL 是一行一个 JSON 对象的文本格式，适合逐次追加记录。不要把多行排版的 JSON 对象直接插入其中。使用 `lab.py review` 可以按工具约定写入。

保存响应时保留原始围栏、错误字段和错误文字。若产品另有工具轨迹或错误详情，单独存入同次运行的附件，再在评审说明中引用。只有最终文字时，应明确证据范围。

## B.2 评分状态的含义

| 状态 | 含义 | 示例 |
| --- | --- | --- |
| pass | 机械检查和所有人工必需项均满足 | 冲突两侧都有依据，未擅自选定容量 |
| fail | 已获得响应，但有不符合 | JSON 合法，却把未确认房间写成 201 室 |
| error | 实际请求或运行发生故障 | 已发送请求后服务超时，无正常响应 |
| missing | 尚未运行或尚未完成评审 | 计划中存在该编号，但没有评审记录 |

error 保留在计划次数的分母中，并单列数量；missing 让汇总保持不完整。没有开始的请求不应被标为服务故障。模型拒绝回答是否属于 fail，取决于任务判据；不能仅凭“拒绝”这个词把它改成基础设施错误。

机械检查可以发现类型、字段、题号和逐字引文不符合，不能完成所有事实判断。回答“收费”却引用“免费”的情况，在[第 16 章](ch16.md)有完整示例。人工评审要读结论与引文的关系。

## B.3 写一条可追查的评审说明

“不够好”无法帮助复查。说明应指出哪个必需项未满足，摘录相关输出，再指向材料。例如下面只是人工记录样式，不是某个模型的结果：

```text
结果：fail
未满足：V01 必须保留两种容量及对应依据。
观察：响应只引用通知甲的12人，并写成最终容量；没有处理通知乙。
依据：X01-v1 的两份通知同批发布，现有材料无法确认有效版本。
后续：保留原始响应，不补写引文；在下一版提示中研究冲突处理。
```

对应的命令形式是：

```text
python prompt/examples/lab.py review <实验目录> <运行编号> --outcome fail --note "填写实际未满足条目、响应原句与依据"
```

脚本拒绝同一编号重复登记。如果人工评分有误，保留原始记录，另做一份说明或复核副本，注明改判原因。不要把旧记录覆盖成无法看出更正。

## B.4 当前证据与待补内容

本册[验证目录](evidence/README.md)保留名额程序、上下文导出、机械检查边界和未运行计划的实际结果。名额故障版 8/12、参考版 12/12，比较对象是程序实现。三种 D02 输入长度来自导出脚本，单位是字符和字节。模型对照的 28 份输入已经准备，但模型调用为零。

真实模型实验还需要补充产品与模型标识、可控制参数、实际输入、首轮与重复响应、工具轨迹、人工判读，以及能够获取的用量和费用。无法获取的量保持未知，不以估算冒充账单。

实验结束后，再检查计划中每个编号是否都有记录。重新打开保留的响应，确认指纹仍然匹配。哈希可以发现内容改变，却不能证明响应来自某个模型；来源需要实际服务或宿主记录支持。
