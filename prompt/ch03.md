# 第 3 章：让结果便于阅读，也便于检查

<!-- block: prompt-ch03.b-opening -->
居民需要容易读懂的说明，检查程序需要稳定的字段。青禾案例用同一组事实制作这两种输出，并分别核对格式、引文与业务含义。

表格整齐不保证内容正确，JSON 能解析也不保证事实成立。决定输出格式之前，先看下一步谁会使用它：居民读通知，组织者核对事实，程序保存记录。不同用途需要的结构并不完全相同。

先手工整理 N01-v1，再用随书工具检查结果。下面的 JSON 示例都能保存成普通文本文件；没有编程经验，也可以按字段逐项阅读。

## 人读的结果应当突出决定

居民最关心何时参加、去哪里、是否收费、何时截止报名。如果让他先读来源编号和字段名，再从中拼出安排，结构虽然严谨，却增加了阅读负担。

给居民的说明分成两小段就能看清安排：前一段写时间、地点和材料，后一段写报名与候补。组织者还要核对来源和状态，可以另附一张表：

| 事项 | 内容 | 来源与状态 |
| --- | --- | --- |
| 活动时间 | 2026 年 12 月 5 日 14:00—16:00，北京时间 | N01-v1，已给出 |
| 具体房间 | 尚未确认 | N01-v1 明确说明 |
| 报名截止 | 12 月 4 日 18:00 | N01-v1，已给出 |

表里用“尚未确认”说明房间状态。如果留成空格，接手者无法判断是没读到、忘了填，还是材料确实没有信息。

若后续系统需要把未知存成 `null`，应在字段约定里解释它的含义。不要在同一个字段中随意混用空字符串、零、`null` 和“无”；“费用为零”与“费用未知”尤其不能共用一个值。

## 先约定字段，再写示例

随书检查工具使用四个字段保存答复与依据。它的用途限于检查任务输出，不承担完整报名数据库的功能：

| 字段 | 内容 | 为什么需要 |
| --- | --- | --- |
| `case_id` | 题目编号字符串 | 防止把另一题的答复放错位置 |
| `answer` | 非空说明文字 | 保存要交给读者的内容 |
| `evidence` | 来源 ID 与逐字引文的数组 | 让人能回到实际提供的材料 |
| `actions` | 本轮实际执行的动作数组 | 本章只整理，因此必须为空 |

数组用方括号表示，可以保存多项。对象用花括号表示，通过字段名说明每个值是什么。JSON 的字段名和字符串使用英文双引号，末尾不能多一个逗号，也不能插入解释性注释。

下面是人工编写的简短教学记录，只回答“费用与地点”，用来说明结构；它没有覆盖开发题 D01 的全部交付要求：

```json
{
  "case_id": "D01",
  "answer": "活动免费，地点为青禾社区中心，具体房间尚未确认。",
  "evidence": [
    {"source": "N01-v1", "quote": "活动免费"},
    {"source": "N01-v1", "quote": "地点为青禾社区中心，具体房间尚未确认。"}
  ],
  "actions": []
}
```

当你要求模型采用这个结构时，应同时给出字段约定和真实材料。只有示例而没有规则，模型可能把 D01、某个固定句子或两条引文当成所有任务都要照抄的内容。

## 跑一次机械检查

从仓库根目录导出 D01 的输入：

```bash
python prompt/examples/lab.py context D01 --out .scratch/prompt-format-d01
```

打开输出目录，`request.txt` 包含任务、材料和字段约定；`context.json` 记录实际提供的内容。将上面的人工 JSON 保存为同目录的 `response.txt`，文件只包含花括号里的 JSON，不包含本书排版所用的代码围栏。

```bash
python prompt/examples/lab.py check .scratch/prompt-format-d01/context.json .scratch/prompt-format-d01/response.txt
```

检查程序会判断字段是否齐全、类型是否正确、题号是否匹配、引文是否逐字存在于这次提供的来源，以及动作数组是否为空。它会返回 `mechanical_ok` 和 `manual_review_required`。后一个字段始终提醒你继续做人工语义复核。

现在只把 `answer` 改成“活动收费 500 元”，保留“活动免费”这个引文，再运行检查。引文仍然真实存在，机械条件仍可能满足，答案却明显错误。读到 `mechanical_ok` 时，还不能据此认定回答正确。

接着试试删除 `case_id`，把 `evidence` 改成字符串，或者在 JSON 前面加一句“以下是结果”，观察格式检查怎样失败。修复时要找准位置：缺字段就补字段，事实有错就回查材料；一项改对了，不会让另一项自动合格。

## 三种约束分别起什么作用

提示中的格式要求，是把输出约定告诉模型。模型是否遵循，需要看响应。产品或接口提供的结构化输出能力，则可能在生成或返回阶段约束字段与类型；支持哪些约束，要按具体版本核对。本书的离线脚本没有调用这类接口。

程序校验发生在拿到结果以后。它可以拒绝不符合格式的内容，也可以检查已经写成程序的业务规则，但不能自动理解任意自然语言结论。三者可以配合使用，作用位置不同：

```mermaid
flowchart LR
    A[任务与材料] --> B[提示约定<br/>告诉模型输出什么]
    B --> C[获得原始响应]
    C --> D[程序检查<br/>字段、类型、逐字引文]
    D --> E[语义与业务核对<br/>事实、遗漏、动作依据]
```

即使采用了接口级结构化输出，也要完成后两步。合法字段里可以放错误日期，符合类型的数字也可能超过容量。对于本书名额程序，人数不得超过容量是可计算规则；对于“一段引文是否足以证明这句话”，仍需更具体的语义判断。

## 格式失败后怎样保留记录

如果真实模型返回了带围栏的 JSON，而约定要求只有对象，应保存原始响应并记录失败。你可以另写修复程序去除围栏，但那是新增的处理步骤，需要保存修复规则与修复后的文件。不要覆盖原始响应后说模型第一次就符合要求。

人工整理阶段可以直接改草稿；比较提示效果时则要保留首次结果。这两个场景的记录要求不同，不能把“为了交付而编辑过的最终稿”拿来冒充某版提示的原始表现。

再做一个练习：把居民说明压缩成两段，同时保留完整核对表。先检查表格是否漏了截止钟点，再检查正文有没有把“可自带”改成“须自带”。将格式问题、事实问题、遗漏问题分列，而不是只给一个“不错”或“不准确”的总评。

在每处问题旁写下它出现在哪一层，以及需要改字段、补材料还是改任务。下一章继续使用示例说明输出要求，同时检查示例本身有没有夹带错误事实。
