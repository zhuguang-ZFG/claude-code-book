# 第 9 章：需要哪一步中间结果，怎样核对

<!-- block: prompt-ch09.b-opening -->
拆解任务时，每一步都应留下后一步能使用、别人也能检查的结果，避免把未经核对的判断一路传到最终答复。

居民问：“我现在报名还能拿到正式名额吗？”如果助手只看到活动通知，它知道容量为 12，却不知道当前正式名单有多少人。此时继续写一段热情的报名答复，无法补上缺失的名单。任务需要先取得有效状态，再应用规则，最后向居民解释。

用本地的小名单就能练习这个顺序，观察结论怎样从输入走到输出。代码与文字都可以成为中间结果，只要它们足以支持下一步。

## 哪些步骤真的有依赖

先把任务写成“材料核对—状态判断—结果说明”三个动作。它们之间传递的内容分别是有效规则、名单状态和处理结果。

```mermaid
flowchart LR
    A[规则与输入] --> B[检查字段与状态]
    B --> C[检查重复申请]
    C --> D[按容量或取消规则处理]
    D --> E[核对新名单]
    E --> F[写给读者的说明]
```

这张图的顺序来自青禾规则。编号已经在正式或候补名单中时，应返回 duplicate；不能先发现名额满了，就把它再放入候补。输入本身不合法时，也不能绕过检查，继续计算所谓的剩余名额。

任务拆解不必越细越好。把“读文件”“想一下”“再认真想一下”列成三个步骤，没有新增可检查成果。只有当拆分能暴露一个独立判断，或者允许使用不同工具核验时，才值得增加一道交接。

## 从一个具体输入算起

打开 [full-request.json](examples/full-request.json)。容量为 2，正式名单为 Q01、Q02，候补为空，Q03 申请报名。根据 [R01-v1](materials/rules-v1.md)，可以留下以下简短记录：

| 中间判断 | 依据与结果 |
| --- | --- |
| 输入是否合法 | 容量是非负整数，名单无重复，正式人数未超容量 |
| 是否重复申请 | Q03 不在正式或候补名单中 |
| 剩余名额 | 2 − 2 = 0 |
| 应采取的状态转换 | 正式名单保持不变，Q03 追加到候补 |

这已经足够解释为什么进入候补。读者不需要看一大段不可核对的内心独白，只需要知道采用的规则、输入值、必要算式与最终状态。

如果某一步给出错误，后面的文字仍可能很流畅。例如把“正式人数等于容量”理解成“还可以再收一人”，最终答复就可能写成“您已成功报名”。流畅不能修复前面的边界判断；应回到产生分歧的那个判断点。

另一个输入是正式名单 Q01、Q02，候补 Q03，Q03 再次申请。此时容量仍为 2，但无需重新分配名额。R2 已经决定返回 duplicate，并保持两个名单不变。这说明中间检查既能补充依据，也能让后续步骤在适当位置停止。

## 把中间结果交给下一步

如果用两个请求串接任务，第一步可以先输出状态判断，第二步只负责解释。下面是人工编写的第一步任务：

```text
依据 R01-v1 检查给定报名输入。
先判断输入是否合法；合法时，再判断是否重复申请。
需要分配名额时，给出人数与容量的算式。
输出：采用的规则编号、输入事实、应有状态和名单变化。
没有实际执行程序时，明确标为规则推演。
```

第二步接收经过核对的结果：

```text
把已核对的状态判断改写成给申请人的简短说明。
保留“候补”“重复申请”或“信息不足”的实际状态。
不要把规则推演写成已完成报名，也不要补写通知发送记录。
```

串接时有一个容易忽略的问题：第二步可能没有看到原始规则，只看到第一步的摘要。如果第一步把“候补队首”漏成了“任选一人”，第二步就无从纠正。对关键条件，应把规则编号与对应原句随中间结果一起传递，或让第二步能够回查原文。

同一模型连续完成两步，不等于获得了两次独立验证。后一步可能沿用前一步的错误。需要独立依据时，可使用公开规则、算术检查、实际程序执行或另一位审阅者，而不是仅仅追加一句“检查上面的答案”。

## 用程序检查状态变化

在仓库根目录运行：

```bash
python prompt/examples/workshop.py prompt/examples/full-request.json --mode faulty
python prompt/examples/workshop.py prompt/examples/full-request.json --mode reference
```

故障版会把 Q03 放进正式名单，参考版把它放进候补。此时你拥有两种证据：根据规则写出的预期，以及程序真正返回的结果。发现不一致时，应把二者并列保存，不能为了让说明看起来正确，只贴参考结果。

也可以运行同一组十二例：

```bash
python prompt/examples/check_workshop.py --mode faulty
```

这条命令会发现满额、零容量、候补重复、取消递补四种不符合。测试用例已经列明每个输入与预期，读者可以逐例核对。预期直接依据规则编写，没有调用故障实现生成；遇到分歧时，应回查对应规则。

程序检查仍有范围。它不判断一个真实报名者是否有资格参加，不知道当前日期是否已经过了截止时间，也不会向社区发送消息。解释程序结果时，应沿用这个范围，避免从一次名单计算扩展成完整报名已办理。

## 哪一步值得交给工具，哪一步留给人

明确的整数计算、名单去重和字段检查适合程序处理。判断两份通知是否有权相互替代，需要核对发布关系；决定一段对居民的说明是否容易误读，则需要阅读和编辑。把它们放到各自适合的位置，能减少同一种错误被反复加工。

可以给中间结果设置停止条件。例如规则文件缺失，就先报告无法判断；输入不合法，就返回 invalid；检查发现实际输出与预期不同，就先保留差异，停止使用那份输出起草成功通知。停止条件应针对具体缺口，避免把所有问题都变成一句模糊的“需要进一步确认”。

对于只需两行回答的简单任务，一次请求同时给出结论与依据可能更合适。拆成许多轮会增加时间、上下文传递与格式出错的机会。采用链式提示之前，先说明哪一步需要单独验收；如果说不出来，暂时不拆也没有损失。

## 练习一条取消路径

设容量为 2，正式名单 Q01、Q02，候补 Q03、Q04，现在取消 Q01。先写出你自己的规则推演，再运行或检查对应程序。最终应关注三个变化：Q01 从正式名单移除，Q03 从候补队首递补，Q04 保持在候补中。

不要只检查正式人数仍为 2。一个程序把 Q04 提前递补，也可能满足人数限制，却违反顺序规则。中间结果必须覆盖任务真正关心的条件，不能只选最容易通过的一项。

保存这次输入、预期、实际结果和差异说明。下一章会把这类执行整理成真实工具回执，让“准备运行”“已经运行”和“运行失败”在记录里有明确区别。
