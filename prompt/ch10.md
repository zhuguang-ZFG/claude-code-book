# 第 10 章：从“建议执行”到真实工具回执

<!-- block: prompt-ch10.b-opening -->
一次工具调用要留下实际命令、输入版本、退出码和输出；助手的计划与成功描述都不能替代这些回执。

“我会运行检查”出现在回答里，只说明助手提出了一个动作。它是否真的启动程序，程序有没有找到文件，返回了什么，都需要另外观察。在 Agent 任务中，读者最容易跳过的正是这段过程：看到最后一句“检查通过”，就把前面的动作当成已经发生。

本章准备一个独立的报名练习目录，真实执行其中的检查程序，再故意观察缺文件、语法错误和超时的区别。你可以直接在终端操作，不需要模型账户。

## 准备可独立运行的副本

在书籍仓库根目录执行：

```bash
python prompt/examples/exercise.py prepare --out .scratch/prompt-repair
```

输出目录必须尚不存在，工具不会覆盖旧练习。生成的副本只有五个文件：

```text
prompt-repair/
  registration.py
  check.py
  cases.json
  rules.md
  exercise-lock.json
```

`registration.py` 是要审查的故障实现，里面没有切换到参考答案的选项。`rules.md` 保存业务规则，`cases.json` 保存十二个公开输入与预期，`check.py` 逐例执行候选程序。`exercise-lock.json` 记录规则、用例和检查入口的指纹。

公开用例用于学习和回归。读者可以阅读预期，但不能将“看过公开预期后通过”描述成未见测试表现。后面的留出题与这里的代码练习属于不同验收层次。

## 让程序给出回执

运行下面的命令。回执文件名也必须是新的，以免把修前结果覆盖掉。

```bash
python prompt/examples/exercise.py check --project .scratch/prompt-repair --receipt .scratch/prompt-baseline.json
```

包装工具会在练习目录启动真实 Python 子进程，运行 `check.py`。它保存实际执行命令、工作目录、候选代码指纹、标准输出、标准错误和退出码。标准输出通常放检查结果；标准错误通常放解释器或运行故障，两者都需要保留。

本书实际执行初始副本得到 `business_failed`，子进程退出码为 1，通过数为 8/12。完整记录见[独立练习实测](evidence/exercise-verification.json)。这是预设故障被检查发现后的结果，不能在报告里写成“测试工具无法运行”。

进入练习目录后，也可以直接运行：

```bash
python check.py
```

直接运行便于观察，但不会得到外层工具保存的完整回执。提交给下一位读者时，应保留带命令、输入指纹和退出码的记录，让他能够确认这份结果针对哪一版代码。

## 读懂不同的失败

同样是“没通过”，下一步可能完全不同。包装工具把几类情况分别记录：

| 状态 | 实际含义 | 合适的后续处理 |
| --- | --- | --- |
| passed | 子进程正常返回，公开十二例均通过 | 继续审查改动范围与尚未覆盖的情形 |
| business_failed | 程序跑出了结果，存在业务不符合 | 查失败输入、预期和实际名单 |
| invalid_project | 项目缺文件或冻结文件发生变化，尚未启动检查 | 修正路径或核对版本，不编造业务分数 |
| execution_failed | 启动或解释执行失败，未获得合格检查报告 | 查看标准错误与退出码 |
| timeout | 等待超过指定时间，子进程被终止 | 保留这次尝试，定位卡住原因 |
| input_changed_during_check | 执行期间代码或冻结材料变化 | 这份结果不能作为稳定版本的验收 |

本次离线实测还准备了三种故障：检查不存在的项目、把候选文件写成语法错误、让候选导入时等待五秒并设置 0.1 秒超时。它们分别得到 invalid_project、execution_failed 和 timeout。五秒等待是人工构造的测试，不是模型响应慢的证据。

超时记录的子进程退出码为 null，表示没有获得正常结束的代码。不能把它填成 0，也不能把它当成十二例全部失败。任务没有完成，原因在执行层，需要单独记录。

## 给 Agent 的动作说明要有参数

如果由 Agent 帮忙调用本地检查，可以使用下面的任务。先把目录名改成真实副本路径，并确认宿主具备相应的本地命令权限。

```text
检查指定练习副本，暂不修改候选程序。
只运行 exercise.py check，project 使用给定目录，receipt 使用新的基线文件名。
保存真实命令、退出码、stdout、stderr 和回执路径。
若项目不完整、冻结文件变动或发生超时，说明原因并停止重试。
若是业务不符合，列出失败输入，不把它称为工具故障。
不要改测试预期，也不要把未执行的动作写成已完成。
```

本章的包装命令默认最多等待十秒，也可通过 `--timeout` 指定正数。增加等待时间是一项运行设置变化，应该注明原因，不能在看到失败后悄悄多跑几次，只留下最好的回执。

动作与观察可以组成循环：请求检查，读取回执，针对发现修改，再次检查。循环要有终点。例如这一轮只做基线，不修复；修复轮最多验证一次候选，失败则列出剩余问题。具体次数由任务规模决定，不要把“持续尝试直到成功”当成默认要求。

## 重试之前确认动作是否可重复

当前检查主要读取文件并计算结果，可以重复运行，但新的回执应使用新名字。准备目录会写文件，重复调用则被明确拒绝。真实报名的取消与通知发送又是另一类动作，不能套用相同重试规则。

回看 [T01-v1](materials/receipts-v1.md)：t-02 已记录 cancel-07 成功，恢复时只需整理说明。若请求已发出而结果未知，应先根据操作号查询；没有查询方式，就保留未知状态。否则一次网络超时可能被错误解释为“服务没执行”，导致重复动作。

程序返回“not_found”也不自动说明此前取消失败。它可能意味着编号原本不存在，也可能意味着前一次取消已经成功。判断原因需要历史状态或操作记录，不能仅凭当前返回词猜测。

## 检查工具也有边界

这套包装器适合在自己控制的教学副本上记录结果。它会核对冻结文件是否改变，却不是隔离恶意代码的沙箱。Python 候选代码仍以当前账户权限执行；一个刻意伪造输出的候选也不能仅凭打印的分数获得可信验收。真实项目需要宿主权限限制、独立检查和代码审阅共同支撑结论。

指纹同样只能帮助确认内容变化。若有人同时修改用例和锁文件，单靠本地自检无法证明规则未被改写。交付时应保存独立的原始基线，或让审阅者从固定版本取得检查材料。

打开自己的基线回执，核对里面的命令、候选指纹与失败输入，再与当前文件比较。保留这份记录，[第 11 章](ch11.md)的审查报告会用它确认问题，修复后的结果也要与它对照。
