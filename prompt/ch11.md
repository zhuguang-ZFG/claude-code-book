# 第 11 章：审查与修复怎样分开交代

<!-- block: prompt-ch11.b-opening -->
先用规则和触发输入确认问题，再限定修复文件并复跑相同用例，可以让改动的原因与效果都留得下来。

把一段代码交给助手说“看看有没有问题”，它可能直接提交一份新实现。即使新代码能运行，你也未必知道原问题在哪、它改了多少东西，以及测试为什么通过。对于要学习和审阅的任务，先留下缺陷报告，会更容易判断后续修复是否对准了问题。

本章继续使用[第 10 章](ch10.md)生成的独立副本。故障实现没有参考模式开关，助手必须根据规则处理代码，而不能把参数从 faulty 改成 reference 就宣称修复完成。

## 先规定只读阶段的产物

让审查者阅读 `rules.md`、`registration.py`、`cases.json` 和已经取得的基线回执。先读规则，再看实现，可以减少把代码现状当成业务要求的机会。

```text
请只读审查报名练习副本，不修改文件。
业务要求以 rules.md 为准；公开用例用于复现，不能修改预期。
每个发现写出：规则编号、触发输入、预期、实际行为、代码位置和影响。
有真实回执时注明运行证据；没有运行时注明静态推演。
把同一原因导致的多例失败归在一起，但保留各自输入。
最后列出尚未验证的范围，不提交修复代码。
```

“代码位置”可以是函数名和相关语句，不必完全依赖行号。后续增加注释可能改变行号，但 `transition` 中的容量判断仍然能被找到。使用行号时同时保存文件版本，避免审阅者定位到另一段代码。

文本要求只读还需要宿主配置配合。如果角色仍拥有写文件工具，提示中的“不要改”只是行为要求，不能当作实际权限隔离。使用具体工具时，核对它支持的读取、命令和写入范围；没有执行权限的审查者可以阅读别人提供的回执，不能假装自己跑了测试。

## 一份有证据的缺陷报告

初始副本运行十二例，通过八例。四个失败可以归为三个实现问题。以下是根据实际程序输出整理的人工审查示例，不是模型审查成绩。

| 发现 | 触发与预期 | 当前表现 |
| --- | --- | --- |
| 容量边界允许超额 | 满额或零容量时，新申请应候补 | `<=` 让等于容量时继续加入正式名单 |
| 重复检查遗漏候补 | Q03 已在候补，再申请应 duplicate 且名单不变 | 只检查正式名单，Q03 被再次处理 |
| 取消正式名额后未递补 | 取消 Q01，候补队首 Q03 应进入正式名单 | 仅删除 Q01，候补保持原状 |

第二个问题可能与第一个问题共同影响同一个输入。候补重复用例中，程序既没有识别重复，又因容量判断错误把 Q03 加入正式名单。报告应说明这条路径，不必硬把每个失败归成互不相关的独立错误。

这也解释了为什么不能只按“失败例数减少”确认每个缺陷都修好。若只修容量比较，重复申请可能从错误转正变成重复候补，仍然违反 R2。需要重新观察同一个输入的完整名单，而不是只看状态词有没有改变。

## 修复任务要限定可改范围

确认报告后，另写修复任务：

```text
依据已确认的三项发现，只修改练习副本中的 registration.py。
保持 transition 的输入字段和输出字段；不得修改 rules.md、cases.json、check.py 或锁文件。
保留原始基线回执。
修复后用同一公开用例检查，回执写到新的文件。
交付改动说明、修前修后逐例差异和剩余限制；不能只给“已完成”。
```

文件范围让审阅者知道应该检查哪里。保持接口是为了让原检查程序仍能调用候选；禁止改预期是为了让修复对照保留共同标准。若实现确实发现规则矛盾，应先把矛盾单独提出，不能在修代码时悄悄改业务要求。

小修复也不意味着必须压成最少字符。有时把一段条件改得更清楚，比保留难懂表达更容易维护。但每个改动都应能对应已确认问题，避免同时重写整个程序、调整输入格式和添加无关功能，让结果难以比较。

## 检查改动与实际结果

修复后的回执使用新文件名：

```bash
python prompt/examples/exercise.py check --project .scratch/prompt-repair --receipt .scratch/prompt-after.json
```

本书为验证教学工具，由作者人工完成三处修正，再运行相同检查，实际得到 12/12，退出码为 0；原始故障副本为 8/12，退出码为 1。两份完整回执保存在[离线修复记录](evidence/exercise-verification.json)。这里证明公开业务检查能区分这两个候选，未证明某个模型已经自主完成修复。

读者自己的结果必须重新运行，不能把书里的 12/12 复制进交付说明。检查之后还要阅读代码差异：是否只是修了三处逻辑，是否增加了固定识别 Q01、Q02 的特例，是否修改了输入对象，是否引入额外文件或外部调用。

公开十二例全部通过也可能掩盖针对题目硬编码的实现。可以再按规则检查性质：无论编号怎样变化，正式人数都不能超过容量；同一编号重复报名不能增加总人数；取消正式名额时，候补顺序应保留。新增检查应说明它验证的规则，避免机械复制实现的每个分支当成答案。

## 一种修复成功的假象

如果把检查器里的“预期候补”改成“预期正式”，故障实现就可能得到更高分。实际问题仍在，只是尺子被换了。本章包装工具会检测规则、用例或检查入口的意外变化，停止执行并返回 invalid_project。

这个保护有明确范围：锁文件和冻结文件都由同一人任意修改时，工具无法提供独立可信证明。因此，审阅时仍要把它们与原始副本或固定版本比较。把基线放到候选可随意覆盖的位置，也会削弱修前修后的可追查性。

另一个假象是只展示新增的成功用例，不复跑原失败输入。若候补重复和取消递补仍然失败，“普通报名已经成功”并没有完成修复。回归的含义就是让原来会触发问题的输入再次经过新实现，同时检查此前通过的情况有没有退步。

## 交付一个能复查的修复

最终说明可以很短，但应写清三个问题的处理、实际执行命令、检查结果和范围。比如：“正式名额判断改为严格小于容量；重复检查同时覆盖两份名单；取消正式名额后按候补队首递补。公开十二例通过，规则与检查文件未改动。未覆盖真实并发、身份认证和持久化。”

如果还有失败，就保留失败输入和当前原因，不要把“已经找到问题”写成“已经修好”。另一位操作者应能从候选文件和回执复现你说的结果，而无需回到原会话询问每一步。

现在可以把这套重复过程保存成项目资源。[第 12 章](ch12.md)会区分长期规则、单次任务和 Skill，避免每次审查都重新拼一份长提示。
