# 第 12 章：把有效做法保存成项目规则与 Skill

<!-- block: prompt-ch12.b-opening -->
稳定的业务规则与可重复的审查步骤应分别维护，单次任务再指定目标文件和范围，减少复制旧提示时带入过期要求。

你已经完成一次报名程序审查。下一次换成取消逻辑，仍需要提醒助手读规则、给出触发输入、区分静态推演和运行结果。把上一轮整段对话复制过来虽然方便，也会带入旧文件名、旧回执和已经解决的问题。

更合适的保存方式，是把会重复使用的部分从本次工作状态中取出来。青禾的业务规则、审查方法和“今天改哪个文件”并不具有同样的寿命，放到同一个长提示里，维护时容易误改。

## 先把三种内容分开

`rules.md` 说明报名怎样才算正确：容量、重复、候补和取消规则。它能被程序员、测试者和文案整理者共同使用。审查方法说明怎样检查一份实现：先读规则，再列边界输入，核对实际输出。单次任务则指定这次读取哪个副本、是否允许修改、产物保存在哪里。

| 内容 | 合适的存放位置 | 变化时要检查什么 |
| --- | --- | --- |
| 名额与取消规则 | 版本化业务材料 | 用例预期和居民说明是否需要同步 |
| 项目工作习惯 | 项目说明文件 | 是否与实际目录、命令和权限相符 |
| 一类任务的方法 | Skill 或可复用任务文档 | 入口、辅助文件与输出要求是否仍可用 |
| 当前进度与下一步 | 任务说明、交接单 | 文件是否存在，状态是否过期 |

不要把“本轮 Q03 的申请失败”写成永久项目规则，也不要把“每人限一个名额”只留在某次聊天里。判断一条说明该放哪里，可以问它在下一次类似任务里是否仍然成立。

## 项目说明写可执行的约定

项目说明无需列出所有可能的好习惯。对当前练习，下面几条已经能减少具体错误。这是教学样稿，文件是否会被工具自动读取，要按实际宿主确认。

```markdown
# 青禾报名练习工作约定

业务依据见 rules.md，公开回归用例见 cases.json。
审查阶段只读；进入修复阶段后，默认只修改 registration.py。
不要通过修改预期、删除失败用例或覆盖基线回执让检查变绿。
运行结果保留命令、输入版本、退出码和原始输出。
未运行的检查写明未运行；静态推演不得写成实际回执。
新增业务要求先记录规则版本，再同步用例与实现。
```

这里没有写“保证质量”“严格遵循最佳实践”，因为这些词不能告诉助手遇到一个具体问题时该怎么做。文件范围、依据和记录要求则能直接用于审阅。

不同工具的项目文件名、查找层级和加载时机不相同。不要因为一个产品识别 `AGENTS.md`，就假定任何聊天窗口都自动读取它。最基本的验证是观察新任务里实际加载的材料；无法观察时，可以显式提供文件，并把验证状态记清。

## 把审查方法整理成一个小资源包

通用的资源组织可以是：

```text
review-registration/
  SKILL.md
  references/
    rules.md
```

入口正文先说明适用任务，再写必要步骤和产物。下面的内容可以作为方法草稿；开头的元数据字段需按所用宿主格式添加，不能直接声称这是所有产品都支持的安装包。

```markdown
# 审查报名状态转换

适用：依据明确业务规则，审查本地报名或取消函数。
不适用：替组织者决定新政策，或直接处理真实报名数据。

先确认目标文件和任务范围，读取 references/rules.md。
按规则列出正常、边界、重复和取消输入。
将预期与实现逐项比较；有执行权限时使用指定检查入口。
每项发现给出规则编号、触发输入、预期、实际行为和位置。
没有实际执行时注明静态推演。
只读任务输出报告；修复须由当前任务另行指定文件范围。
```

相对路径有一个实际作用：资源包移到另一台电脑后，入口仍能找到自己的辅助材料。但路径写对不等于内容同步。若项目规则已到新版本，而 Skill 里还复制着旧规则，应当明确哪份是依据，并重新核对预期。更长期的做法可以只保留一份权威规则，再用可维护的引用方式提供给任务。

描述字段应让工具知道何时选择这个资源。写“万能专家，解决所有问题”会使适用范围模糊；写“依据业务规则审查本地报名状态转换，输出可复现缺陷”则能表达具体用途。正文负责方法，描述负责发现，两处不必重复整段步骤。

## 接到一个具体宿主时

本系列 [Kimi Skill 章节](../kimi/ch09.md)固定讨论 Kimi Code 2.5.2，并给出目录入口、元数据和普通技能发现方式；[只读角色章节](../kimi/ch10.md)说明工具列表；[插件章节](../kimi/ch11.md)说明打包、安装副本与重新加载。需要在 Kimi 中实践时，按这些固定版本资料接入，不把本章通用草稿当成已安装的技能。

固定资料的上游入口是 [Skill 格式说明](https://github.com/MoonshotAI/kimi-code/blob/1c142a007c10e881602690def96057c23a2baa12/docs/en/customization/skills.md)。本章使用它说明一种具体资源格式；这里没有重新运行 Kimi 的完整模型审查，也没有验证其他工具读取相同文件后的效果。

接入时检查四件实事：宿主发现了哪个目录，显示的技能名称是什么，正文能否找到规则，角色有没有运行步骤所需的工具。比如只读角色没有命令工具，却被 Skill 要求“必须运行测试”，说明这两份配置不相容。可以改为阅读已提供回执，或在实际授权范围内另设能执行检查的角色。

Skill 本身不能授予文件写入、网络访问或发布权限。正文要求“测试后发送通知”，并不构成用户对通知发送的授权。动作必须同时满足当前任务范围与宿主权限；这也是为什么稳定方法中不宜埋入针对某一次工作的外部操作。

## 验证复用是否真的省事

先用一个新副本做小试验：只给任务目标与资源入口，观察它能否定位规则、输出带触发输入的报告，并正确标明没有执行的检查。再换一个不同的边界输入，避免只对上次失败的 Q03 做出正确答复。

没有模型环境时，可以先做文件与流程检查：目录是否完整，相对路径是否成立，所列命令能否在指定工作目录运行，规则是否与用例一致。这些检查有价值，但不能写成“模型已经稳定调用 Skill”。真实调用需要另外保存宿主版本、输入和输出。

如果每次调用都还要追加大量解释，回头看是方法缺了步骤，还是任务本身发生了变化。前者适合修订 Skill，后者应留在单次任务中。把所有特例塞进资源入口，会让它越来越难读，也更容易带入不相关要求。

## 一次升级怎样留下变化

假设组织者要求把“同一人取消后可以重新申请”明确写入规则并补充用例。当前规则和实现已经允许这一行为，仍值得核对它与稳定编号、候补顺序的关系。审查步骤可能不用改，只需确认它会读取正确版本，并检查用例是否覆盖这一转换场景。

交付时记录资源版本、规则版本和实际验证范围。若某个宿主升级后改变了发现目录或字段格式，应先在新环境检查加载，再沿原任务复测。不要因文件仍叫 `SKILL.md`，就认为行为一定沿用。

如果准备让多个 Agent 使用这份资源，还需分别给出目标文件、允许修改的范围和交付位置。同一份方法不会替它们分配文件归属，这部分将在[第 13 章](ch13.md)展开。
