# 第 13 章：多个 Agent 如何分工、合并和接手

<!-- block: prompt-ch13.b-opening -->
把规则核对和代码审查交给不同的 Agent，可以让两项独立工作同时推进。能否节省时间，取决于每个人拿到什么材料、允许改哪些文件，以及最后由谁核对合并结果。

青禾练习中的报名函数很短。如果只是修正一个边界条件，一个 Agent 通常已经够用。为了练习交接证据，我们把审查拆成两个角度，给出各自的任务包。当前尚未用这些任务包开展真实多 Agent 运行。

## 先找能独立推进的部分

第 11 章的修复练习包含 `registration.py`、业务规则和十二个公开用例。规则审阅者可以检查“每条规则是否有对应的输入”；实现审阅者可以检查“某个输入经过哪些条件分支，会得到什么结果”。两人都只读现有文件，各自交一份发现，彼此不必等对方先写结论。

修复者则需要等问题得到确认后再改代码。如果让三个角色同时修改同一个函数，最后得到的文件可能混入三种方案。即使没有文本冲突，也可能出现逻辑冲突：一人让取消后自动递补，另一人又把递补留给调用者。工具成功合并文本，不表示业务约定一致。

适合并行的边界通常是输入已经齐全、输出相对独立、最后能够核对。若第二步必须使用第一步新产生的结果，它们存在依赖，应先后执行。把尚未完成的规则定义同时交给两个人各猜一份，会增加重新对齐的成本。

| 角色 | 输入 | 可写内容 | 交付给谁 |
| --- | --- | --- | --- |
| 规则审阅者 | R01-v1、公开业务用例 | 自己的规则核对报告 | 汇总者 |
| 实现审阅者 | 同版规则、故障代码、初始回执 | 自己的实现审查报告 | 汇总者 |
| 汇总与修复者 | 两份发现、原文件、复现结果 | 确认后的 `registration.py` | 验收者 |
| 验收者 | 修后文件、冻结规则与用例 | 新的检查回执和验收记录 | 接手者 |

角色数量不等于必须启动的 Agent 数量。一名操作者可以先后完成几个角色；有独立同事时，也可以把验收交给另一人。决定顺序时，先看依赖和成本。

## 给每个角色一份能独立阅读的任务包

在仓库根目录准备新的副本，并保留初始检查回执：

```bash
python prompt/examples/exercise.py prepare --out .scratch/prompt-team
python prompt/examples/exercise.py check --project .scratch/prompt-team --receipt .scratch/prompt-team-before.json
```

初始故障实现预期通过 8/12，检查会记录实际退出状态。这个失败基线说明练习中确实有待修问题，不能为了开局“全绿”就修改用例。

规则审阅任务可以这样交代：

```text
任务：核对本练习的业务规则是否被公开用例覆盖。
输入：副本中的 rules.md、cases.json；以当前冻结版本为准。
范围：只读，不修改规则、用例、检查器或报名函数。
交付：按规则编号列出现有用例、尚未覆盖的边界，以及理由。
没有覆盖不等于实现一定有错；请分开写。
将报告交给汇总者，不直接给另一位审查者追加任务。
```

实现审阅者需要另一份说明：

```text
任务：检查 registration.py 是否符合 rules.md。
输入：故障代码、同版规则、初始检查回执和公开用例。
范围：只读，不修复，不更改评分标准。
每项发现包括触发输入、实际输出、规则预期、代码位置。
不能复现的怀疑单列，不写成已经确认的缺陷。
交付完成后停下，由汇总者决定修复范围。
```

“请结合前面的讨论”不适合独立任务包。新 Agent 可能没有前面的消息；即使产品自动复制部分历史，也应确认包含了哪些内容。把真正影响判断的文件、版本和限制明确列出，比假定共享记忆可靠。

报告放在各自独立路径，例如 `reviews/rules.md` 和 `reviews/implementation.md`。共享工作目录时还要告诉每位参与者：有其他人正在工作，不得恢复、覆盖或清理别人的修改。能使用独立副本或工作树时，可以进一步减少误写；具体配置按所用工具的能力处理。

## 汇总发现时回到原始依据

两份报告可能都指出满额仍放入正式名单，也可能用不同语言描述同一个问题。汇总者先按“触发条件与受影响规则”去重，再在当前文件中复现。下面是一份人工教学记录的结构：

```text
发现 F01：正式人数等于容量时仍接纳新编号。
规则依据：R1、R3。
触发输入：容量2，正式Q01/Q02，候补空，Q03申请。
复现：以本次工具回执为准，附回执路径。
处理：确认后修正容量比较；保留零容量用例检查同类边界。
```

不要因为两个 Agent 都说“有问题”就省略复现。它们可能看了同一份错误摘要，或共享了同一个误解。多份一致意见提供了线索，不能替代原始规则、输入与执行结果。

如果规则审阅者认为“取消后应等待人工批准”，实现审阅者却认为“立即递补”，汇总者应回到 R4。当前规则明确要求立即递补，争议可以据此解决；若规则没有说明，就先向有权决定业务的人确认，不能按角色数量投票决定新规则。

汇总报告还应保留“未采用的发现及原因”。例如某人建议把名额改为 15，那是业务变更，不属于修复已定义行为。简短写明排除理由，可以防止下一位参与者又把相同建议带回来。

## 让修改只有一个清楚的落点

确认问题后，再给修复者完整任务。工作范围限定为 `registration.py`，冻结的规则、用例与检查器继续保持原样。修复者需要知道已经确认哪些问题，也要看到原始回执，不能只收到一句“把所有测试修绿”。

改完以后，用新文件名保存检查：

```bash
python prompt/examples/exercise.py check --project .scratch/prompt-team --receipt .scratch/prompt-team-after.json
```

检查工具会核对冻结文件。如果候选同时改掉预期结果，验收入口应拒绝这种变化。检查通过以后仍查看代码差异：有没有把所有输入都直接返回一个固定答案，有没有改变原状态，是否留下超出练习范围的外部动作。

当两个人必须分别修改不同文件时，先约定文件所有权和接口。例如一人只改实现，一人只补独立说明；跨文件接口变更由汇总者协调。合并后运行集成检查，不能把两个分支各自的通过记录相加，冒充合并状态已经通过。

## 中断时，留下可恢复的状态

假设规则报告已完成，实现审阅还没提交。交接单应写明哪些报告已有文件、哪个任务仍在运行、当前代码指纹、是否允许开始修复。不要把“已分派”写成“已完成”，也不要为了获得整齐结论让新 Agent 重做所有任务。

下一位接手者先读文件和回执，再决定是否重跑。若代码在上次检查后已经变化，应重新检查；若同一次取消操作已经有成功回执，就先核对状态，不能因为会话中断再做一遍。

做完一次协作后，把准备、等待、合并和返工的时间也记下来。有时实际审查只需几分钟，创建多个任务包反而更慢。下次遇到相近任务，可以据此决定一个 Agent 是否已经够用。
