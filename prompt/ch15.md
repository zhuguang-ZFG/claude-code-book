# 第 15 章：先定怎样评，再改一句提示

<!-- block: prompt-ch15.b-opening -->
评测先规定什么结果可以接受，再观察提示是否让这些结果更常出现。青禾案例把题目、评分依据和原始响应分开保存，让一次修改能够被检查，也能被否决。

如果先看到一段流畅回答，再临时决定它哪里算对，评分标准很容易跟着答案走。尤其在你亲手改了提示之后，会更注意候选版做得好的地方，而把遗漏解释成“小问题”。本章先建立判断办法，下一章再运行和比较。

## 从真实用途拆出必需项

V01 的任务是判断同批容量冲突是否已经解决。材料同时写了 12 人和 16 人，又没有能够确认有效版本的信息。一个合格结果至少要呈现两种说法、指出无法裁定、说明需要组织者确认，并保持本轮只整理的范围。

“回答详细”“逻辑清晰”“有帮助”可以作为阅读感受，但无法稳定决定是否允许把数字写入通知。将它们改成可观察的要求后，审阅者才知道哪些错误影响任务完成。

| 模糊标准 | 可复核的标准 | 需要查什么 |
| --- | --- | --- |
| 识别冲突 | 同时指出两种容量，保留对应依据 | 两句来源与响应 |
| 不胡说 | 没有在缺乏版本依据时选定一个容量 | 结论及其支撑 |
| 提出建议 | 明确提出确认有效版本这一下一步 | 建议是否针对缺口 |
| 行为安全 | 没有执行或声称已经发布通知 | 回答、工具轨迹和回执 |

标准不要求回答逐字复述参考稿。只要含义满足任务，表达可以不同。也不要要求冗长解释掩盖信息不全：列出十条活动建议，却没有保留容量冲突，仍未完成当前任务。

## 三组题分别承担不同工作

本册的[开发题](cases/development.json)有三题，用于理解任务和修改提示；[验证题](cases/validation.json)有七题，用于比较候选方案；留出材料有两题，留到方案确定后再打开。划分依据是题目在开发中怎样使用，与难度无关。

开发阶段可以看题、看判据、分析错误，再改提示。验证阶段先冻结候选与标准，再看完整结果决定是否采用。如果看过验证失败以后继续针对这些题修改，记录这个事实；它们已经参与方案选择，不能再当作未见材料。

留出材料需要隔离到实际检验之前。把答案文件移到另一个目录只减少误操作，不构成访问权限。Agent 能读取整个仓库时，仍然可能读到判据。只向待测模型提供单次导出的请求，在宿主中限制额外文件访问；已经看过留出题的人，也应登记暴露。

正式项目可以由另一人保管留出题，或在发布前补写新材料。不要把书中公开题目的分数理解为陌生业务上的预测。这里的题库帮助你学会评测过程，不代表所有活动、文档或工具故障都已覆盖。

## 分开检查格式、依据、含义和动作

`lab.py` 能检查 JSON 字段与类型、题号、逐字引文以及只读任务的动作数组。检查通过只意味着这几项机械条件成立。引用真实存在，仍可能被用于支撑相反结论；这需要人工阅读答案与材料。

青禾的[逐题判据](evaluation/criteria.json)为每题列出必需项。人工评分时逐条检查，全部满足才记 pass；获得了响应但存在不符合，记 fail；真实调用发生故障、无法获得正常响应，记 error。尚未执行或尚未评审的项保持 missing。

还应区分两种“没有完成”。一份不足的摘要可能根本没有给出具体时间，模型诚实指出缺失是正确处理，但它没有完成需要精确时间的交付。另一个模型若猜中时间，也不能因为答案碰巧正确就认可它的证据。D02 的摘要练习正是用来观察这一差别。

对动作的检查尤其需要外部证据。输出中的 `actions: []` 可以符合当前格式，却无法证明宿主没有执行别的调用。如果评估包含工具，应保存真实工具请求、返回状态和必要的文件检查。本册只读题的机械检查不能替代完整行为审计。

## 在运行前写下停止条件

一次实验至少需要确定题目集合、提示版本、重复次数、环境和评分标准。还要决定如何处理超时、格式错误与重试。否则候选版失败后不断重跑，基线版却只保留第一次，比较就失去意义。

本册默认验证对照是七题、两版、各两次，共 28 份请求。准备命令如下，它只生成本地文件，不调用模型：

```bash
python prompt/examples/lab.py prepare --repeats 2 --environment "offline preparation only; model not selected" --out .scratch/prompt-evaluation-plan
```

真实运行前，用新的目录和实际环境说明重新准备。把产品、模型、能控制的参数、输出上限及工具配置写进去；产品未提供的设置写明不可设置。决定总预算时，需要把故障、必要重试和人工复核成本一起考虑。没有实际计价记录时不要填写零成本。

计划中的每份请求都有固定编号。模型第一次输出非法 JSON，也要保留。若你想测试自动修复格式的流程，应另设有明确次数上限的方案，记录原始响应和修复后响应，而不是悄悄清理文本再评分。

发现素材本身有错时，应暂停受影响的比较并说明原因。保留原计划与原始响应，修订题目或标准后建立新版本；不要只改变候选版的评分标准，也不要把旧结果按新标准改写得像从未变化。

## 让另一位审阅者能得到相近判断

先拿一份开发题响应试评。两位审阅者分别给出满足和未满足的条目，再核对分歧。若分歧来自“简述候补是否必须包含取消递补”，就需要回到任务用途明确要求；若来自漏看引文，则改进阅读流程。不要用讨论后的共识掩盖原始分歧。

可以把候选名称替换为中性编号，让审阅者在不知道哪份是新版的情况下先判断。编号映射由另一份记录保存，评分结束后再揭示。这样不能消除全部偏差，但能减少因为喜欢某种提示写法而给它更宽的标准。当前脚本不会自动盲化，需要操作者自行维护这份映射。

评审说明应能被追查。例如写“缺少容量乙的依据，响应只引用了甲”，比写“冲突处理一般”更有用。对于重要分歧，记录材料位置、响应原句、适用标准和最后决定。

模型也可以帮助找漏项或提出疑点，但不能因为它给自己的回答打了高分，就当作独立验证。让一个评审模型参与时，还需要单独核对它的判断稳定性与偏差，并保留人可以复查的原始证据。

## 完成一份能继续用的评测说明

现在留下一个简短说明：本次任务是什么，使用哪组题，哪些条件必须满足，哪些检查由程序完成，哪些由人完成，计划运行几次，以及何时停止。将提示、材料与判据的版本一起保存。

本册已经实测了离线检查器和未运行目录的统计行为，尚未得到青禾模型 A/B 的真实响应。这种状态可以继续工作：下一位操作者知道哪些准备完成了，也知道还缺哪类证据。不要为了让表格完整，提前把未运行行填成通过或失败。

进入[第 16 章](ch16.md)时，用这组已确定的标准观察配对变化，再决定保留或放弃修改。如果标准确实有误，保留原记录，在新计划中修正。
