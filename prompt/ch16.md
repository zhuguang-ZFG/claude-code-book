# 第 16 章：提示变好了，结果一定更好吗

<!-- block: prompt-ch16.b-opening -->
你发现一条提示没有交代“材料不足时怎么办”，于是补上了这句话：

> 回答前逐项核对材料是否足够；对缺失或冲突的信息，在 answer 中明确指出并保留对应依据。

这句话补齐了要求。要知道它是否有用，还得在相同任务、材料和运行条件下，观察回答是否少犯了错误。

本章先用一个确实跑过的程序对照说明如何看结果，再准备提示 A/B 对照。程序检查有实际输出；新册模型对照还未运行。你可以不开通模型服务，先把输入、判据和记录流程做完整。

## 先分清比较的是哪一层

青禾工作坊的离线程序接收容量、正式名单、候补名单、申请人和动作。按照[名额规则 R01-v1](materials/rules-v1.md)，容量为 2、正式名单已有两人时，新申请必须进入候补。

原始请求保存在 [full-request.json](examples/full-request.json)：

```json
{
  "capacity": 2,
  "confirmed": ["Q01", "Q02"],
  "waiting": [],
  "person": "Q03",
  "action": "register"
}
```

JSON 是一种用字段记录数据的文本格式。这里的方括号表示名单，双引号中的名字是字段或编号。程序不会把这些编号当成真实人员，也不会发通知。

在仓库根目录执行两个版本：

```bash
python prompt/examples/workshop.py prompt/examples/full-request.json --mode faulty
python prompt/examples/workshop.py prompt/examples/full-request.json --mode reference
```

故障版本返回的正式名单含 Q01、Q02、Q03，已经超过容量。参考版本的正式名单仍是 Q01、Q02，候补为 Q03。两条命令都正常运行到了结尾，但业务含义不同。“没有报错”只能说明程序完成了计算，不能说明计算符合要求。

所以我们另外准备了[十二个业务用例](evaluation/business-cases.json)，直接根据规则写出预期，再拿两个版本比较：

```bash
python prompt/examples/check_workshop.py --mode faulty --output .scratch/prompt-business-faulty.json
python prompt/examples/check_workshop.py --mode reference --output .scratch/prompt-business-reference.json
```

2026-11-10 的实际运行结果如下，完整逐例输出保存在[故障版记录](evidence/business-faulty.json)与[参考版记录](evidence/business-reference.json)。

| 场景 | 故障版 | 参考版 | 核对的规则 |
| --- | --- | --- | --- |
| 有空位报名 | 通过 | 通过 | 新编号占用剩余名额 |
| 已满额报名 | 失败 | 通过 | 等于容量时进入候补 |
| 零容量报名 | 失败 | 通过 | 没有正式名额可分配 |
| 正式名单重复报名 | 通过 | 通过 | 不改变名单 |
| 候补重复报名 | 失败 | 通过 | 不追加第二次，也不转正 |
| 取消正式名额并递补 | 失败 | 通过 | 候补队首先递补 |
| 取消候补 | 通过 | 通过 | 删除对应候补，保留其他顺序 |
| 取消不存在的编号 | 通过 | 通过 | 返回 not_found |
| 布尔容量、负容量、超额初态、空白编号，共四例 | 四例通过 | 四例通过 | 非法输入不改变状态 |
| 合计 | 8/12 | 12/12 | 同一组十二例 |

检查故障版时退出码为 1，表示业务检查发现失败；参考版为 0，表示这十二例全部通过。这里的退出码是检查程序给终端的结果，不是模型评分。

这次比较没有模型参与，能得到的结论是：“参考实现通过了这组规则用例，故障实现有四例不符合。”后续若让 Agent 提交修复，还需保存它实际读取的代码、收到的任务、修改与工具回执，才能评价那一次协作。

## 把提示对照写成一个可失败的假设

本章提供两个提示文件：[A 版](prompts/a.txt)与 [B 版](prompts/b.txt)。B 完整保留 A，只增加开头那句核对不足与冲突的要求。题目、来源、输出字段和只读范围保持相同。

你可以把假设写成：“增加逐项核对要求后，在当前验证题中，遗漏不足或冲突的错误会减少。”这允许结果支持，也允许结果不支持。不要写成“验证 B 比 A 更好”，再在运行中不断换题，直到出现想要的分数。

验证集有七题，涵盖同批容量冲突、备注夹带指令、错误示例、读取工具失败、重复申请、未经授权的发送建议和会话中断后的恢复。它们属于不同失败类型，完整内容在[验证题](cases/validation.json)，逐项标准在[判据](evaluation/criteria.json)。

如果模型把同批冲突处理对了，却开始错误地把普通重复申请说成“无法判断”，新增提示未必值得采用。总分能帮助观察，逐例变化才告诉你损失发生在哪里。

验证题可以用于选择方案。看过验证失败后再改提示，这些题就成为你已经熟悉的题。最终还应使用未参与修改的留出材料。仓库里公开的留出文件不具有保密性；若已经读过，需要登记暴露并另编新题，不能继续称作未见测试。

## 冻结要比较的输入

脚本会按七题、两版、各两次准备 28 份请求。两次重复只是让你开始观察波动，不足以支持普遍结论。若准备做更多次数，应在运行前确定数量，不能因某版第一轮好看就提前停止。

```bash
python prompt/examples/lab.py prepare --repeats 2 --environment "offline preparation only; model not selected" --out .scratch/prompt-comparison-practice
```

这条命令用于离线练习，会报告 `planned_responses: 28` 和 `executed_model_calls: 0`。它没有连接任何服务。你会看到：

```text
.scratch/prompt-comparison-practice/
  plan.json
  plan.sha256
  criteria.json
  V01-01-a/
    request.txt
    context.json
  V01-01-b/
    request.txt
    context.json
  ...
```

真实运行前，另建一个实验目录，把 `--environment` 写成实际环境说明，至少包括产品与版本、模型标识、可控制的采样参数、输出上限和工具开关。聊天产品不提供某项设置，就写“不可设置”；不要凭空填写一个参数，假装已经固定。工具支持的具体设置回查对应 Agent 分册。

`plan.json` 固定题目、重复次数、遍历顺序、环境说明与输入指纹。第二次重复先运行 B 再运行 A，减少总是同一版先运行带来的简单顺序偏差；这种交替仍不能消除服务负载和时间变化。`criteria.json` 保存准备时的评分标准，后续材料更新不应悄悄改掉本轮判据。

文件指纹可发现意外修改，却不阻止人同时改文件与指纹。正式协作时可把实验目录另行归档或提交到版本管理，留下固定版本。模型能看到整个实验目录时，也可能读到判据；应只交给它单次 `request.txt`，并在宿主层限制其他文件访问。

## 保存每一次原始响应

每个运行目录对应一次独立请求。例如 `V01-01-a` 表示 V01、第 1 次、A 版。为每次请求开干净会话，按计划使用同一环境，完整发送 `request.txt`，将响应原样保存为同目录的 `response.txt`。

如果你在同一会话先问 A、再让模型“参照上一条改进成 B”，B 已经看到了额外内容，比较条件变了。若产品自动加入历史记忆或项目规则，也要记录这些实际输入；无法关掉时，结论只能限于这个产品配置。

原样保存包含两层意思。第一，不把失败的第一条删掉，只保留后来满意的答案。第二，不先替模型去掉围栏、补 JSON 字段、修正引用，再当作原始响应。你可以研究一层格式修复是否有用，但应另设实验，记录修复前后与额外成本。

如果服务返回超时，没有回答，就留下错误详情、发生时间与该运行编号。如果任务根本还没执行，保持未运行。没有响应的失败和没有发出的请求不能记成同一种状态。

本章工具不负责调用模型，也不核实响应来源。它管理文件和评审记录。若需要自动调用，后续接入必须另存请求、服务标识和原始回执；本地目录中的一段文字本身不能证明出自哪个模型。

## 格式通过以后，还要核对什么

模型输出约定有四个字段：`case_id`、`answer`、`evidence` 和 `actions`。`answer` 存放说明文字；`evidence` 保存来源 ID 与逐字引文；这些任务只有整理权限，因此 `actions` 应为空数组。来源中的历史回执可以在答复里说明，不得冒充本轮新执行的动作。

保存响应后运行：

```bash
python prompt/examples/lab.py check .scratch/prompt-comparison-practice/V01-01-a/context.json .scratch/prompt-comparison-practice/V01-01-a/response.txt
```

检查工具能发现非法 JSON、多余或缺失字段、错误题号、未提供的来源、对不上的引文以及非空动作数组。但它不理解任意自然语言主张是否正确。

看一个人工编写的错误示例：

```json
{
  "case_id": "D01",
  "answer": "活动收费 500 元。",
  "evidence": [{"source": "N01-v1", "quote": "活动免费"}],
  "actions": []
}
```

字段正确，引用也逐字存在，答案却与引用相反。用 D01 的上下文检查，它可以通过机械检查；工具会同时保留 `manual_review_required: true`。我们专门用测试保证这条边界不会被报告成“事实正确”。

人工复核时，逐条阅读冻结判据，检查答案有没有覆盖、引文是否支持结论、未知与冲突是否处理准确、有没有声称未发生的动作。若返回了真实工具轨迹，还应对照轨迹与宿主权限；输出里填空动作数组，并不证明系统实际上没做其他事。

评分完成后，把具体发现写入记录。下面是命令形式，运行前必须已经得到实际响应并做完复核：

```text
python prompt/examples/lab.py review <实验目录> V01-01-a --outcome fail --note "填写未满足的判据、响应原句和对应材料"
```

pass 表示全部必需项通过，fail 表示获得响应但存在不符合，error 表示实际调用或运行故障。pass 会再次检查机械条件。服务故障没有响应时允许记录 error；空说明和重复评审会被拒绝。若需要纠正误评，应保留原始评审，在新一轮复核记录中说明原因，不覆盖得像原来就没有误判。

## 先看成对变化，再看总数

同一题、同一次重复下的 A 与 B 组成一对。配对能区分四种变化：两版都通过、只有 A 通过、只有 B 通过、两版都未通过。若其中一版尚未评审，这一对不完整。

```bash
python prompt/examples/lab.py compare .scratch/prompt-comparison-practice
```

我们在只准备输入、尚未调用模型的目录中实际运行了这条汇总。结果是 A、B 各计划 14 次、各缺 14 次评审，14 对都不完整；`complete` 为 false，通过数差值为 null。记录见[未运行对照](evidence/unrun-comparison.json)。它不能写成“A 和 B 都得零分”，因为两版根本没有参加测试。

完成运行后，比较时至少同时保留三组信息：每版的计划总次数与通过数，fail/error 的分布，以及成对变化。error 留在预定次数的分母中，并单独展示。这样既不会因删掉调用失败而抬高成绩，也能看出差异可能来自服务状态。

假设一个教学算例有四对结果：两对共同通过，一对仅 A 通过，一对仅 B 通过。那么两版都是 3/4，净差为零，但错误位置发生了交换。这个算例没有对应模型运行，只用来解释统计：总分没变，不等于所有行为相同；某一题变好，也不等于可以忽略新增失败。

相同题目重复两次，不会变成两道独立的新题。重复用于观察同一条件下的稳定程度；更多不同题目用于观察任务覆盖。小题库里多出一次通过，尚不足以推断其他领域、模型或工具上的效果。不要把配对通过数差直接称为显著提升。

## 一个真实的“修正了提示，但成绩没提高”

同系列的大模型课程保留过一次[固定版本的 EVALUATION-04 记录](https://github.com/zhuguang-ZFG/vibe-coding-101-course/blob/e74c7315bb8e72aa501e11ba4aef29a8efc66c17/book/llm/examples/assistant/EVALUATION-04.md)。原 extract 模式的用户消息要求 `chunk_id/quote`，系统消息却要求另一组字段，存在输出约定冲突。候选修正了 extract 的系统提示，保持用户消息、资料、校验器和原预算。

该记录使用 Qwen2.5-1.5B-Instruct 的固定权重版本，在 CPU 上运行。extract 修前、修后均为 5/8，逐例状态相同。因此可以说约定冲突消除了，但没有观察到质量分数提高。

八题里还包含权限、缺源、缺模型等不调用模型的边界检查，不能把 5/8 换成“模型生成正确率为 62.5%”。运行来自共用工作站，也不据此比较速度。本书引用的是原项目记录，没有在青禾案例中复跑它。

约定自相矛盾足以成为保留修正的理由，剩余的生成失败还需要继续调查。记录中的采用理由应写“消除字段冲突”，因为这次分数没有显示准确率提升。

## 下一次该改哪里

发现失败后，沿输入和输出回查。模型没有看到有效时间修订，就补材料；看到材料却写出旧时间，就检查提示、示例和版本说明；回答正确但 JSON 不合约定，则检查格式约束。工具返回 file_missing 时，先解决文件问题，反复要求模型更仔细并不能恢复缺失的输入。

如果两版使用的模型、输出上限或工具设置不同，先把它们作为两种配置比较。这样的结果能帮助选方案，但无法单独归因为提示那一句话。没有控制住的变量应保留在记录中，不要在总结时消失。

采用或放弃一个修改时，写下题目版本、实际环境、完整结果、已知回退条件和未测范围。本版已将离线名额对照与模型记录流程跑通；提示 A/B 的效果仍待真实响应。下一位接手者拿到这些文件，可以从未运行的位置开始，而无需猜测哪一个“成功”只是示例。
