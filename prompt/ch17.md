# 第 17 章：换模型或换工具后，哪些需要重做

<!-- block: prompt-ch17.b-opening -->
迁移提示时，需要重新核对模型实际收到的内容、工具能执行的动作和结果的检查方式。同一段文字能被两个产品接收，并不说明两个环境已经完成了同一种任务。

假设你在一个聊天窗口里用青禾通知完成了答复，接下来想把相同任务放进本地 Agent。聊天窗口可能只看到粘贴的两份文字，Agent 却可能自动读取项目规则、历史记录和更多文件。与此同时，输出上限、工具格式和错误处理也可能不同。迁移从查明这些差别开始。

下面从输入检查开始准备迁移。本册的离线程序可以检查材料与记录；两种模型环境的实际表现尚未测量，需要在所选环境中另行运行。

## 先说明你正在比较什么

有两种常见目标。第一种是研究模型差异：尽可能保持任务、材料、提示和可控制参数一致，只替换模型。第二种是选择工作方案：比较聊天产品与 Agent 各自在实际配置下的整体表现。后者可能同时改变文件读取、工具、历史和提示装配，不能把差异全部归给模型。

把目标写成一句话，可以避免边跑边换问题。例如：“比较两个环境用同一批公开材料完成只读答复的情况，工具全部关闭。”或者：“比较两个产品按各自可用能力完成本地代码审查的整体效果，分别记录它们实际读取的内容。”两者都可以有用，报告中的归因范围不同。

模型显示名称也不总是一个长期固定版本。能获得固定标识时就保存；只有产品别名时，记录观察日期和别名，并明确无法确认后端是否变化。不要把一个外观相同的菜单项当成所有运行条件相同的证明。

## 逐项核对输入怎样进入模型

开始运行前，填写下面的迁移表。它记录差异，不要求所有格子都强行一致。

| 项目 | 需要记录的内容 | 发现差异后怎么处理 |
| --- | --- | --- |
| 任务与材料 | 实际发送文本或文件读取结果、版本指纹 | 保存每个环境自己的输入快照 |
| 消息职责 | 哪些文字是任务、规则、引用资料 | 按目标接口映射，保留映射说明 |
| 历史内容 | 会话历史、项目规则、记忆是否加入 | 能清空则清空；不能清空则注明 |
| 输入与输出上限 | 可用容量、截断迹象、输出限制 | 不足时先调整材料方案，重新冻结 |
| 输出格式 | 普通文字约定还是接口约束 | 分开评估格式能力与语义完成 |
| 工具 | 工具定义、权限、返回结构和错误状态 | 用本地无敏感数据练习先验证 |

不要把所有消息简单拼成一个字符串，就声称保留了原来的角色关系；也不要把普通文字中的“系统规则”标题当作接口层的系统消息。具体字段取决于实际产品，需要按固定版本资料核对。本书的 `request.txt` 是可独立阅读的任务文本，不声明自己已经适配每个宿主的角色接口。

如果一个环境只能输出文本，另一个环境支持接口层的结构约束，可以先做共同的文本约定对照，再另测后者的结构化能力。这样能知道改进来自哪一层。不要把自动修复过的 JSON 与未经处理的原始响应直接混为同一条件。

## 先用一个小任务检查通路

迁移前先选开发题 D03。它只有名额规则和一个满额申请，便于核对材料是否真的被读入、题号是否保留、响应能否原样保存。

```bash
python prompt/examples/lab.py context D03 --out .scratch/prompt-migration-probe
```

把同一份 `request.txt` 分别送入两个干净环境，保存各自原始响应和环境说明。这里只检查通路是否可用，不用一题结果给模型排名。若一个环境报格式错误，先检查接口和字段；若它根本没有读到材料，先修复输入方式。

带工具的迁移还要单独跑工具检查。用独立副本观察正常返回、非法参数、文件缺失和超时如何显示。模型输出“工具失败”与宿主返回非零退出不是同一种证据；应保存原始回执，再看模型能否据此停下或继续。

一个环境能够读取任意工作区文件，另一个只看到指定材料时，不能称为严格相同的输入条件。可以把两者限制到共同能力后再比，也可以承认这是两套完整工作流程的比较。选哪一种，应由最初的目标决定。

## 用两份冻结计划保存环境差异

通路可用后，再准备完整验证集。下面的命令形式各准备七题、两版提示、一次重复，每个环境 14 份请求，共 28 份。先把环境说明替换成实际信息，再创建目录。

```text
python prompt/examples/lab.py prepare --repeats 1 --environment "填写环境A的实际产品、模型、设置与工具状态" --out .scratch/prompt-migration-a
python prompt/examples/lab.py prepare --repeats 1 --environment "填写环境B的实际产品、模型、设置与工具状态" --out .scratch/prompt-migration-b
```

这里两版提示仍是本册的 A、B，目录名中的环境 A、B 则表示两套运行配置。实际记录时可以把目录改成更明确的产品简称，避免把“候选提示 B”与“环境 B”混淆。一个环境内比较提示差异；跨环境比较时，必须拿相同提示版本、相同题目和对应重复次数配对。

一次重复只适合作为初步检查。正式比较要在运行前确定更多重复次数与可承担的总调用量。模型运行有成本时，先决定能承担的计划，不能准备了大表之后靠漏跑失败题缩小分母。

如果只有一个环境可用，就完成该环境的准备和运行，另一个保持未测。`lab.py` 的完整性检查会保留缺项；不会因为你希望得到比较结论就自动补出另一边成绩。

## 把迁移修改单独记下来

有时新模型持续漏掉引文，你增加了一个示例；有时新宿主要求更短输出，你拆成两步；有时工具返回字段不同，你增加了适配器。这些都属于迁移修改，应给新任务包单独编号。

建议先保留一次原样迁移结果，再记录每个必要改动的原因和影响。改动后重新核对全部必需项，特别是原先通过的边界。若换模型、改提示、加示例同时发生，可以说新组合在当前题集上有什么结果，但不能单独计算“换模型带来的提升”。

比较耗时也需要统一范围。有人从点击发送计时，有人只记服务返回的生成时间，还有人把模型首次加载算进去，这些数字不能直接放在同一列。费用无法获取时保留未知，字符数不能冒充账单 token 数，更不能据此给出精确收费。

还要记录失败如何影响实际使用。一次正确但极慢的回复，可能不适合现场答疑；一套快速但偶尔伪造成功回执的流程，也可能无法用于报名状态变更。总分之外，任务的时间要求和动作后果也会影响选择。

## 决定保留、适配或暂缓迁移

完成后给出范围明确的决定：哪些任务可以直接迁移，哪些需要新增适配，哪些尚无证据支持。将输入快照、原始响应、判据、工具记录和环境说明一起保留，便于下次升级时复查。

本系列的具体 Agent 册提供固定版本入口与已有验证范围，见[附录 C](appendix-c.md)。它们可以帮助你找到规则、会话和权限的差异，却不能代替青禾任务在目标环境中的实际运行。

如果结果没有改善，或者迁移后的维护成本高于收益，可以继续使用原方案。能够说明暂缓的依据，同样是一次完整的工程判断。下一章把这些选择整理成别人可以接手的交付物。
