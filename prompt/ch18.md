# 第 18 章：交付一套别人能够接着用的任务方法

<!-- block: prompt-ch18.b-opening -->
交付完成的标志，是接手者能从保存的材料和说明中恢复任务，知道哪些结果已经核对、哪些还没运行，并能在需要时重新检查或退回旧版本。

青禾项目已经经过通知整理、材料选择、名额检查和提示对照准备。如果只交出最终一段提示，接手者仍会遇到几个问题：该配哪份通知，哪个时间修订有效，检查器从哪里来，所谓“通过”指程序用例还是模型答复。本章把这些依赖一起整理。

## 先确定交付对象会拿到什么

面向居民的交付是一份经组织者核对的说明；面向维护者的交付则包含任务、材料、程序与证据。两者用途不同，不需要把实验日志全部塞进居民通知，但维护者必须能找到它们。

一个可用的教学交付包可以按下面的层次组织：

```text
qinghe-delivery/
  README.md              从哪里开始，当前版本和范围
  tasks/                 任务说明与提示版本
  materials/             实际使用的通知、修订与规则
  inputs/                每次提供给模型的原始请求
  exercise/              独立报名练习与检查入口
  observations/          原始响应、工具回执和环境说明
  review-only/           判据、人工评审和汇总
```

这是一种交付结构示例，不是脚本自动生成的完整目录。只向待测模型提供它需要的任务与材料；评审者读取 `review-only/`。如果模型能访问整个目录，文件夹名称不会阻止它打开答案，需要在实际宿主中限制访问范围。

交付包也应说明需要什么环境。离线练习只用 Python 标准库；模型实验另需所选产品、模型与可用权限。没有在某个平台运行过，就写未测，不要把“理论上可以”写成已经兼容。

## 让另一个目录能够重跑

先用随书工具建立独立练习项目：

```bash
python prompt/examples/exercise.py prepare --out .scratch/prompt-delivery
python prompt/examples/exercise.py check --project .scratch/prompt-delivery --receipt .scratch/prompt-delivery-before.json
```

副本只包含故障实现、公开规则、用例、检查入口和冻结记录，不包含参考修复。初始检查预期为 8/12。将副本复制到另一个新的位置后，在那个副本目录运行：

```bash
python check.py
```

如果命令还依赖作者机器上的绝对路径，或者只有打开原仓库才能找到规则，独立交付就没有完成。检查说明应该告诉接手者命令在哪个目录运行，以及退出码 1 在初始故障版中表示发现不符合。

完成自己的修复后，用新的回执文件保存检查结果。只改 `registration.py`；冻结规则、用例和检查器由工具核对。若需要改变业务规则，应新建规则版本和实验计划，不能在旧检查中偷偷替换预期。

当前书中有参考实现通过十二例的离线记录，这不代表某位读者或模型已经完成了修复。接手者提交的候选应使用自己的代码与实际回执证明，不能直接借用书中的通过结果。

## 用一页说明留下当前状态

交接说明可以很短，但要写出足以开始工作的事实。下面是一份人工教学样稿，使用时将版本与路径换成自己的实际记录：

```text
项目：青禾工作坊报名助手
本次交付：只读通知草稿、本地名额练习、提示对照准备
材料：列出实际使用的通知与修订ID；附输入快照
程序状态：记录候选文件指纹与实际检查回执路径
模型状态：逐项列出已运行环境；没有运行的保持未测
仍需确认：列出当前材料确实缺少的内容
恢复步骤：先核对文件版本，再读最近回执，最后处理未完成项
行动范围：当前包不连接真实报名、支付或消息服务
回退方式：保留上一版任务与代码，不覆盖首次响应
```

“已经处理好了，后续按需优化”无法告诉接手者下一步做什么。相反，明确写“对照输入已准备，模型请求尚未发送”，就能避免重复准备，也不会把未发生的试验当成既定证据。

还应注明资料的来源和再分发条件。随书原创材料与引用的上游源码、第三方说明不能混成一个无来源文件夹。共享系列导航不代表所有内容都能自由复制；实际分发时沿用各自的许可说明。

## 用陌生材料检查方法是否可以迁移

经过很多轮青禾练习，你可能已经记住正确时间、容量和候补规则。最后一次练习换成 H02 的借阅场景。不要先打开判据，也不要把旧活动答案作为示例一起发给模型。

```bash
python prompt/examples/lab.py context H02 --split holdout --out .scratch/prompt-transfer-h02
```

导出的 `request.txt` 自带新任务和材料，只把这份文本提供给待测者。不要把包含评分文件的整个仓库作为它的工作区。先写下自己的任务理解与拟采用的方法，再保存首轮回答，最后由评审者打开对应判据核对。

先根据新材料确定任务、区分事实和待确认项，再选择交付形式。留意回答中有没有混入旧工作坊的数字和状态。材料已经读过的人，应登记暴露情况，改用另一份未参与练习的原创场景。

如果失败，先找到迁移中断的位置：是否把旧业务规则当成通用规则，是否根据名称相似猜测结果，是否漏看新的确认条件。修正方法后可以再练，但首次结果仍保留；修改后的再次通过不能倒填成第一次就成功。

## 让验收包含接手者的实际操作

作者自己能运行，说明环境与文件在作者机器上能够配合。独立接手者还需要验证说明是否足够：能否找到入口、准备新目录、区分故障版与候选版、理解结果并定位失败。阅读理解和无障碍体验，也不能由程序测试代替。

可以请接手者按说明操作一次，只记录他卡在哪里，先不要口头补充隐藏步骤。若必须靠你解释“其实还需要那个未打包文件”，就把它补进交付。若报错被误认为正常结果，改进结果说明。这样的反馈能直接改善交付，而不只是得到一句“看起来不错”。

离线程序结果、出版检查、真实模型 A/B、跨模型迁移和独立学习效果分别登记。后续补做某项实验时，将环境、输入和结果接到记录里，再更新相应的验证范围。

## 为下一次变化留出位置

活动时间、模型版本和工具接口都会变化。维护者需要知道什么变化会触发重跑：材料修订时检查引用与答案；提示修改时重跑相关题和原先通过的边界；工具升级时重查参数、权限与回执；业务规则改变时另存新预期。

发现回退需求时，恢复的是一组相互匹配的文件：提示、材料、代码、规则与运行条件。只把提示换回旧版，却保留新接口和新摘要，不一定能恢复原来的行为。

交付时可以写一个明确结论：“本地案例可按说明复做，已知边界有记录；模型效果仍待指定环境验证。”也可以在真实实验完成后，把它更新为更具体的结果。让结论随着证据增加而变化，比一开始就许诺所有场景稳定可靠，更方便下一位使用者继续工作。
