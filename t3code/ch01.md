# 第 1 章：T3 Code 不是另一个 harness
<!-- block: t3code-ch01.b-opening -->

如果你以为 T3 Code 又是一个自己卖 token 的编码助手，这一章先把这个误解拆掉。官方文档把它称作 coding agent 的控制平面（control plane）：你电脑上已经登录的 Claude Code、Codex、Cursor、OpenCode 等 agent 才是干活的模型，T3 Code 负责把它们接进一个可远程操作、可追溯、可回滚的控制台。读完你会知道它管什么、不管什么。

本章按四步走：先给出控制平面与模型、harness 的分工，再列出服务器、客户端、契约三条所有权边界以及适配器这条补充边界；然后说明一个服务器如何对应多个客户端、订阅为什么仍然属于你自己；最后划清它不做的事情和适合使用的场景。术语第一次出现时给出英文原名，便于对照官方文档核对。

## 1.1 控制平面不是模型

官方 README 给 T3 Code 的定位是 "the open-source control plane for coding agents"：它驱动的是用户已经登录的 agent，包括 Claude Code、Codex、Cursor、OpenCode、Grok Build、Antigravity、Kiro、Pi 等。模型负责「想」，控制平面负责「记住、排队、呈现、回滚」。架构文档写明，orchestrator 串行化 command（命令）、只决定 event（事件）而不做 I/O；EventSink 把事件、投影（projection）、command receipt 与 outbox effect 放进同一个数据库事务提交。这是一条明确的并发边界：命令确认只代表意图已提交。

```text
你 → web / desktop / mobile 客户端 → 鉴权 RPC → 环境里的服务器
                                      ↓
                          provider adapter → 已登录的 coding agent
```

术语表把一次 user-to-agent cycle 定义为 turn（也叫 run），把跨 provider 进程退出仍存在的对话与工作历史定义为 thread（线程）。要注意：turn 结束与后续结算是两个里程碑，provider 回合结束后检查点和 diff 工作可能还在跑。架构文档要求，迟到的收尾不能让客户端继续把 provider 工作显示为 active，也不能拉长记录的 provider duration。换句话说，控制平面交付的不是「模型吐完字的那一刻」，而是一段有明确里程碑、有持久状态的工作。command receipt 让重试幂等，投影是应用之后的真相源；你可以这么理解：模型输出只是输入，真正被管理的是这些事实与它们触发的副作用。

## 1.2 它管的都是谁

控制平面管的是「环境」里的全部执行资源，而不是模型权重。术语表定义一个 environment（环境）为一台运行中的服务器，加上它拥有的机器、凭据、工作区访问权和状态；project（项目）是环境本地、以某个目录为根的工作区记录；workspace root 是它在环境机器上的基础目录；worktree 是线程可以替代主 checkout 使用的独立 Git 检出。T3 home 是基础数据目录，运行时状态通常放在它的 `userdata` 下。

| 术语 | 官方定义中的要点 |
|---|---|
| Environment | 一个运行中的服务器及其机器、凭据、工作区与状态 |
| Client | 连接环境的 web / desktop / mobile 界面，桌面端也可托管服务器 |
| Project | 环境本地、以目录为根的工作区记录 |
| Thread | 项目的持久化对话与工作历史，provider 进程退出后仍存在 |
| Turn | 一次用户到 agent 的周期，也叫 run |
| Checkpoint | 用于 diff 与恢复的已保存工作区状态，存为隐藏 Git ref |

这张表就是阅读后续章节的坐标系：线程是容器，turn 是里面的一段工作，检查点是把工作区状态钉在隐藏 ref 上的手段。

## 1.3 三条所有权边界

架构文档把执行资源划给服务器：`apps/server` 拥有 provider 进程、终端、Git、检查点、持久状态和项目文件。第二条边界是连接：`packages/client-runtime` 拥有 web、desktop、mobile 共用的连接管理与域状态，让重连和多环境行为不分化；客户端只提供平台服务和 UI。第三条是线协议：`packages/contracts` 是独立版本演进的客户端与服务器之间的 typed wire boundary，订阅只发送客户端需要的状态，而且 socket 通过鉴权不等于该 socket 上每个方法都被授权。

此外还有一条常被并提的边界：provider 专属协议和怪癖留在 adapter 后面，编排与客户端只读 capabilities，不读 provider 名字。可以这么理解：三条边界回答「谁拥有什么」，适配器边界回答「差异在哪里被吸收」。设置也遵守归属：客户端偏好留在当前客户端，环境默认与项目覆盖留在对应服务器，目标环境不可用时绝不回退到另一个环境。

## 1.4 一个服务器与多个客户端

一条连接把一个客户端接到一个环境。桌面应用打包了服务器，但它的 renderer 仍遵守同一条边界：远程客户端绝不能用自己的文件系统、provider 凭据或机器状态去替代环境的。服务器拥有执行，客户端拥有呈现与交互；重连后的域状态由 client-runtime 统一维护，因此三端看到的是同一份投影。

设置归属在这里尤其具体：`All environments`（所有环境）只是对当前已连接服务器的一次批量编辑，不是持久的全局默认，也不是同步承诺；某个环境不可达时它保持原值。项目覆盖与客户端偏好分层保存，不能覆盖的设置在选中项目时显示为只读。并发边界是：握手成功不增加权限，每个 RPC 都要单独检查 scope——这一条在环境鉴权文档里有完整展开，第 12 章会细讲。

## 1.5 自带订阅，不转售 token

README 明确写的是：T3 Code 驱动你已登录的 Claude Code、Codex、Cursor、OpenCode、Grok Build、Antigravity、Kiro、Pi 等 agent，不转售 token。也就是说，资格与账单关系留在你和 provider 之间，控制平面接管的是这些进程的生命周期与它们产出的状态。

```text
你的订阅/账号  → provider 登录态（属于环境机器）
T3 Code        → 进程、线程、终端、检查点、投影、RPC 授权
```

可以这么理解：如果 provider 会话在环境机器上失效，缺的是「干活的资格」，不是控制平面的功能；反过来，控制平面再完善也不会替你生成模型能力。README 列出的 agent 名单之所以长，正是因为它把各家差异压到适配层后面，而不是自己再做一家。登录态属于环境机器：你在手机上点按钮，实际用的是那台机器上已登录的 agent，凭据不会因为换了客户端而被复制过去。官方文档允许先启动 T3 Code 再配置 provider，也允许先装好 provider 再开第一个线程——这个顺序上的宽松本身就体现了两层分离：控制平面先有壳，模型资格随后填进去。对多账号用户，provider 实例（instance）各自持有自己的凭据与状态，同一 driver 下的两个实例不会串味。

## 1.6 它不做什么

架构文档列了不少「禁止项」，读它们比读功能清单更能看清边界。command 决策和数据库事务里不做外部 I/O；EventSink 一次提交后才由 EffectWorker 跑副作用并把结果作为 command 喂回；绑定在已丢失 provider 进程上的 effect 在恢复时退役，而不是重放。事件日志只保留有界重放窗口，所以投影不能从日志从头重建；保留的事件必须跨升级仍可解码，schema 变更影响启动时的存储历史，而不只是实时 RPC 流量。

其他否定项同样具体：检查点用隐藏 Git ref，不给用户分支加 commit；回滚前若 provider 无法回滚会话，必须在动文件前拒绝；线程 settlement 由服务器拥有，客户端渲染持久化的结算状态，而不是从本地时钟或 PR 缓存推导；桌面端原生模块不进 Electron 主进程启动路径，可能崩溃的原生能力放进带截止时间的子进程或 worker。

## 1.7 什么时候值得用

可以这么理解：当你只有一个短任务、一个模型、一台机器时，控制平面带来的抽象看不出优势；当任务跨多个 agent、多块屏幕、多次中断时，它提供的所有权边界才开始值钱。官方文档给出的能力是这种判断的依据：thread 跨越 provider 进程退出继续存在；turn 结束与 settlement 分离，迟到的收尾不会让客户端继续显示 provider 在工作；重连和多环境行为由 client-runtime 统一；终端、Git、检查点都在服务器上，换设备不换执行现场。

一个很实际的使用信号是「我需要把一个 turn 的工作区状态钉住、对比甚至恢复」：检查点走隐藏 Git ref，不污染你的分支；但恢复必须与 provider 会话协同，做不到就先拒绝。另一个信号是「我需要从手机或另一台机器看着同一个线程」：客户端只是控制面，凭据与文件仍在环境里，因此不用把项目复制到每个设备。按官方文档 `internals/01_architecture.md` 与 `internals/00_glossary.md` 的条目，可以自己核对这些判断。

## 1.8 本章要点与来源

记住六句话就够了。第一，T3 Code 是 coding agent 的控制平面，模型与订阅属于你自己；README 的英文原话和已登录 agent 名单可以直接核对。第二，thread 是持久容器，turn 是一次用户到 agent 的周期，两者结束时刻不同，turn-end checkpoint 还是线程 effect lane 上的一个 outbox effect。第三，服务器拥有 provider 进程、终端、Git、检查点、持久状态和项目文件；客户端只拥有连接与域状态；契约是类型化线协议；provider 差异收在 adapter 后面，编排与客户端只读 capabilities。第四，command 确认的是意图提交，不是副作用完成，副作用在事务提交后才由 EffectWorker 跑。第五，检查点用隐藏 Git ref，不给用户分支加 commit；回滚要在动文件前先确认 provider 能回滚会话。第六，客户端不自己推导 settlement，设置目标不可用时也不回退到别的环境，`All environments` 只是批量编辑。后面几章按安装、provider、线程、消息、权限的顺序逐一展开。
