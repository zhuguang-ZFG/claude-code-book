# 第 3 章：Provider 是适配器
<!-- block: t3code-ch03.b-opening -->

T3 Code 能同时驱动 Claude Code、Codex、OpenCode、Pi 以及一批 ACP agent，靠的不是在编排器里堆 `if` 判断，而是把差异压到一层适配器（adapter）后面。这一章从内部文档 `internals/03_providers.md` 出发，讲清 app ID 与 provider ID 的身份规则、能力声明的诚实原则、实例级凭据隔离，以及版本兼容与跨 agent 委派时最容易踩的几个坑。

后半章转到用户侧：文本生成模型设置、自定义模型、模型默认值，以及跨 agent 委派时为什么会看到某些行为。这里要特别区分「文档明说的机制」与「可以这么理解」的推断——尤其在中途换模型这个话题上，官方文档只描述了选择入口与优先级，并没有承诺运行中热切换，本章不会替它许诺。

## 3.1 为什么需要适配层

内部文档把协议、账号归属、权限和能力全部放在 adapter boundary，具体是 `packages/provider-core/src/server/ProviderAdapter.ts`。编排（orchestration）和客户端读的是声明出来的 capabilities，永远不读 provider 名字。这条规则解释了第 1 章那句「provider 差异关在 adapter 后面」：它不是口号，而是导入方向上的硬约束。新增一家 provider，要先想清楚它属于哪一类协议、能给出什么能力清单，再决定写原生 adapter、专用 ACP flavor，还是直接走共享 ACP 适配器；顺序反过来就容易把厂商细节漏进编排器。

```text
编排 / 客户端  →  capabilities（能力声明）  →  provider adapter  →  各家原生协议
packages/provider-<name>  ←  Pi 是参考实现
apps/server 只 import @t3tools/provider-core/server/*、contracts、shared
```

包边界也写得很死：provider 住在 `packages/provider-<name>`；server 代码只导入 core 的 server 子路径、contracts 和 shared，通过 `ProviderHost` 拿宿主能力，而不是伸手进 `apps/server`；客户端定义放在 `./client`，必须保持浏览器与 React Native 安全。可以这么理解：适配层既翻译协议，也承担「不让厂商细节漏到上层」的结构性责任。所以新增一家 agent 的正确姿势是实现自己的 adapter 并声明能力，而不是在编排器里加分支。

## 3.2 协议差异藏在哪里

第一处差异是身份。app ID 是主键，provider ID 只是引用：没有 provider / session / thread 范围，不要拿原生 provider ID 做全局匹配；子 provider turn 的完成也不能关掉父 run。第二处是 ACP 路线：非一方 agent（generic ACP Registry 与本地 ACP 命令）严格遵循 ACP 规范，共享适配器里不加 agent-id 检查、厂商扩展或针对某个 driver 的 workaround；上游不合规或缺功能时，让编排通过 capabilities 降级。专用 ACP flavor（`packages/provider-acp`）留给需要规范外行为的一方 driver，原生 `ProviderAdapterV2` 只服务非 ACP 协议。

其他常见的跨 provider 陷阱如下：

| 陷阱 | 文档给出的处理方式 |
|---|---|
| Lazy config advertisement | 等 advertised 之后再应用设置，跳过未提供过的存储选项 |
| `"Default"` 是哨兵 | 绝不发给 provider，清空或重置会话的模型选择 |
| Early Stop | 取消要等 turn-started 信号，否则可能被忽略或留下僵死会话 |
| Work outliving a turn | 后台任务、subagent、续跑可能在 turn 结算后才回报 |
| Terminal settlement | 完成、Stop、provider error、进程退出都要收尾未决调用 |
| Symlinked workspace | 测 macOS `/tmp` 这类路径，避免 cwd 规范化不一致 |

用量与限额错误要归到 `usage_limit`，有重置时间就带上，不能混成普通失败。这些条目都来自适配器文档，逐条对照就能判断某个异常属于协议差异还是产品缺陷。

## 3.3 能力声明与优雅降级

能力声明的第一原则是「只声明 provider 真支持的」：缺少 fork、rollback、steering 或 subagent 能力就把对应能力关掉，让编排干净降级，例如 fork 改用可移植的上下文交接。一个留着开启却会在运行时失败的能力，被文档直接定义为 bug。权限同理：绝不模拟缺失的权限模式，只暴露 provider 原生强制执行的模式；不要在 T3 Code 里自动回答审批来假装某个模式。存储的模式如果 provider 不提供，回落到 Supervised；原生审批和问题的 option ID 要原样透传，且每个请求都能被拒绝。plan mode 也要藏起来，除非它能产出 proposed-plan cards。

文件安全边界同样属于适配器职责：回滚前若 provider 不能回滚会话，必须在碰文件系统之前拒绝；后台状态和模型探测必须被动，不能开一个会启动 MCP server、跑 hook 或触发登录流程的会话，重度探测留给显式刷新或设置。T3 MCP 工具要注入线程自己的已鉴权 MCP server，并且在该 server 不可达时让 turn 继续。可以这么理解：能力声明是「能力清单」，而这些前置检查是「安全护栏」，两者共同决定编排能走到哪一步。

## 3.4 实例、凭据与状态隔离

路由单位是 provider instance（实例），不是 driver kind：session 状态、模型目录和凭据都属于实例，所以同一 driver 下的两个账号不能共享可变状态；实例未配置的 ambient credentials 要剥离。安装文档也呼应这一点——每个实例可以有自己的环境变量（API key、自定义 base URL），标记为 sensitive 的值保存后不再显示原文；多个服务账号要加实例而不是复用。

文本生成器的凭据落在环境侧。**Settings → Providers → Text generators → Add generator** 提供 OpenAI / Anthropic（填 API key）、OpenRouter（填 key 即可用它服务的模型）、Custom (OpenAI-compatible)（填 base URL，例如 Ollama 的 `http://localhost:11434/v1` 或 LM Studio，本地端点通常不要 key）。请求由环境里的服务器发出，所以远程环境下 `localhost` 指的是那台机器，不是你的电脑。key 像其他 secrets 一样存在环境上，也可以由 secret provider 提供。列出模型用来核对连接，**Test** 会让选中的模型回答一个极小 prompt 来证明 key 可用；有些服务只列模型不验 key。

附件边界也属于这里：上传文件绝不复制进项目工作区去绕过 provider 的沙箱或审批规则，始终留在项目树之外。可以这样理解：实例隔离管「谁的凭据」，附件隔离管「文件落在谁的地盘」，两者都不能靠客户端自觉。

## 3.5 版本兼容与 model manifest

服务器内置 `apps/server/src/provider/model-manifest.json`，用于离线启动；从 `main` 远程抓取的元数据在两次发布之间更新目录。比较规则是 `updatedAt`：内置 manifest 比缓存的远程副本更新时优先，所以每次编辑都必须 bump `updatedAt`，否则改动不会生效。已知坏版本的下限写在 manifest policy 里，不要写成 driver 常量。测试目录与适配器语义时用合成模型名，这样新增模型不必在测试里复制配置。

行为证明要用真实 provider 录制的 replay fixtures，并通过真实 orchestrator、adapter 和投影回放；手写协议帧只是对线上行为的猜测。纯逻辑和真实 provider 无法按需触发的失败路径再用单元测试。这种「录制真实帧再回放」的做法也解释了为什么能力声明要保守：某个能力若靠猜，回放会立刻暴露。

自定义模型分两层。用户在网页和桌面端走 **Settings → Providers → Models**，添加未列出的模型和选项，只有 provider 集成支持的选项才影响 turn；Antigravity 用账号目录，不支持自定义模型。要给所有客户端重命名内置模型，则编辑服务器 `userdata` 目录下的 `settings.json`：

```json
{
  "providerInstances": {
    "codex": {
      "driver": "codex",
      "config": { "customModels": [{ "slug": "gpt-5.5", "name": "Team GPT" }] }
    }
  }
}
```

这里 `slug` 是内置模型 ID，`name` 是新显示名——注意这改的是展示，不是能力。

## 3.6 中途换模型

先把「模型」分成两类。一类是干活的 coding agent：新线程的模型与选项会被记住，项目的模型配置优先，重置项目设置回到记忆中的选择；推理强度或服务层级不设置时用 provider 自己的配置。网页和桌面端用 `mod+shift+m` 打开模型选择器，消息里也能用 `/model`；在模型选择器里按 Left 或 Shift+Tab 到 provider 列表，`mod+shift+up` / `mod+shift+down` 直接切 provider 并清搜索。

另一类是替你写字的 text generator：**Settings → Threads → Text generation model** 管线程标题、commit message、PR 标题与描述、分支名、语音转写清理；**Settings → Source control & issues** 和 **Settings → Voice** 可各选一个。默认由编码 agent 每次开一个 session 来写，文本生成 API 通常更快更便宜。关掉或移除某个 generator，工作就退回环境的文本生成模型；托管策略（managed policy）限制 provider 时也会关掉文本生成器。

关于「中途换模型」，官方文档明确的是选择入口、记忆与项目优先级，以及 `"Default"` 只能是哨兵、不能当模型 ID 发给 provider（要清空或重置会话选择）。可以这么理解：选择发生在线程与会话的配置层，切换后再发的消息按新配置走；但文档没有描述在一个正在运行的 turn 内部热替换模型，所以不要把选择器里的切换理解成对当前 turn 的保证。lazy config advertisement 也提醒我们：存下来的选项若 provider 尚未 advertise，应当跳过而不是硬套。

## 3.7 跨 agent 委派

跨 agent 的第一条纪律是：后台任务、subagent 和 provider 主动发起的续跑可以在 T3 Code 的 turn 结算之后才回报。subagent 更新要按 subagent 路由，而不是按当前 active run；需要时主动请求续跑，并报告待处理的后台工作，让空闲清理不会误杀会话。用量到限额时归为 `usage_limit` 并保留重置时间，而不是让委派链把它当普通失败。

在消息侧，输入 `@` 加模型或 provider 名的一部分（例如 `@opus`，词之间用 `:`、`/` 或 `-` 连接，如 `@opus:opencode`）可以点名让 agent 用哪个模型——文档明确说这不会改线程模型，常用于委派。要引用另一个线程，输入 `@` 加标题片段；附带的只是引用，agent 按需读取历史，附加长线程本身不花上下文。

文本生成的跨 agent 规则也很具体：review guide 要跨多步读 checkout，所以始终用编码 agent；如果 source control writer 选的是文本生成器，review guide 改用 Codex 或 Claude，两者都没配就失败，可在 **Settings → Source control & issues → Review guide model** 里指定。委派时的身份边界同样重要：子 turn 的完成不能关掉父 run，app ID 才是主键——这两条在 3.2 节出现过，是跨 agent 场景最常踩的坑。

## 3.8 本章要点与来源

适配器的边界是 `packages/provider-core/src/server/ProviderAdapter.ts`，编排与客户端只读 capabilities，不读 provider 名字；provider 住在 `packages/provider-<name>`，Pi 是参考实现，server 只经 `ProviderHost` 与 core 的 server 子路径取宿主能力，客户端定义要保持浏览器与 React Native 安全。身份上 app ID 为主、provider ID 为引用，路由按实例而非 driver，非一方 agent 严格走 ACP。能力要诚实：不模拟权限模式，未提供过的存储模式回落 Supervised，原生 option ID 原样透传且每个请求可拒绝；回滚要在动文件前判断 provider 能否配合。版本方面，内置 `model-manifest.json` 靠 `updatedAt` 胜过远程缓存，每次编辑都要 bump；坏版本下限写在 manifest policy。用户侧要分清编码 agent 与 text generator，前者有记忆和项目优先级，后者管标题、commit、PR 文本等任务；review guide 永远用编码 agent。遇到异常时按表逐项排查：lazy advertisement 要等 advertise 后再应用设置，`"Default"` 要清空而不是转发，Early Stop 要等 turn-started，`usage_limit` 要带重置时间，符号链接工作区要测规范化。按官方文档 `internals/03_providers.md`、`user/text-generation.md` 与 `user/composer.md` 的条目，可以自己核对字段名、`updatedAt` 比较规则和菜单路径。
