# 第 4 章：线程：一个任务的容器
<!-- block: t3code-ch04.b-opening -->

线程（thread）是 T3 Code 里最容易被当成「聊天窗口」、其实远不止于此的对象。官方文档把它定义为项目的持久化对话与工作历史，provider 进程退出后仍然存在；它同时是权限档位、模型选择、工作区、检查点和结算状态的挂载点。这一章按「是什么—怎么建—有什么限制—怎么管理—谁来决定结束」的顺序拆开它。

读的时候请记住第 1 章的所有权边界：终端、Git、检查点和持久状态都归服务器，客户端只渲染投影。因此你会看到一些看似琐碎的规定——同一 checkout 的线程在有人工作时拒绝切分支、settlement 由服务器拥有、客户端不用本地时钟推导状态——它们其实是同一条边界在不同界面上的表现。

## 4.1 线程是什么

术语表的定义很紧凑：thread 是一个项目持久的对话与工作历史，能在 provider 进程退出后存活；turn 是一次 user-to-agent cycle（也叫 run）；worktree 是线程可用来替代项目主 checkout 的独立 Git 检出；T3 home 是基础数据目录，运行时状态一般在 `userdata` 下。换句话说，线程是容器，turn 是里面的一段工作，worktree 是这段工作可以占用的独立地盘。

```text
project（环境本地、以目录为根的工作区记录）
  └─ thread（持久对话与工作历史）
       ├─ turn / run（一次用户到 agent 的周期）
       ├─ runtime mode（权限档位）、model、workspace
       └─ checkpoint（隐藏 Git ref）、terminal、settlement 状态
```

服务器拥有 provider 进程、终端、Git、检查点、持久状态和项目文件；客户端运行时拥有跨 web / desktop / mobile 的共享连接管理与域状态。一个直接后果是：会话（session）可以停止和恢复而不删除线程，你在手机上看到的线程和桌面上是同一个对象。线程还可能没有项目：那类线程在自己的 scratch 文件夹里工作，没有分支与 diff 控件，属于「先干起来再说」的形态，下一节会讲到。

## 4.2 新建线程与 worktree

在网页和桌面端，**New thread** 在默认侧栏或项目分组侧栏里有多个打开项目时弹出项目选择器，归档项目不算；Shift-click 直接在当前项目开始，也可以用项目自己的新建动作。新线程继承当前模型和模式，除非目标项目有自己的模型默认；分支与工作区模式来自你配置的默认值。要在既有 worktree 里继续，用分支工具栏的 **New thread in this worktree**。侧栏筛到单个项目时，**New thread** 直接在该项目里建，不再询问。想让代码改动独立成支，选 **New worktree**：它带来独立分支和独立工作目录，这是官方给出的判别标准。

并行开工有两种入口。后台方式是在桌面浏览器或桌面应用里按 `Cmd+Enter`（macOS）/ `Ctrl+Enter`（Windows、Linux）：新线程立刻开跑，同时给你一个新草稿，下一次提交沿用刚选的工作区模式和基准分支。多模型方式是在新线程模型选择里 Shift-click 多个模型：每次选择启动一个独立线程和 worktree，你留在原草稿里；这要求 Git 项目。

无项目线程可以从新线程标题下的 **or start without a project**、项目菜单的 **No project**、命令面板的 **New thread in...** 或 `mod+alt+n` 进入，各自使用 `~/.t3/scratch` 下以日期、首条消息词和短 id 命名的文件夹。删线程不删文件夹；工作长成正经项目时，从线程菜单选 **Turn into project**，原地变成项目，再 **Initialize Git** 拿回分支和 diff 控件。

## 4.3 同 checkout 的限制

「同一个 checkout 的线程共享分支」是理解一批限制的钥匙。官方文档明确写道：当某线程正在工作时，T3 Code 拒绝在这个 checkout 上切分支。因为分支是 checkout 级状态，而不是线程级状态；两个线程同时在该目录里写文件，切分支会把彼此的工作换位。需要互不干扰的分支时，正确做法不是切分支，而是给线程分配一个 worktree。

恢复与回滚也受同样的边界约束。**Edit from here** 之后选 **Revert files too**，只在线程运行于 worktree 时提供；若另一个线程、agent session 或某个文件夹与待恢复目录重叠（在它内部、包含它，或就是它），恢复会被拒绝，因为那会抹掉别人的改动。属于当前线程、已经完成的 subagent 不阻塞恢复，前提是它们没有排队工作、活动工作、待处理请求或后台任务。在普通项目目录里工作的线程只能回退对话，不能回退文件——文档写得很清楚，这一点不是权限问题，而是目录共享的必然结果。

还有一个并发边界来自检查点：turn-end checkpoint 作为 outbox effect 排在线程自己的 effect lane 上，未提交前 steers、排队 turn、rollback 和 restore 都要排在它后面。可以这么理解：线程不仅是一段对话，还是一条串行化工作的队列边界。

## 4.4 侧栏、筛选与归档

侧栏把线程分成几类区域，操作方式很具体。线程菜单里的 **Pin** 把它固定在活动工作之上；网页和桌面端可拖动线程跨区：拖到 pinned 区置顶，拖回 active 区取消固定，拖到 **Settled** 标题上结算，拖进 active 区取消结算。snoozed 线程可以拖出来唤醒，但不能拖进去，因为 snooze 需要一个唤醒时间。拖动时行会滑开显示落点，跨区时显示 **Pin / Unpin / Settle / Un-settle / Wake** 动作。取消固定、结算、snooze、归档或丢弃草稿后，通知里的 **Undo** 保留 5 秒；`mod+z` 触发最近一次 Undo，即使焦点在 composer 里也有效。

| 侧栏机制 | 关键事实 |
|---|---|
| 搜索 | `Cmd/Ctrl+K` 跨已连接环境按标题、分支、PR、项目搜索 |
| 消息搜索 | 至少一个三字母词，中日韩文字两个；命中处打开 |
| Working（beta） | 工作中或等待续做的线程折叠到活动列表下方 |
| Boring sidebar（beta） | **Settings → Labs → Boring sidebar (group by project)** 按项目分文件夹 |
| 排序 | 服务器保存顺序，刷新与其他设备都保留；Working 开启时禁用拖动 |
| 标题 | 线程菜单 **Regenerate title**；规则写在 **Settings → Threads → Text generation** |

**Settle** 与 **Archive** 是两回事：settled 线程仍在侧栏 Settled 区和搜索里，收消息就重新活动；archived 线程离开侧栏与搜索，只在 **Settings → Archive** 出现，并拒绝包括 agent 与定时任务在内的新消息。删除项目会连线程一起删掉，两种状态都一样。归档一个被定时任务投递的线程不会让任务停止，它每跑一次就失败一次——应该改投到别的线程，或者 settle 它。

## 4.5 移动端的新建线程

手机上的项目选择遵循一条回退链：**New thread** 先取当前线程的项目，否则取线程列表筛选的项目，否则取本机上次打开或选中的项目；都没有才打开项目选择器。关掉 **Settings → General → Use last project** 可以每次都选。选中的项目若同时存在于多台机器，只要其中一台已连接，线程就在那台上启动；改变新线程的项目时，只要项目在当前环境存在就留在当前环境，否则改选拥有它的环境。

移动端的侧栏操作走另一套路径：打开线程菜单选 **Arrange threads**，拖动句柄在 **Pinned** 与 **Active** 之间重排、固定或取消固定，拖到 **Settled** 分隔线上结算；卡片在松手前显示将要执行的动作。每次放置都会保存，顺序由服务器保存，因此刷新和换设备后仍然一致。线程菜单也有 **Move up** 和 **Move down**。带键盘的 iPad 用 `Cmd+K` 打开与桌面相同的命令面板，`Cmd+1` 到 `Cmd+9` 打开前九个显示的线程，顺序跟随当前筛选结果。

正在运行的线程在移动端仍能被看见：**Agents** 列出 subagent，点开后在有 inspector 的布局里并排显示，可最大化到全屏。停止父线程会一并停止它委派的 subagent；归档父线程前要等委派任务结束或取消它们。由 agent 启动的 subagent 线程不能接收消息，要给父线程发；它需要审批或回答时，也是父线程出面询问。

## 4.6 服务器决定的 settlement

settlement 不是客户端的本地推算。架构文档要求线程 settlement 由服务器拥有，客户端只渲染持久化的结算状态，不从本地时钟或 PR 缓存推导。因此你在三端看到的结果是一致的，即使发起结算的那台设备早就关了。settled 线程保存的 PR 链接会保留；服务器即使在应用关闭时也会为未结算线程保存的分支找 PR，自动链接没出现通常意味着该升级服务器。

默认规则写在 **Settings → Threads**：环境在线程闲置七天后自动结算，PR 合并后也会结算；关闭的 PR 可以让空闲线程结算。进行中的工作、待回答问题或审批、agent 正在等待的后台工作都会阻止自动结算。打开的 PR 默认不阻止闲置结算，除非打开 **Keep threads with a PR**；PR 关闭后你重新开工，旧的关闭或合并 PR 不会再把它结算掉。你自己发的消息算「恢复」，agent 用 `t3_thread_send` 或 `t3 thread send` 发的也算；而一个因后台工作或 PR 监听而自行启动的 turn 不算。某个线程想永不自动结算，就从菜单选 **Auto-settle behavior → Never**。

结算还牵动终端：手动结算会关闭停在 idle prompt 的终端但保留输出；正在跑命令（例如 dev server）的终端保持打开，除非其 action 勾了 **Stop this action when the thread settles**，或在 `t3.json` 里设置 `"stopOnSettle": true` 并通过该 action 启动。修改规则可以选单个环境，也可以选 **All environments** 对当前已连接环境批量编辑；离线环境和旧服务器保持原值，规则改动不会重开已结算线程。

## 4.7 完整生命周期

把前面所有机制串起来，一条典型线程的旅程是：草稿（可丢弃且 5 秒内可撤销）→ 选定项目 / worktree 与模型、权限 → turn 运行，可能排队或 steer → provider turn 结束，run 变为 `completed` → turn-end checkpoint 作为 outbox effect 在线程 effect lane 上捕获 → 提交前读者把缺失的检查点视为 pending，command 决策仍视 run 为 `waiting` → 结算（手动或自动）进入 Settled → 归档或删除。

```text
draft → running turn → turn-end（completed）
      → checkpoint effect（pending，steer/rollback 排队）
      → checkpoint committed → settled → archived / deleted
```

几个细节决定这条链路的正确性。迟到的收尾不能让客户端继续把 provider 工作显示为 active，也不能拉长记录的 provider duration；如果 provider 进程丢失，绑在它上面的 effect 在恢复时退役而不是重放。settlement 由服务器拥有，客户端渲染持久化状态。settled 线程收到消息会重新活动，archived 线程拒绝新消息；删除项目会连线程一起删除。检查点用隐藏 Git ref，不给用户分支加 commit；恢复文件前若 provider 不能回滚会话，必须先拒绝。可以这么理解：生命周期的核心不是「对话结束」，而是「副作用和状态都到达了一个可持久化的里程碑」。

## 4.8 本章要点与来源

线程是项目的持久对话与工作历史，跨 provider 进程退出仍存在；turn 是一次用户到 agent 的周期，两者结束时刻不同。要独立分支就用 **New worktree**，同一 checkout 的线程共享分支，有人在跑时拒绝切分支；恢复文件会拒绝与其他线程或会话共享目录的情况，普通项目目录只能回退对话。侧栏支持拖动分区、5 秒 Undo、`Cmd/Ctrl+K` 跨环境搜索、Working 与按项目分组两个 beta；Settle 保留在搜索里且可复活，Archive 拒绝新消息。移动端的项目选择按「当前线程 → 筛选项目 → 上次项目」回退，排序由服务器保存。Settlement 归服务器：默认闲置七天或 PR 合并后结算，进行中的工作、审批、后台任务会阻止；`stopOnSettle` 决定终端是否随之停止。`All environments` 是批量编辑，不是全局默认值。按官方文档 `user/thread-sidebar.md` 与 `internals/01_architecture.md` 的条目，可以自己核对菜单名与里程碑顺序。
