# 第 6 章：权限四档：谁决定「可以动手」
<!-- block: t3code-ch06.b-opening -->

权限档位（permission mode）决定 agent 执行命令或修改文件前是否需要批准。它在 composer 中选择，只作用于当前线程。T3 Code 只提供 provider 原生支持的档位；可选项和实际行为还取决于 provider、默认值与项目覆盖。

排查审批行为时，要分开看权限档位（runtime mode）、规划等交互方式（interaction mode）、provider 原生检查和管理员的托管策略（managed policy）。较宽松的档位不一定关闭危险命令、网络访问或删除保护；托管策略也可能限制可用档位。

## 6.1 权限挂在线程上

在 composer 里选档位，它只作用于当前线程；新线程的档位会显示在 composer 下方。若线程用的是默认档位，打开模型选择器并在底部选 **Permissions**，或直接按 `mod+shift+a`；线程用别的档位时，档位名称显示在模型旁边。批准或拒绝在对话里完成，批准后 agent 继续；档位不会阻止 agent 问你任务相关的问题，两者是不同通道。subagent 的审批请求出现在父会话里并带 subagent 名字，你不用切线程就能回应。管理员可用托管策略限制机器上可用档位，超过上限的档位会显示是谁在管理。

| 档位 | 官方定义的行为 |
|---|---|
| Supervised | 命令和文件改动都请求批准 |
| Auto-accept edits | 文件改动自动批准，其他动作仍可能需要批准 |
| Auto | 用 provider 的自动审阅批准常规动作，其余询问 |
| Full access | 命令和改动不需批准提示 |

可以这么理解：档位是线程的策略，审批是会话里的事件；同一环境里不同线程完全可以各用各的档位。ACP Registry agent 比较特殊：它们用自己的模式跑自己的工具，T3 Code 按你选的权限档位来回答它们的审批请求。托管策略的上限与 provider 的能力上限是两道不同的闸门，前者管「允许你选什么」，后者管「选了以后真能执行什么」。

## 6.2 Supervised

Supervised 的定义最直接：命令和文件改动都要请求批准。但「都要」在 provider 侧有细微差别——官方文档指出，某些只读动作在 Supervised 下可以直接进行，不必逐个批准。审批请求的选项 ID 要原样透传 provider 的原生值，每个请求都必须能被拒绝；这是适配器文档对权限实现的硬要求，目的是避免 UI 把厂商的审批语义改写掉。

Claude 在审批挂起时有个很好用的细节：直接键入一段文字回复，就能拒绝那个请求并把反馈交给请求方（包括 subagent），其他待处理请求保持未答。Kiro 只提供 Supervised 和 Full access，而且在 Supervised 下还会要求你审阅一个 turn 的文件改动——这比「逐条命令审批」多了一层。Muse Code 同样只提供 Supervised 与 Full access；任何被设成别档的 Muse 线程都会以 Supervised 运行。

对不支持自动审阅的 provider，Supervised 往往就是事实上的回落点：Auto 档在 OpenCode 这类没有等价机制的 provider 上会退回「逐个询问」。所以把 Supervised 理解为「最保守、兼容面最宽」的档位是合适的；它也是存储档位在 provider 不提供时回落的目标。按官方文档的说法，Unoffered stored modes fall back to Supervised——存储里的档位若当前 provider 不提供，就按 Supervised 跑，而不是报错。

## 6.3 Auto-accept edits

Auto-accept edits 的官方定义是：文件编辑自动批准，其他动作仍可能需要批准。注意「其他动作」这个措辞——命令执行、网络访问、工具调用并不因为文件编辑被放行就一并放行。这也是它和 Full access 的分界：前者只省掉一类审批，后者免去所有批准提示。

几家 provider 并不提供这一档。fx 没有 Auto-accept edits，Grok 也没有；Grok 线程若已被设成这一档，会以 Supervised 运行。Muse Code、Kiro 只提供 Supervised 与 Full access，自然也没有这一档。存储档位遇到这种情况的通用处理就是回落到 Supervised，而不是悄悄升级到更宽松的模式——这一点在适配器文档里是明确禁止的：不要通过自动回答审批来伪造缺失的权限模式。

Grok 有个专门的细节：它的文件改动审批提供 **Allow all edits this session**，但命令审批没有会话级全选，因为 Grok 会把那条命令记到整个项目范围。文件改动与命令的持久影响不同，所以 UI 给出的选择也不同。档位名称和实际可用按钮由 provider 的原生审批能力决定，T3 Code 透传 option ID 而不改写其含义。要核对某家 provider 到底提供哪些档位，最可靠的位置是 **Settings → Providers** 与该提供方的指南。

## 6.4 Auto

Auto 的行为是「用 provider 的自动审阅批准常规动作，其余的问你」。它依赖 provider 真有自动审阅：Codex、Claude、Cursor、Grok、Antigravity 和 fx 有；没有等价机制的 provider（官方文档点名 OpenCode）会退回逐个询问。在 Grok 和 Antigravity 上，自动审阅没有批准的动作会回到你这里；在 fx 上，它仍然发送的审批提示也会同时呈给你。Auto 不是「无人值守」，而是「把一部分判断外包给 provider 的审阅器，剩下仍由你把关」。

Antigravity 的限制尤其要记住：只有当你的 Antigravity 登录态提供 Auto 模式时才有这一档；某些账号（包括某些个人 Google 账号）没有。没有时，一个已经设为 Auto 的 Antigravity 线程会以 Supervised 运行。这与适配器文档的诚实能力原则一致：只声明 provider 真正支持的能力，一个留着开启却会在运行时失败的能力被视作 bug。

交互方式也要分清。规划（plan）属于 interaction mode，而不是权限；文档要求隐藏 plan mode，除非它能产出 proposed-plan cards。把「让 agent 先出方案」和「让 agent 不用批准就动手」混为一谈，是配置权限时最常见的错误之一。要查看当前线程的档位，不用进设置：模型旁边就显示着；要切换，`mod+shift+a` 一步到位。子 agent 的审批则回到父线程显示，不必因为它换了执行者就换一套理解。

## 6.5 Full access

Full access 的定义是：命令和编辑都不弹批准提示。它也是新线程的初始默认档位；已存在的线程、以及你在草稿里选过的档位会保留原值，不会被默认值覆盖。注意「不弹提示」不等于「provider 的所有安全机制都关闭」。

Codex 在 Full access 下，危险命令检查本来会问的那些命令不再问；但托管网络设置不允许的网络访问仍会问，除非你已在该会话批准过命令。Claude 在 Full access 下仍可能询问：它的设置禁用了 bypass permissions，或某动作要求批准时就会问。bypass 模式下的危险删除安全检查会带着原始警告拒绝命令；若警告给出安全重写就用它，否则 Claude 跳过该删除并告诉你跳过了什么。Antigravity 在 Full access 下也能发原生审批请求，而且只对支持记住的动作提供「记住批准」。

这些例外的方向并不一致：有的 provider 在宽松档位下仍然询问，有的会拒绝而不是执行，有的允许安全改写。可以这么理解：权限档位控制的是 T3 Code 侧的审批策略，provider 自己的安全策略仍按各自实现运行；适配器不能替它们做决定。因此看到 Full access 线程里仍出现一条审批，先查 provider 指南中的 provider differences 段落，再判断是否属于 bug，而不要以为档位没生效。管理员还可以用托管策略压低上限，把高于上限的档位标成由他人管理。

## 6.6 默认值与项目覆盖

新线程默认档位设在 **Settings → Threads → New threads → Permissions**。新线程用的是这个设置，而不是你刚才查看的那个线程的档位；已有线程和在草稿里选过的档位保持不变。项目可以覆盖环境默认，于是同一台机器上的两个项目可以一个宽松、一个保守。

设置页顶部的 “Applying settings for …” 句子告诉你这次改动作用于哪个项目和哪个环境；纯设备偏好页（例如外观）不显示它。服务器侧设置从 **All projects** 与 **All environments** 开始：选一个环境只改它；保持 **All environments** 则对当前已连接环境批量编辑，离线环境保持原值——文档特意强调这不是同步的全局默认。多个环境取值不一致时控件显示 **Mixed**，layers 图标变琥珀色；选一个值会应用到所有选中环境。每个服务器行标题旁的 layers 图标能展开取值链，显示来自内置默认、环境还是项目覆盖；覆盖可以 reset 回继承。改环境值不会碰项目自己的覆盖，图标会数出有多少项目覆盖了它。

```text
项目覆盖 → 环境设置 → t3.json（若仓库可声明） → 内置默认
```

对仓库也能在 `t3.json` 里声明的设置，解析顺序如上；留成 **Inherit** 就让下一层决定。移动端在 **Settings** 顶部筛选器里选环境与项目：**All projects** 时改所选环境的默认值，选中项目时改其覆盖；**Use defaults** 移除该页的项目覆盖。一个容易忽略的例外是 provider 开关：选中项目后，**Settings → Providers** 里的开关只影响该项目，可以在全机关闭的项目里单独打开，也可以把全局开启的 provider 关掉；但其余 provider 设置仍按机器保存。

## 6.7 不伪造不支持的模式

适配器文档的规则毫不含糊：never emulate missing permission modes。只暴露 provider 原生强制执行的模式，不要靠在 T3 Code 里自动回答审批来假装某个模式存在；存储里不被提供的档位回落到 Supervised；原生审批与问题的 option ID 原样透传，并确保每个请求都能被拒绝。能力声明也同理——声明未真正支持的能力（fork、rollback、steering、subagent）却在运行中失败，被定义为 bug。

```text
请求档位 → provider 是否原生支持？
    ├─ 是 → 透传原生 option ID，允许拒绝
    └─ 否 → 回落到 Supervised，不模拟、不自动批准
```

这条规则还延伸到相邻功能：plan mode 要藏起来，除非它能产出 proposed-plan cards；provider 无法回滚会话时，必须在动文件前拒绝回滚；健康探测必须被动，不能为了查状态开一个会启动 MCP server、跑 hook 或触发登录的会话。可以这么理解：权限的可信度来自「UI 说的和底层做的一致」，任何一层偷偷补位都会破坏它。非一方 agent 严格遵循 ACP，共享适配器不为特定厂商加分支或扩展；需要规范外行为的一方 driver 才用专用 ACP flavor，原生 `ProviderAdapterV2` 只服务非 ACP 协议。

## 6.8 本章要点与来源

四档定义要记牢：Supervised 对命令与文件改动都请求批准；Auto-accept edits 只自动放行文件编辑；Auto 借 provider 自动审阅处理常规动作，剩下问你；Full access 免去批准提示，是新线程初始默认。档位按线程设置，在 composer 或 `mod+shift+a` 切换，subagent 的审批回到父线程；托管策略可压低可用上限，provider 的安全检查可能继续生效。默认值在 **Settings → Threads → New threads → Permissions**，项目可覆盖环境；**All environments** 只是对当前已连接环境的批量编辑，出现分歧时显示 **Mixed**，layers 图标展示取值链。档位回落的方向只能是 Supervised，不能靠自动回答审批伪造模式；option ID 要原样透传、每个请求可拒绝，plan mode 没有 proposed-plan cards 就隐藏。provider 差异值得单独复查：Auto 依赖 Codex、Claude、Cursor、Grok、Antigravity、fx 的自动审阅，OpenCode 等退回询问；Antigravity 的 Auto 还取决于登录态；Grok 文件审批有会话级全选而命令审批没有；Claude 与 Codex 在 Full access 下仍各有安全例外。选中项目时 provider 开关只影响该项目，其余 provider 设置仍按机器保存。按官方文档 `user/permission-modes.md`、`internals/03_providers.md` 与 `user/project-settings.md` 的条目，可以自己核对各家差异与设置路径。
