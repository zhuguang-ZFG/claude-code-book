# 第 7 章：工作树、检查点与回滚
<!-- block: t3code-ch07.b-opening -->

这一章回答一个很实际的问题：agent 改完文件之后，T3 Code 凭什么说“这些改动属于这一轮”，又凭什么敢把工作区倒回去。我们从 worktree（工作树）这个隔离单位讲起，再看检查点如何落到隐藏 Git ref，最后走到 Diff 面板与 Revert 按钮。先把这两件事的先后顺序钉住，再谈界面上的按钮。

阅读顺序是先机制、后界面：7.1—7.3 解释隔离与提交顺序，7.4—7.5 说明回滚能做什么、不能做什么，7.6—7.7 处理多仓库和失败恢复，7.8 收束。文中命令与菜单均出自钉版文档，按官方文档给出的路径可以自己核对。

## 7.1 每线程一个 worktree

工作树（worktree）是 T3 Code 把“一个任务的改动”关起来的容器。按官方文档，独立任务用新线程；代码改动需要独立分支时用 **New worktree**。架构上，服务器（`apps/server`）拥有 provider 进程、终端、Git、检查点、持久状态和项目文件，客户端运行时（`packages/client-runtime`）只拥有连接与域状态，因此目录、分支与回滚都由服务器决定，网页、桌面和手机只是把持久化状态画出来。同一 checkout 上的线程共享分支；有线程在跑时，切换分支会被拒绝——这是并发边界，不是一条 UI 提示。消息文档进一步收紧了这条边界：**Revert files too** 只对运行在 worktree 里的线程提供；若另一个线程或 agent 会话也在使用同一目录、它的子目录，或包含它的目录，文件还原会被拒绝，因为还原会抹掉对方的工作。属于当前线程、已完成的 subagent 不阻塞还原，前提是它们没有排队工作、活动工作、待处理请求或后台任务。可以这么理解：worktree 同时承担隔离与授权两件事。

## 7.2 隐藏 Git ref 检查点

检查点（checkpoint）不是一次提交。架构文档把 provider 的一轮结束与后续结算（checkpoint、diff、PR 同步）明确分成两个里程碑：run 在 provider turn 结束时变为 `completed`，而 turn-end checkpoint 在之后才被捕获，作为线程 effect lane 上的一个 outbox effect。捕获提交之前，读者把缺失的检查点当作 pending，command 决策仍然把这个 run 看成 `waiting`，于是 steer、排队 turn、rollback 与 restore 都排在捕获之后。检查点使用隐藏的 Git ref，工作区快照不会给用户的分支增加任何 commit——这是它与手工 `git commit` 的根本差别。可以这么理解：`completed` 说的是“agent 停口了”，`waiting` 说的是“这一轮还没结算完”，两者并存是设计而非故障。架构文档还要求，迟到的结算不能让客户端继续把 provider 显示为工作中，也不能拉长记录的 provider 时长；客户端渲染的是持久化的 settlement 状态，而不是从本地时钟或 PR 缓存推导出来。检查点虽不出现在分支历史里，却能让 Restore 找到完整的工作区。

```text
provider turn 结束  →  run = completed
        ↓  （线程 effect lane 上的 outbox effect）
checkpoint 提交      →  投影可见  →  run 不再 waiting
        ↓
diff / PR 同步等 settlement 由服务器拥有
```

## 7.3 effect lane 与先拒后改

回滚不是一次本地文件操作，而是一条贯穿编排链路的决定。orchestrator 串行化 command、只决定 events、不做 I/O；EventSink 在一个数据库事务里提交 events、持久化投影、command receipts 与 outbox effects，再通知订阅者；EffectWorker 在提交后跑副作用，并把结果作为 command 喂回。因此 command 的确认只代表意图已提交，不代表检查点、provider 或后续工作完成。

| 环节 | 拥有什么 | 对回滚的含义 |
| --- | --- | --- |
| orchestrator | 决定 events，不碰 I/O | 串行化 command，不直接改文件 |
| EventSink | 单次数据库事务 | events、投影、receipts、effects 同生共死 |
| EffectWorker | 提交后的副作用 | 把结果作为新 command 喂回 |

架构文档给出一条硬规则：如果 provider 无法回滚自己的会话，必须在动文件系统之前拒绝 revert。和恢复时把丢失 provider 进程绑定的 effect 退休（retire）而不是重放一样，这条规则把不可逆的动作挡在起点。可以这么理解：effect lane 规定了先后顺序，“先拒后改”规定了失败的代价上限。

## 7.4 回滚的边界

在界面上，回滚从一条已发送消息的 **Edit from here** 开始。消息文档列出两个分支：**Revert and keep changes** 保留工作区文件原样，只把对话倒回；**Revert files too** 把工作区放回该消息之前的检查点，而且会一并撤销用户自己做的编辑。后者只在 worktree 线程里提供，遇到 7.1 所述的共享目录会被拒绝；在直接工作于项目目录的线程里，只能倒回对话。撤销会把所选消息及其后续对话从活动线程和 provider 历史中移除，但不撤销外部动作，也不清理 provider 自己保存的记忆；该动作只在 provider 支持 rewind 时可用。另一头，源代码管理文档提醒：**Restore** 返回的始终是完整保存的工作区，而 turn 的 diff 只展示这一轮自己的改动。可以这么理解：diff 是视角，restore 是状态，两者不该混为一谈。所以 Revert 是一次带前置条件的 command，而不是直接写盘。

## 7.5 编辑历史里的 Revert

回滚之后，交互落在 composer 上：所选提示及其附件会回到输入框供编辑与重发，尚未发送的草稿保留在被恢复提示的上方。若只想找回原文，在空 composer 里按 `ArrowUp` 会召回本线程最近发送的提示，再按一次继续往前，`ArrowDown` 往回走；召回只还原文本，附件、终端上下文等附加内容不会恢复，且一旦编辑就变回普通草稿。更长的停留由 prompt stash 承担：`Cmd+S`（macOS）或 `Ctrl+S`（Windows/Linux）保存当前提示与附件，空 composer 时同一快捷键恢复；含上传文件的 stash 必须在原环境恢复，这些文件保留 24 小时，过期后需用 **Attach again** 或移除缺失文件再发送。引用回复形成的 chip 也跟随这条链：复制含 chip 的文本粘进另一条草稿，chip 连同指向一起过去，图片与文件会从原环境重新抓取，期间显示虚线边框；若原文已不可用，同样以虚线提示，悬停会告诉你该怎么处理。删除 chip 像删除字符一样简单。

```text
已发送消息
  └─ Edit from here
       ├─ Revert and keep changes   →  文件原样，对话倒回
       └─ Revert files too          →  回到该消息前的检查点
```

## 7.6 多仓库下的 diff

源代码管理文档明确：一个 turn 的变更文件与 diff 只显示这一轮自己的工作。pull、merge、rebase 带进来的文件被排除；但若本轮编辑过、提交过，或在其中解决过冲突，文件仍留在列表里。想看相对基线分支的全部变化，要使用分支比较。在多仓库项目里，Diff 面板会显示本轮改动过的每一个仓库，旁边的 repository picker 可以收窄到其中一个；diff 里的路径从线程文件夹开始，因此两个仓库里的同名文件不会混在一起。分支比较与未提交改动每次只读一个仓库，同样从该 picker 选择。线程详情面板按最近使用顺序列出各仓库及其分支与未提交改动，展开即可提交、推送或开 PR；**Other repositories...** 能把项目里的其他仓库加进来，直到刷新为止。仓库较多时，先用 repository picker 收窄范围更省力；同名路径以线程文件夹为根，因此不会被误判为同一文件。

## 7.7 恢复失败的工作区

失败恢复的第一原则是别把“确认”当成“完成”。command receipt 只说明意图已写入；turn-end checkpoint 在提交前仍是 pending，此时读到的 run 还处于 `waiting`。若 provider 会话无法回滚，revert 会在触碰文件系统之前被拒绝；若目录还被别的线程或 agent 会话使用，文件还原同样会被拒绝。架构文档还规定：与丢失的 provider 进程绑定的 effect 在恢复时退休，而不是重放——所以重连后不该期待那些副作用再跑一遍。附件侧也有对应边界：上传在添加附件时就开始，全部完成才能发送；失败的上传要重试或移除，网页和桌面在上传完成前重载就得重新附加文件。可以这么理解：恢复是一个“重新对齐已提交状态”的过程，不是把整段时间重演。收到 receipt 只说明意图已提交，还要等 EffectWorker 把结果作为 command 喂回，投影更新才算可见。

## 7.8 本章要点与来源

本章的关键结论有四条。第一，worktree 是任务隔离单位，服务器拥有 Git 与文件，共享目录上的并发会被明确拒绝。第二，检查点走隐藏 Git ref，不给用户分支加 commit；turn-end checkpoint 是 effect lane 上的 outbox effect，提交前读者看到 pending、决策侧看到 `waiting`。第三，EventSink 的单事务把 events、投影、receipts、effects 绑在一起，而“provider 不能回滚会话就先拒绝 revert”是不可越过的顺序规则。第四，turn diff 只是本轮视角，Restore 返回完整工作区；多仓库要按 repository picker 一次看一个。遇到异常时，先查 command 是否已提交、检查点是否已落地，再决定是否重试，而不是先动文件。按官方文档给出的路径，可以逐项核对 worktree 的共享目录判定、effect lane 的顺序以及 Revert 的两个分支，不必依赖界面上的直觉。换句话说，安全性来自顺序约束，而不是来自按钮所在的位置。
