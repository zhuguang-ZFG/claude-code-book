# 第 8 章：从 diff 到一键 PR
<!-- block: t3code-ch08.b-opening -->

上一章把改动关进了检查点，这一章看它们怎样离开本地。Diff 面板回答“这一轮做了什么”，Git 操作回答“把它放到哪个分支并提交”，Pull requests 页面回答“别人怎样审”。T3 Code 把这三步都接进同一台环境服务器，凭据留在那台机器上。

读法是从小到大的交付半径：8.1—8.3 讲 diff 的口径与提交入口，8.4 列出支持的 forge 与登录命令，8.5—8.6 走推送、开 PR 与审查同步，8.7 处理一个项目里有多个仓库的情况，8.8 收束。所有菜单路径与命令都来自钉版文档，按官方文档给出的路径可以自己核对。

## 8.1 从 diff 到交付

交付的起点是线程里的 Git 操作：提交、推送、创建 pull request 都能从线程的 Git actions 发起。T3 Code 可以依据改动生成 commit 消息、审阅 PR 标题和描述，描述还会引用线程里的工作，包括跑过的检查。写作风格由 **Settings → Source control & issues → Commits & pull requests** 决定：**Repository conventions** 使用项目说明与最近的 commit subject，**Custom instructions** 使用用户自己的指令。本地从零开始时，命令面板（`Cmd/Ctrl+K`）的 **New project** 会在 `~/.t3/projects`（T3 数据目录的 `projects` 文件夹）里建仓库、README、图标和首个 commit，再用它开新线程；打开 **Create private repository on GitHub** 会同时发布。若 Git 没配 name/email，项目仍会创建，只是没有首个 commit。想按 ghq 的布局存放克隆，可在 **Settings → Threads**（移动端是 Source control）打开 **Clone into host folders**，并把 **Add project starts in** 设为 `~/ghq`；克隆前仍可修改目标目录。只有 GitHub 默认出现在克隆来源列表，其他 provider 要先在 **Settings → Source control & issues** 打开开关才会列出；从 GitHub、GitLab、GitCafe、Codeberg 或 Bitbucket 复制的分支页、文件页也能直接克隆其默认分支。可以这么理解：diff 是交付的输入，线程上下文是消息的语料，设置项决定语气。

## 8.2 turn 自己的改动

Diff 的第一条口径是“只属于本轮”。一个 turn 的变更文件与 diff 只显示这一轮自己的工作：pull、merge、rebase 由 Git 带进来的文件被排除；本轮编辑过、提交过，或在其中解决过冲突的文件仍会留下。想看相对基线分支的完整变化，要用分支比较，而不是盯着 turn diff。另一条口径是“还原看全量”：**Restore** 返回的始终是完整保存的工作区，这与 turn diff 的局部视角并不矛盾。代码托管站点上的 commit 链接也能进入 Diff 面板：只要线程仓库本地拥有该 commit，无论它在哪个分支，链接都会在面板里打开；否则 PR 上的 commit 链接会打开对应 PR。其余 commit 链接遵循 **Open links in** 设置，网页端在新标签打开时先显示 **Open link** 按钮；`Command/Ctrl+Click` 始终用浏览器打开。是否走 T3 Code 内部，由 **Settings → Diffs → Open pull requests in T3 Code** 控制。merge commit 只按第一父提交比对，能避免把合入分支的历史误算成本轮工作。

## 8.3 分支比较与提交

在网页和桌面上，Diff 面板的 source picker 里有 **Commits** 一项，用于逐个查看本地提交；列表显示分支比较中最近的 100 个 commit，merge commit 按它的第一个父提交展示差异。提交从线程详情面板或 Git actions 发起；若已有 fork PR 与分支并存，而推送时没设置 upstream，徽章可能缺失，这时用命令固定远端：

```sh
git branch --set-upstream-to=<remote>/<branch>
```

提交消息与 PR 文本按 8.1 的设置生成。审阅时可打开 **Pull requests** 页，在那里请求 reviewer、 checkout 分支或合并；GitLab 把 PR 叫作 merge request。合并或审阅作用于开 PR 时的那批 commit：若期间有人推送，网页和桌面会提供 **Load new commits**，在此之前合并与审阅会被拒绝，草稿保留。视图可用 **Views → Save current view** 保存搜索、筛选、排序和范围，但保存的视图只留在创建它的浏览器或应用里，不跨设备同步。改了筛选之后，用 **Update saved view** 更新原视图，或者另存一个；同一菜单里也能重命名和删除；视图会记住搜索词、筛选、排序以及服务器与项目范围。

## 8.4 支持的 forge

源代码管理文档列出的集成包括 GitHub、GitLab、Forgejo、Gitea、Bitbucket、Azure DevOps、GitCafe 和 Cursor Origin；TanStack Source 处于私有 beta，需要服务端设置 `T3CODE_FEATURE_FLAGS=tanstack_source` 并重启。各家登录入口不同，但共同点是凭据配置在运行 T3 Code 服务器的那台机器上，远程环境就要在远程机器上做。

```sh
gh auth login                    # GitHub：需 2.81.0+
gh auth login --hostname YOUR_HOST
glab auth login                  # GitLab
fj --host https://your-server auth add-token   # Forgejo
tea login add                    # Gitea
bun install -g @gitcafe/cli && cafe auth login --host https://git.cafe/api
az extension add --name azure-devops && az login
```

| forge | 凭据入口 | 需要注意 |
| --- | --- | --- |
| GitHub | Settings 保存 token / `GH_TOKEN` / `gh auth login` | CLI 至少 2.81.0 |
| GitLab | `glab auth login` | PR 叫作 merge request |
| Forgejo / Gitea | `fj --host … auth add-token` 或 `tea login add` | 共用一个集成入口 |
| Bitbucket | Settings 里填 token 或邮箱加 API token | 两者并存时 token 优先 |
| Azure DevOps | `az extension add --name azure-devops` 后 `az login` | 需先装扩展 |
| GitCafe / Cursor Origin | `cafe auth login` / `origin auth login` | 行级评论/私有发布 |

GitHub 的优先级是：Settings 里保存的 token（存在服务器 secret store，不依赖 CLI）→ 环境变量 `GH_TOKEN`（Enterprise 配 `GH_HOST` 时用 `GH_ENTERPRISE_TOKEN`）→ 已登录的 GitHub CLI。Forgejo 与 Gitea 共用一个入口，优先匹配 `fj`，无登录或不可用时回退 `tea`；URL 子路径部署（如 `https://example.com/forgejo`）要用 `tea`。登录完成后回到 **Settings → Source control & issues → Rescan**。Bitbucket 在同一设置页二选一：针对单个仓库、项目或工作区的 access token，或 Atlassian 邮箱加 API token（需要 repositories 读写、`read:user:bitbucket` 与 `read:workspace:bitbucket`）；两者都填时 access token 优先，保存后不可再次查看。无头服务器可在启动服务器的环境里设 `T3CODE_BITBUCKET_ACCESS_TOKEN`，或成套设 `T3CODE_BITBUCKET_EMAIL` 与 `T3CODE_BITBUCKET_API_TOKEN`；后台服务则写进 T3 home 的 `service.env` 再运行 `t3 service restart`。Cursor Origin 若推送时索要用户名，运行 `origin auth setup-git` 重新指向 CLI 凭据。

## 8.5 推送与开 PR

创建 PR 同样从线程的 Git actions 走：先提交、再推送、再开 PR，T3 Code 会审阅标题和描述，描述也会纳入线程里跑过的检查。对本地已有仓库、尚无远端的情况，**Publish Repository** 会创建托管仓库、把它加为 `origin` 并推送已有 commit；若还没有 commit，则只先建远端，用户需先提交再推。克隆时，选择 hosting provider 或粘贴 Git URL，再选保存位置；只有 GitHub 默认列出，其他 forge 需在 **Settings → Source control & issues** 打开开关。项目会在克隆于后台运行时立刻打开，此时可以写第一条提示，发送会等到文件就位；进度条可取消，失败可从提示重试。若主机拒绝本机 SSH key，T3 Code 改用该主机的 HTTPS 与 Git 凭据，项目 remote 也随之使用 HTTPS URL。GitCafe 的 PR 暂不支持行级评论，合并 stack 会通过 GitCafe 落地。Origin 仓库走 HTTPS 且私有发布；从 GitHub 镜像来的仓库，PR 仍留在 GitHub，要从 GitHub remote 打开。Origin 登录时也会为 `origin.cursor.com` 配好 Git 凭据，推送通常无需再设置；克隆与推送仍需对应服务器的 Git 凭据或 SSH key。

## 8.6 PR 同步与审查

Pull requests 页负责审查与合并：可以看评论、请求 reviewer、checkout 分支、合并；主机允许时还能编辑标题、描述和自己的评论，Summary（移动端是 Overview）标签页里可勾选描述中的复选框。行文件可被标记 viewed：GitHub 使用站点自身的记录，T3 Code 与 github.com 双向同步；Forgejo、GitLab、Bitbucket、Azure DevOps、Cursor Origin 没有可读记录，改由连接的服务器保存，显示为 *viewed in T3 Code*，主机网站上不会显示。审查指南（Review guides）是 beta，在 **Settings → Source control & issues** 打开后会给 PR 加上 **Guide** 标签页，按阅读顺序组织停留点；写作模型来自同一设置，未指定时用 source control writer model。合并信息可用 **Remove agent credits when merging** 去掉识别出的 agent co-author 与 generated-by 行，默认关闭且项目可覆盖。PR 共享默认关闭：在 **Settings → Environments → Pull request sharing** 为每个环境选择 **Read PRs** 或 **Read and act**；后者可能用到比原环境凭据更广的权限，只应对自己控制的环境开启。审查指南按阅读顺序给出停留点，机械性改动（重命名、快照）集中放在末尾，每条停留点指出值得读的行；需要维护者判断的会标 **Look closely**。

## 8.7 多仓库发布

一个项目可以覆盖多个仓库，但发布动作一次只作用于一个仓库。网页和桌面的线程详情面板按最近变更顺序列出仓库，每个带分支和未提交改动，展开后在该仓库提交、推送或开 PR；移动端打开 **Git controls**，在 **Repositories** 下选一个仓库再操作。**Other repositories...** 可临时加入项目里的其他仓库，直到刷新；在 worktree 线程中，它加入的是该仓库的 worktree。新开的 PR 挂在具体仓库下，而不是项目下。若要排除项目文件夹里的某个仓库，在项目根的 `t3.json` 写明相对路径：

```json
{ "ignoreRepositories": ["vendor/big"] }
```

t3.json 会随仓库提交，因此该选择在所有机器生效。限制也要记牢：一次 Git 动作只在一个仓库运行，没有跨仓库的批量 commit 或 push；只有项目文件夹的 `t3.json` 会被读取，仓库内部的脚本与动作不会；Diff 面板的 repository picker 与纯文件夹的基线分支输入框只在网页和桌面提供。

## 8.8 本章要点与来源

交付链可以压缩成四句话。第一，turn diff 只算本轮的账，pull/merge/rebase 带进来的文件不算，完整视角靠分支比较。第二，提交与开 PR 从线程 Git actions 发起，消息风格由 Settings → Source control & issues → Commits & pull requests 决定；merge commit 在 **Commits** 视图里按第一父提交看差异。第三，凭据归环境：GitHub 走保存 token、`GH_TOKEN` 或 2.81.0 以上的 `gh`，其他 forge 走各自的 CLI，登录后要 Rescan。第四，多仓库项目里 diff 可以一次看全，Git 动作却一次只能作用于一个仓库，且被 `t3.json` 的 `ignoreRepositories` 约束。按上述菜单逐项对照，就能从一条 diff 走到可审的 PR。别忘了 turn diff 的排除规则在多仓库里同样成立：pull、merge、rebase 带进来的文件不会出现在某一轮里，完整范围要看分支比较，而每个仓库的 PR 都挂在自己名下。这样就不会把“这一轮做了什么”和“这个分支一共改了什么”混起来。排障时也要先在服务器上登录对应 provider，再回设置页 Rescan。
