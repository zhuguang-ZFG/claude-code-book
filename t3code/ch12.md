# 第 12 章：关联环境：统一鉴权与作用域
<!-- block: t3code-ch12.b-opening -->

前面几章反复出现“scope”“凭据”“会话”这些词，本章把它们收束成一套规则。T3 Code 的鉴权中心不是云端账号，而是环境本身：环境签发会话、执行作用域检查、决定谁能拿到凭据。guest link 与 secret 是两套刻意分开的机制，不能冒充会话。

阅读顺序从主体到边界：12.1—12.3 讲谁发会话、作用域如何收窄、`access:write` 为何特殊；12.4—12.5 讲 DPoP、WebSocket 票据与逐 RPC 授权；12.6—12.7 处理 guest link、文件系统与 secret；12.8 收束。字段名与路径均来自钉版文档，按官方文档给出的路径可以自己核对。特别留意“不是会话”的两个例子：访客链接与 secret 引用。

## 12.1 环境自己发会话

环境自己签发会话，并强制会话的能力边界。云身份与 relay 凭据属于另一条信任边界：relay token 永远不是环境登录。默认授权包含 `terminal:operate` 与 `orchestration:operate`，因为二者已经等于以 OS 用户身份执行（可以调用 `t3 auth session issue`），若把访问或 relay 管理从默认授权里扣掉，并不会形成真正的边界；需要更窄的客户端则显式指定 scope。浏览器 cookie、bearer token 与 DPoP token 共用这套作用域会话模型。开发服务器上可用固定的 `T3CODE_DEV_AUTH_TOKEN` 跨 worktree 与端口工作，但每个环境把值哈希进自己的数据库记录，并各自持有 SQLite 状态、签名密钥和撤销状态；正常凭据优先，正常凭据被拒绝时不会回退到开发凭据。它还会被桌面应用和非开发服务器忽略。

| 主体 | 归属 | 关键边界 |
| --- | --- | --- |
| 环境会话 | 环境自己 | 签发、撤销、scope 检查都在环境 |
| relay / 云身份 | 另一信任边界 | relay token 不是环境登录 |
| 开发凭据 | 单个环境数据库 | 正常凭据优先，不跨环境复用 |

## 12.2 作用域只能收窄

配对是一次委派：它交出一组 scope。用 bootstrap 凭据换取会话时只能缩小授权，永远不能放大；客户端自报的标签与设备元数据在授权上没有任何作用。令牌交换把请求的 scope 与配对授权求交，丢弃已退役或无法识别的名字；若 intersection 后一个 scope 都不剩，就在消耗配对链接之前失败。已存储的授权在 scope 拆分时从不被扩张。为了兼容新旧端，鉴权响应同时保留旧的 `scopes` 字段与精确的 `permissions` 字段：前者给旧客户端读，后者给新代码逐项判定。

```text
配对授权 = { orchestration:read, terminal:operate, relay:read }
请求交换 = { orchestration:read, relay:read, retired:scope }
实际会话 = { orchestration:read, relay:read }   #  retired 被丢弃，不能新增
```

这条规则可以这么理解：配对链接是一张有面额的支票，兑换时只能撕掉一角，不能补写数字。同一环境上的多次配对各自独立，新链接不会让旧链接获得更大权限。网络路径的变化（详见第 11 章）也不改变面额，只是改变谁能把支票送到环境面前。

## 12.3 access:write 的特殊地位

凡是“把凭据返回给调用方”的路由，都要求 `access:write`，并且要求该凭据携带的每一个 scope：配对链接、MCP 登录批准、关联环境发来的 link code、读取线程的 guest link，都在此列。撤销则不受调用方 scope 上限约束——能撤销任何东西，这是刻意的非对称设计。接纳一台 T3 Connect 设备不属于委派，因此不走这条规则。

读模型里没有可恢复的密钥。原始配对凭据只在创建响应里出现一次；访问列表只返回元数据。这意味着即使某个会话能列出凭据，也拿不到可重放的秘密值。同样，MCP 客户端是独立 audience：外部 agent 在 `/mcp` 上通过 PKCE OAuth 登录，客户端注册是无状态的，未认证调用者不能借此增长服务端状态；用户授予的是只读访问或运行时模式上限，而不是一把原始 scope。可以这么理解：读得到“有一把钥匙”的描述，不等于读得到钥匙本身；而 `access:write` 是唯一允许发钥匙的那道门。

## 12.4 DPoP 与票据

DPoP（demonstration of proof-of-possession）把令牌绑定到客户端的证明密钥。浏览器 cookie、bearer token 与 DPoP token 共享作用域会话模型，但 DPoP 请求必须带有效证明：证明无效就失败，绝不能退化成 bearer 认证。普通配对产生的 DPoP 会话会就地续期，因此活动 WebSocket 与 **Sharing & access** 里的会话行保持稳定；T3 Connect、CLI 和桌面会话不会自我续期，所以撤销或解除链接能真正切断它们。

WebSocket 使用短期票据。Bearer 与 DPoP 客户端先通过已鉴权的 HTTP 铸造短期票据，长期令牌因此不会出现在 socket URL 里；DPoP 的 RPC 票据在升级时仍绑定证明密钥。这里有两个并发边界值得记住：票据有效期短于会话，且握手成功不增加任何权限。可以这么理解：URL 里能看到的只是“入场券”，真正的身份与权限仍然留在 HTTP 层校验，升级不重新发牌。浏览器 cookie 也遵守同一套 DPoP 绑定，不存在一条绕过证明密钥的旁路。

## 12.5 每个 RPC 单独授权

握手成功不授予额外权威：每个 RPC 都声明并检查自己需要的 scope，判定集中在 `RpcAuthorization.ts`。所以“socket 连上了”和“能调用某个方法”是两件事，订阅只发送客户端需要的状态。非标准主体有更细的隔离：MCP 客户端（`mcp-client`）是独立 audience，除只读线程中继和限定给 peer link 的客户端配对路由外，所有非 `/mcp` 的 HTTP 与 WebSocket 路由都拒绝它；每个 MCP 工具必须在 `McpToolAccess.ts` 静态声明访问级别，而线程内专属工具还必须在处理函数里再次拒绝外部调用者——从工具列表中隐藏只是发现层，不是授权层。

关联环境（peer link）通过以普通 OAuth 客户端 `t3code-peer-link` 登录目标 `/mcp` 来工作，接收方像管理其他会话一样列出和撤销它，并拥有到期与续期。转发的调用在 `T3-Mode-Limit` 里携带调用 agent 的模式，接收方只能把它与 link 批准的访问求交，永远只能向下收窄。非 full access 的 link 还受不可变 `linkOrigin` 围栏：其线程及派生 fork、subagent 只能改动同源线程，不能碰项目、设置、定时任务或更多 link，并跳过项目初始化脚本。只有 full access 的 peer link 才能在被关联环境上铸造一次性客户端配对码，而且保留为人类触发的 RPC/HTTP 路由，不是 MCP 工具。

## 12.6 guest link 不是会话

guest link（访客链接）让别人在浏览器里跟着一个线程看并提问，无需账号。它是 beta：在运行线程的机器上打开 **Settings → Labs → Guest links**，且该机器必须通过 T3 Connect 登录并链接，因为链接指向它的 T3 Connect 地址；机器离线时链接不可用，设置关闭时本机所有 guest link 停止工作，重新打开后未过期的链接恢复。实现上，GuestShareService 签发的是绑定到线程投影中某一次分享的 HMAC token，不是 `SessionStore` 的记录，因此任何 RPC、WebSocket 或 MCP 路由都不能接受它；关闭、替换分享或归档线程会撤销全部 token。访客路由还要求 T3 Connect 仍在服务该链接的主机名，不能只信请求的 `Host` 头。

使用上，右键侧栏线程选 **Share with guest**，链接只在一个浏览器里有效、24 小时后过期；访客发来的消息先排队，侧栏显示 **Request**，由你 **Send** 或 **Dismiss**。访客能看到近期与后续消息流、agent 的推理、计划、问题和命令输出，但看不到 diff，也不能 fork、revert、打开你机器上的文件或替你回答。附件每条消息最多 4 个、合计 10 MB，图片限 PNG/JPEG/GIF/WebP；待处理消息的文件合计可达 20 MB。被忽略的消息在结束分享或归档线程时删除文件，已发送的消息则保留。agent 读过或打印过的内容都可能出现在页面里，分享前要先确认线程内容可以公开。

## 12.7 文件系统边界

项目是组织边界而非文件系统沙箱。`filesystem:read` 允许读取服务器 OS 用户能读的任何文件（例如 agent 写在临时目录的产物），相对路径与写入仍受 `WorkspaceFileSystem.ts` 约束。签名资源 URL 是针对单个规范文件的 bearer 凭据，服务时会按 device/inode 再核对身份，因此不能访问同级文件；但 `filesystem:read` 只在铸造时检查，所以已发出的 URL 在到期前有效，即使会话或授权被撤销也不会立刻失效。

secret 是另一条通道。当前支持的 provider 是 1Password：T3 Code 用 `op` CLI 读取，因此 `op` 必须安装并登录在运行服务器的机器上——手机或另一台电脑连接时，指的是远程机器。设置里可在凭据字段旁选择来源：**Value** 保存值本身，或选 secret provider 填 `op://vault/item/field` 引用；T3 Code 在真正需要时（如 provider 启动）才读取，改完 1Password 里的值后刷新即可生效。若 agent 需要密码，线程里出现的是私有 secret request 卡片，值不进入对话；多数请求连 agent 也看不到，T3 Code 直接把它交给需要的工具。若 agent 必须拿值跑命令，卡片会说明，值会写入私有文件供命令读取约 24 小时。

```text
op://vault/item/field  →  T3 Code 在需要时读取（如 provider 启动）
卡片中的值             →  交给需要的工具，不进入对话
必须用值跑命令          →  私有文件，命令可读约 24 小时
```

| 边界 | 允许 | 不允许 |
| --- | --- | --- |
| 项目 | 组织仓库与设置 | 充当文件沙箱 |
| 签名资源 URL | 单个规范文件，到期前有效 | 同级文件、撤销即失效 |
| secret 引用 | 需要时读取、刷新更新 | 明文进入对话 |

## 12.8 本章要点与来源

记住五个结论即可。第一，环境是鉴权主体：它签发会话、保存撤销状态，relay 凭据不是环境登录。第二，作用域只能收窄，令牌交换按交集裁剪并丢弃未知名字，响应同时带旧 `scopes` 与精确 `permissions`。第三，`access:write` 是所有发放凭据路由的前提，撤销却不受调用方 scope 限制；读模型不含可恢复密钥。第四，DPoP 证明无效就失败、票据短期且不放进 socket URL、握手后每个 RPC 仍单独检查 scope；MCP 是独立 audience，工具级声明与处理函数拒绝缺一不可。第五，guest link 是绑定一次分享的 HMAC token、不是会话；项目不是文件沙箱，签名 URL 只指向单文件且撤销不立即使其失效，secret 则以引用形式留在 1Password。按上述路径可以逐项核对。尤其是 `access:write` 与 `filesystem:read` 这两处：前者决定谁能发凭据，后者只决定铸造资源 URL 时的读权限。
