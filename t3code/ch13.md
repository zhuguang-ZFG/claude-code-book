# 第 13 章：MCP：让外面的 agent 进来
<!-- block: t3code-ch13.b-opening -->

日常终端里的 Claude Code、Codex，以及 ChatGPT 中的 agent，都可以通过环境自己的 MCP server 接入 T3 Code。官方文档把它们称为 outside agents；接入后的访问范围仍由环境授权。

接入时需要取得 MCP URL、完成审批并选择访问级别。下面给出各客户端的命令，再说明线程专用工具、登录有效期和撤销入口，便于核对接入后实际开放了哪些操作。

## 13.1 外面的 agent 如何进来

T3 Code 没有启动的 agent，可以通过环境的 MCP server 与这个环境协作：读项目和线程、启动与发消息、查询可用的 provider 与 model。官方文档点名的对象包括你自己的终端里的 Claude Code、Codex，ChatGPT，以及任何支持 MCP 的机器人；每个 agent 登录一次，你决定它能做什么。

入口有两个。其一是命令面板 `Cmd/Ctrl+K`（Windows/Linux 为 `Ctrl+K`）里的 **Use T3 Code in another app (MCP)**；其二是 **Settings → Sharing & access** 里的同名按钮。Poke、Claude 这类在云端运行的助手，向导会先要求登录 T3 Connect 并为该环境打开它；想通过同一条连接到达其他机器，还要在 Labs 里打开 **Linked environments** 并先把它们链接起来。

老环境走的是另一条路：向导不弹 OAuth 页面，而是给出一个 code 让你粘贴。文档写明这个 code 只能用一次、有效期 5 分钟，而且只批准当时选中的那一个级别。还有一类 app 明确要求使用自己的 client ID，官方文档说这类 app 无法连接——所以不要在这上面反复尝试。

## 13.2 拿到 MCP URL

在 **Settings → Environments** 打开一个已保存环境的菜单，选择 **Copy MCP URL**。这个 URL 就是环境地址后面接 `/mcp`：

```text
https://<environment-address>/mcp
```

复制到的地址取决于环境怎么被服务。若环境由 T3 Connect 提供，复制的是它的 T3 Connect 地址，agent 可以从任何地方访问；否则用的是当前设备正在使用的那条路由，同一台设备上的 agent 能直接到达。这个差别不是细节：它决定了 hosted agent 能否连上。

复制前要确认选中的是目标环境：URL 只指向一个环境，不会自动切到别的项目或机器。同一台机器上保存了多个环境时，菜单里的每一项对应一个环境，复制错地址就意味着登录到另一个环境，审批页上写明的访问去处也会不同。

登录会把 agent 的凭据送进环境，所以文档只接受 `https` 或 `localhost`。一个形如 `http://100.x.y.z:3773` 的明文局域网或 Tailscale 地址，能让 agent 找到环境，却不能完成登录。自己机器上的 agent 可以用主机上的 `localhost`、T3 Connect 或任何 `https` 地址（包括 Tailscale HTTPS）；ChatGPT 或云端机器人必须从公网到达环境，只能用 T3 Connect 地址，Tailscale 地址只在自己的 tailnet 内有效。

## 13.3 OAuth 登录与审批

MCP 客户端在鉴权模型里是独立 audience：`mcp-client` 会话通过 `/mcp` 上的 PKCE OAuth 登录，客户端注册是无状态的，未登录的调用方不能借此增长服务端状态。用户授予的是只读访问或一个运行时级别上限，而不是原始 scope。

agent 第一次连接时会打开登录页。经 T3 Connect 到达环境时，页面开在 T3 Code web app 上，用该环境链接的 T3 Connect 账号登录并在那里批准，不需要 code；其他情况页面开在环境自己的地址上。两个页面都会写明 agent 是谁、访问通往哪里：本机 agent 的批准回到发起页面的那台机器的 `localhost`，hosted agent 的批准则回到 `chatgpt.com` 这类服务——文档直说，运行那个服务的任何人都会得到这份访问。

环境自己的页面上需要输入 code，来源可以是 **Use T3 Code in another app (MCP)**、**Settings → Sharing & access**，或主机上的 `t3 auth pairing create`。已经登录该环境且有管理访问权限的浏览器可以不带 code 批准；web app 上的 **Use a sign-in code instead** 则切回环境自己的页面。只批准你刚刚发起的那次登录。

## 13.4 四档访问级别

带 code 的批准已经携带了你在向导里选的级别。用其他 code 时在这里再选，默认是 **Auto**，或者组织策略允许的最接近的更低档；完全不带 code 的批准从 **Read only** 开始。Read only 只能读项目与线程、查看可用 provider 与 model，不能改动任何东西。

从 Supervised 到 Full access 则额外允许在所有项目里启动、发消息和停止线程，并且该 agent 启动或 steer 的线程，运行时权限不能高于你选的级别。运行时上限仍是权限四档：

| 档位 | 文档给出的行为 |
|---|---|
| Supervised | 命令与文件改动都征求批准 |
| Auto-accept edits | 文件改动自动批准，其他动作仍可能要批准 |
| Auto | 用 provider 的自动审阅批准常规动作 |
| Full access | T3 内的初始默认档；作为外部访问上限时仍受你选的级别约束 |

执行层面有两道保险。每个 MCP 工具都必须在 `McpToolAccess.ts` 里静态声明访问级别；线程专属工具即便从工具列表里隐藏，仍要在 handler 里拒绝外部调用方。除只读线程转发和面向 peer link 的客户端配对路由外，每个非 `/mcp` 的 HTTP 与 WebSocket 路由都拒绝 `mcp-client` 会话。

## 13.5 各家的接入命令

对已列出的客户端，文档给出的是两条命令：先添加 HTTP 传输的 MCP server，再登录。

```sh
claude mcp add --transport http t3 https://<environment-address>/mcp
claude mcp login t3

codex mcp add t3 --url https://<environment-address>/mcp
codex mcp login t3
```

`claude mcp login` 和 `codex mcp login` 都会打开浏览器登录页；无浏览器的机器可以加 `--no-browser`，到别处打开打印出的 URL，再把最终 URL 粘回去。批准后 `claude mcp list`、`codex mcp list` 会显示 `t3` 已连接。ChatGPT 则是在 apps 设置里新建自定义 MCP app：服务器 URL 填同一个 `/mcp` 地址，认证选 **OAuth**，不需要 client ID 或 secret，然后批准弹出的登录页。

没被列出的 app 选 **Something else…**，在其中添加带 OAuth 的远程 MCP server 并粘贴 URL；不支持 OAuth 的 agent 连不上。命令里的 `<environment-address>` 就是上一步复制的地址去掉 `/mcp` 后的部分；hosted agent 务必填 T3 Connect 地址。列表里显示 OAuth 才说明登录生效，若只有连接标记，回到登录步骤重做。

在跑环境的主机上另有免登录路径：`t3 thread start . "Find why the tests are slow"` 启动，`t3 thread send "$id" "Now fix it" --wait` 继续，`t3 thread show "$id"` 与 `t3 thread list` 查看。`.` 指当前目录所属项目或其仓库的 worktree，新线程沿用项目默认 model 与权限档；主机路径不需要再走一遍 OAuth。

## 13.6 哪些工具只能在线程内

有几类工具只有运行在 T3 线程内部的 agent 才能调用，因为它们就是以那个线程身份行动：subagent、secret 请求、渲染后的 HTML、浏览器预览、设备，以及 worktree handoff。它们仍然会出现在外部 agent 的工具列表里，但调用会返回错误，说明需要运行在 T3 Code 内部的 agent。

文档特别纠正了一种常见误用：要交接工作，应先用 `t3_thread_launch` 启动线程，再用 `t3_thread_wait` 或 `t3_thread_read` 跟进，而不是 `create_threads` 或 `delegate_task`。凡是默认作用于调用方自己项目或线程的工具，都要显式传 `projectId` 或 `threadId`；跨项目列出线程用 `t3_thread_list` 的 `allProjects: true`，或改用 `t3_thread_search`。

外部 agent 还能通过 MCP Events（`io.modelcontextprotocol/events`）订阅事件，而不必反复读线程：turn 结束、agent 等人回答、guest 提问、被关注的 PR 唤醒线程，以及 workflow run 的开始、暂停、恢复、结束与等人。环境在内存里保留最近 1,000 个里程碑，离线过久或重启后重连会被告知可能缺失。webhook 只发往公开 `https` 地址，订阅最长 1 小时需续期，agent 登出即结束订阅；本地测试可设置 `T3CODE_MCP_WEBHOOK_ALLOWED_HOSTS=localhost,127.0.0.1`，这些主机允许明文 `http`。

## 13.7 撤销与有效期

已批准的 agent 和别的客户端一样出现在 **Settings → Sharing & access**，在那里撤销即可立即切断访问；登录有效期 30 天，到期后 agent 会再次请求批准。撤销后它手上已有的 token 与票据立即失效，下一次请求会被拒绝，而不是等到期；撤销本身不受调用方 scope 限制：`access:write` 能撤销任何东西，包括它自己拿不到的权限。

若某个 agent 是通过 T3 Connect 进入的，要注意「撤销这个 agent」和「把它从 T3 Connect 解绑」是两件事；前者只收回它对环境的访问。

传输层也有约束。DPoP 把 token 绑定到客户端证明密钥，证明无效必须失败，不能退化成 bearer；WebSocket 票据是经已鉴权 HTTP 铸造的短期票据，长期 token 不出现在 socket URL 里，DPoP 的 RPC 票据在升级时仍保持 proof-key 绑定。握手成功不增加任何权限，每个 RPC 都在 `RpcAuthorization.ts` 里声明并单独检查所需 scope。guest link 则是另一种东西：它是绑定到线程投影中某次分享的 HMAC token，不是 session，任何 RPC、WebSocket 或 MCP 路由都不会接受它。

## 13.8 本章要点与来源

外部 agent 的入口始终是环境的 `/mcp`，OAuth 登录按 audience 分开；批准级别决定上限，且线程内专属工具有 handler 层的兜底拒绝。

- 入口：`Cmd/Ctrl+K` → **Use T3 Code in another app (MCP)**，或 **Settings → Sharing & access**；URL 从 **Settings → Environments** 的菜单复制。
- 登录：T3 Connect 走 web app，否则走环境页面；code 一次性、5 分钟；无 code 批准从 Read only 起。
- 边界：四档运行时上限、`McpToolAccess.ts` 静态声明、非 `/mcp` 路由拒绝 `mcp-client`、每 RPC 单独查 scope。
- 生命周期：30 天有效期，可在 Sharing & access 立即撤销；事件订阅最长 1 小时、最近 1,000 个里程碑。

把这几处串起来看，外部 agent 的能力上限由三个地方共同决定：批准时选的级别、每个工具静态声明的访问级别、以及每个 RPC 单独检查的 scope。任何一处收紧都会生效；靠隐藏工具列表并不是安全措施，文档明确要求线程专属工具在 handler 里拒绝外部调用方。事件订阅是另一种入口，它不调用线程工具，只接收里程碑通知，因此有自己的有效期与本机 webhook 主机白名单。
