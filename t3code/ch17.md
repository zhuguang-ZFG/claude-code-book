# 第 17 章：性能是被测出来的
<!-- block: t3code-ch17.b-opening -->

T3 Code 对线协议设置字节与行数预算，用服务端基准测量资源开销，并对移动端动画和桌面原生模块规定实现限制。这些检查用于识别传输量、服务器负载和界面响应的回归。

读测试结果时，需要同时看测量对象与场景。下面分别说明 wire 不变量、事件与投影的成本、前后台负载，以及原生模块的隔离要求；章末列出测量命令和对比条件。

## 17.1 性能是被测出来的

线协议回归测试的命令是：

```sh
vp run test:perf:v2-wire
```

它跑的是真实的 V2 投影和客户端 reducer，而不是假数据。payload 预算在 `transferBudgetV2.integration.test.ts` 里强制，CI 通过 `TransferBudgetReport.integration.ts` 报告。文档特别说明，opt-in 对象按 contracts 标成 `Required`，因此新增的客户端 opt-in 必须配测试，不能悄悄绕开预算。

什么时候该跑？官方列出四类改动：投影 schema、历史分页、shell 同步、线程状态。这四类恰好都是「数据量会随使用时长增长」的地方，也正因如此，靠手工点几下很难发现回归。

服务端基准脚本 `scripts/server-metrics.ts` 使用 Anthropic API 替身和真实的 `claude` CLI，测量 CPU、唤醒次数、RSS、堆和首请求延迟。它与线协议预算测试的测量对象不同：前者观察服务器资源消耗，后者检查传输量。

新增客户端 opt-in 时需要补测试；payload 超出预算会在 CI 中报告，供审查本次改动是否引入回归。

## 17.2 掉帧即 bug

移动端文档把一类动画问题写成硬约束。`apps/mobile/package.json` 为 iOS 键盘避让启用了 Reanimated 的 `DISABLE_COMMIT_PAUSING_MECHANISM`，同时没有启用 React Native 的 `preventShadowTreeCommitExhaustion`。在这种配置下，连续的 Reanimated 帧（`withRepeat`）每帧都向 shadow tree 提交，可能饿死 React 的 JS 提交，导致屏幕冻结；开发版会以 `ShadowTree.cpp: assertion failed` 中断。

结论很具体：在重内容旁边跑循环动画时，改用 React Native 的 `Animated` 并设 `useNativeDriver: true`，文档给出的参考实现是 `thread-work-log.tsx`。这不是风格偏好，而是「掉帧即 bug」的判定——动画让交互失响应，就是回归。

失败时的现象也很明确：屏幕冻结，或开发版直接以断言中断。看到这类现象时，先检查循环动画是不是用了 Reanimated 的逐帧提交，而不是先去翻服务端指标。

这条规则也说明性能检查不能只看服务端指标：线程工作量日志这类界面与持续动画叠加时，问题出现在 JS 与 shadow tree 的提交节奏上，服务端再快也没用。

## 17.3 性能回归检查

wire 层面有四条不变量，文档把它们当作回归检查的核心：

| 不变量 | 文档给出的做法 |
|---|---|
| 有界窗口 | 冷启动、历史分页、resume 追赶在解码完整 payload 前先检查字节与行数，并排除活动窗口外的已结束 run 与重复消息表 |
| 快照不含原始工具体 | 原始命令输出、动态工具结果体、内联文件改动体在 wire 边界省略；diff 与显式 transcript 导出按需取全量 |
| 实时输出绕过事件 | adapter 把原始命令输出先流给 `CommandOutputHub`，先于事件入库；客户端只在命令行展开时订阅 |
| 增量 shell 同步 | 初次只发活动导航行，省掉归档行、空闲 subagent 与较老的已结算线程；resume 只发增量 |

其中最容易被写错的是第三条。文档明确禁止把输出增量走 `turn_item.updated` 事件：一条忙碌命令足以淹没事件存储，让所有线程都卡住。实时输出是一条旁路，只有命令行被展开时才订阅——这是并发边界，不是渲染优化。

## 17.4 事件与投影的成本

服务端的不变量同样具体。事件存储的 sequence cursor 与启动恢复的候选选择必须走索引，不能扫描保留历史，也不能仅仅为了确认「没事可做」而解码已完成的线程。trace 与 provider 日志必须用异步、串行化写入并做轮转；同步追加会在慢盘上拖住事件循环，Windows 尤其明显。后台感知与结算工作必须按线程合并（coalesce），并忽略高频的 transcript 与工具输出增量。

把这些与架构文档连起来看：orchestrator 串行裁定 command，EventSink 在一个事务里提交事件、投影、receipt 与 effect，EffectWorker 提交后才跑副作用。这个顺序本身就为成本划了界——高频数据不该进事件存储，所以才有 `CommandOutputHub` 旁路；事件日志只有有界重放窗口，所以启动恢复不能靠遍历历史。

这里可以分别核对三类成本：投影保存当前状态，事件记录已发生的变化，实时输出提供即时反馈。高频输出走独立通道，避免持续增加事件存储的负担。

## 17.5 前台与后台的分界

`scripts/server-metrics.ts` 用不同场景区分成本来源。`working` 场景让许多 worktree 线程同时编辑文件，而一个客户端订阅所有这些线程；如果线程数增加时每分钟 turn 数保持持平，文档说这意味着瓶颈在服务器而不在 agent。`scaling` 场景则把每线程成本与服务器固定开销分开。

默认重连场景是「用户的 3 台设备各持 10 个线程」；像 20 个客户端同时重连这种日常不会遇到的上界，只在 `--stress` 下跑。堆斜率要用 `--soak <minutes>` 观察泄漏，`--quick` 缩短所有窗口供每个 PR 或夜间检查使用，而 `compare` 拒绝把 quick 与 full 混在一起比。

还有一个平台陷阱：macOS、Windows、Linux 都要用 `--no-agent-scope` 测。Linux 的 systemd agent scope 会掩盖那些在其他平台上真实存在的按进程轮询路径；不关掉它，跨平台数据就不可比。同理，`--stress` 的数字不应被当成日常容量承诺，它只是看系统在极端情况下是否还能稳定。

## 17.6 原生模块的进程隔离

桌面端有一条明确规则：原生模块绝不进入 Electron 主进程的启动路径。可能崩溃或卡住的原生能力——文档举例是无障碍与窗口捕获辅助程序——要放进隔离的子进程或 worker，并设截止时间，绝不能作为主进程的顶层 import。

这与移动端的掉帧规则是同一类问题的两端：一端怕每帧提交饿死 JS，另一端怕一个顶层 import 把整个主进程拖住。可以这么理解，「性能约束」在这里已经变成了架构约束：能否隔离、能否设截止时间，决定了某个能力能不能被接进来。

架构文档同时要求迟到的收尾不能让客户端继续把 provider 工作显示成 active，也不能拉长记录的 provider 时长。这条看似属于正确性，实际上也是性能契约的一部分——界面显示的工作量与真实工作量必须一致。

## 17.7 测量与诊断清单

按官方文档，一次可信的性能核对大致是这样：

```sh
vp run test:perf:v2-wire                 # V2 投影与 reducer 的线协议预算
ab <checkoutA> <checkoutB>               # 同一台机器上对比两个 ref
server-metrics scaling                   # 分离每线程成本与固定开销
server-metrics working                   # 多 worktree 线程 + 一个订阅者
server-metrics --soak 30 --no-agent-scope
server-metrics --help                    # 哪个场景该信什么
```

要点是：永远用 `ab <checkoutA> <checkoutB>` 在同一台机器上对比两个 ref，而不是比较两次孤立的运行。之所以强调同机，是因为 CPU、磁盘与网络差异足以淹没几十个百分点以内的回归，孤立两次运行没有可比性。`--stress` 只用于上界，`--quick` 只用于快速检查，`compare` 不会让两者混合；`server-metrics --help` 会说明每个场景该信什么。

改动涉及投影 schema、历史分页、shell 同步或线程状态时，线协议预算测试必须跟着跑；涉及慢盘或 Windows 时，别忘了日志写入方式这条不变量。清单里的每一步都对应前面的一节，不要跳过预算测试只看服务端数字。

## 17.8 本章要点与来源

性能检查按线协议、服务端、移动端和桌面端分别进行：

- 线协议：`vp run test:perf:v2-wire`，预算在 `transferBudgetV2.integration.test.ts`，CI 由 `TransferBudgetReport.integration.ts` 报告。
- 输出旁路：实时命令输出走 `CommandOutputHub`，绝不走 `turn_item.updated`。
- 服务端：`ab` 同机对比，`scaling` / `working` / `--soak` / `--stress` / `--quick` 各管一种问题；`--no-agent-scope` 保证跨平台可比。
- 客户端：循环动画用 `Animated` + `useNativeDriver: true`；原生模块不进 Electron 主进程启动路径。

实现限制与测量场景需要分别遵守。实时输出不能走 `turn_item.updated`，原生模块不能进入主进程启动路径，日志也不能同步写入。`--stress` 与 `--quick` 则用于不同的测量目的，结果不能互相替代，也不能直接当作日常容量承诺。
