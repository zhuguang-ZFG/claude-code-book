# 第 18 章：更新、后台服务与排障
<!-- block: t3code-ch18.b-opening -->

更新是控制平面最容易出事的操作之一：你在用的客户端、跑 agent 的服务器、provider 的 CLI，可能分属三台机器和三条发布轨。这一章把它们拆开讲清楚——谁先更新、谁会重启、版本不匹配时连接为什么被拒，以及出了问题该从哪里看日志、什么时候动数据库。

<!-- block: t3code-ch18.b-t3-update -->

读法按运维顺序展开：先看一键更新和 provider 更新的实际顺序，再看后台服务的安装与配置、`t3 update` 的版本参数、健康探测为何必须被动，随后是 doctor 与日志路线，最后列出升级前该确认的线程续跑条件。命令与菜单按官方文档写，可以自己核对。

## 18.1 更新模型与服务器

你用的 app 和跑 agent 的服务器可以在不同机器上。侧栏底部的更新按钮与 **Settings → Environments** 都会提示更新落后的服务器。一键更新的顺序是：先更新过时的 provider，再更新落后的服务器，最后更新你正在用的桌面 app。服务器会升到桌面 app 正在装的版本（web 场景则升到 web app 的版本）；后台服务留在其当前 release channel，远端桌面 app 从自己的 channel 装最新版。把鼠标悬停在按钮上可以看到将更新哪些机器。

执行时按钮会变宽显示进度，点名耗时异常的机器，并对更新失败的服务器给出 **Retry**；点按钮可查看每台机器。**Later** 让你继续工作，稍后再从更新按钮重启桌面 app；仍在重启的服务器会自己完成，桌面 app 重启后按钮仍显示它。每台服务器在重启前会检查能否安装该 release；若 release 还不可得，更新失败但服务器继续运行，可以重试。

Provider 更新集中在 **Settings → Providers**。**Update all** 会一次更新所有已连接环境里过时的 provider；只要某个已启用且过时的实例只提供手动命令，或同一 provider 的实例用了不同更新命令，它就会被跳过。CLI 更新成功后，T3 Code 会用各实例自己的配置刷新模型发现；provider 更新检查必须打开，才能下载最新的模型目录。

## 18.2 后台服务

在 Linux、macOS、Windows 上，T3 Code 可以作为用户级服务运行，不必一直开着终端。先装 `t3` CLI，再在托管机器上运行这些命令：

| 任务 | 命令 |
|---|---|
| 设置其他设备的访问 | `t3 up` |
| 查看其他设备如何到达 | `t3 status` |
| 安装并启动 | `t3 service install` |
| 查看状态与日志位置 | `t3 service status` |
| 升级到新版本 | `t3 update` |
| 重启 | `t3 service restart` |
| 停止并取消开机启动 | `t3 service uninstall` |

卸载服务不会动项目、线程和设置；`t3 service status` 报 broken 时，重跑 `t3 service install` 可修复。

新服务只在本机应答。`t3 up` 里选择局域网，或运行 `t3 up --lan`（它会在 `service.env` 写入 `T3CODE_LAN=true`），才会监听局域网与 Tailscale 地址；仍然不监听公网地址。自定义环境变量放在服务的 T3 home 下的 `service.env`，通常是 `~/.t3/service.env`，例如 `T3CODE_PORT=3773`、`T3CODE_HOST=127.0.0.1`。条目是字面值 `KEY=VALUE`，不做 shell 展开；`PATH`、`T3CODE_HOME` 等少数变量例外。改完要 `t3 service restart`；若文件含凭据，应限制该文件权限。

平台差异也值得记：Linux 用 systemd user service 并开启 lingering；macOS 在登录时启动、登出时停止；Windows 以 `t3code-<domain>-<user name>` 任务运行在任务计划程序中，退出后一分钟内会自动重启，无人值守时应锁屏而不是登出。

## 18.3 t3 update

`t3 update` 下载当前 channel 的最新 release，并把 `t3` 与服务切过去；重启会中断正在跑的 turn、终端和远端客户端，所以它会先询问，回答 no 则服务继续跑旧版本，直到你执行 `t3 service restart`。脚本里可以传 `--yes`。手动启动的服务器不会被它动，需要自己停掉再启。

```sh
t3 update 0.0.42                          # 固定到精确版本
t3 update --channel nightly               # 切换发布轨
t3 update --allow-downgrade               # 允许降级
t3 update --channel stable --allow-downgrade
t3 update <client-version>                # 版本不匹配时按提示更新
```

`preview` 是维护者测试轨，构建可能损坏，永远不作为更新提供，安装时安装器与 `t3 update` 都会要求确认。Stable 比 Nightly 旧时，后台服务不能远程降级，要在那台机器上运行 `t3 update --channel stable --allow-downgrade`。若用 `npx` 而非安装的 `t3`，主机上没有可更新的东西：停掉服务器，用 `npx t3@<client-version>` 加原来的子命令和选项重启。

版本不匹配时，连接会被拒绝而不是半升级运行：app 比服务器新，会在连接前被拦下并提示更新指定机器上的 T3 Code；服务器比 app 新，会以更新消息拒绝连接。更新提示点名的那一侧，然后重连。

## 18.4 健康探测为什么被动

provider 文档规定：后台状态检查和 model 探测必须保持被动。它们绝不能打开一个会启动 MCP server、运行 hooks 或触发登录流程的 session；更重的探测留给显式的刷新或设置动作。原因很直接——一个「看看状态」的定时动作，如果顺手拉起 provider session，就等于在后台改变了环境与外部系统的关系。

更新本身也有归属约束：只能通过能证明所有权的安装器进行。可以从解析出的可执行文件路径证明所有权，或用会检查自身安装的自更新器；含糊的、钉死版本的、只读的安装（文档点名 Nix）只能手动更新。这样 `t3 update` 才不会改到一个不属于它的 CLI。

还有一组相关的边界：附件留在项目工作区之外；注入线程的 T3 MCP server 即使不可达，turn 也应继续工作。它们是「后台动作不能悄悄扩大影响面」的同一条原则在不同位置的体现。

## 18.5 doctor 与诊断

`t3 doctor` 在托管环境的机器上运行，主要用于回收数据库空间。T3 Code 自己会清理超过一天的内部历史（对话保留），但旧数据库仍占着磁盘；**Settings → Maintenance** 在可回收至少 1 GiB 时建议做一次离线修复。web/桌面点 **Reclaim**，服务会停止、修复、再启动；手动启动的服务器则运行：

```sh
t3 doctor
t3 doctor --fix       # 直接执行推荐修复，供脚本使用
t3 doctor --dry-run   # 只报告
t3 doctor --base-dir <其他数据目录>
```

它会报告数据库大小与可回收空间，询问要执行哪些修复；同一数据目录上的后台服务会为修复而停启，修复失败也会再启动。手工服务器或桌面 app 必须先退出，因为修复拒绝碰正在使用的数据库。

两个容量与历史陷阱：修复耗时随整个数据库大小增长，大库或慢盘上可能超过一小时；它通过临时副本重建，因此需要约为「仍在用的数据」两倍的空闲空间。从 0.1.0 之前的版本升级时，旧的 `state.sqlite` 会保留以便回滚；`t3 doctor` 会提供删除选项，但不会替你选中，`--fix` 会跳过它。

开发侧的快速检查入口是 `vp run check:changed`（CI 的快速检查），聚焦迭代可用 `vp test run <files>`、`vp lint <files>` 与 `vp run profile:startup`（抓取前 20 秒 Node 进程）。

## 18.6 日志与排障路线

排障从主机上的 `t3 service status` 开始：它打印日志路径，在 Linux 上还检查服务是否运行、已启用、能否挺过登出。若 SSH 一断开服务就停，检查 `linger-disabled`，由管理员用 `sudo loginctl enable-linger "$(id -un)"` 开启；通过 SSH 时加 `-t` 让 sudo 能提示密码。只把 `loginctl` 那条命令用 sudo 执行——以 root 跑 T3 Code 会产生另一套安装和 Connect 身份。

```sh
t3 service status
loginctl show-user "$(id -un)" --property=Linger
systemctl --user status t3code.service
ssh -t your-server 'sudo loginctl enable-linger "$(id -un)"'
```

状态字对应下一步：`linger-unavailable` 查 systemd-logind；`user-manager-unavailable` 在登录会话里查 `systemctl --user status`；`service-disabled` 或 `service-stopped` 读日志并用 T3 打印的修复命令；`restart-pending` 说明新版本已装但服务还跑旧的，执行 `t3 service restart`。macOS 上还要看 **System Settings → General → Login Items**；若 agent 访问不了 Desktop/Documents/Downloads，可能需要给 `~/Library/LaunchAgents/com.t3tools.t3code.service.plist` 中 `ProgramArguments` 列出的 `t3` 可执行文件完全磁盘访问权限。

更新失败时还有几条专门路线：每台服务器各自用自己的 npm 检查 release 与 npm 安装的 provider，注册表不可达就显示 release 不可用，不会偷偷改查公共注册表——所以要在这台机器上配 npm。桌面 app 起不来时会显示 "T3 Code could not start" 窗口，可选 **Update** 或下载上一次能启动的版本，并用 **Copy details** 带上错误去报 issue。

## 18.7 升级前的准备

服务器更新会重启连接、中断活跃 agent 与终端；先确认 **Settings → Maintenance → Continue threads after restarts** 的状态（默认开启）。它会在更新、崩溃或机器重启后续跑受支持的活跃线程，设置改动会写进支持它的已连接环境；离线或值不同的环境连上后在 Settings 里用 **Apply to all**。该设置不会让机器自动开机启动，T3 Code 必须真的再次启动。

续跑有明确例外：终端命令仍可能中断；没有已保存 provider 续跑状态的线程需要你再发一条消息。若 turn 已结束、正在等 subagent、后台任务、Claude monitor 或 agent 明说在等的命令/监视器，线程会被唤醒并告知这些工作停了；其他后台 shell 与监视器（如 dev server 及其 watchdog）不会唤醒它，线程要等你下一条消息才知道。等待你批准、回答或秘密的线程，以及归档、稍后提醒或已结算的线程，都不会续跑。一个未完成的 turn 连续崩溃恢复三次后，也会改为等你的下一条消息，哪怕三次间隔超过五分钟；完成的 turn 或计划内关闭会重置这个计数。

从旧编排系统升级时，对话记录会保留，但不是所有运行时历史都能带过来；重要旧线程应先读 thread migration 文档。还要记住一个硬边界：同一时间只有一个服务器能使用某个 T3 home；若启动报告已被占用，先停掉那个服务器，或换一个 home 目录再配对。

## 18.8 本章要点与来源

更新的顺序、服务的生命周期、探测的被动性，都是控制平面约束的一部分，而不是安装说明里的边角料。排障时先定位机器与日志，再决定是否动数据库。

- 一键更新顺序：provider → 服务器 → 桌面 app；后台服务留在原 channel，`Later` 可推迟桌面重启。
- 服务：`t3 up` / `t3 service install` / `status` / `restart` / `uninstall`；`service.env` 字面值，改后重启生效。
- 版本：`t3 update 0.0.42`、`--channel nightly`、`--allow-downgrade`、`--yes`；不匹配时连接直接拒绝。
- 诊断：`t3 service status` 看日志，Linux 查 `linger`；`t3 doctor --dry-run` 先看可回收空间，`--fix` 才动手。
- 升级前：确认续跑设置与例外，尊重「一个 T3 home 一个服务器」。

把本章顺序倒过来看，也能得到一条排障思路：先看版本是否匹配，避免把半升级状态当成故障；再看服务是否真的在跑、日志在哪里；只有当问题指向数据库占用或空间回收时，才进入 `t3 doctor`。这样安排的代价是步骤多，好处是每一次操作都只改变一个变量。
