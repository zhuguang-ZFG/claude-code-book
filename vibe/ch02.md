# 第 2 章：把一句话写成任务卡

<!-- block: vibe-ch02.b-opening -->
上一章把愿望压成了一句可执行的话。现在把它放到一张纸上，要求在动手前填完。任务卡不是提示词模板，而是一份你和模型都要遵守的约定：写清输入、输出、规则、验收和回退。这些空位如果留白，模型只能自己猜；猜错后的返工成本最高。

## 五个部分

一张够用的任务卡只有五块：

| 块 | 要回答的问题 | 旧书市集的例子 |
| --- | --- | --- |
| 目标 | 做完后谁拿它做什么 | 组织者把书架页发到群，摊主核对自家书目 |
| 输入 | 读哪些文件，哪些列必填 | `books.csv`，`title` 与 `owner` 不能为空 |
| 规则 | 去重、排序、脱敏、异常 | 书名与作者相同算重复；按品相新→旧；不输出 `contact` |
| 验收 | 跑什么命令，看什么结果 | 生成 `shelf.html`；终端打印重复组数与跳过行数 |
| 回退 | 出错时退回哪一版 | 保留上一版 `shelf.html`，或从 Git 恢复 |

目标不是“做一个网站”，而是“让组织者能发布、摊主能核对”。这两件事决定了页面要显示什么、不必显示什么。目标一变，规则和验收也跟着变。

## 把规则写成可判定的句子

“处理好空值”“去重一下”“页面好看点”都无法验收。把它们改写成程序能判定的条件：

- 空值：`title` 或 `owner` 去掉首尾空格后为空的行跳过，并在终端报告行号。
- 去重：`title` 与 `author` 都做 `casefold()` 后相同，视为同一本书；保留品相较好的那条，合并摊主名单。
- 排序：品相按 `new`、`good`、`worn`、`unknown` 的顺序；同品相按书名排序。
- 脱敏：公开页面只出现书名、作者、品相、摊主名；`contact` 不进入 HTML。
- 编码：输入按 `utf-8-sig` 读取，兼容带 BOM 的表格。

这些句子有共同点：都指向一个具体字段、一个具体动作、一个可观察结果。模型不需要猜“好”是什么意思。

## 一份可以直接用的任务卡

把下面这段存成 `task-card.md`，每次改需求先改这张卡，再让模型动代码。

```text
目标：把旧书市集的 books.csv 变成可发布的 shelf.html，供组织者发群、摊主核对。

输入：
- books.csv，UTF-8（允许 BOM），列：title, author, condition, owner, contact
- 教学样例见 fixtures/books.csv

规则：
1. title 或 owner 为空的行跳过，终端打印行号。
2. title + author 忽略大小写后相同视为重复；保留品相较好的一条，合并摊主名。
3. condition 只接受 new / good / worn；其他值记为 unknown，排在最后。
4. 按品相、书名排序。
5. contact 不写入任何公开文件。
6. 生成单个 shelf.html，不依赖网络资源。

验收：
- 运行 python shelf.py fixtures/books.csv -o shelf.html，退出码 0。
- 页面包含 4 张卡片；重复组 2 组；跳过 2 行。
- 页面源码中不出现 @example.com 或手机号。
- 删除 fixtures/books.csv 后运行，程序报错并以非 0 退出，不生成半成品。

回退：
- 每次运行前保留上一版 shelf.html；代码用 Git 提交。
```

这份卡仍然允许模型自由选择实现：可以用 `csv` 模块，也可以先读进列表再处理；可以手写 HTML，也可以用模板字符串。实现方式可以自由选择，验收结果必须一致。

## 先写验收，再让模型实现

一个常见顺序是：先让模型写，再看它生成了什么，最后补验收。这样很容易把“模型碰巧做出来的行为”当成需求。更稳的顺序是反过来的：

1. 写三条验收，其中至少一条是否定条件（不应该出现什么）。
2. 准备一份小样例，能在一屏内看完。
3. 再让模型实现。
4. 运行验收，失败就修，不改验收去迁就实现。

否定条件尤其重要。旧书案例里，“页面不出现联系方式”比“页面看起来专业”更能防止真实事故。类似的条件还有“不覆盖原 CSV”“不调用外部网络”“不删除目录”。

## 任务卡不是一次写完的

第一版任务卡通常漏东西。跑完一次后，把新发现写回卡里，而不是只留在聊天记录中。例如发现书名里有逗号，补一条“按 CSV 标准引号解析”；发现某行品相是“九成新”，补一条“中文品相映射到 new/good/worn，无法映射记 unknown”。

任务卡每改一次，就在文件末尾加一行日期和原因。这样下一个人能看到规则为什么这样定，而不是面对一版没有来历的代码。

## 动手做

为你的小工具填一张任务卡，至少包含：

- 一个否定验收：什么出现就算失败。
- 一份不超过 10 行的样例输入。
- 一个回退动作：出错后具体恢复哪个文件或哪个提交。

然后把任务卡交给模型，要求它先复述规则，再开始写。复述错了，先改卡，不要急着改代码。

## 关键要点

- 任务卡写五块：目标、输入、规则、验收、回退。
- 规则要落到字段和动作上，避免“处理好”“好看点”。
- 验收先写，至少一条是否定条件。
- 每次跑完把新发现写回卡里，后来的人才知道规则为什么这样定。
