# 第 4 章：第一圈之前：环境、版本与回退点

<!-- block: vibe-ch04.b-opening -->

模型给出第一条安装命令时，很多人会直接粘贴。命令跑完，页面也出来了，但换一台机器就失败：Python 版本不同，工作目录不同，某个包只装在当前用户的环境里。此时再回头查，已经分不清是代码问题还是环境问题。

写业务规则之前，先把四件事固定下来：运行命令、输入与输出的位置、第一个 Git 提交、一个能跑通的最小版本。它们不增加功能，但能让后面每一圈都有可比较的起点。

## 一条命令和三个路径

旧书市集的运行命令定为：

```bash
python shelf.py fixtures/books.csv -o shelf.html
```

这条命令包含三个路径：程序 `shelf.py`、输入 `fixtures/books.csv`、输出 `shelf.html`。三个路径都相对于项目根目录，不依赖你当前在哪个文件夹。以后每圈都用同一条命令，输出才有可比性。

先在项目根目录记录环境：

```bash
python --version
pwd
```

本书的示例在 Python 3.12 下运行，只使用标准库。你的版本可以不同，但要写进 README；如果模型引入第三方包，安装命令和版本也要写进去。不要用“最新版”这种会随时间变化的说法。

## 输入文件不改，输出文件可重建

把项目整理成四个位置：

```text
vibe-shelf/
├── shelf.py
├── fixtures/
│   └── books.csv
├── task-card.md
└── README.md
```

```ill
vibe-ch04-paths
```

`fixtures/books.csv` 是输入，程序只读，不写。`shelf.html` 是输出，任何时候都可以删掉重跑。`shelf.py` 和 `task-card.md` 是源文件，需要进版本库。这个划分能防止一种常见事故：程序为了“修正”数据，直接覆盖了原始 CSV，等到发现去重规则错了，原数据已经没了。

运行前记下输入的摘要：

```bash
sha256sum fixtures/books.csv
```

运行后再算一次。两次一致，说明程序没有改输入。Windows 没有 `sha256sum` 时，用 `certutil -hashfile fixtures\books.csv SHA256`，或者直接在 Git 里看这个文件有没有变化。

## 第一个提交

在项目根目录初始化 Git，先提交输入、任务卡和 README，再写业务代码：

```bash
git init
printf 'shelf.html\n__pycache__/\n' > .gitignore
git add .gitignore task-card.md README.md fixtures/books.csv
git commit -m "shelf: add fixture, task card and run contract"
```

这次提交是后面所有回退的起点。之后每圈开始前运行 `git status`，确认工作区里没有别人的改动；每圈结束后只提交这一圈改过的文件。生成的 `shelf.html` 不进版本库，它可以从输入重建。

如果暂时不用 Git，至少保留一个带日期的副本，例如 `shelf-2026-11-15.py`。副本不能替代版本记录，但能在改坏时把文件恢复回来。

## 最小版本先跑通

第一版不实现去重、排序和页面，只读 CSV 并打印行数：

```python
#!/usr/bin/env python3
"""Count the data rows in a book-fair CSV."""
import csv
import sys
from pathlib import Path


def main(argv: list[str]) -> int:
    path = Path(argv[1])
    with path.open(newline="", encoding="utf-8-sig") as handle:
        rows = list(csv.DictReader(handle))
    print(f"行数：{len(rows)}")
    return 0


if __name__ == "__main__":
    raise SystemExit(main(sys.argv))
```

运行：

```bash
python shelf.py fixtures/books.csv
```

输出应为：

```text
行数：8
```

`csv.DictReader` 把第一行当表头，所以八条数据记录得到 8。若输出 0，先检查分隔符和表头；若输出 9，说明表头被当成了数据。这个版本只验证“文件能打开、表头能识别”，不验证业务规则。跑通后提交：

```bash
git add shelf.py
git commit -m "shelf: read the CSV and report its row count"
```

## 把运行方式写进 README

README 只写别人复现所需的内容：

```text
运行：python shelf.py fixtures/books.csv
环境：Python 3.12，仅标准库
期望：终端输出“行数：8”
失败时先查：文件路径、CSV 表头、文件编码（UTF-8，可带 BOM）
```

这四行会在第 12 章交接时再次用到。现在写下来，比事后凭记忆补更准确。

## 动手做

为你的小工具完成下面四项，并把结果写进 README：

- 固定一条运行命令，写出输入、输出和程序三个路径。
- 运行前后各算一次输入文件的摘要，确认输入没有被改。
- 建立第一个 Git 提交，提交信息说明这次提交包含什么。
- 跑通最小版本，记录实际输出；输出与预期不符时，先查环境，不要改业务代码。

## 关键要点

- 运行命令、输入路径、输出路径在项目根目录固定下来，后续每圈复用。
- 输入文件只读，输出文件可以从输入重建；源文件和生成物分开管理。
- 第一个提交包含输入、任务卡和运行说明，为后续回退提供起点。
- 最小版本只验证读取路径，业务规则留到下一章逐条加入。
