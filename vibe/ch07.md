# 第 7 章：一次只改一个原因

<!-- block: vibe-ch07.b-opening -->

旧书市集收到一份新表格，里面有两本同名、作者不同的书。发布后，摊主来信说其中一本不见了。你让模型“把去重修一下”，它同时改了去重键、排序规则和页面标题。重新运行，消失的书回来了，但卡片顺序也变了。现在你无法判断：书能回来，是因为去重键改对了，还是因为排序碰巧把它排进了结果？

这类改动可以拆成两步：先用一条测试固定期望，再只改导致失败的那一处。测试先失败，改完再通过，原因和结果才对得上。

## 先写一条会失败的测试

在项目根目录新建 `test_shelf.py`：

```python
import unittest

import shelf


class DuplicateKeyTests(unittest.TestCase):
    def test_same_title_different_authors_stay_separate(self):
        books = [
            {"title": "同名", "author": "甲", "condition": "new", "owner": "林"},
            {"title": "同名", "author": "乙", "condition": "good", "owner": "周"},
        ]
        merged, groups = shelf.merge(books)
        self.assertEqual(len(merged), 2)
        self.assertEqual(groups, 0)


if __name__ == "__main__":
    unittest.main()
```

运行：

```bash
python -m unittest test_shelf.py -v
```

当前版本会失败，关键一行是：

```text
AssertionError: 1 != 2
```

这条测试没有读 CSV，也没有渲染页面。它只调用 `merge()`，把“同名不同作者不能合并”这个条件单独拿出来。输入只有两条记录，失败时不需要再缩小范围。

## 只改去重键

打开 `shelf.py` 的 `merge()`，找到这一行：

```python
key = (book["title"].casefold(),)
```

它只按书名分组。把作者加进去：

```python
key = (book["title"].casefold(), book["author"].casefold())
```

其他行不动：排序、品相比较、摊主合并、页面渲染都保持原样。再跑同一条测试：

```bash
python -m unittest test_shelf.py -v
```

现在应通过。接着跑完整命令，确认四张卡片、两个重复组、跳过行号都没有变化：

```bash
python shelf.py fixtures/books.csv -o shelf.html
```

如果测试通过但完整输出变了，说明还有第二处改动混进来。先看 `git diff`，把与去重键无关的修改撤回，再重跑。不要用“反正结果对了”结束这一圈。

## 最小复现只要两行

这条测试能成立，是因为输入足够小：

| 书名 | 作者 | 品相 | 摊主 |
| --- | --- | --- | --- |
| 同名 | 甲 | new | 林 |
| 同名 | 乙 | good | 周 |

两行数据只保留一个变量：作者不同。书名、品相、摊主都不构成干扰。真实表格有几十行时，先用两行复现，再回到完整表格验证。这样报错信息短，判断也短。

如果两行无法复现，再逐条加入真实数据，直到失败出现。最后加入的那条就是触发条件；把它单独留下，其他行移回原表。这个过程比让模型“再看看整个文件”更可靠。

## 回归测试留在仓库

修好后不要删测试。它记录的是一个曾经真实发生的错误假设：书名相同就视为同一本书。以后有人为了“减少重复”把作者从键里拿掉，这条测试会立即失败。

测试名写行为，不写实现。`test_same_title_different_authors_stay_separate` 说明期望；`test_merge_key_has_two_fields` 只是在描述当前写法，改实现时就会误报。

一条回归测试只锁一个行为。把空值、重复、排序、脱敏全塞进一个测试方法，失败时仍然要读完整段才能定位。按行为拆开，失败信息会直接指向出问题的那一条。

## 一次只改一个原因

“一次只改一处”不是要求每圈只能敲一行代码，而是要求这一圈只有一个**可观察行为**发生变化。允许的配套改动包括：

- 为这个行为补一条测试。
- 为重命名更新调用点。
- 为通过类型检查补一个类型标注。

不允许顺手做的事：

- 改页面颜色或文案。
- 调整排序规则。
- 升级依赖。
- 删除看起来没用的函数。

模型往往会把它们当成“顺手优化”。在任务说明里写清本轮范围，并在提交前看 `git diff`；出现范围外的改动，就退回或留到下一圈。

## 动手做

在你的项目里完成一轮只改一个原因的修复：

- 选一个曾经出错、但目前没有测试覆盖的行为。
- 写一条测试，先运行并确认它失败。
- 只改导致失败的那一处，再运行测试。
- 跑完整命令，对比输出；提交时在信息里写明修的是哪个行为。

如果找不到失败测试，说明这个行为还没有被固定下来。先补测试，不要先改代码。

## 关键要点

- 先用一条小测试固定期望，再改代码；失败信息会指出分歧在哪。
- 最小复现只保留一个变量，通常两行数据就够。
- 回归测试锁住行为，不锁实现；修好后留在仓库。
- 一圈只有一个可观察行为变化，范围外的改动留到下一圈。
