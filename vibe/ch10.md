# 第 10 章：数据、权限与隐私

<!-- block: vibe-ch10.b-opening -->

组织者提出两个新需求：摊主可以登录修改自己的书目，往届表格也能导入。页面还是那个页面，但任务已经从“生成静态 HTML”变成“保存用户数据、判断谁能改哪一行”。第 8 章的风险分级里，这已经进入“处理他人数据”一级，并涉及权限判断。

这里不引入 Web 框架，只用 Python 标准库的 `sqlite3` 说明三件事：数据放在哪里、谁可以读写、联系方式保留多久。具体框架可以换，这三件事不能省。

## 先画数据流

在写表结构之前，把每个字段走一遍：

| 字段 | 从哪里来 | 存在哪里 | 谁可以读 | 保留多久 |
| --- | --- | --- | --- | --- |
| 书名、作者 | 摊主填写 | `books` 表 | 公开页面 | 活动结束前 |
| 品相 | 摊主选择 | `books` 表 | 公开页面 | 活动结束前 |
| 摊主名 | 摊主填写 | `users` 表 | 公开页面 | 活动结束前 |
| 联系方式 | 摊主填写 | `contacts` 表 | 组织者 | 活动结束后删除 |
| 登录标识 | 登录服务 | 用户表 | 本人与组织者 | 账号存续期间 |

这张表决定后面所有实现。若某个字段没有明确的“谁可以读”，先不要收集。若某个字段没有删除时间，先不要写入数据库。

## 表结构固定边界

旧书市集的数据库可以只有三张表：

```sql
CREATE TABLE users(
  id INTEGER PRIMARY KEY,
  name TEXT NOT NULL UNIQUE
);

CREATE TABLE books(
  id INTEGER PRIMARY KEY,
  title TEXT NOT NULL,
  author TEXT NOT NULL,
  condition TEXT NOT NULL,
  owner_id INTEGER NOT NULL REFERENCES users(id),
  UNIQUE(title, author)
);

CREATE TABLE contacts(
  book_id INTEGER PRIMARY KEY REFERENCES books(id) ON DELETE CASCADE,
  email TEXT NOT NULL,
  expires_on TEXT NOT NULL
);

CREATE VIEW public_books AS
  SELECT b.id, b.title, b.author, b.condition, u.name AS owner
  FROM books AS b JOIN users AS u ON u.id = b.owner_id;
```

`UNIQUE(title, author)` 把“同名同作者只保留一条”的规则交给数据库执行。程序里的 `merge()` 仍然需要，用于导入时合并品相和摊主；但即使某次导入漏了合并，数据库也会拒绝重复键，不会悄悄写出两条。

`contacts` 单独成表，公开视图 `public_books` 不包含它。页面查询只读视图，就不存在“渲染时忘了过滤邮箱”这一层风险。删除书目时，`ON DELETE CASCADE` 一并删除联系方式。

`owner_id` 指向 `users`，公开视图再连接出摊主名。不要把名字直接存进 `books` 并拿来判权：名字会重复，也会修改；权限应绑定不可变的用户 ID。

## 参数化查询，不拼字符串

插入书目时使用占位符：

```python
import sqlite3

con = sqlite3.connect("shelf.db")
con.execute("INSERT INTO users(name) VALUES(?)", ("林",))
con.execute(
    "INSERT INTO books(title, author, condition, owner_id) VALUES(?, ?, ?, ?)",
    ("夜航西飞", "柏瑞尔·马卡姆", "good", 1),
)
con.execute(
    "INSERT INTO contacts(book_id, email, expires_on) VALUES(?, ?, ?)",
    (1, "lin@example.com", "2026-12-31"),
)
con.commit()
```

不要把书名或摊主名格式化进 SQL。`?` 让数据库把值当数据，而不是 SQL 片段。字符串拼接会把引号、分号甚至整条语句带进查询，这是注入的入口。

查询公开页时只读视图：

```python
rows = con.execute(
    "SELECT title, author, condition, owner FROM public_books ORDER BY title"
).fetchall()
```

这里不需要 `WHERE contact IS NULL`，因为视图里根本没有 `contact` 列。边界写在表结构里，比写在每个查询里更难漏。

## 权限检查放在服务端

页面隐藏“编辑”按钮，只改变界面，不构成权限。服务端每次修改都要重新判断：

```python
def can_edit(user: dict, book: dict) -> bool:
    if user["role"] == "organizer":
        return True
    return book["owner_id"] == user["id"]
```

调用顺序是：先登录，取出 `user`；再按 `book_id` 查书目；最后调用 `can_edit()`。任何一步失败都返回拒绝，不继续执行更新。不要先更新再检查，也不要把角色写进前端请求参数。

数据库账号同样按最小权限配置：公开页面只读视图；导入程序只允许插入和更新；迁移脚本单独使用更高权限。一个账号能删表，就不该拿它跑日常导入。

## 联系方式单独保留

联系方式只用于活动期间联系摊主。写入时记录到期日，活动结束后运行一次清理：

```python
con.execute("DELETE FROM contacts WHERE expires_on < date('now')")
con.commit()
```

日志里不要打印完整邮箱。需要排查时记录 `book_id` 和失败原因，例如“联系人缺失”“到期日格式错误”，不要记录 `lin@example.com`。备份文件同样包含个人信息，备份的访问权限和保留时间要与主库一致。

如果摊主要求删除自己的联系方式，删除 `contacts` 中对应行即可，书目本身仍可公开。把“删除账号”和“删除公开书目”分开处理，避免一次请求误删整条记录。

## 测试三条边界

把下面三条写进测试，比在页面上点几次可靠：

- 插入同名同作者的第二条记录，数据库抛出 `IntegrityError`。
- 公开查询的列里没有 `email` 或 `contact`。
- 非本人、非组织者调用 `can_edit()` 返回 `False`。

第一条验证约束，第二条验证视图，第三条验证授权。三条都不依赖页面样式，换前端框架也不需要重写。

## 迁移前先备份

表结构会变。加字段、改约束、拆表时，先复制数据库文件，再执行迁移：

```bash
cp shelf.db shelf-2026-11-15.db
```

迁移脚本用 `PRAGMA user_version` 记录版本，每一步可重复执行；执行后在副本上跑一次完整导入和公开查询，确认无误再替换主库。迁移失败时恢复副本，不要在主库上反复试。

### 恢复也要演练

备份复制成功，不等于能恢复。演练时不要碰 `shelf.db`：先把备份复制到临时路径，再打开临时副本，与主库对照行数，并查一次 `public_books`。

```bash
cp shelf-2026-11-15.db shelf-restore-check.db
python - <<'PY'
import sqlite3

def counts(path):
    con = sqlite3.connect(path)
    books, contacts = con.execute(
        "SELECT (SELECT COUNT(*) FROM books), (SELECT COUNT(*) FROM contacts)"
    ).fetchone()
    con.close()
    return books, contacts

live = counts("shelf.db")
restored = counts("shelf-restore-check.db")
print("live:", live, "restored:", restored)

con = sqlite3.connect("shelf-restore-check.db")
columns = [row[1] for row in con.execute("PRAGMA table_info(public_books)")]
print("public_books:", columns)
print("sample:", con.execute(
    "SELECT title, owner FROM public_books ORDER BY title LIMIT 3").fetchall())
con.close()
PY
```

通过的条件是两组 `(books, contacts)` 计数相同，`public_books` 的列里没有 `email` 或 `contact`，且样例查询仍能返回书目。任何一项不符，就检查备份文件本身，不要拿主库试。备份是否可用，不看 `cp` 是否报错，只看恢复副本能不能被读回并通过这些检查。

## 动手做

为你的项目补一份数据流表，并完成下面三项：

- 为公开页面建一个不包含隐私字段的视图，查询只读这个视图。
- 给一个业务约束加数据库级限制，例如唯一键或非空约束。
- 写一条授权测试：非本人修改返回拒绝，并确认数据库没有被改动。

## 关键要点

- 先列字段的数据流：来源、存储、读者、保留时间；缺一项就先不收集。
- 用表结构和视图固定隐私边界，公开查询不接触联系方式。
- SQL 使用占位符；权限检查放在服务端，每次修改重新判断。
- 联系方式记录到期日并单独删除；备份与日志同样按敏感数据管理。
