# 第 11 章：从原型到可部署

<!-- block: vibe-ch11.b-opening -->

页面在你的机器上能打开，换到组织者的电脑就报 `FileNotFoundError`：程序从当前目录找 `fixtures/books.csv`，而对方在另一个目录运行。又或者定时任务的环境变量不同，输出被写到了别处。代码没有变，运行环境变了。

把原型推进到可部署状态，要处理四件事：配置从哪里来、每次运行留下什么记录、失败后怎样恢复、发布前检查哪些项。仍然只用标准库，部署对象可以是一个静态页面，也可以是一个小服务。

## 配置放在环境变量里

把路径和日志级别从代码里移到环境变量，并提供默认值：

```python
import os
from pathlib import Path

DATA = Path(os.environ.get("SHELF_DATA", "fixtures/books.csv"))
OUTPUT = Path(os.environ.get("SHELF_OUT", "shelf.html"))
LOG_LEVEL = os.environ.get("SHELF_LOG_LEVEL", "info").lower()
```

启动时先验证：

```python
if not DATA.is_file():
    raise SystemExit(f"输入文件不存在：{DATA}")
if not OUTPUT.parent.is_dir():
    raise SystemExit(f"输出目录不存在：{OUTPUT.parent}")
```

错误信息里带实际路径，不要只写“文件不存在”。部署时最常见的故障就是路径与预期不同；把路径打印出来，排查时间会短很多。

不要把密钥、邮箱、数据库密码写进代码或提交到仓库。示例程序不需要密钥；真实服务用环境变量或部署平台的密钥管理，仓库里只保留 `.env.example`，且示例值必须是假数据。

## 每次运行留一行日志

日志记录运行事实，不记录用户数据。程序结束时向标准错误打印一行：

```python
import sys
from datetime import datetime, timezone

print(
    f"{datetime.now(timezone.utc).isoformat()} "
    f"input={DATA} output={OUTPUT} cards={len(merged)} "
    f"duplicates={duplicate_groups} skipped={len(skipped)} exit=0",
    file=sys.stderr,
)
```

失败时也打印一行，把 `exit` 改成对应退出码，并写清失败阶段，例如 `stage=read` 或 `stage=render`。不要打印完整 CSV 行，也不要打印联系方式；日志会被收集、转发、长期保存，敏感字段进去就很难收回。

一行日志足够回答三个问题：这次运行读了哪个文件、生成了多少条记录、成功还是失败。需要更细的排查时，再临时提高日志级别，不要默认输出整份数据。

## 失败时不覆盖上一版

第 5 章的脚本已经使用临时文件加 `replace()`：

```python
temporary = OUTPUT.with_suffix(OUTPUT.suffix + ".tmp")
temporary.write_text(page, encoding="utf-8")
temporary.replace(OUTPUT)
```

渲染失败时，旧页面仍然存在。这对发布是好事，对判断结果却可能是陷阱：命令退出码非 0，但目录里有一个旧的 `shelf.html`，同事看到文件就上传了。发布脚本必须同时检查退出码和产物时间，不能只看文件是否存在。

更稳的做法是先把新产物写到带时间戳的文件，验证通过后再替换正式文件：

```bash
python shelf.py fixtures/books.csv -o shelf-2026-11-15.html
# 检查退出码、卡片数、邮箱扫描
mv shelf-2026-11-15.html shelf.html
```

保留上一版 `shelf-2026-11-14.html`。回滚时把它复制回 `shelf.html`，再检查页面和退出码。回滚动作要在发布前演练一次，不要等事故时第一次执行。

## 选择最简单的部署形态

如果产物只是一个静态页面，部署就是把 HTML 放到 Web 服务器目录：

1. 在本地生成并验证。
2. 计算文件摘要，记录到发布记录。
3. 上传到服务器的新文件名。
4. 用浏览器和手机宽度各打开一次。
5. 通过后再替换入口文件。

如果要做成服务，至少满足四条：进程不以 root 运行；数据目录只读挂载；配置来自环境变量；启动时检查输入与端口。下面是一个最小容器示例，只用于说明边界：

```dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY shelf.py .
COPY fixtures/ ./fixtures/
USER 1000
ENTRYPOINT ["python", "shelf.py"]
```

容器把代码和样例数据打进去，适合演示；真实数据应挂载到只读卷，输出写到可写卷。不要把数据库文件打进镜像，也不要在镜像里放密钥。

## 发布前检查单

| 检查 | 通过条件 |
| --- | --- |
| 命令 | 退出码 0；失败路径退出码非 0 |
| 产物 | 文件时间与本次运行一致；摘要已记录 |
| 数据 | 卡片数、重复组、跳过行与预期一致 |
| 隐私 | 公开文件搜不到邮箱、手机号、`contact` |
| 页面 | 手机宽度无横向滚动；长书名不覆盖摊主名 |
| 回滚 | 上一版文件存在，复制命令演练过 |
| 日志 | 本次运行有一行记录，失败阶段可辨认 |

检查单写进 README 或发布脚本，不靠记忆。每次发布按顺序执行，失败就停，不要带着未通过的项继续。

## 观测一次运行是否成功

不需要完整的监控系统，先回答一个问题：发布后，下一次运行失败时，谁会发现？

最小方案是让定时任务在退出码非 0 时发一条通知，通知内容只包含时间、阶段和日志文件位置，不带用户数据。每周看一次失败次数；连续失败两次就停下来查，不要自动重试到成功为止。重试会掩盖输入错误，也会把同一份坏数据写多次。

如果页面由别人手动运行，就在 README 里写清“看到非 0 退出码时不要上传产物”，并给出回滚命令。人的操作步骤也是可观测性的一部分。

## 动手做

把你的小工具推进到可部署状态：

- 把输入路径、输出路径和日志级别改成环境变量，并验证默认值。
- 在成功和失败路径各打印一行日志，确认不含个人信息。
- 生成一份带日期的产物，演练一次“替换入口文件再回滚”。
- 按发布检查单走一遍，记录哪一项失败过、怎样修复。

## 关键要点

- 路径和日志级别来自环境变量，启动时验证并打印实际路径。
- 每次运行留一行日志，记录输入、输出、计数、退出码，不记录个人信息。
- 退出码与产物时间一起检查；旧文件存在不代表本次发布成功。
- 部署形态选最简单的；回滚命令在发布前演练，失败告警只带运行事实。
