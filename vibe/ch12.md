# 第 12 章：交给下一个人

<!-- block: vibe-ch12.b-opening -->
工具用了两周，组织者想加一个“按摊主筛选”的功能。她打开目录，看到 `shelf.py`、`shelf.v3.py`、`shelf-final.py`、`shelf-final-2.py`，还有一份没写完的 `notes.txt`。她不知道哪个在跑，也不知道上一次为什么把 `utf-8` 改成了 `utf-8-sig`。

个人使用时，运行条件和决策可以靠记忆。多人接手时，这些信息必须写在项目里。下面讲怎样把“我当时是这么想的”留下来。

## 交接包的三样东西

一个能交接的项目，至少包含：

1. **可复现的运行方式**：一条命令，从干净目录跑到产物。
2. **当前有效的规则**：任务卡与 fixtures，而不是散落的聊天记录。
3. **决策记录**：哪些方案试过、为什么放弃、哪些边界不能碰。

代码只是其中一件。接手的人还需要知道：怎么跑、怎么判断对错、出错先看哪里。

## 一条命令启动

把运行方式写进 `README.md`，并在干净目录里实际走一遍：

```bash
python -m venv .venv
# Windows: .venv\Scripts\activate
# macOS/Linux: source .venv/bin/activate
python shelf.py fixtures/books.csv -o shelf.html
python -m unittest test_shelf.py -v
```

如果项目没有第三方依赖，明确写“只用 Python 3.12 标准库”。如果有依赖，给出锁文件或精确版本，不要写“装最新版”。第 8 章的风险分级里，“依赖”也是边界之一。

`README.md` 还应写明：输入文件从哪来、输出文件给谁、哪些字段不能公开、上一次已知问题是什么。四行就够，不要写成营销页。

## 把代理规则写成文件

如果团队用编码 Agent，把不能让步的规则放进 `AGENTS.md` 或同类项目说明。它记录项目约束，不是提示词收藏：

```markdown
# shelf

- 运行：python shelf.py fixtures/books.csv -o shelf.html
- 测试：python -m unittest test_shelf.py -v
- 数据：books.csv 只读；任何写操作先备份。
- 公开页不得出现 contact、邮箱、手机号。
- 新增依赖前先说明用途与 license；能不用就不用。
- 提交前必须通过测试；不要修改 fixtures 里的期望来迁就实现。
```

规则要短、可执行、能验证。写“注意安全”没有用；写“不得把 contact 写进 HTML”才能被检查。

## 决策记录怎么写

在 `DECISIONS.md` 里按时间倒序记，每条四行：

```text
2026-11-15 去重键加入 author
原因：同名不同作者被误合并（摊主反馈）。
取舍：同一作者同一书名的不同版本仍会合并；当前数据没有版本列。
验证：test_same_title_different_authors_stay_separate。
```

不要写“优化了去重逻辑”。要写下触发事实、取舍和验证。下一个人看到这条，能判断自己的新需求是否推翻了原来的假设。

## 依赖、许可证与维护成本

原型阶段装上的包，交付后会变成维护对象。每次发布前更新一份清单：

- **直接依赖**：包名、版本、用途。能删的删，能换标准库的换。
- **传递依赖**：安装后实际拉进来多少包，有没有重复版本。
- **许可证**：项目自身的 `LICENSE` 是否覆盖发布方式；依赖的许可证是否允许当前用途；需要保留的版权声明有没有放进 `NOTICE` 或 README。
- **来源**：哪段代码由模型生成、从哪个仓库或网页复制。来源不明的片段要重写或补上出处。
- **已知技术债**：哪些地方为了赶时间先绕过，触发条件是什么，下一次改哪里。

技术债不要只写“以后优化”。写成“如果摊主数量超过 100，当前逐行扫描会变慢；届时先加索引或分页”，接手的人才知道什么时候该处理。

许可证不是法律意见。拿不准时，查依赖仓库的 `LICENSE` 原文，或让团队里负责发布的人确认。不要把“GitHub 上公开”当成“可以随便用”。

## 提交信息要写行为和证据

Vibe coding 的提交信息最容易写成“update”或“fix bug”。换成“行为 + 证据”：

```text
shelf: keep same-title books by different authors apart

- merge key now uses title + author
- regression: test_same_title_different_authors_stay_separate
- verified: python -m unittest test_shelf.py -v (5 tests)
```

三行就能让审查者知道改了什么、怎么验的。不要把所有生成内容都塞进一个提交；一圈一个提交，回退才精确。

## 团队里的三条边界

1. **写明生成过程**。哪部分是模型起草、哪部分人工改过、哪些没有验证，都要记录。审查者据此决定重点看哪里。
2. **不要让 Agent 直接改共享分支**。至少走一个分支和一次人工审查。审查重点看数据边界、权限、依赖和测试，不必逐行看样式。
3. **团队验收使用四层检查**。按第 9 章的单元、端到端、人工和回滚逐项检查；个人 demo 的标准不能直接搬到生产。

如果团队还没有审查流程，先从一条开始：任何碰到真实数据的改动，必须由第二个人跑一遍验收命令。这个人不需要会写代码，只需要会对照清单。

## 评审时按影响面排序

Google 的工程实践文档把评审拆成设计、功能、复杂度、测试、命名与一致性几类（链接见附录 B.3）。对模型生成的代码，把数据边界和失败路径提前，顺序更接近风险：

| 顺序 | 看什么 | 常见问题 |
| --- | --- | --- |
| 1 | 行为是否与任务卡一致 | 顺手加了未要求的筛选、字段或页面 |
| 2 | 数据边界 | 新查询绕过公开视图，联系方式进入日志 |
| 3 | 失败路径 | 覆盖前没有备份，异常后留下半成品 |
| 4 | 测试 | 只测主路径，没有固定这次修复的行为 |
| 5 | 依赖与许可证 | 新包未锁版本，许可证与发布方式冲突 |

样式和命名仍要看，但排在数据与失败路径之后；它们影响维护成本，前四项优先暴露数据丢失和不可恢复的问题。

## 一个最小交接演练

发布前，找一位没参与的人，只给他项目目录和 README，让他完成：

1. 在干净环境跑出 `shelf.html`。
2. 故意删掉输入文件，确认程序报错且不生成半成品。
3. 找到“联系方式不公开”这条规则的实现位置。
4. 说出回滚时恢复哪个文件或提交。

四件事都完成，接手的人不必再问运行方式。任何一步需要问你，说明交接包还缺东西。

## 动手做

为你的项目补三样：

- 一条从干净目录可执行的命令。
- 一份不超过 10 行的 `AGENTS.md` 或项目规则。
- 三条决策记录，每条包含原因、取舍和验证。

然后按上面的演练找一个人走一遍，记录他卡在哪一步。

## 关键要点

- 交接包要包含运行方式、规则和决策记录，代码只是其中一件。
- README 写清输入、输出、隐私边界和已知问题。
- 代理规则要短、可执行、能验证。
- 依赖清单要连同版本、许可证、来源和技术债一起交接。
- 提交信息写行为与证据；团队审查优先看数据、权限和测试。
